# 测试运行环境：第 0 步多要一样输入，环境需求据此写

Status: done

## Problem Statement

`test-case-design` 第 0 步只要三样开工输入：测试依据、风险信息、测试完成准则。测试环境是漏的——第 5 步 TD4 识别出的环境项全靠临场想，而「测试规程在哪儿跑」这件事只有用户那边知道。

实情是：技能测评的规程基本都要在 WSL2 或 Docker 下跑（规程要有干净、能重来的一处地方），而被测代码的执行可以在 Windows 下。这两处都不在技能的问话清单里，agent 也不会问——基线跑出来原话是「开工前还差一样：**风险信息**」，运行环境一个字没提。

## Solution

第 0 步加第四样：**测试运行环境**，向用户要，**只在测试项是技能时要**（测试依据指向的是 `SKILL.md`／技能目录）。问法是**落地一处、摊开一处**——问「测试规程在哪儿跑」（WSL2、Docker、别的机器），同时把「被测代码在哪儿执行」（技能测评这类通常就是本机 Windows）摊出来让用户确认或改；不问「要不要建环境」「用不用容器」。

落点两处：第 0 步当步落进决策依据的「用户决策」那一块（来源 `用户给的`，免得上下文一压缩就丢）；第 5 步落成测试环境需求里的头两条环境项——一条规程在哪儿跑、一条代码在哪儿执行。

改四个文件，都在技能里，不动脚本：

- `SKILL.md`：主流程表第 0 步那行、第 0 步正文（表的第四行、问法一段、落点一段）、「手上已经有一组用例」那条路。
- `references/流程.md`：第一节的输入清单与那条注、TD4 的环境项那一句。
- `references/文档模板.md`：第七节加「头两条就是它」、第九节「四样开工输入」。
- 技能自己的 `README.md`：「要给三样」改四样、表加一行、底下补一句落点。

版本号 `1.25.1` → `1.25.2`：改的是已有技能，按仓库规矩抬末位。

## Testing Decisions

本体层一条：`evals/test-case-design/cases/startup-inputs-sourced-right/` 加第三份判据 `graders/env-asked.md`——问没问、问的是不是跑规程那一处、有没有摊开代码执行那一处、有没有不等回答就自己编。场景与用户消息一个字没动（测试项本来就是技能）。另把六条脚本测试项的用例里「三样开工输入都给全」「第 0 步要的三样」的计数去掉，免得 agent 拿技能里的四样去对、以为少给了一样。

脚本层不受影响（改的都是 `.md`），仍跑 `bash tests/run.sh test-case-design` 兜底。

## 基线证据

改动前跑一轮（2026-09-29，1.25.1），**不通过**：agent 只问了风险信息，原话「开工前还差一样：**风险信息**」，运行环境一个字没提，也没写盘。它只在一处顺带写了「同一条文本换机器、换环境跑，结果应当一致」——那是测试结果的一致性，不是这一样输入。

改动后复跑两轮，**两轮都通过**：两轮都问了「规程在哪儿跑」（WSL2／Docker／别的机器）、都把「代码就在本机 Windows 上」摊出来让他确认或改、都停在等回答且没写盘；两轮也都没把完成准则反过来问用户，风险信息照问、没被带坏。

逐轮原文见 `evals/test-case-design/cases/startup-inputs-sourced-right/prompt.md` 的「基线证据」。

## Out of Scope

- **不给「必须照写的几个词」加「测试运行环境」那一行**：禁用词按子串匹配（`check_docs.py` 的 `banned_words()`），右列写「运行环境」会把正确的「测试运行环境」一起报出来；要加得先动那个脚本的 `NOT_BANNED`。
- **`check_docs.py` 不加机械检查**：这一条管的是问话与落点，产出里的环境项写得对不对仍由人看。
- **不该问的时候问了**（测试项是普通脚本却问运行环境）：这一路没有评测用例覆盖。
- **测试项不是技能、却确实要特定环境**（比如要某个版本的中间件）：仍按第 5 步从用例与规程往外推，不经第 0 步这一问。
