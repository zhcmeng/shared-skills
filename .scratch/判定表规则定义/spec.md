# 判定表规则定义：每条规则在同一份文档里查得到

Status: done

## Problem Statement

`test-case-design` 跑出来的产出里，判定表模型的表头只写「规则 1」「规则 2」……编号本身不说明任何事：读者要知道「规则 5」是什么，得横着扫过表里每一列的取值与动作，自己在脑子里拼一遍。表一宽、或者有几列是合并列（取值栏写「—」，这一条规则同时管两种条件组合），就拼不出来。文档别处照样引这些编号——「规则 3 与规则 5 的动作都是『一个字不动』」——读者回头查不到。

现成证据：`evals/plain-language/test-case-design/Test Model Specification.md`（本技能跑出来的一套真实产出）里 TM-2、TM-3 两个模型就是判定表，表头只有「规则 1」到「规则 5」，全篇没有一处逐条说明这些编号各是什么。

技能里也没有这条要求：`references/文档模板.md` 第三节「测试模型」栏只说「把模型本体展示出来」；`references/技术/判定表测试.md` 第一节讲的是判定表怎么读，没讲写进产出时每条规则要不要单独交代；`references/文档示例.md` 那套示例里一个判定表模型都没有——照示例抄的人见不到这种表该怎么落成文档。

## Solution

模型这份文档里，判定表的每条规则要能单独读出来：表后面跟一份清单，一行一条，写清这条规则管哪些条件取值、落到哪些动作。合并列要写明它覆盖哪几种条件组合；不可行的规则要写明为什么不可行。文档别处引「规则 N」时，读者在同一份文档里查得到。

改两处，都在技能里，不动脚本：

- `references/技术/判定表测试.md` 第一节加这条要求；算例里补一份清单当样子（表后面、覆盖项之前）。
- `references/文档模板.md` 第三节「测试模型」栏加结构位——填这一栏时，判定表后面要跟什么。

## Testing Decisions

本体层一条：`evals/test-case-design/cases/decision-table-rules-defined/`。fixture 是三项布尔条件判一个去处的 `approve.py` 与 `SPEC.md`，需求里带合并列（没有发票附件时不论违规记录）；grader 查每条规则在不在、不写死取值的列有没有交代、别处引的编号查不查得到。

脚本层不受影响（改的都是 `.md`），仍跑 `bash tests/run.sh test-case-design` 兜底——`tests/test-case-design/test_example.py` 会拿 `references/文档示例.md` 喂 `check_docs.py`，另外两处改动碰不到它。

## 基线证据

改动前跑了一轮（fixture 是三项布尔条件判一个去处的 `approve.py`，走满主流程八步），**不通过**：TM-1 那张判定表表头只有「判定规则 1」到「判定规则 6」，表后只交代了规则 3 与规则 6 的 `*` 合并列，没有逐条讲这 6 个编号各是什么；`check_docs.py` 报 0 错 0 提示。

改动后复跑两轮，都通过：一轮 8 条规则、一轮 6 条规则，两轮的表后都跟了逐条清单；第二轮那两条合并列（取「—」）各写明了它管哪两种组合。两轮的建模选择不同、清单都在，说明这条落在模板的结构位上。

逐轮原文见 `evals/test-case-design/cases/decision-table-rules-defined/prompt.md` 的「基线证据」。

## Out of Scope

- **状态转移表、等价类清单这类模型**：一行就把自己说明白了，不要求再列一份逐条说明。
- **`check_docs.py` 的机械检查**：合并列与不可行规则的写法在表里长得不齐（「—」「*」或留空都有人用），脚本一判就是假错；这一条由评测用例守。
- **`references/流程.md`**：TD1 各条讲的是这一步做什么，不重复模型怎么写。
