# test-case-design 维护者文档

这份文档在 `plugin/` 外，不随插件发出。安装后的技能目录是只读的：使用者只能改自己的产出，改不了技能文件。维护者改的是 `plugin/skills/test-case-design/` 与 `checks/` 下的文件；改完跑 `bash checks/verify.sh test-case-design`。

## 一、谁能维护

- **维护者**：本工程（`C:\Study\shared-skills`）下的作者。技能文件、参考文档、检查脚本都归他改。
- **使用者**：装了这个插件的人。技能装在 `~/.claude/skills/` 或插件缓存里，那一份是只读的；他能改的只有自己的产出目录（六份通用稿与按需的第七份）。
- 使用者撞见文档里说得不对的地方，不能自己回写；只能把偏离写进第七份的「说明」，或告诉维护者。

| 某个测评方案实际跑起来是什么样、做不到什么、哪里要挑 | `references/评测方案/<方案名>/usage-notes.md`——本技能自己写的实际使用说明；对着的版本看它顶部 |
| 某个测评方案的配置字段、命令参数 | **不在本技能里**，在 `/skill-upper` 技能下（`~/.claude/skills/skill-upper/` 的 `SKILL.md` 与它 `references/` 那几份）。写第七份之前先确认它装着——这条写在 `SKILL.md` 的「只出实施方案那一份」里 |

另有几条写文件时的经验：

- **复述别处事实的地方要跟着改**：README 里复述别处事实的地方（开工要哪几样、六份产出的名字与内容、文件结构、来源与效力这些），那边改了这边要跟着改。拿不准就把你改掉的说法在 README 里搜一遍。
- **改文件名要改两种写法**：文件之间互相引用，多数用 Markdown 相对链接，`SKILL.md` 与 `references/文档模板.md` 里是反引号包着的路径（那是给 Claude 照着读的指令，不是给人点的链接）。改文件名时两种都要一起改——稳妥的办法是拿文件名全文搜一遍，只搜 `](` 会漏掉反引号那一类。
- **主流程表「读哪份文件」一栏要列全**（2026-10-02 实测）：Claude 把这一栏当穷举清单执行，不跟随文内交叉引用——`references/文档模板.md` 第三节正文写着「对应表格式见第八节」，只读材料的样本都没去读，而第 2 步要写的正是那张表，一直要到第 7 步跑 `check_docs.py` 才报错。列清单的依据是各步「写进产出」一栏：这一步要写哪一份文档，那一份的栏目与格式来源就要在清单里。反过来，每步都要用的节不逐步骤列（第九节决策依据就是每步都用），靠主流程表下方那段说明——真正写入产出时读得到，同一次实测里验过。

## 三、skill-up 两份文档

`references/评测方案/skill-up/` 下的 `usage-notes.md` 与 `README.md` 都是本技能自己写的，不是上游原文。来源只有两类：`~/.claude/skills/skill-upper/references/*.md`（写文件名与小节名）与 CLI 实跑（写日期与版本）。

### 3.1 落成时撞见的新折扣往哪儿写

落成那一步撞见的、`usage-notes.md` 里没写的折扣（哪一样铺不进去、哪一处路径算歪了、哪一条其实落不成原样），照下面写回来：

- **写进 `usage-notes.md` 对应那一节**，不另起一节：工作区与夹具的事写第二节，命令与字段的事写第五节，Windows 的事写第四节。
- **句末标实测日期与版本**，体例：`（YYYY-MM-DD 实测，skill-up vX.Y.Z）`。
- **在本文 3.3 的核验索引里补一笔**——哪一条、什么时候、在哪个版本上核的。
- **只有实测过的才写成事实**。没实测的标「待确认」——这一份旧了不会报错，只会说错话。

写回之后，第七份「说明」那一块里引到这一份的话跟着核一遍：那里写着「与设计稿一致，没有出入」的条目，可能已经不是了。

### 3.2 换版本之后怎么重核

1. 跑 `skill-up --version`，确认装的是哪个发布版；发布那个号和 `main` 的头会各走各的，别当成对得上。
2. 按 3.3 的核验索引逐条重核。来源只用 `/skill-upper` 的 `references/` 与 CLI 实跑；不读上游源码，不翻公网文档站与 GitHub 的 CHANGELOG、release。
3. 对不上的照实改 `usage-notes.md`，并改它顶部的版本行与同目录 `README.md` 里的锁定版本（两处一起改）。
4. 跑 `bash checks/verify.sh test-case-design`。

### 3.4 版本号

## 四、检查与插件版本号

- `bash checks/verify.sh test-case-design` 跑两件事：`tests/test-case-design/test_*.py`，以及 `evals/*/eval.yaml` 的 `skill-up validate`（本机没有 `skill-up` 时只跑前一件）。
- 升级 skill-up 后按 3.3 的核验索引重核，并改 `usage-notes.md` 顶部的版本行（版本自查在使用者侧，`checks/` 里不做比对）。
- 插件版本在 `plugin/.claude-plugin/plugin.json` 与 `.claude-plugin/marketplace.json` 两处，一起抬、必须一致。新增功能抬中间那位；对原有内容的修改抬最后一位。只在 `plugin/` 有实际变动时抬——仓库根下的 `checks/`、`docs/`、`evals/`、`tests/` 不随插件发出，改了不抬。

## 五、不随插件发出

`docs/` 不在 `plugin/` 下，插件安装只拷 `plugin/` 整个目录。技能目录里的文件不写这个路径；使用者看不到它，也不需要。
