# 测试用例指南技能 — 设计文档

- 日期：2026-09-23
- 状态：已批准（brainstorming 流程）
- 场景：仓库里有一批 GB/T 38634 修订征求意见稿（`techblog/gbt-38634/`），需要从中提炼出一个 Claude Code 技能，指导模型创建、修改、检验测试用例
- 触发点：模型写测试用例时没有统一依据，格式和步骤各写各的；标准原文 1.3 万行，直接喂给模型既超上下文又夹带大量用不上的管理层内容

## 1. 目标与读者

**目标读者**：调用这个技能的模型。它拿到一份测试依据（需求或规格说明）和一个输出目录，要独立走完从建模到出规程的全过程。

**第二读者**：仓库主人。他要能复核产出对不对，而不用回头翻标准。

**成功判据**：

1. 模型只读本技能的文件，不读标准原文，就能产出五份格式合规的规格说明
2. 每份产出里的字段与标准第 3 部分的规定逐项对得上
3. 仓库主人能凭本技能的文件判断"这组用例够不够"
4. 四个决定——选了哪几门技术、怎么组合、各建什么模型、做到什么程度——在产出里都查得到依据，不是心里想过就算

**明确不是目标**：

- 不做全流程管控。组织级测试方针、测试计划的编写、测试执行、测试事件报告都不在范围内
- 不做测试术语的普及读物。术语照用标准原词，不另造说法
- 不追求覆盖标准里的全部 20 门测试设计技术，只做 7 门（见 D3）

## 4. 技能结构

```
.claude/skills/test-case-design/
├── README.md                     给人读的说明书，模型不读
├── SKILL.md                      主流程，模型默认只读这一份
└── references/
    ├── 流程.md                   TD1–TD4 的任务原文与可追溯性要求
    ├── 文档模板.md               五种规格说明的字段定义
    ├── 文档示例.md               五种规格说明的填写示例
    ├── 覆盖率与完成准则.md        覆盖率通则、分母速查、够不够的自检
    ├── 技术选型与组合.md          三类分工、组合搭配、7 门之外的换用告知
    └── 技术/
        ├── 等价类划分.md
        ├── 分类树方法.md
        ├── 边界值分析.md
        ├── 判定表测试.md
        ├── 状态转移测试.md
        ├── 场景测试.md
        └── 组合测试.md
```

**README 与 SKILL.md 的分工**：SKILL.md 是给模型的作业指导，进模型上下文；README.md 是给人的说明书，不进模型上下文。人想知道"这技能干什么、怎么触发、要给什么、会产出什么、管到哪为止"看 README；想改技能行为看 SKILL.md。两份不重复：README 不写操作步骤，SKILL.md 不写背景与来源。

README 收这几块：

1. 一句话说明这技能干什么
2. 什么时候会触发（自动触发的语境、以及手动怎么调）
3. 调用时要给什么：测试依据 + 输出目录
4. 产出什么：五份 Markdown，各自是什么
5. 管到哪为止：不含测试执行与事件报告
6. 来源与效力：取自 GB/T 38634 修订征求意见稿（**不是现行标准**），并说明这一点意味着什么
7. 文件结构说明，以及"想改行为该动哪个文件"

**为什么这么分**：七门技术各自独立成文件，一次任务用哪几门就读哪几门，没用到的不进上下文。一次用几门不固定——标准说这些技术是互补的、组合使用更有效，附录 F 举的例子就是一份测试计划同时要求边界值分析出第一批用例、并达到 100% 分支覆盖。分开成文件，读三门时不必付另外四门的代价，改一门也不碰其他。

**流程不按 TD1–TD4 拆成四份**。技术是选着用的，流程是每次全走的——不存在只用 TD3 不用 TD1 的正常任务，四步本来就是一串，拆开不省上下文，只多三次文件读取。而且四步是一条可追溯链（依据 → 模型 → 覆盖项 → 用例 → 规程），放一起才看得出链怎么接。整份约 200 行，也没到要拆的规模。返工时（如覆盖不够要补用例，重新进 TD3）反而更需要看到前几步建了什么。

## 5. 主流程设计（SKILL.md）

模型接到"写测试用例"类任务后按这个顺序走：

| 步 | 做什么 | 读哪份文件 |
|:---|:---|:---|
| 0 | **开工前先要到三样东西**：测试依据、测试完成准则（要求的覆盖率）、风险信息。三样缺一不可——后面每一步"做到什么程度"都由它们定。缺了就说缺什么，不硬开工 | — |
| 1 | **定技术方案**：选哪几门技术、怎么组合、各建什么模型、做到什么程度。四个决定每个都要写出依据（见下） | `技术选型与组合.md` ＋ `流程.md` |
| 2 | TD1 建测试模型：分析依据，按选定技术确定模型表示方法，建模型，记录依据与模型的可追溯性 | `流程.md` ＋ 选中的技术文件 |
| 3 | TD2 定测试覆盖项：对模型套用技术导出覆盖项，按风险定优先级，记录可追溯性 | 同上 |
| 4 | TD3 导出测试用例：定前置条件、选输入值、定预期结果，记录可追溯性 | 同上 |
| 5 | TD4 编测试规程：给用例排序，识别测试数据和环境需求，记录可追溯性 | `流程.md` |
| 6 | 自检：算覆盖率，判断是否达到完成准则 | `覆盖率与完成准则.md` |
| 7 | 按文档模板写出五份规格说明到指定目录 | `文档模板.md` ＋ `文档示例.md` |

**第 1 步的四个决定与各自的依据来源**：

| 决定 | 依据从哪来 |
|:---|:---|
| 选哪几门技术 | 三类技术的分工（规格说明类查遗漏型缺陷、结构类查多余型缺陷）、质量特性到技术的映射表、依据本身的形状。**这一项标准明确不给方案**——业界对哪门技术有效性最高没有共识，只给了上面这些材料。材料不够就如实说，不编规则 |
| 怎么组合 | 标准的几组搭配：一门技术的产出喂给另一门（等价类划分的覆盖项作场景测试的输入参数等）；以及规格说明类与结构类互补，补各自漏掉的那类缺陷 |
| 各建什么模型 | 技术决定模型形态——状态转移测试建状态图、判定表测试建判定表。选定技术后模型形态就定了；形态由技术反推，不自由发挥 |
| 做到什么程度 | 测试完成准则（要求的覆盖率）和风险级别。模型建到多细、边界取二值还是三值、分类树取最小化还是最大化、组合测试取哪一档、状态转移取哪一档、覆盖项取全还是取子集、高风险处要不要多导用例，都由这两样定 |

**依据只有两个来源**，每一步、每个字段都要能归到其中之一；归不到的就是设计漏了：

| 来源 | 有哪些 | 技能能不能自己给 |
|:---|:---|:---|
| ① 技能自己给的 | 模型形态由技术决定、覆盖项怎么导出、输入值怎么选、预期结果从测试依据推、规程按前后置依赖排序、环境项的类型清单、编号方案 | 能，写进 references |
| ② 开工输入 | 测试完成准则（要求的覆盖率）、风险信息 | 用法技能给，内容得先从用户或测试计划拿到 |

原本还有第三类——编号规则、责任人、需要的周期、重置与归档这些取决于被测项目组织安排的字段。它们已全部砍掉：编号改由技能给建议方案，责任与周期等字段从产出里移除。**所以技能没有需要"合理默认"的地方**——凡是技能给不出的，都是 ② 那两样开工输入，直接问用户。

**依据必须写进产出**，不是心里想过就算：技术选型与完成准则写进测试模型规格说明的「测试策略摘要」字段，风险决定的优先级写进各文档的「优先级」字段。写不进产出的依据等于没有依据。

**四个决定里任何一个写不出依据，就停下来问用户**，不硬选。标准对"选哪几门技术"没给规则，填充这一项只能靠测试计划里的信息或用户的判断。

主文件还要写清五件事：

1. **技术只覆盖 TD1–TD3，不覆盖 TD4**（第 4 部分 5.1 明文规定）。规程的排序与编写只在 `流程.md` 里讲，技术文件里不出现
2. **管理级只作接口**：测试完成准则和风险等级从被测项目已有的测试计划里取；取不到就向用户问，不自己编
3. **换用告知**：判断出某处更适合 7 门之外的技术时，明确告诉用户"这里更适合 X"，并说明 X 管什么，但不代做
4. **用词差异清单**（见 §7.7）
5. **本技能自包含，不许去找原文**：写明既不要联网搜标准，也不要读本仓库的 `techblog/gbt-38634/`。理由写清楚——现行版没有免费公开渠道，搜到的多是二手转述，与原文对不上；本地存档 1.3 万行，翻进去只会把上下文撑爆。技能里确实没覆盖的细节，直接问用户，不猜也不翻

**frontmatter 的 `description` 写触发时机**，照 `.claude/skills/` 下已有技能的写法：什么情况下该用本技能（要为某段需求或某个功能写测试用例、要改已有用例、要检验一组用例够不够），触发语举例（"给这个功能写测试用例""这组用例覆盖够吗"），并写明本技能管到用例产完为止、不管执行。

## 6. 产出设计

五份 Markdown，文件名即文档名，写入调用时传入的目录：

| 文件 | 内容 |
|:---|:---|
| `测试模型规格说明.md` | 每个模型给唯一标识符、目标、优先级、测试策略摘要、模型本体；末尾附「依据 → 模型」对应表 |
| `测试用例规格说明.md` | 三块：测试覆盖项清单（唯一标识符、描述、优先级、可追溯性）；测试用例（唯一标识符、目标、优先级、前置条件、输入、预期结果）；「覆盖项 ↔ 用例」对应表 |
| `测试规程规格说明.md` | 唯一标识符、目标、优先级、启动、有序执行测试用例、与其他规程的关系、停止与结束 |
| `测试数据需求.md` | 每条数据项给唯一标识符、描述 |
| `测试环境需求.md` | 每个环境项给唯一标识符、测试环境项、描述 |

**可追溯性**串起全链：测试依据 → 测试模型 → 测试覆盖项 → 测试用例 → 测试规程。用两张对应表承接，不另出追踪矩阵文件：

- **「依据 → 模型」表**（测试模型规格说明）：说明每个模型是照着依据的哪部分建的
- **「覆盖项 ↔ 用例」表**（测试用例规格说明）：**这张最有用**——一眼看出哪些覆盖项还没有任何用例覆盖，正是覆盖率自检要的
- 规程那份不用另出：规程本身就是"有序执行测试用例"的列表，用例编号就在里面

表比"每条用例里挂一个可追溯性字段"好在能直接看空行；字段形式要自己数才知道漏没漏。

**通用信息的取舍**：标准规定所有测试文档都带一组通用信息元素，共 8 项。本技能只保留「唯一标识符」，其余 7 项（发布组织、审批权限、变更历史、状态、范围、引用文档、词汇表）不收——它们是文档进入发布与审批流程时才需要的信息，本技能的产出是设计过程的中间产物，不参与那套流程（与 D9「管理级只作接口」一致）。这 7 项要在 `文档模板.md` 里点明"有意不收"，不是漏掉。

**目录约定**：调用时传入输出目录；未传则先问，不猜默认路径。目录不存在就创建。

## 7. 各文件的内容边界

### 7.1 `流程.md`

TD1–TD4 四段，每段按原文写出标准的任务条目，意思不变即可。每段后附该步要求记录的可追溯性。开头写清本过程的输入（测试依据、所需覆盖率、风险信息）与产出（本过程该生成哪些信息项）。

识别测试数据和环境需求的部分并入 TD4——它本来就是 TD4 的任务之一。

**有一组任务不适用，照原文时要标出来略过**：与利益相关方就测试模型达成一致、测试用例规格说明得到利益相关方同意、测试规格说明得到利益相关方同意（TD1、TD3、TD4 各一条）。本技能的场合没有那套组织角色，不必另设确认环节。条目照原文写出能保住完整性，但要紧跟一句说明，免得模型去找"利益相关方"。

末尾附上那个完整示例，它是全库唯一走完整条链的样板：先定测试完成准则（等价类划分覆盖率达到 100%），再据此建模型，再导出覆盖项与用例。每一步都点明"根据什么"——这正是本技能要求产出写依据的示范。

**不写**：技术在每步怎么用（那是技术文件的事）、规程的执行（超出边界）。

### 7.2 `文档模板.md`

五种文档的字段定义，逐字段说明"这一栏该写什么"。例如"输入"栏要写到达可与预期结果比对的状态所需的各项操作，操作之间有先后关系的要写明；"预期结果"栏要逐个输出给预期值，必要时带允许误差范围。字段定义取自正文——目录、字段标题、以及规则末尾那些讲怎么填的句子，不是正文里的「示例：」段落。

**例外**：这份文件是给模型照着填的，纯字段名读不出该填什么，所以允许在说明之后带一句"例如……"把抽象要求具象一下，句子从正文同处的示例、注解里提炼，点到为止。完整的填写示例仍归 `文档示例.md`。

三个字段要单独点明，它们是依据落地的地方：

- **测试策略摘要**（测试模型规格说明）：写清用了哪几门技术、怎么组合、测试完成准则是什么。第 1 步四个决定里前两个半落在这里。标准还提了一句"可注明测试是自动化执行还是人工执行"——这句略过，本技能一律是模型产出
- **目标**（模型、用例、规程三处都有）：模型这条写它关注测试项的哪一部分
- **优先级**（模型、覆盖项、用例三处都有）：写风险等级，不是随手标高低。第 1 步第四个决定"做到什么程度"由它承接

**唯一标识符标准只给了名字、没给怎么填**，这份文件要直接给出方案：

| 对象 | 编号 |
|:---|:---|
| 测试模型 | TM-1、TM-2… |
| 测试覆盖项 | TCOV-1… |
| 测试用例 | TC-1… |
| 测试规程 | TP-1… |
| 测试数据项 | DATA-1… |
| 测试环境项 | ENV-1… |

数据项与环境项不用 TD、TE 打头——那两个字母已经被 TD1–TD4、TE1–TE3 这组活动代号占了，混在一起读不清。项目有惯例就跟随惯例，没有就用这套。

两张对应表（「依据 → 模型」「覆盖项 ↔ 用例」）的列怎么设也在这份文件里定。

另外两处是**标准草案的正文串位**（见 §9）：测试模型规格说明的「目标」、用例规格说明的「可追溯性」。这两节的正文被转到了相邻小节下，要从上下文判回原位再写进模板。「可追溯性」那一处归位后，内容就是「覆盖项 ↔ 用例」表；「目标」那处归位后，就是"这份模型关注测试项的哪一部分"。

**覆盖项清单的可追溯性单列一栏**（见 §6 那张字段表）：用例规格说明里有两个同名字段——测试覆盖项的「可追溯性」写这个覆盖项出自哪个模型的哪个元素，测试用例的「可追溯性」由「覆盖项 ↔ 用例」表承接。两个形态不同是有来源依据的，不合并。

### 7.3 `文档示例.md`

五种规格说明的填写示例，敏捷企业 A 与传统企业 B 两个项目各一套。保留原格式。

### 7.4 `覆盖率与完成准则.md`

三块：

1. **通则**：覆盖率公式 C＝N／T，N 与 T 各自是什么；不可行覆盖项的定义与处理——能证明某覆盖项无法被执行则定义为不可行，计算时计入还是剔除要在测试计划里明确，剔除要记录原因
2. **分母速查**：七门技术一行一门，写清各自 T 是什么、指到对应技术文件
3. **各技术的覆盖率要求**：七门各自默认要求到什么程度，见下表
4. **够不够的自检**：测试完成准则从哪里取、要求未达 100% 时怎么选子集（按风险暴露级别放弃低风险覆盖项）、什么情况下不要求 100%

**各技术的覆盖率要求**——多数技术就是全覆盖，三门有档位可选：

| 技术 | 要求 |
|:---|:---|
| 等价类划分 | 全面覆盖所有等价类 |
| 边界值分析 | 全面覆盖所有边界值（二值边界测试；也可取三值） |
| 判定表测试 | 全面覆盖判定表中所有有效（可行）规则 |
| 场景测试 | 覆盖主场景和备选场景 |
| 分类树方法 | **有档位**：最小化（每个类至少在一个用例中出现）／最大化（所有类的唯一组合） |
| 组合测试 | **有档位**：完全组合／成对／单一选择／基本选择 |
| 状态转移测试 | **有档位**：全状态／0-switch／全转移／N-switch |

**一条必须标注的前提**：这些要求出自标准的算例，属资料性内容，不是强制规定。标准的原则是"要求的覆盖率由测试计划定"。技能里要写清这是惯例，不是标准强制，免得模型拿它当硬性要求去否决用户的完成准则。

**100% 的立场**：默认按 100% 要求。标准的态度是理想情况下尽量设 100%，而它给的覆盖率定义允许剔除不可行覆盖项——剔完之后 100% 就是可达成的目标。所以碰到覆盖不满时，正确的做法是**剔除不可行项并记录原因**，不是把要求本身降下来。若完成准则定得低于 100%，才按规则挑子集，并说明为什么。

### 7.5 `技术选型与组合.md`

这份文件服务第 1 步的四个决定，按决定分块。

**一、选哪几门技术**

- 三类技术的分工：基于规格说明／基于结构／基于经验各自拿什么当主要信息来源；灰盒的含义
- 遗漏型与多余型缺陷：基于规格说明的技术擅长检出遗漏型缺陷，基于结构的技术只能检出多余型缺陷
- 质量特性到技术的映射表
- **标准对这一项不给方案**——要写明这一点，并写明能拿来判断的只有上面这些材料，加上风险等级、关键程度、应用领域、实施成本。不许自己编选型规则
- 换用告知条目：7 门之外的技术各一条，写清它管什么、什么时候该端出来

**二、怎么组合**

- 组合的几组搭配：等价类划分导出的覆盖项用作场景测试的输入参数；边界值分析选输入值后由成对测试设计完整用例；等价类划分为分类树方法选分类和类别后由单一选择测试构造用例；边界值分析出第一批用例 ＋ 100% 分支覆盖用分支测试补漏
- 组合的理由：两类技术补各自漏掉的那类缺陷
- 有效与无效用例的两种导出方法：无效用例用"一对一"（每条只含一个无效输入，避免故障遮蔽），有效用例用"最小化"（减少用例数）

**三、各建什么模型**

模型形态由技术决定，把七门各自对应的形态列成一张对照表：状态转移测试→状态图或状态表；判定表测试→判定表；分类树方法→分类树；场景测试→交互序列；组合测试→参数取值表；等价类划分与边界值分析→等价类（可用图形或纯文本表示）。表述方式不限——同一模型用自然语言、表格或图形都行。

**四、做到什么程度**

把可调的那几处集中列出来，每处写明由什么决定：模型的详细程度、边界取二值还是三值、分类树取最小化还是最大化、覆盖项取全还是按风险取子集、高风险覆盖项要不要多导用例。这几处全部由测试完成准则和风险级别决定。

**准则包含关系及其局限**：分支覆盖包含语句覆盖等，但只在基于结构的准则之间有；规格说明类与结构类之间不存在包含关系；包含关系不能用来排技术的有效性高低。

**这份文件必须写明的边界**：只用规格说明类技术会漏掉多余型缺陷。不能写成"选一门就够"。

### 7.6 `技术/<名>.md`

七份，每份同一个骨架：

1. **测试模型是什么**：模型由什么构成、边界在哪
2. **测试覆盖项怎么定**：覆盖项是什么、有哪几种覆盖程度可选
3. **测试用例怎么导**：带编号的导出步骤，照原文写，不改意思
4. **覆盖率怎么算**：C／N／T 三个量在技术里的具体取值；以及这门技术默认要求到什么程度（多数是全覆盖，有档位的列出档位）
5. **算例**：完整走一遍，从测试依据到用例

技术文件里**不出现**规程排序、执行、事件报告的内容，也不出现标准名称、章节号或条款号。取材落点见 §3.1——那些落点只写在本设计文档里，不进技能文件。

### 7.7 `SKILL.md` 的用词差异清单

**不建术语表**。等价类划分、边界值分析、前置条件、预期结果这类词的通用含义模型已经知道，逐条解释纯属占地方。要写的是**标准用专有用法、与业界常见说法不同**的那几个词——训练数据里更常见的恰恰是错的那个，不写就会踩坑。

放主文件而非单独一份文件：它是每次产出都要遵守的约定，放主文件才不会被跳过；十来行，不影响 500 行上限。

清单至少含这几条：

| 标准要求 | 容易写成 | 为什么 |
|:---|:---|:---|
| 测试模型 | 测试条件 | 这一版明确弃用了「测试条件」这个说法，改用它。两个词只差一个字，不单列出来容易写错 |
| 测试依据 | 测试的证据、测试数据 | 它是设计用例所依据的信息源（需求、规格说明、模型、用户需求） |
| 测试项 | 测试用例、被测对象 | 指被测的那个东西 |
| 测试覆盖项 | 覆盖点、覆盖目标 | 指模型里要被覆盖的那个元素 |
| 测试规程 | 测试脚本、测试流程 | 指用例的执行顺序，加启动与收尾动作 |
| 测试用例规格说明 | 测试用例文档 | 它是正式的文档名 |
| 应／宜／可 | 统写成"要" | 顺手把这三个字改成"要"，会把原话的语气带偏 |

实现时对照原文核对每一条，不只抄列出来的这几条。收窄后用得上的其他专有用法都要收，例如「有效测试用例／无效测试用例」与「一对一方式／最小化方式」这组导出方法的名。

## 8. 写作纪律

1. **内容以标准原文为准**，只做删减和归类，不自行改写成"更好懂"的说法。术语一变就跟标准对不上
2. **不造词**。标准里的中文原词照用；需要解释的地方用一句白话说明，不替换原词
3. **技能文件里零引用**（D7）。不出现标准名称、章节号、条款号、出处标注，也不写「详见」「参见」。只在技能开头一句带过来源。理由：引用即指针——本仓库存着 1.3 万行标准原文，模型顺着指针翻进去，既爆上下文，又可能跟着草案的转换缺陷走。断掉指针不影响复核能力：本地存档可用关键词搜到，逐条列出处省下的只是一次搜索
4. **不把标准原文搬进 SKILL.md**。主文件只写流程与调度，细节一律进 references
5. **别把原话的语气改掉**。照原文写下来就行——不改意思、不添词、不用自己的说法替换原词
6. **取材落点只留在本设计文档里**。第 3 节那张表是给实现者和复核者看的，不搬进技能文件。零引用不等于降低取材要求——实现者照样要逐条读标准原文，并按住第 9 节绕开草案的转换缺陷

**技能格式照 skill-creator 的约定**：

- SKILL.md 控制在 500 行以内（超过就再分一层，主文件只留流程与指针）
- references 文件超过 300 行要带目录
- SKILL.md 逐个文件写明"什么时候读它"，不留悬空引用
- `description` 是唯一的触发入口，把"做什么"和"什么情况下用"都写进去；skill-creator 提到模型有漏触发的倾向，措辞要稍微推一把
- 指令用祈使句；解释为什么这么做，而不是堆"必须"

## 10. 验收判据

1. 只看 `SKILL.md` 能说出完整流程，且知道每一步该翻哪份 references
2. 七份技术文件各自自包含：给出测试依据，照着能建模型、定覆盖项、导出用例、算覆盖率，不需要翻别的技术文件
3. 五份产出模板的字段与标准第 3 部分逐项对得上，无多无缺
4. `技术选型与组合.md` 里写明了"只用规格说明类技术会漏掉多余型缺陷"
5. 全库 grep 不到组织级测试方针、测试计划编写、测试执行、事件报告的内容
6. 无自造术语
7. 只读 `README.md` 就能说出这技能干什么、怎么触发、要给什么、产出什么、管到哪为止；README 里没有操作步骤，SKILL.md 里没有背景与来源
