# 评测用例目录名：字母序与规程顺序由构造保证 — 设计文档

日期：2026-09-29
状态：待评审

这份动 `test-case-design` 的产出契约：测试规程规格说明的「各批落到哪」加一栏「用例目录名」，目录名的形制定死，自检脚本跟着查这一栏与规程顺序对不对得上。技能的产出一律是六份文档，这份设计不碰这个边界。

## 1. 由头

上一轮实测出一条规律：官方 `claude plugin eval` 的执行顺序是**用例目录名的字母序**，`--case` 接的也是目录名（官方文档存档 `C:\Study\work\techblog\claude-code-docs\en\plugin-evals.md:341`、`:116`）。

`evals/plain-language/test-case-design` 那套产出的「有序执行测试用例」栏排的是 TC-1、TC-2、TC-3、TC-6、TC-7（TP-1）与 TC-4、TC-5（TP-2），恰好等于 `tp1-TC-1-…`、`tp1-TC-2-…` 的字母序。**核查下来这是巧合，不是技能兜住的。**

技能从头到尾没有把「字符串序」与「执行顺序」挂上关系：

- 唯一沾到这件事的是 `references/文档模板.md:178`——规定「用例 id 带上规程编号前缀」（例子 `tp3-TC-42-gate-any-true`），同一条里又把它推给工具：「评测工具自己怎么排这个 id 是它的事（写成 `tc-042` 之类的也有）」。
- 规程那边的排序规则在 `references/流程.md:111`：按前置与后置依赖排；`流程.md:113` 的示例是风险等级高的排前面。这是「怎么排」，不是「排出来叫什么」。
- 三个脚本都不看命名（见 §1.1）。

同一份产出里还并存两套命名，技能里没有哪句话能判哪个对：「各批落到哪」表写 `tp1-TC-1-fix-only-what-should-change`（`evals/plain-language/test-case-design/Test Procedure Specification.md:51`），而八条用例的预期结果栏写的判据路径是 `cases/fix-only-what-should-change/graders/…`（同一目录 `Test Case Specification.md:64` 到 `:68`、`:74` 到 `:76`），没有 `tpN-TC-M-` 这一段。

会出什么错是算得出来的。用例编号是第 4 步导出时按写下来的先后发的，规程顺序是第 5 步另排的，两个顺序各来各的；目录名按 `tpN-TC-M` 排，字母序先在编号那一段分出胜负——一条规程里若有 12 条用例，排出来是 `TC-1、TC-10、TC-11、TC-12、TC-2、…`。规程数一过 9 同理（`tp10-` 排在 `tp2-` 前面）。

## 2. 判据：字母序等于规程顺序，靠什么保证

两件事一起成立就够：

1. **形制把两段数字定成两位**（`tp01`、`01`）。位数一致，字母序就等于「先规程号、再规程内位次」。
2. **位次写的是执行顺序**——这条用例在该规程「有序执行测试用例」栏里排第几，就写几。

两条都成立时，字母序等于规程顺序是构造上的必然，不必再写一条「把清单排一遍看顺序对不对」的检查——那是白查：形制管着位数、位次又逐条对过，排出来不可能不对。

**判哪一行是评测批**：看「各批落到哪」表里这一行的「执行器」栏，取值 `控制器` 或 `子代理` 的就是。这是 `references/文档模板.md:175` 已经写明的归属（「「执行器」那一栏里的「控制器」与「子代理」都归后一批」），不是新立的规矩。取值 `脚本` 的行这一栏不查；一张表里一行评测批都没有时（全部落成可跑测试），这一栏整个不要求，缺栏不报错。

**补零的是目录名里新起的两段位次，不是条目编号。** `文档模板.md:93` 那条「数字照原样、不补零」照旧管着 `TC-30` 这样的编号，两条并存，不冲突。

**位次不靠手数。** `issue_ids.py` 照「有序执行测试用例」栏数一遍，连同其余三段一起打出整条目录名，模型照抄（见 §4.3）。手数是这条链上唯一一处会数错的地方。

## 3. 决策记录

| # | 决策点 | 选了什么 | 为什么 |
|:---|:---|:---|:---|
| D1 | 目录名形制 | **四段**：`tp<规程号两位>-<规程内执行位次两位>-TC-<用例编号>-<英文名>` | 位次段是新增的那一段，它就是执行顺序本身；规程号与位次都补零，字母序才等于「先规程、再位次」 |
| D2 | 位次按什么范围编 | **规程内**（每条规程从 `01` 起），不走全局序号 | 全局序号在中间插一条用例时要整体重编；按规程内编只动那一条规程 |
| D3 | 目录名里留不留 `TC-` 编号 | **留** | 报告逐行看 id 能认出对应文档里哪条用例，`--case` 也能筛到具体那一条。拿掉的话这两样都没了 |
| D4 | 清单落在产出哪里 | **「各批落到哪」表加一栏，一条规程一行** | 规程的绑定是结构性的（不用另写一栏去对）；改动最小；与现有产出的习惯一致（现在就是在一格里列一串） |

| D6 | 校验放哪个脚本 | **`check_docs.py`**，设计阶段就查 | 目录名在第 5 步就定得下来，不必等落成。放 `check_landing.py` 的话要等盘上真有目录才查得动，而且它现在只读正文，得改成读名字 |
| D7 | 补零几位、超了怎么办 | **两位**；规程或用例超过 99 条时整套一起改三位 | 两位够用（典型技能评测十几条用例、几条规程）；不许有的两位有三位，混着写字母序就错位 |
| D8 | 查不查「把清单排一遍看顺序」 | **不查** | 形制管着位数、位次又逐条对过，顺序由构造保证——再排一遍是白查 |

| D10 | 落成可跑测试那一批的文件名 | **不进这条规矩** | pytest 按文件内顺序跑，文件名不影响执行顺序 |
| D11 | 位次谁来定 | **由脚本打出整条目录名**，模型照抄 | 手数「排第几」是这条链上唯一一处会数错的地方，脚本读同一栏数一遍不会错，顺带省掉「自己拼四段」这一手。放 `issue_ids.py` 里成一个新入口、不另开脚本：它是模型已经知道要跑的那件工具，跑法也同形（读盘上六份文档 → 打出要抄的东西）。**没取「脚本只打位次、名字由模型拼」**——拼回去就又把那处会错的地方交还给了模型 |

## 4. 设计

### 4.1 `references/文档模板.md` 第五节

**一、表头加一栏。** 「各批落到哪」的表样（`:172`）改成：

| 批次 | 规程 | 执行器 | 落到哪 | 用例目录名 | 说明 |
|:---|:---|:---|:---|:---|:---|

**二、`:178` 那一条整条重写。** 现在那条只讲「用例 id 带上规程编号前缀」，新的一条讲五件事：

1. **哪一行要填**：落成评测用例的那一批，一条规程一行，按执行顺序把该规程全部用例的目录名列全、顿号隔开；落可跑测试那一批的行这一栏空着。
2. **形制**：`tp<规程号两位>-<规程内执行位次两位>-TC-<用例编号>-<英文名>`，例如 `tp01-01-TC-1-fix-only-what-should-change`。四段各是什么、两段数字怎么补零、超过 99 条时整套一起改三位（不许有的两位有三位）。
3. **位次是执行顺序**：这条用例在该规程「有序执行测试用例」栏里排第几，就写几；清单与那一栏必须逐条对得上，少一条、多一条、位次写错都算错。
4. **为什么**：评测工具按目录名的字母序跑，名字排成什么顺序就跑成什么顺序；`--case` 接的也是目录名。编号本身不补零，`TC-10` 会在字母序里跑到 `TC-2` 前面，所以顺序要单独编一段。
5. **同一条用例被两条规程排到时**落成两个目录，各带自己那条规程的前缀。

现在那句「评测工具自己怎么排这个 id 是它的事（写成 `tc-042` 之类的也有）」删掉——它给了一个与新形制打架的许可。换成：盘上的目录名与文档里写的一字不差，报告里那一列怎么显示是工具的事；文档里的编号仍要照第二节「落成约定」原样出现一次。

### 4.3 `scripts/issue_ids.py`：新入口，打整条目录名

```
python scripts/issue_ids.py <产出目录> --case-dirs          每条规程一行
python scripts/issue_ids.py <产出目录> --case-dirs TP-1     只打这一条规程
```

一条规程一行，`TP-n：`打头，后面是顿号隔开的目录名，照抄进「用例目录名」栏：

```
TP-1：tp01-01-TC-1-fix-only-what-should-change、tp01-02-TC-2-quotes-kept-and-glossed、tp01-03-TC-3-scope-of-review
TP-2：tp02-01-TC-4-restate-whole-answer、tp02-02-TC-5-restate-nothing-to-fix
```

位次就是「有序执行测试用例」栏里的次序，脚本数一遍；规程号、用例号、英文名都从文档里取。**脚本只读不写**（`SKILL.md:73` 那条纪律不变），打出来的东西由模型抄进产出。

**切规程块这件事只留一份实现。** `check_proc` 现在把切块写在函数体里（`:612` 起），要提出来成一个小函数（返回 `{规程号: [用例号，按顺序]}`），`check_proc` 与这个新入口都用它——与 `check_landing.py` 开头那句「契约不在这份脚本里另立一套」同一个理由：两边各写一份，迟早一边认得出、一边认不出。

**出错时说的话要能直接照做**：

| 情况 | 打什么 |
|:---|:---|
| 那条规程还没写「有序执行测试用例」栏 | 点名 TP-n，说先写这一栏再跑 |
| 栏里引的用例在文档里没有定义处 | 点名 TC-n，说查不到这条 |
| 那条用例没有「英文名」栏 | 点名 TC-n，说这一栏必填（`文档模板.md:73`） |
| 规程号或用例数到了三位数 | 说两位装不下，整套要一起改成三位（见 §4.1） |
| 产出目录里没有测试规程规格说明 | 说文件名对不对、目录对不对 |

### 4.4 `scripts/check_docs.py`

**位置**：并在 `check_batches`（`:483`）里——那张表已经切在手里；每条规程的用例序列按 §4.3 提出来的那个函数取。

**五条检查**（判哪一行是评测批见 §2）：

1. 评测那一行没有「用例目录名」栏、或栏空着 → 错误。
2. 每条目录名的四段形制：两段数字各两位、`TC-` 段不补零、英文名段合小写规则 → 不合就错误。
3. 第一段的规程号等于本行「规程」栏那条；第三段的用例号在文档里有定义处；第四段的英文名与用例表里那一栏一字不差 → 任一条不成立就错误。
4. 第二段的位次等于该用例在本规程「有序执行测试用例」栏里排第几 → 对不上就错误。
5. 清单里一条不多、一条不少、一条不重，与该规程那一栏的用例集合对得上 → 对不上就错误。

**`BATCH_COLS`（`:87`）不动**：它只要求「批次」「规程」「落到哪」三栏在，多出来的栏不报错，加这一栏不必动它。

## 7. 已知的连带代价

- **第 5 步多一趟落盘**：规程那几栏先落盘 → 跑打目录名的命令 → 把打出来的抄进「各批落到哪」那一栏 → 再落盘一次。多这一趟是因为脚本只读不写，它得先能读到盘上的规程栏。
- `evals/plain-language/test-case-design/` 那套产出要改八处判据路径加一张表，是本轮里最琐碎的一段；改漏一处 `check_docs.py` 不报（它不管判据路径），要人核。
- 目录名变长（多两段共 6 个字符加一个连字符），`--case` 通配要写得更长。
- 一条规程里用例超过 99 条这条路没人走过，真撞上了要整套重命名——这条写在模板里，但没有任何东西会提醒你。
- 技能自己的两套命名（`evals/test-case-design/cases/` 用英文名、技能产出的评测目录用 `tpNN-MM-…`）会长期并存，后来的人可能想「统一」一下——D9 的理由写在 spec 里，技能本体里不解释这一层。
