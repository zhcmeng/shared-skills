# pdf-to-md：用 PaddleOCR 把 PDF 转成 Markdown

日期：2026-09-20
状态：待评审

## 背景

给本仓库加一个 skill：把 PDF 转成 Markdown，落到磁盘上。

解析交给 PaddleOCR 在 AI Studio 上的接口。这是个云端服务——**整份 PDF 会上传到对方服务器**，解析也在那边做。

接口是异步的，三步：

1. `POST /api/v2/ocr/jobs` 提交，拿到一个任务号
2. `GET /api/v2/ocr/jobs/<任务号>` 反复问，直到状态变成 `done` 或 `failed`
3. 拿 `done` 里给的地址下载结果——一份 JSONL。行里的 `layoutParsingResults` 一页一项，**每行装 3 页**（105 页那份是 35 行）

**不用 `paddleocr-mcp` 这个包。** 它既能当库 import，也能当 MCP 服务跑，但本 skill 真正需要的三样，它一样都不给：

- **等不了**：轮询超时写死 600 秒，超了就扔 `PollTimeoutError`——而任务在服务端还在跑
- **看不见进度**：接口在 `extractProgress` 里实时报「已解析几页 / 共几页」，库不往外给
- **看不见错误**：服务端给的失败原因在 `errorMsg` 里，库那层裹一层或者抹掉

它另外支持的本地推理、自建服务、别的云厂商、base64 输入，本 skill 一样都用不上。直接打接口，代码不多，上面三样全有——这条路上本机已经跑过好几次（见「验过什么、还没验什么」）。

## 目标

- 输入是本地 PDF 文件、装着 PDF 的目录（批量），或 PDF 的公网网址
- 输出一份干净的 Markdown：正文里出现的图片全部落到本地，引用改成相对路径
- 转换过程不进对话——正文多长都不占上下文
- 落盘的正文就是文档内容本身，不带转换过程的产物：没有分页标记、没有没还原的占位符、没有残留的包裹标签、没有临时路径、没有我们自己加的说明
- 批量时显示进度和预计剩余时间，转过的跳过

## 非目标

- 不做领域专属的正文清理（删目录、按标题截断某一类章节）。要这类行为，调用方在转换之后自己处理
- 不做扫描件的识别参数调优，不做版面还原的人工干预
- 不收图片输入。图片转 Markdown 是另一回事——没有分页，也没有正文里的图片引用要改写，混进来只会把命令行的语义弄浑
- 不动 `hooks/`、状态栏、常驻规则

## 决策记录

| 决策 | 选了什么 | 为什么 |
|:---|:---|:---|
| 怎么调解析 | 直接打 AI Studio 的 HTTP 接口，不用 `paddleocr-mcp` | 库把超时写死、不给进度、不给失败原因，而它多给的那些我们一样用不上。详见「背景」 |
| token 从哪来 | **只从环境变量读，绝不落进代码、注释、测试或仓库**；变量名 `PADDLEOCR_MCP_AISTUDIO_ACCESS_TOKEN`，设在 `~/.claude/settings.json` 的 `env` 段（本机已配好） | token 一旦进了 git 就等于泄露，而且收不回来。名字里那个 `MCP` 是历史原因，与本 skill 无关；但本机已按它配好，换名字只为了让名字好看，代价是每个使用者都要重配一次 |
| 输入从哪来 | 本地路径、目录，或公网网址 | 网址走接口的 `fileUrl`，由服务自己去取，本 skill 一个字节都不下——省掉一次上传 |
| 大文档怎么处理 | 整份一次提交，不切段 | 105 页冷跑 85 秒，没有「100 页」这道墙。见「为什么不切段」 |
| 图片从哪来 | 结果里给一张「图片名 → 图床网址」对照表，脚本照网址把图取回本地 | 正文里只有引用名，图片本体不在结果里；接口没有「连字节一起返回」的口子 |
| `outputImages` 要不要落 | 不落 | 本机跑出来它只有一类键 `layout_det_res`——版面检测图，把识别框画在页面上给人看的那种，不是文档内容。见「结果里有两份图」 |
| 输出布局 | `<输出根>/<名字>/<名字>.md` + `<输出根>/<名字>/images/` | md 与图片同在一个目录，整个目录能单独搬走 |
| 默认模型 | `PaddleOCR-VL-1.6`（带版本号是有意的） | 官方文档里它是新一代，擅长扫描、倾斜与多语言；换模型由调用方显式指定，本 skill 不做自动路由。名字带版本号，服务升级换了名字时要改的就是这一处 |
| 清理范围 | 只做通用的（表格、包裹标签、空白、图片引用），不带配置文件 | 通用的才收进本仓库 |
| 依赖缺失时 | 直接报错退出 | `lxml`/`tabulate` 缺了表格会静默退化成原始 HTML，那正是「正文不干净」的来源 |
| 网络出错怎么处理 | 轮询和提交都自动重试 | 轮询问的是同一个任务号，重试安全；提交重发的是同一份文件，服务端认得出、直接给缓存，不会真的多解析一遍 |
| 并发 | 池子按**文件**排队，一个文件一个任务，上限默认 4（`--jobs` 可调） | 配额是固定的一笔账，串行只是慢。按文件排队让进度、失败、落盘、图片名天然按文件划分，不必额外记账 |
| 已转过的 | 输出目录里有那份 md 就跳过，**不看源文件变没变** | 断点续跑靠它；要重转加 `--force`。只看 md 在不在是有意的——省掉记账，代价是源 PDF 更新后得自己加 `--force`（记在「已知局限」里） |
| 图取不回来时 | 不算这份文件失败，末尾点名 | 正文和其余图片都是好的，为一张图把整份判失败太重。退出码照旧为 0 |
| 落盘正文的形态 | 就是文档内容本身，不带转换过程的产物——分页标记、没还原的占位符、残留的包裹标签都不留 | 「正文干净」这条要求 |

## 设计

### 文件清单

```
skills/pdf-to-md/SKILL.md              用法说明：怎么调、两种模型各自适合什么、配额与错误
skills/pdf-to-md/scripts/convert.py    CLI 入口与编排：参数、任务池、进度条、已转过判断、落盘
skills/pdf-to-md/scripts/aistudio.py   跟接口打交道：取 token、上传、轮询、取结果、照网址取回图片
skills/pdf-to-md/scripts/markdown.py   纯文本：表格、包裹标签、空白、图片引用改写、图片名分配、多页拼装
skills/pdf-to-md/tests/test_pdf_to_md.py
```

`markdown.py` 不导入网络和文件相关的库，也不依赖 token——所有能单测的逻辑都集中在这里，包括图片名的分配和把 JSONL 拼成一份文档（它们只是拿字典和字符串做事，不碰网络）。`aistudio.py` 是唯一 import `requests` 的地方。

`SKILL.md` 的 frontmatter 要有 `name: pdf-to-md` 和一段带触发词的 `description`，照 `download-md-images` 那份的写法——写明什么时候用它，也写明什么时候不用（导出成 PDF 是 `md-export` 的事）。

顺带把 `.claude-plugin/plugin.json` 和 `.claude-plugin/marketplace.json` 的版本号一起从 1.9.0 抬到 1.10.0（两个文件本来就一致，加 skill 算一次功能升级），并在 `README.md` 的 skill 表里补一行。

### 接口怎么用

三处细节照官方示例抄，不自己规范化：

- **提交**：本地文件走 multipart（`files={"file": f}`），`model` 和 `optionalPayload` 放在表单字段里；网址走 JSON 体，字段叫 `fileUrl`
- **返回的信封**：成功是 `{"code": 0, "msg": "Success", "data": {…}}`；失败是 HTTP 400 加 `{"traceId": "…", "code": 10002, "msg": "文件 URL 无法识别"}`。`code` 非 0 就是失败，`msg` 是服务给的中文原话——**直接转给使用者，别自己编解释**
- **轮询**：`running` 时 `extractProgress` 不一定在——官方示例专门拿 `try/except KeyError` 兜了，所以读进度要按「可能没有」写。本机见到的样子：`running` 时轮询只返回 `jobId`、`state`、`extractProgress` 三个键（**没有 `resultUrl`**），`extractProgress` 里只有 `extractedPages`、`startTime`、`totalPages`（**没有 `endTime`**）；要到 `done` 才多出 `endTime` 和 `resultUrl`
- **模型名**：两个名字的写法不一样。`PaddleOCR-VL-1.6` 带横杠还带版本号，`PP-StructureV3` 不带横杠。照抄，别自己统一

`optionalPayload` 那三个开关（`useDocOrientationClassify`、`useDocUnwarping`、`useChartRecognition`）官方示例都给的 `False`，本 skill 照给，也不给使用者开关——这三个都是「多花时间换更好的还原」，本机没试过效果，等真碰上需要的文档再说。

### 数据流

```
输入（文件 / 目录 / 网址）
  └ 网址：原样交给接口的 fileUrl，服务自己去取，本 skill 不下载
文件排进池子并发处理（上限 --jobs）
提交，拿任务号
  └ 本地文件：整份 multipart 上传
轮询，把 extractProgress 的「已解析页数 / 总页数」喂给进度条
done → 下载 resultUrl.jsonUrl 那份 JSONL
逐行、逐页摊平，拼出 {正文, 图片清单}
图片清单按（第几页，图片名）收，**不按图片名收**——见下一节
  └ 同一个网址 → 同一个本地文件
  └ 本地文件名取自网址路径里的文件名；已被别的网址占用就追加 -2、-3
照网址从图床把图片取回本地
改写正文里的图片引用为 images/<本地文件名>
落盘
```

### 一份结果怎么摊成正文

**页码只能靠顺序算出来。** 结果里的页码标记全是**行内**的：`inputImage` 每行都从 `input_img_0.jpg` 重新开始，图片网址里的 `markdown_N` 也是每行从 0 重新开始，`dataInfo.numPages` 说的同样是「这一行有几页」，不是整份文档有几页。

本机那份 105 页的：35 行，每行 3 页，`dataInfo.numPages` 每行都是 3。

所以拼装规则是：**按行序、项序摊平，第 n 个就是第 n 页。**

这个顺序验过了，不是假设：105 页那份摊出来的正文，第 0 页是 RFC 的标题页，第 2–4 页是目录（3.7 节、5.6.6 节、7.8 节一路排下来），第 20 页是 3.7 节的正文，第 51 页是 7.6.2 节——内容确实是文档顺序。

「每行 3 页」是手上的样本都这样，**代码里别写死 3**：有多少页摊多少页。

顺带一件事：图片网址的前缀不止一个。同一份结果里的两张图，一张在 `…/95d672fb-…/markdown_2/imgs/…`，另一张在 `…/6dd354e7-…/` 下——不同的 UUID 目录。所以收图只认完整网址，别去拆前缀。

图片名的作用域是**一份文档**：同一份文档的各页合起来分配——**同一个网址**重复出现要指向同一个文件，不同图恰好同名要错开。**不跨文档共用名字表**，否则 A 文档用掉的图名会逼 B 文档的同名图平白加后缀。所以先收齐再分配，最后才取图和改写。

### 图片名会在页与页之间撞

图片名是按**页内坐标**起的，形如 `img_in_image_box_152_136_1048_296.jpg`（左、上、右、下）。**键里只有坐标，没有页码**——页码藏在网址的目录里：

```
第 0 页  imgs/img_in_image_box_152_136_1048_296.jpg  →  …/markdown_0/imgs/img_in_image_box_152_136_1048_296.jpg
第 1 页  imgs/img_in_image_box_152_136_1048_296.jpg  →  …/markdown_1/imgs/img_in_image_box_152_136_1048_296.jpg
```

**这是实跑出来的。** 把 `probeA.pdf` 的第 0 页复制一份插到最前（4 页），第 0 页和第 1 页一模一样，两页的键就一字不差，只有网址里的 `markdown_0` / `markdown_1` 不同。

所以**不能只按对方给的名字落盘**：那样第 1 页的图会盖掉第 0 页的，正文里两处指向同一个文件，看着却像好的。两条对策：

- **收图按（第几页，图片名）收**，不按图片名收——键只在页内有意义，跨页拿页码分开
- **本地文件名还是用对方给的那个**（`img_in_image_box_152_136_1048_296.jpg`），不自己另起；只在两个不同网址落到同一个文件名时才加 `-2`、`-3`。加后缀是兜底不是常态，没撞的时候落下来的就是原名字

取图要**紧跟解析**：网址带签名，有有效期，不能先存着回头再取。

**取图这一步绕不开联网。** 接口给的就是网址——官方示例也是拿 `requests.get` 一张张下。没有「连图片字节一起返回」的口子。

图床返回的 `Content-Type` 一律是 `application/octet-stream`，不是 `image/jpeg`——**别拿它判断类型**。本地文件名和扩展名按网址路径里那个文件名来。

注意这跟「网址输入」不是一回事：PDF 的网址是**交给服务去取**，本 skill 不下；图片的网址**只有本 skill 自己去取**——服务不返回字节。代价是一个网络依赖，按它的性质处理：紧跟解析立刻取，失败了吵出来。

另外，不从本地 PDF 里自己抠图：正文引用的那些图是版面模型判定的区域，可能是矢量画的图表，也可能跨几个元素，跟 PDF 内部存的图片对象不是一一对应。

### 结果里有两份图

一页的结果里有两处放图，别混：

- **`markdown.images`**：正文引用到的图。**这是要落的**——正文的 `<img>` 指向的就是它
- **`outputImages`**：本机实跑出来，它的键只有一个——`layout_det_res`。名字就说明了：**版面检测结果图**，把识别框画在页面上给人看的那种。一页一张，579 KB；同一页正文引用那张真图才 53 KB

**不落 `outputImages`。** 它不是文档内容，是转换过程的可视化——落进去正好犯「把转换过程的产物混进正文」那条。官方示例把它存了，但那是演示代码。

`result` 里还有两样，也都不落：`dataInfo` 报**这一行**的页数和每页尺寸（`{"numPages": 3, "pages": [{"width": 1224, "height": 1584}, …], "type": "pdf"}`），`preprocessedImages` 是预处理过的整页图。

### 命令行

```
convert.py <输入…> --output <输出根目录> [--model <名字>] [--force] [--jobs <N>]
```

- `<输入…>`：PDF 文件、目录、或 PDF 的公网网址，可以给多个。给目录就递归找 `*.pdf`
- `--output`：输出根目录，**必填，不给就报错退出**。不猜——猜错了要么把结果撒进源目录，要么撒在「当时正好在的那个工作目录」里，两种都不好收拾
- `--model`：接口认的模型名，默认 `PaddleOCR-VL-1.6`，另一个是 `PP-StructureV3`
- `--force`：已转过的也重转
- `--jobs`：同时最多几个文件在转，默认 4。一个文件同一时刻只有一个任务在跑，所以这个数也约等于同时在飞的请求数

批量时进度分两层：一行随进度重画，写整体——已完成/总数、进行中几个、已用时间、预计剩余时间；进行中的文件把服务报的页数进度一并写上。每转完一个文件在上面留一行永久的记录，写文件名、页数、用时。这样进度在动，事后也查得到每个文件花了多久。单文件时只有那一行动态行。那行动态行会有好几个任务同时想改，重画要加锁，否则字符会串。

**页数进度是服务报的，不是我们估的**——任务跑起来之前那格是空的。本机那几次，第一次轮询（1.1 秒）就已经是 `running` 了，所以空的那一小段几乎看不见。

并发下一个文件失败不影响别的：失败的那份记下来（连 `errorMsg` 一起），其余的照转。跑完在末尾汇总列出失败的文件，退出码非零。**缺图的不算失败**（见「落盘」），只在汇总里点个名。

### 网址输入

网址**原样交给接口**的 `fileUrl`，服务自己去取，本 skill 不下载它。省掉一次上传。

本机验过：外部的公网地址也收，不是只认它自家存储。拿 `https://www.w3.org/WAI/ER/tests/xhtml/testfiles/resources/pdf/dummy.pdf` 试的，1 页，正文正常出来。

输出目录名取自网址最后一段（去掉扩展名与查询串）。

服务取不到那个网址时，**提交那一步就会被拒**：本机拿一个指向目录（不是文件）的网址试过，HTTP 400 加 `{"code": 10002, "msg": "文件 URL 无法识别"}`。要登录、要 referer、有反爬这几种没试过，但看形状也是在那一处拒。

### 依赖与调用

```
uv run --with requests --with lxml --with tabulate \
  python <skill目录>/scripts/convert.py <输入…>
```

三个依赖各有各的用处：`requests` 负责提交、轮询和取图，`lxml` 与 `tabulate` 把 HTML 表格转成 Markdown 表格。

要 `uv` 在 PATH 上。脚本开头自己检查三个依赖在不在，缺哪个就报哪个的名字——缺 `lxml`/`tabulate` 时后两者不会报错，只是表格悄悄退回原始 HTML，那种坏法看不出来。

### 落盘

```
<输出根>/<PDF 文件名>/<PDF 文件名>.md
<输出根>/<PDF 文件名>/images/<图片>
```

正文里的引用写成 `![](images/xxx.jpg)`。**正文里的图片引用不出现远程地址**——图片地址带签名，会过期，留在正文里等于埋一批死链。

这条只管**图片引用**，不是「正文里不许有网址」：正文自己讲到网址那是文档内容。本机拿 RFC 9110 前 105 页实测过，那份正文里合法地有 23 处 `http(s)://`（示例 URI、IANA 注册表、许可链接），它们是内容，删了就是丢内容。

**两份输入文件同名时会撞。** `/a/report.pdf` 和 `/b/report.pdf` 都推到 `<输出根>/report/`：串行时后者把前者盖掉，并发时两边同时往一个目录里写，更乱。所以排出任务前先按输出目录去重，撞上的在目录名后面缀区分，并在屏幕上说明改了哪个。

某张图取不回来时：**正文里什么都不加**——引用保持原样指向那个本地文件名，只是文件不存在，渲染出来是个坏图。不留注释（注释是我们这一趟加进去的产物），也不留远程地址（那个地址过一阵子就打不开，看起来却像好的）。失败只在运行输出里报，列清楚哪份文件缺了哪几张。

**这不改变这份文件的成败。** 正文和其余图片都是好的，为一张图把整份判成失败太重——不算转换失败，退出码照旧。

### 正文清理

无条件跑，按顺序：

1. HTML 表格转 Markdown 表格（`lxml` + `tabulate`）
2. 去掉没有内容的包裹标签：`div`、`span`、`center`、`html`、`body`、`p`
3. 连续空行归一，行尾空白去掉
4. `<img src="…">` 整标签改成 `![](images/…)`

HTML 标签里的 `width`、`style` 这类属性一并丢掉——Markdown 没有对应的写法，留着只是噪音。

#### 什么叫「转换过程的产物」

要清掉的是**这一趟转换留下的东西**，不是文档里的内容。分五类：

| 产物 | 从哪来 | 怎么办 |
|:---|:---|:---|
| 分页标记 | 解析结果里可能带 | 去掉。样例那份里没见着，但规则按「出现了就去掉」写，不按「不会出现」假设。只认「整行除了页码什么都没有」——页码是页脚那种独立的一行；夹在正文里的（「详见第 3 页」）分不出来是页码还是内容，一律不动 |
| 占位符 | HTML 表格转 Markdown 时的中间标记 | 必须全部还原。剩下一个就说明这次转换漏了，报错退出，别把标记落进正文 |
| 残留标签 | `div`/`span`/`center` 这类包裹标签，以及**已知的**裸残标签 | 去掉。只删名字在一张已知名单里的那些——按「名字不认识又没属性就删」写会把正文里的 `List<String>`、`<name>`、RFC 里的 `<n>` 当成标签吃掉，那是静默丢内容，比留一个看得见的原始标签坏得多。名单里现在只有一个 `<image>` |
| `<img>` 上的属性 | 解析器给的 `width`、`style` | 整标签换成 Markdown 语法时一并丢掉 |
| 我们自己加的说明 | —— | 「本文由…转换」「共 N 页」这类一律不加 |

样例里数出来的是 8 个 `<div style="text-align: center;">`、3 个带 `width` 的 `<img>`，外加一个 `<image>`——最后那个按第三类清掉。那次普查把每一个不同的标签连计数一起列了出来，里面没有 `</image>`，所以它是个孤零零的开标签，没有配对的收尾。

### 模型怎么挑

默认 `PaddleOCR-VL-1.6`。换模型由调用方或使用者显式传 `--model`。

**本 skill 不做自动路由。** 要判断该用哪个，得先知道这份文档表格多不多、是不是扫描件——而这件事只有解析完才知道，PDF 里没有标记可看。让模型凭文件名或上下文猜，猜错了整篇都得重来。真正会用到另一个模型的通常是批处理，而批处理自己就知道手里这批是什么文档，直接指定就行。

下表照官方文档整理，供指定时参考——**本仓库没有做过两个模型的横向对比**：

| | PaddleOCR-VL | PP-StructureV3 |
|:---|:---|:---|
| `--model` 怎么写 | `PaddleOCR-VL-1.6` | `PP-StructureV3` |
| 结构 | 版面分析 + 视觉语言模型 | 版面检测 + OCR + 表格 + 公式 + 印章 + 图表，多个模块串联 |
| 擅长 | 扫描、倾斜、弯折、屏幕拍摄、复杂光照；多语言 | 表格：有线表与无线表分两套模型，能细到单元格 |
| 弱点 | 模型大，推理慢 | 官方自述纯英文识别能力有限（默认是中英模型） |

### token 从哪来

只认环境变量 `PADDLEOCR_MCP_AISTUDIO_ACCESS_TOKEN`。名字里那个 `MCP` 是历史原因——它原本是给 `paddleocr-mcp` 配的，本 skill 已经不用那个包了，但名字留着：本机已经按它配好，换名字只为了让名字好看，代价是每个使用者都要重配一次。`SKILL.md` 里要写明这一处。

它设在 `~/.claude/settings.json` 的 `env` 段，本机已配好：

```json
{
  "env": {
    "PADDLEOCR_MCP_AISTUDIO_ACCESS_TOKEN": "……"
  }
}
```

官方文档对 `env` 的说法是「给每个会话及其子进程设环境变量」，Bash 工具跑的命令正在其中；本机也核对过一遍，用户 `settings.json` 里 `env` 段的键在 Bash 子进程里都在。`env` 还有两个顺手的性质：设置文件里的值优先于 shell 里 export 的同名变量；保存文件时运行中的会话就会应用新值，不必重开。

**不放进插件的 `userConfig`。** 那条路的值只导出给 hook 进程（`CLAUDE_PLUGIN_OPTION_<KEY>`），到不了 Bash 工具，而本 skill 的脚本正是通过 Bash 工具跑的。何况那会在启用插件时给每个使用者弹一个要 token 的框——通用 skill 不该有这种前提。

缺 token 时的报错要写清楚去哪儿加。`SKILL.md` 里也要写明这一处——本机配好了不代表别人也配了。

### 配额与错误

**本机复现过的两种失败**，都发生在提交那一步，都是 HTTP 400：

| 提交了什么 | 返回 |
|:---|:---|
| 一个不是 PDF 的文件 | `{"code": 10004, "msg": "文件格式不支持"}` |
| 一个取不到的网址（指向目录而不是文件） | `{"code": 10002, "msg": "文件 URL 无法识别"}` |

两种都是**提交时就拒**，不会先收下再失败。`msg` 是服务给的中文原话，直接转给使用者，别自己编解释。

**文档里写、本机没复现过的**：每天 20000 页的配额；403 token 无效或无权限；413 文件过大；429 超出配额或触发限流；500/503/504 服务端问题。碰到时把 HTTP 状态码和响应体一起打出来。

**任务跑起来之后才失败的**是另一回事：那时状态变成 `failed`，原因在 `errorMsg` 里。本机还没见过——跑过的几次都直接 `done` 了。

**网络这一侧单独说。** 本机撞过三次 DNS 解析失败（`getaddrinfo failed`），不是服务的问题，是本机到服务之间断了。所以：

- **轮询自动重试。** 问的是同一个任务号，重试安全，任务在服务端照跑。重试要有间隔和上限，不能变成死循环
- **提交也自动重试。** 提交断在半路时我们不知道服务端收没收到，但重发的是**同一份文件**，服务端认得出来、直接给缓存的结果（本机见到的：同一份文件第二次提交 0.3 秒返回），所以重复建的那个任务不会真的多解析一遍
- **取图自动重试几次。** 也是 GET，重试安全；但网址带签名有有效期，重试别拖太久

报错要让人分得清是「连不上」还是「服务说不行」：前者是网络问题，后者带状态码或 `errorMsg`。

## 测试计划

`tests/test_pdf_to_md.py`，照 `download-md-images` 那份测试的写法：`unittest`，把 `scripts/` 插进 `sys.path` 再 import。**一个测试都不发请求**——`aistudio.py` 可以 import（它只要 `requests` 装着），测的是拿假响应喂进去的状态判断。

- HTML 表格转 Markdown：合并单元格、格子里还嵌着别的标签、表格之外的其他 HTML 原样保留
- 包裹标签拆掉；已知的裸残标签（`<image>`）拆掉，看着像标签的正文（`List<String>`、`<name>`、RFC 里的 `<n>`）原样留着；`table` 留着；`<img>` 整个换成 Markdown 语法、`width` 之类的属性丢掉
- 正文里的分页标记（「第 N 页」、分页符）：整行只有页码的那些行去掉；夹在正文里的不动
- 占位符没还原完：报错退出，不把标记落进正文
- 空行归一、行尾空白
- 图片引用改写：`<img>` 与 `![](…)` 两种写法都认
- JSONL 拼成一份文档：多行按行序摊平、一行里多页按页序摊平、空行跳过、图片清单收齐；**行数和每行页数都不写死**（样本是每行 3 页，但按「有多少算多少」写）
- 页码只看顺序：`inputImage` 和 `markdown_N` 都是行内编号，拼装不能拿它们当页码
- 图片名分配：同名不同图错开、同地址重复出现指向同一文件；作用域是一份文档，两个文档的同名图互不影响
- **跨页同坐标的图**：两页在同一位置各有一张图，键一模一样——要收成两条，分配后指向两个不同文件，正文里各改各的
- 轮询状态机：`pending`/`running`/`done`/`failed` 各走对分支；`running` 时没有 `extractProgress` 不炸（官方示例专门兜了这个）
- 已转过的判据：输出目录里有那份 md 就跳过、没有就转；**不看源文件的修改时间**
- `--output` 不给就报错退出，不猜路径
- 缺图不算失败：正文照落、退出码 0，只在汇总里点名
- 重名输入：两份同名 PDF 在排队前就被分开，输出目录不互相覆盖
- 网址推出输出目录名：带查询串、带 URL 转义、末尾不是 `.pdf` 的
- 取图失败：引用保持原样指向本地名，正文里不加任何东西，也不留远程地址

跑法：`python skills/pdf-to-md/tests/test_pdf_to_md.py`。

端到端（真 PDF、真 token、真配额）不进测试文件，手工跑一次确认。要专门试的几样：

- 路径里带中文、空格、全角括号的那份——**这条比原计划多一层风险**：文件名现在要随 multipart 上传带到服务端，是另一条路，本机没验过
- 一份带图的，确认 `images/` 里的图正是正文引用的那些、数得上、能打开
- 一份比 105 页更大的，看耗时是不是还按 0.8 秒/页走

## 验过什么、还没验什么

**跑通的**（都是本机实跑，2026-09-20）：

| 验的 | 结果 |
|:---|:---|
| 105 页冷跑（服务没见过这份文件） | **84.9 秒**，进度从 0/105 一路报到 105/105 |
| 3 页本地文件 | multipart 上传 1.1 秒，提交到 `done` 1.5 秒（命中缓存） |
| 网址输入 | 公网地址（w3.org 那份），1 页，1.3 秒 |
| 进度是实时的 | `running` 时 `extractedPages` 一路上涨：0 → 6 → 18 → 36 → 51 → 78 → 93 → 105 |
| 提交不是 PDF 的文件 | HTTP 400，`{"code": 10004, "msg": "文件格式不支持"}` |
| 提交取不到的网址 | HTTP 400，`{"code": 10002, "msg": "文件 URL 无法识别"}` |
| `outputImages` 是什么 | 只有 `layout_det_res` 一类——版面检测图 |
| JSONL 的行结构 | 每行 3 页；105 页 = 35 行 × 3 项 |
| 摊平的顺序 | 按行序、项序摊出来的正文确实是文档顺序（标题页 → 目录 → 3.7 节 → …） |
| `markdown.images` 的键 | `imgs/img_in_image_box_左_上_右_下.jpg`，页码在网址的目录里 |
| 图片名跨页会不会撞 | **会**。把第 0 页复制一份插到最前（4 页），两页的键一模一样，只有网址里的 `markdown_0`/`markdown_1` 不同 |
| 取图 | 裸下就成，不用带 token；返回的是真 JPEG |

**还没验的**：

| 项 | 影响 |
|:---|:---|
| `pending` 状态 | 一次没见着——第一次轮询（1.1 秒）就已经是 `running` 了。不影响进度条，但那个分支没跑过 |
| 比 105 页大得多的文档 | 105 页 85 秒；没理由认为更大会出问题，但确实没试过 |
| 每行是不是恒为 3 页 | 手上的样本全是 3。拼装按「有多少算多少」写，不写死 3 |
| 中文/空格/全角括号的文件名 | 本机验过的输入路径走的是库调用；改走 multipart 之后文件名要随请求带过去，是另一回事 |
| 每天的页数配额 | 20000 页是官方文档口径，本机没撞到过 |
| `failed` 状态长什么样 | 只见过提交时的 400；跑到一半失败的情形没碰过 |

**时间数字的适用范围。** 85 秒是 105 页的全过程，约 0.8 秒/页——本机网络正常时的一次结果，不是保证。前面那几个「1.5 秒」「0.3 秒」是命中服务端缓存：同一份文件第二次提交就是这个数。

## 已知局限

- 图片下载失败就找不回来了——地址带签名，过期即失效，重试必须重新解析
- 大文档整份一次提交：中途失败就得整份重来。不切段是有意的（见「为什么不切段」），代价就是这个
- 源 PDF 更新过、但输出目录里那份 md 还在时，会被当成「已转过」跳过，拿到的是旧结果——要自己加 `--force`
- **跨页的表格会断成两截**：结果是一页一项，服务就是这么返回的，跟本 skill 切不切段无关。要接回去得做领域相关的后处理，不在本 skill 范围内。本机没拿一份真跨页表格验过，是从「一页一项」这个结构推的
- 图片名按页内坐标起，跨页同坐标的两张不同图会同名（实测撞过）；已在分配环节错开，但错开后的名字看不出哪张是哪张
- 网址输入只支持直接指向 PDF 的公网地址：要登录、要 referer、有反爬的站点，服务那边取不到
- 模型名带版本号（`PaddleOCR-VL-1.6`），服务升级后可能不认旧名字；那时改 `--model` 的默认值
- 分页标记只删「整行只有一个页码」的那些行。页眉页脚里混着别的字（书名、章节名）时，那一行整个留着——本机没在实际结果里见过页码，这几种写法都是照着常见排版猜的

## 设计取舍

**为什么不切段。** 原先打算按 100 页切段，前提是「单次调用有 100 页上限」。这个前提本机没验出来：194 页的 PDF 服务收下了，105 页的冷跑一次过——**84.9 秒**，进度从 0/105 一路报到 105/105。所以既没有 100 页这道墙，大文档也不像原先以为的那么慢。

原先那个「150 页跑过 600 秒还没完」的判断要撤回。按 105 页 85 秒这个速率，150 页约两分钟；那次的 600 秒多半是本机网络在抖——库在静默重试，把时间耗光了，服务那边其实未必慢。

拆段要付的代价还是实的：读页数、按页边界切、处理接缝、跨页分配图片名，多写一堆代码；而段是串行的，总时长一点不变，只是「能跑完」而已。

原先这里还写过一条「拆段会把跨页的表格切断」——**这条是错的**：解析结果本来就是**一页一项**（105 页那份正好 105 项），跨页的表格不管切不切段都会断。而切段切的地方又正好是页边界，跟本来就断的地方重合，并不会多切一刀。所以拆段在质量上一分不亏，它亏的纯粹是那堆机器。

既然整份提交本来就跑得完，这堆机器就是白搭的。真撞上上限，`errorMsg` 会告诉我们，那时再加不迟。

**为什么提交和轮询都自动重试。** 起初只看幂等：轮询问的是同一个任务号，问一百遍结果一样，安全；提交每发一次就是一个新任务，不幂等，所以本来打算不重试——网络断了的时候不知道服务端收没收到，重试可能白算一份配额。

后来这条不成立：重发的是**同一份文件**，服务端有缓存，重复建的那个任务不会真多解析一遍。既然重复是便宜的，就没有理由让一次网络抖动废掉整趟。

**为什么直接打接口而不用 `paddleocr-mcp` 库。** 见「背景」。

**为什么把 `outputImages` 放着不落。** 见「结果里有两份图」。

**为什么不带配置文件。** 解析结果里的正文噪声跟文档类型强相关——同一套「删哪些章节」的规则，换个领域就是错的。与其带一份看着能用、实际会误删的默认配置，不如不带，把这件事明确交给调用方。
