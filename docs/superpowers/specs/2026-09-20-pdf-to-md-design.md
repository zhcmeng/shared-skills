# pdf-to-md：用 PaddleOCR 把 PDF 转成 Markdown

日期：2026-09-20
状态：待评审

## 背景

给本仓库加一个 skill：把 PDF 转成 Markdown，落到磁盘上。

解析交给 PaddleOCR 在 AI Studio 上的接口。这是个云端服务——**整份 PDF 会上传到对方服务器**，解析也在那边做。

接口是异步的，三步：

1. `POST /api/v2/ocr/jobs` 提交，拿到一个任务号
2. `GET /api/v2/ocr/jobs/<任务号>` 反复问，直到状态变成 `done` 或 `failed`
3. 拿 `done` 里给的地址下载结果——一份 JSONL，**一页一行**

**不用 `paddleocr-mcp` 这个包。** 它既能当库 import，也能当 MCP 服务跑，但本 skill 真正需要的三样，它一样都不给：

- **等不了**：轮询超时写死 600 秒，超了就扔 `PollTimeoutError`——而任务在服务端还在跑
- **看不见进度**：接口在 `extractProgress` 里实时报「已解析几页 / 共几页」，库不往外给
- **看不见错误**：服务端给的失败原因在 `errorMsg` 里，库那层裹一层或者抹掉

它另外支持的本地推理、自建服务、别的云厂商、base64 输入，本 skill 一样都用不上。直接打接口，代码不多，上面三样全有。

## 目标

- 输入是本地 PDF 文件、装着 PDF 的目录（批量），或 PDF 的公网网址
- 输出一份干净的 Markdown：正文里出现的图片全部落到本地，引用改成相对路径
- 转换过程不进对话——正文多长都不占上下文
- 落盘的正文就是文档内容本身，不带转换过程的产物：没有分页标记、没有没还原的占位符、没有残留的包裹标签、没有临时路径、没有我们自己加的说明
- 批量时显示进度和预计剩余时间，转过的跳过

## 非目标

- 不做领域专属的正文清理（删目录、按标题截断某一类章节）。要这类行为，调用方在转换之后自己处理
- 不做扫描件的识别参数调优，不做版面还原的人工干预
- 不收图片输入。图片转 Markdown 是另一回事——没有分页，也没有正文里的图片引用要改写，混进来只会把命令行的语义弄浑
- 不动 `hooks/`、状态栏、常驻规则

## 决策记录

|:---|:---|:---|

| 输入从哪来 | 本地路径、目录，或公网网址 | 网址走接口的 `fileUrl`，由服务自己去取，本 skill 一个字节都不下——省掉一次上传 |
| 大文档怎么处理 | 整份一次提交，不切段 | 见「为什么不切段」 |
| 图片从哪来 | 结果里给一张「图片名 → 图床网址」对照表，脚本照网址把图取回本地 | 正文里只有引用名，图片本体不在结果里；接口没有「连字节一起返回」的口子 |

| 输出布局 | `<输出根>/<名字>/<名字>.md` + `<输出根>/<名字>/images/` | md 与图片同在一个目录，整个目录能单独搬走 |
| 默认模型 | `PaddleOCR-VL-1.6` | 官方文档里它是新一代，擅长扫描、倾斜与多语言；换模型由调用方显式指定，本 skill 不做自动路由 |
| 清理范围 | 只做通用的（表格、包裹标签、空白、图片引用），不带配置文件 | 通用的才收进本仓库 |

| 并发 | 池子按**文件**排队，一个文件一个任务，上限默认 4（`--jobs` 可调） | 配额是固定的一笔账，串行只是慢。按文件排队让进度、失败、落盘、图片名天然按文件划分，不必额外记账 |
| 已转过的 | 默认跳过 | 断点续跑靠它；要重转加 `--force` |
| 落盘正文的形态 | 就是文档内容本身，不带转换过程的产物——分页标记、没还原的占位符、残留的包裹标签都不留 | 「正文干净」这条要求 |

## 设计

### 文件清单

```
skills/pdf-to-md/SKILL.md              用法说明：怎么调、两个模型各自的特点、配额与错误
skills/pdf-to-md/scripts/convert.py    CLI 入口与编排：参数、任务池、进度条、已转过判断、落盘
skills/pdf-to-md/scripts/aistudio.py   跟接口打交道：取 token、上传、轮询、取结果、照网址取回图片
skills/pdf-to-md/scripts/markdown.py   纯文本：表格、包裹标签、空白、图片引用改写、图片名分配、多页拼装
skills/pdf-to-md/tests/test_pdf_to_md.py
```

`markdown.py` 不导入网络和文件相关的库，也不依赖 token——所有能单测的逻辑都集中在这里，包括图片名的分配和把 JSONL 拼成一份文档（它们只是拿字典和字符串做事，不碰网络）。`aistudio.py` 是唯一 import `requests` 的地方。

`SKILL.md` 的 frontmatter 要有 `name: pdf-to-md` 和一段带触发词的 `description`，照 `download-md-images` 那份的写法——写明什么时候用它，也写明什么时候不用（导出成 PDF 是 `md-export` 的事）。

顺带把 `.claude-plugin/plugin.json`（1.8.3）和 `.claude-plugin/marketplace.json`（1.8.2）的版本号对齐，并在 `README.md` 的 skill 表里补一行。

### 接口怎么用

三处细节照官方示例抄，不自己规范化：

- **提交**：本地文件走 multipart（`files={"file": f}`），`model` 和 `optionalPayload` 放在表单字段里；网址走 JSON 体，字段叫 `fileUrl`
- **轮询**：`running` 时 `extractProgress` 不一定在——官方示例专门拿 `try/except KeyError` 兜了。所以读进度要按「可能没有」写
- **模型名**：两个名字的写法不一样。`PaddleOCR-VL-1.6` 带横杠还带版本号，`PP-StructureV3` 不带横杠。照抄，别自己统一

`optionalPayload` 那三个开关（`useDocOrientationClassify`、`useDocUnwarping`、`useChartRecognition`）官方示例都给的 `False`，本 skill 照给，也不给使用者开关——这三个都是「多花时间换更好的还原」，本机没试过效果，等真碰上需要的文档再说。

### 数据流

```
输入（文件 / 目录 / 网址）
  └ 网址：原样交给接口的 fileUrl，服务自己去取，本 skill 不下载
文件排进池子并发处理（上限 --jobs）
提交，拿任务号
  └ 本地文件：整份 multipart 上传
轮询，把 extractProgress 的「已解析页数 / 总页数」喂给进度条
done → 下载 resultUrl.jsonUrl 那份 JSONL
逐行解析：一页一行，拼出 {正文, 图片名→图床网址 对照表}
收集全部页引用到的图片
  └ 同一个网址 → 同一个本地文件
  └ 本地文件名取自网址里的文件名；已被别的网址占用就追加 -2、-3
照网址从图床把图片取回本地
改写正文里的图片引用为 images/<本地文件名>
落盘
```

图片名的作用域是**一份文档**：同一份文档的各页合起来分配——同一张图重复出现要指向同一个文件，不同图恰好同名要错开。**不跨文档共用名字表**，否则 A 文档用掉的图名会逼 B 文档的同名图平白加后缀。所以先收齐再分配，最后才取图和改写。

取图要**紧跟解析**：网址带签名，有有效期，不能先存着回头再取。

**取图这一步绕不开联网。** 接口给的就是网址——官方示例也是拿 `requests.get` 一张张下。没有「连图片字节一起返回」的口子。

注意这跟「网址输入」不是一回事：PDF 的网址是**交给服务去取**，本 skill 不下；图片的网址**只有本 skill 自己去取**——服务不返回字节。代价是一个网络依赖，按它的性质处理：紧跟解析立刻取，失败了吵出来。

另外，不从本地 PDF 里自己抠图：正文引用的那些图是版面模型判定的区域，可能是矢量画的图表，也可能跨几个元素，跟 PDF 内部存的图片对象不是一一对应。

### 结果里有两份图

JSONL 每一页里有两处放图，别混：

- **`markdown.images`**：正文里引用到的图。**这是要落的**——正文的 `<img>` 指向的就是它
- **`outputImages`**：官方示例也存了，但存的时候自己给文件名缀了页码（`f"{img_name}_{page_num}.jpg"`），说明它没有自带能直接当文件名的路径。按名字和 `PP-StructureV3` 那套的惯例，这多半是**版面检测的可视化图**——把识别框画在页面上给人看的那种

**先不落 `outputImages`。** 它到底是内容图还是带框的页面截图，本机没验过（网络不通）。要落也是一行代码的事：第一次真跑时打开看一眼，是文档里的图就补上；是带框的截图就别落——那正是把转换过程的产物混进正文。

### 命令行

```
convert.py <输入…> [--output <输出根目录>] [--model <名字>] [--force] [--jobs <N>]
```

- `<输入…>`：PDF 文件、目录、或 PDF 的公网网址，可以给多个。给目录就递归找 `*.pdf`
- `--output`：输出根目录。不给时，落在输入所在的目录（目录批量就落在那个目录）；输入是网址时必须给——没有本地目录可推断
- `--model`：接口认的模型名，默认 `PaddleOCR-VL-1.6`，另一个是 `PP-StructureV3`
- `--force`：已转过的也重转
- `--jobs`：同时最多几个文件在转，默认 4。一个文件同一时刻只有一个任务在跑，所以这个数也约等于同时在飞的请求数

批量时进度分两层：一行随进度重画，写整体——已完成/总数、进行中几个、已用时间、预计剩余时间；进行中的文件把服务报的页数进度一并写上。每转完一个文件在上面留一行永久的记录，写文件名、页数、用时。这样进度在动，事后也查得到每个文件花了多久。单文件时只有那一行动态行。那行动态行会有好几个任务同时想改，重画要加锁，否则字符会串。

**页数进度是服务报的，不是我们估的**——它只在任务真跑起来之后才有，头几秒（`pending`）那格是空的。

并发下一个文件失败不影响别的：失败的那份记下来（连 `errorMsg` 一起），其余的照转。跑完在末尾汇总列出失败的文件，退出码非零。

### 网址输入

网址**原样交给接口**的 `fileUrl`，服务自己去取，本 skill 不下载它。省掉一次上传。

本机验过：外部的公网地址也收，不是只认它自家存储。拿 `https://www.w3.org/WAI/ER/tests/xhtml/testfiles/resources/pdf/dummy.pdf` 试的，1 页、3.2 秒、正文正常出来。

输出目录名取自网址最后一段（去掉扩展名与查询串）；`--output` 必须给。

服务取不到那个网址时（要登录、要 referer、有反爬、指向的不是 PDF），失败原因由 `errorMsg` 带回，本 skill 原样报出，不自己编解释。这几种失败本机没试过。

### 依赖与调用

```
uv run --with requests --with lxml --with tabulate \
  python <skill目录>/scripts/convert.py <输入…>
```

三个依赖各有各的用处：`requests` 负责提交、轮询和取图，`lxml` 与 `tabulate` 把 HTML 表格转成 Markdown 表格。

要 `uv` 在 PATH 上。脚本开头自己检查三个依赖在不在，缺哪个就报哪个的名字——缺 `lxml`/`tabulate` 时后两者不会报错，只是表格悄悄退回原始 HTML，那种坏法看不出来。

### 落盘

```
<输出根>/<PDF 文件名>/<PDF 文件名>.md
<输出根>/<PDF 文件名>/images/<图片>
```

正文里的引用写成 `![](images/xxx.jpg)`。**正文里不出现远程地址**——图片地址带签名，会过期，留在正文里等于埋一批死链。

**两份输入文件同名时会撞。** `/a/report.pdf` 和 `/b/report.pdf` 都推到 `<输出根>/report/`：串行时后者把前者盖掉，并发时两边同时往一个目录里写，更乱。所以排出任务前先按输出目录去重，撞上的在目录名后面缀区分，并在屏幕上说明改了哪个。

某张图取不回来时：**正文里什么都不加**——引用保持原样指向那个本地文件名，只是文件不存在，渲染出来是个坏图。不留注释（注释是我们这一趟加进去的产物），也不留远程地址（那个地址过一阵子就打不开，看起来却像好的）。失败只在运行输出里报，列清楚哪份文件缺了哪几张。

### 正文清理

无条件跑，按顺序：

1. HTML 表格转 Markdown 表格（`lxml` + `tabulate`）
2. 去掉没有内容的包裹标签：`div`、`span`、`center`、`html`、`body`、`p`
3. 连续空行归一，行尾空白去掉
4. `<img src="…">` 整标签改成 `![](images/…)`

HTML 标签里的 `width`、`style` 这类属性一并丢掉——Markdown 没有对应的写法，留着只是噪音。

#### 什么叫「转换过程的产物」

要清掉的是**这一趟转换留下的东西**，不是文档里的内容。分五类：

| 产物 | 从哪来 | 怎么办 |
|:---|:---|:---|
| 分页标记 | 解析结果里可能带 | 去掉。样例那份里没见着，但规则按「出现了就去掉」写，不按「不会出现」假设 |
| 占位符 | HTML 表格转 Markdown 时的中间标记 | 必须全部还原。剩下一个就说明这次转换漏了，报错退出，别把标记落进正文 |
| 残留标签 | `div`/`span`/`center` 这类包裹标签，以及没属性的残标签 | 去掉 |
| `<img>` 上的属性 | 解析器给的 `width`、`style` | 整标签换成 Markdown 语法时一并丢掉 |
| 我们自己加的说明 | —— | 「本文由…转换」「共 N 页」这类一律不加 |

样例里数出来的是 8 个 `<div style="text-align: center;">`、3 个带 `width` 的 `<img>`，外加一个没属性的 `<image>`——最后那个按第三类清掉。

### 模型怎么挑

默认 `PaddleOCR-VL-1.6`。换模型由调用方或使用者显式传 `--model`。

**本 skill 不做自动路由。** 要判断该用哪个，得先知道这份文档表格多不多、是不是扫描件——而这件事只有解析完才知道，PDF 里没有标记可看。让模型凭文件名或上下文猜，猜错了整篇都得重来。真正会用到另一个模型的通常是批处理，而批处理自己就知道手里这批是什么文档，直接指定就行。

下表照官方文档整理，供指定时参考——**本仓库没有做过两个模型的横向对比**：

| | PaddleOCR-VL | PP-StructureV3 |
|:---|:---|:---|
| `--model` 怎么写 | `PaddleOCR-VL-1.6` | `PP-StructureV3` |
| 结构 | 版面分析 + 视觉语言模型 | 版面检测 + OCR + 表格 + 公式 + 印章 + 图表，多个模块串联 |
| 擅长 | 扫描、倾斜、弯折、屏幕拍摄、复杂光照；多语言 | 表格：有线表与无线表分两套模型，能细到单元格 |
| 弱点 | 模型大，推理慢 | 官方自述纯英文识别能力有限（默认是中英模型） |

### token 从哪来

只认环境变量 `PADDLEOCR_MCP_AISTUDIO_ACCESS_TOKEN`。名字里那个 `MCP` 是历史原因——它原本是给 `paddleocr-mcp` 配的，本 skill 已经不用那个包了，但名字留着：本机已经按它配好，换名字只为了让名字好看，代价是每个使用者都要重配一次。`SKILL.md` 里要写明这一处。

它设在 `~/.claude/settings.json` 的 `env` 段，本机已配好：

```json
{
  "env": {
    "PADDLEOCR_MCP_AISTUDIO_ACCESS_TOKEN": "……"
  }
}
```

官方文档对 `env` 的说法是「给每个会话及其子进程设环境变量」，Bash 工具跑的命令正在其中；本机也核对过一遍，用户 `settings.json` 里 `env` 段的键在 Bash 子进程里都在。它还有两个顺手的性质：设置文件里的值优先于 shell 里 export 的同名变量；保存文件时运行中的会话就会应用新值，不必重开。

**不放进插件的 `userConfig`。** 那条路的值只导出给 hook 进程（`CLAUDE_PLUGIN_OPTION_<KEY>`），到不了 Bash 工具，而本 skill 的脚本正是通过 Bash 工具跑的。何况那会在启用插件时给每个使用者弹一个要 token 的框——通用 skill 不该有这种前提。

缺 token 时的报错要写清楚去哪儿加。`SKILL.md` 里也要写明这一处——本机配好了不代表别人也配了。

### 配额与错误

接口这边：

- 每天 20000 页（官方文档口径，本机没撞到过）
- 403 token 无效或无权限；413 文件过大；429 超出配额或触发限流；500/503/504 服务端问题。这几个本机都没复现过——报错时把状态码和响应体一起打出来，不自己编解释
- 任务状态变成 `failed` 时，`errorMsg` 里是服务端给的原因，原样报出

**网络这一侧单独说。** 本机撞过三次 DNS 解析失败（`getaddrinfo failed`），不是服务的问题，是本机到服务之间断了。所以：

- **轮询自动重试。** 问的是同一个任务号，重试安全，任务在服务端照跑。重试要有间隔和上限，不能变成死循环
- **提交不重试。** POST 一次就是一次解析任务；网络断了的时候不知道服务端收没收到，重试可能白算一份配额。报错退出，让人自己决定要不要再跑一次
- **取图自动重试几次。** 也是 GET，重试安全；但网址带签名有有效期，重试别拖太久

报错要让人分得清是「连不上」还是「服务说不行」：前者是网络问题，后者带状态码或 `errorMsg`。

## 测试计划

`tests/test_pdf_to_md.py`，照 `download-md-images` 那份测试的写法：`unittest`，把 `scripts/` 插进 `sys.path` 再 import。**一个测试都不发请求**——`aistudio.py` 可以 import（它只要 `requests` 装着），测的是拿假响应喂进去的状态判断。

- HTML 表格转 Markdown：合并单元格、格子里还嵌着别的标签、表格之外的其他 HTML 原样保留
- 包裹标签与没属性的残标签拆掉，`table` 留着；`<img>` 整个换成 Markdown 语法、`width` 之类的属性丢掉
- 正文里的分页标记（「第 N 页」、分页符）：出现了就去掉
- 占位符没还原完：报错退出，不把标记落进正文
- 空行归一、行尾空白
- 图片引用改写：`<img>` 与 `![](…)` 两种写法都认
- 图片名分配：同名不同图错开、同地址重复出现指向同一文件；作用域是一份文档，两个文档的同名图互不影响
- JSONL 拼成一份文档：页序正确、空行跳过、一页里有多项 `layoutParsingResults` 时按顺序摊平、图片对照表收齐
- 轮询状态机：`pending`/`running`/`done`/`failed` 各走对分支；`running` 时没有 `extractProgress` 不炸（官方示例专门兜了这个）
- 重名输入：两份同名 PDF 在排队前就被分开，输出目录不互相覆盖
- 网址推出输出目录名：带查询串、带 URL 转义、末尾不是 `.pdf` 的
- 取图失败：引用保持原样指向本地名，正文里不加任何东西，也不留远程地址

跑法：`python skills/pdf-to-md/tests/test_pdf_to_md.py`。

端到端（真 PDF、真 token、真配额）不进测试文件，手工跑一次确认。要专门试的几样：

- 路径里带中文、空格、全角括号的那份——**这条比原计划多一层风险**：文件名现在要随 multipart 上传带到服务端，是另一条路，本机没验过
- 一份带图的，确认 `images/` 里的图正是正文引用的那些，并顺便看一眼 `outputImages` 到底是什么
- 一份超过 100 页的，看服务收不收、要多久

## 还没验过的

凡是「本机验过」的，上面都写了出处。剩下这些是**照官方示例写的，一次没跑过**——等网络通了要一项项补：

| 项 | 影响 |
|:---|:---|
| 直接打接口这条路的全流程 | 提交、轮询、取 JSONL、拼回正文，一次都没跑通 |
| `outputImages` 是什么 | 决定落不落；不落它就不会出现在输出里 |
| `markdown.images` 的键长什么样 | 值确定是网址；键里带不带目录前缀没验过（本机见过的文件名形如 `img_in_image_box_左_上_右_下.jpg`，用的是页内坐标）。影响本地文件名怎么取 |
| 一行 JSONL 是不是只有一页 | 官方示例里一页的 `layoutParsingResults` 可以有多项，按顺序摊平；多页挤一行、一页拆多行这两种情形没见过 |
| 100 页以上到底行不行 | 服务接受过 194 页的提交，但那一次多半命中了缓存，说明不了耗时。150 页那次服务也接受了（给了任务号），只是库的 600 秒超时先到了 |
| 中文/空格/全角括号的文件名 | 本机验过的那次走的是库调用；改走 multipart 之后文件名要随请求带过去，是另一回事 |
| 每天的页数配额 | 20000 页是官方文档口径，本机没撞到过 |

## 已知局限

- 图片下载失败就找不回来了——地址带签名，过期即失效，重试必须重新解析
- 大文档整份一次提交：中途失败就得整份重来。不切段是有意的（见「为什么不切段」），代价就是这个
- 提交那一下网络断了，这次就废了，得重跑（不自动重试的原因见「配额与错误」）
- 图片地址的文件名取自页内坐标，同位置的两张不同图本来会同名；已在分配环节错开，但错开后的名字看不出哪张是哪张
- 网址输入只支持直接指向 PDF 的公网地址：要登录、要 referer、有反爬的站点，服务那边取不到
- 模型名带版本号（`PaddleOCR-VL-1.6`），服务升级后可能不认旧名字；那时改 `--model` 的默认值

## 设计取舍

**为什么不切段。** 原先打算按 100 页切段，前提是「单次调用有 100 页上限」。这个前提本机没验出来：194 页的 PDF 提交后服务接受了，150 页那次服务也接受了（给了任务号），只是库的 600 秒轮询先到了。上限到底在哪、有没有，不知道。

拆段要付的代价是实的：读页数、按页边界切、处理接缝、跨页分配图片名，多写一堆代码；而段是串行的，总时长一点不变，只是「能跑完」而已。质量上还要掉一层——跨页的表格和段落会被切断。

既然现在能自己定超时、能看见进度，等就不再是黑箱，「跑不完」也就不再是理由。所以整份提交；真撞上上限，`errorMsg` 会告诉我们，那时再加不迟。

**为什么轮询重试、提交不重试。** 看的是这两个动作幂等不幂等，不是「网络错误」四个字本身。轮询问的是同一个任务号，问一百遍结果一样；提交每问一次就是一个新任务。

**为什么直接打接口而不用库。** 见「背景」。

**为什么把 `outputImages` 放着不落。** 见「结果里有两份图」。

**为什么不带配置文件。** 解析结果里的正文噪声跟文档类型强相关——同一套「删哪些章节」的规则，换个领域就是错的。与其带一份看着能用、实际会误删的默认配置，不如不带，把这件事明确交给调用方。
