# 测试用例产出：补齐栏目与拴编号 — 设计文档

日期：2026-09-23
状态：待评审

这是 `2026-09-23-测试用例指南技能-design.md` 的修订。那份把技能搭了起来，这份动它三处：测试数据需求补一栏、用例与规程里凡用到数据或环境就写编号、自检脚本加两条校验。

## 1. 由头

拿 `evals/token-counter/test-case-design/` 那套真实产出（token-counter 技能的测试设计，五份文档全在）对着标准逐栏核了一遍，核出三处：

| 问题 | 具体表现 |
|:---|:---|
| 环境编号没人引用 | `ENV-1`～`ENV-9` 只出现在「测试环境需求」自己那份里，用例和规程里一个都没有。规程的「启动」栏其实用大白话把这些环境要素重述了一遍——「确认机器上 `tokenizers` 可以导入」「确认命令行能接管道与重定向，并能分别取到标准输出、标准错误与退出码」——对应的正是 ENV-1、ENV-8、ENV-9，但没挂编号 |
| 数据与用例对不上 | 5 条用例（TC-7、TC-16、TC-17、TC-18、TC-20）的输入没有数据编号；其中 2 条的输入在数据需求里根本不存在（TC-7 的「0 字节标准输入」——DATA-10 是 0 字节的**文件**；TC-16 的「深度求索 DeepSeek」）；同一份数据两种写法——DATA-2 是「hello world」，TC-6 按编号引用，TC-17/18/19/20 写成字面文本，而规程 TP-3 里又按编号写了 |
| 数据需求缺一栏 | 缺「重置需求」 |

第三处是第一处和第二处之外的独立缺口。三处的共同点是：**自检脚本查不出来**——`check_docs.py` 只认两张对应表（「依据 → 模型」「覆盖项 ↔ 用例」），数据与环境的引用完整性不在它的射程里。

## 2. 判据：产出是给模型读的

这条是本次所有取舍的总尺度，先立在前面。

产出的读者是**模型**：模型读这五份文档，照着建测试用例、执行测试。产出不是给人排期、分工、归档用的——没有第二个人拿它去开会。

上一份设计文档 §5 里有一条决策：

> 原本还有第三类——编号规则、责任人、需要的周期、重置与归档这些取决于被测项目组织安排的字段。它们已全部砍掉：编号改由技能给建议方案，责任与周期等字段从产出里移除。

这条把四样归成一类一起砍。归类的错处见 D1：**「重置需求」不属于「取决于被测项目组织安排」那一类**，它取决于测试本身的设计。

## 3. 诊断：对着标准逐栏核

标准（GB/T 38634.3）第 9 章逐条规定了五份文档各有哪些栏目。与现在的产出对照：

| 文档 | 标准规定的栏目 | 现在 | 差 |
|:---|:---|:---|:---|
| 测试模型规格说明 | 9.2.2 唯一标识符、9.2.3 目标、9.2.4 优先级、9.2.5 测试策略摘要、9.2.6 测试模型、9.2.7 可追溯性 | 六栏齐 | 无 |
| 测试用例规格说明 | 9.3.2 覆盖项四栏、9.3.3 用例七栏 | 齐 | 无 |
| 测试规程规格说明 | 9.4.2～9.4.8 七栏 | 齐 | 无 |
| 测试数据需求 | 9.5.2 唯一标识符、9.5.3 描述、9.5.4 责任、9.5.5 需要的周期、**9.5.6 重置需求**、9.5.7 归档或清除 | 只有前两栏 | 缺 4 栏，收 1 栏 |
| 测试环境需求 | 9.6.2 唯一标识符、9.6.3 测试环境项、9.6.4 描述、9.6.5 责任、9.6.6 需要的周期 | 只有前三栏 | 缺 2 栏，全部不收 |

模型、覆盖项、用例三处的「可追溯性」标准允许「记录在测试追踪矩阵中」，本技能用文档末尾的对应表承接，这一栏不算缺。

另有一条与本次相关的标准依据，是「拴编号」那一头的出处：

- **9.5.1 与 9.6.1** 把这两份文档的定位写成「执行**测试规程**规格说明中定义的测试规程所需的」测试数据与测试环境属性——规程是锚点
- **9.6.2** 明说环境项的唯一标识符「用于追溯」（这一句在标准草案里串到了 9.6.3 下，见上一份设计文档 §9 的「字段正文串位」）
- **9.3.3.6 前置条件**：「描述执行测试用例所需的测试环境状态、测试数据，以及与执行测试用例相关的全部特殊约束条件」——用例这头也拴着
- **9.3.3.7 输入**：数据「可以直接给具体数值，也可以按名称指代」——「按名称指代」就是写编号
- **9.7.2、9.8.2**：数据与环境就绪报告靠这两套编号指代。就绪报告是执行阶段的产出，本技能不收，但**它靠编号指代**这一点反过来要求编号先编好、指得到

## 4. 决策记录

| # | 决策点 | 选了什么 | 为什么 |
|:---|:---|:---|:---|
| D1 | 「重置需求」收不收 | **收**，进测试数据需求 | 它回答的是「跑下一条用例之前要不要把数据复位」，是设计问题，设计阶段就定得下来，而且直接决定模型怎么排用例、跑完做什么。token-counter 那套自己就撞上了：TP-3 里每两条用例之间必须重建干净环境、把 wheel 移走再放回，这段现在被塞在规程的「顺序允许变动的程度」那段散文里。9.5.6 的原话是「规定测试数据是否需要在测试过程中重置」 |
| D2 | 「责任」「需要的周期」（数据、环境各一）与「归档或清除」收不收 | **不收** | 责任只管「谁去备」，周期只管排期，归档或清除里「谁去归档」还是人的事——模型读文档执行时三样都用不上。归档或清除另一件事「跑完清掉什么」已有落点，在规程的「停止与结束」栏（9.4.8 的示例就是「终止记录或重置测试数据库」）。这是对标准的剪裁，理由要写进 `文档模板.md` |
| D3 | 编号拴哪一头 | **两头都拴** | 9.3.3.6 拴用例、9.5.1／9.6.1 拴规程，两处依据都在，缺哪头都断。只拴规程的话，最初那个「DATA- 和用例对不上」会原样留着 |
| D4 | 加不加对应表 | **不加** | 照现有先例：规程不另出对应表，靠它自己的用例编号列表承接。引用写在栏目里，完整性交给自检脚本。标准对数据与环境也没设「可追溯性」栏，没要求表这种形式 |
| D5 | 规程里用例之间的复位与准备动作放哪 | 放进「有序执行测试用例」栏 | 9.4.6 给的就是这个位置：「如果规程中一个或多个测试用例的执行结果没有为随后的测试用例准备好前置条件，则可在测试用例之间添加准备前置条件的操作」。现在这段散在「顺序允许变动的程度」那段散文里，模型执行时抓不住 |
| D6 | 自检脚本查到什么程度 | 悬空引用算**错误**，定义了却没人引用算**提示** | 悬空是硬伤——引了一个不存在的数据项，模型查不到就会编。孤儿不一定是错：某个环境项可能确实没有哪条用例直接引它，但它仍是这条规程需要的。错误的归错误，提示的归提示，与本脚本现有做法一致（判不了的东西只提示） |
| D7 | 不收那几栏的理由怎么写 | 从「取决于被测项目的组织安排与排期」改成「这一栏只服务于人的排期与职责分工；本技能的产出是给模型读着建用例、执行测试的」 | 现在那条理由只对 D2 那三样成立，对 D1 那一样不成立。理由写歪了，下一个会话读模板的人就会照着它再砍一刀，把「重置需求」又砍掉 |

## 5. 设计

### 5.1 `文档模板.md` 第六节：测试数据需求

栏从 2 栏扩到 3 栏：

| 栏 | 怎么填 |
|:---|:---|
| 唯一标识符 | 不变（`DATA-…`） |
| 描述 | 不变 |
| **重置需求**（新） | 写这条数据项在测试过程中要不要复位、怎么复位：要复位的写清复位动作是什么；不要复位的写「不需要」。判据：跑完用这条数据项的用例之后，下一条用例的前置条件还成立吗——不成立就要复位。**这一栏不许留空**——`check_docs.py` 的 `check_flat` 要求每格都有字，写「不需要」也算填了 |

「有意不收」那段改写：**责任、需要的周期、归档或清除**三栏不收（原句是四栏，去掉重置需求），理由换成 D7 那条。同时点明这是对标准的剪裁。

### 5.2 `文档模板.md` 第七节：测试环境需求

**栏不变**（唯一标识符、测试环境项、描述）。只改「有意不收」那段的理由，同 D7。

### 5.3 `文档模板.md` 第四、五节：引用编号的规矩

在第四节「测试用例」的**输入**栏与**前置条件**栏、第五节「测试规程规格说明」的**启动**栏，各加一句规矩：

> 凡用到测试数据或测试环境要素，写编号指代，不重述内容——写「样本 DATA-7」，不写「一份内容是……的文件」。

第四节那两栏本来就有相近的话（「可以按名称指代」），这次把「名称」明确成「本技能编的编号」。

### 5.4 `文档模板.md` 第五节：「有序执行测试用例」栏

加一句：用例之间的复位与准备动作**写在这一栏里**，每条动作写在它服务的那条用例前面。现在模板只说「可在两条之间添加准备前置条件的操作」，没说这句该落在哪一栏。

### 5.5 `check_docs.py`

四处改动：

1. `DATA_COLS` 从 `["唯一标识符", "描述"]` 改成 `["唯一标识符", "描述", "重置需求"]`
2. `ENV_COLS` 不动
3. 新增**悬空引用**校验（错误）：用例规格说明与规程规格说明里出现的 `DATA-n` / `ENV-n`，每一个都要在对应文档里有定义处。做法沿用现有的 `defined()`，写在各文档的检查函数里按现有顺序跑
4. 新增**孤儿**校验（提示）：测试数据需求、测试环境需求里定义了、但用例与规程里谁都没引用的编号，报出来

第 3 条有个约束：`check_docs.py` 是分文档逐个检查的，而「悬空」要跨文档看。现有代码已经这么干了（`check_case` 拿 `tms` 判覆盖项的可追溯性、`check_proc` 拿 `tcs` 判规程引的用例），照着同样的做法把 `datas`、`envs` 传进去。

### 5.6 其余要跟着动的文件

- `tests/test-case-design/test_check_docs.py`：现有十二条要跟着改（`DATA_COLS` 相关的用例），另加新校验的用例——先造一套合规产出确认判过，再逐处改坏确认每处都被逮住
- `references/文档示例.md`：第四、五节的表头现在照标准原样留着，与本技能的契约对不上——数据那份是 6 栏（多了责任人、使用期限、归档/处置），环境那份也是 6 栏（多了类型、责任人、占用时间）。改成本技能契约的栏：数据 3 栏、环境 3 栏。环境那份的「类型」并进「测试环境项」栏（写成「硬件：笔记本电脑」）。顺带让传统企业 B 那份规程示例的「启动」栏示范一处编号引用，新规矩有个样子可看
- `references/流程.md`：TD4 里「识别测试数据与环境需求」那条，补一句说明识别出来的东西要拴编号
- `plugin/.claude-plugin/plugin.json` 与 `.claude-plugin/marketplace.json`：抬版本号，两处一致（`feat` 抬中间位）

## 6. 验收判据

1. `文档模板.md` 里测试数据需求是 3 栏、测试环境需求是 3 栏；两份的「有意不收」理由都换成了 D7 那条
2. `文档模板.md` 第四、五节写明了「凡用到就写编号」；第五节点明了用例间动作的位置
3. 全库 grep 不到任何标准名称、章节号、条款号（这条是上一份设计文档 D7 的既有要求，本次新增的内容也要守住）
4. `check_docs.py` 的两条新校验各自能被改坏逮住：删掉一个数据项的定义处，引用它的用例要报错；把某条环境项的引用全删掉，它要报提示
5. `tests/test-case-design/test_check_docs.py` 全过
6. 照 `文档示例.md` 那套改出一套符合新契约的产出，`check_docs.py` 零错、零提示——新加的引用都指得到定义处，没有孤儿
7. `文档示例.md` 第四、五节的表头与模板逐栏一致：数据 3 栏、环境 3 栏，没有责任、期限、类型、归档这些模板里没有的栏
8. `bash checks/verify.sh --changed` 过；两处版本号一致
