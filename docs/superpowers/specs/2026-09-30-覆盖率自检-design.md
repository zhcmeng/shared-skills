# 覆盖率自检：算式写清，算完的数落进产出 — 设计文档

日期：2026-09-30
状态：待评审

这份动 `test-case-design` 的产出契约：第 6 步自检算出来的覆盖率，落到测试用例规格说明新加的一块「覆盖率自检」里；带档位那几门的 T 怎么算出来，写进覆盖率那份文件。技能的产出一律是六份文档，这份设计不碰这个边界。

## 1. 由头

第 6 步是「算覆盖率，判断是否达到完成准则」（`SKILL.md:43`）。这一步现在有两处缺口：

**一、T 怎么数出来没写清。** 大多数技术的 T 就是覆盖项清单的行数，数一下就有。带档位的那几门不是——`覆盖率与完成准则.md:29` 到 `:35` 的速查表只给 N、T 是什么，不给怎么算；各技术文件的算例里直接写出结果数（组合测试成对档 `T＝21`、分类树最大化档 `T＝336`、状态转移全转移档 `T＝16`、1-switch 档 `T＝10`），**这些数是从模型算出来的那几步算式，全库没有一处写过**。真去算的时候，这里只能靠反推。

**二、算完的数没地方落。** 第 6 步的落盘只有决策依据（`SKILL.md:43`：补了哪些、剔了哪些、凭什么）。六份产出里没有一处记 N、T、C——算没算过、算出来多少、过没过，用户从产出里一个字也看不到。技能自己的规矩是「依据要落进产出，不是心里想过就算」（`SKILL.md:146`），覆盖率这一处不满足它。

## 2. 判据

**一、T 数的是识别出来的条数，算式是核对的尺子。** 覆盖率的定义里 T 是「由测试设计技术识别的测试覆盖项总数量」，识别落在覆盖项清单上——所以 **T 就等于清单里这门技术（这一档）的条数**，判为不可行、已剔除的不计入。算式（§4.1）用来核这个条数：算出来多少条，清单里就该有多少条；对不上说明识别漏了或多了，回第 3 步。两者不是二选一，算式管的是「识别全没全」，清单管的是「识别出来的有哪些」。

**二、算完的数落进产出。** 测试用例规格说明加一块「覆盖率自检」，一行一门选定的技术，把 T、N、C 与要求并排列出来。放了这一块，「过没过」在产出里一眼看得到，不必回头翻对话。

**三、脚本核得了的与核不了的，分开说。** 脚本能核：T 与该行列出的编号条数一致、N 与对应表里非空的行数一致、覆盖率栏的算式算得对、栏目齐不齐、引的编号有没有定义处。脚本核不了：T 该是几（那要拿算式核模型，模型是自由格式）、完成准则要求抄得对不对（那是散文）、某一门技术是不是漏了整行（选定技术写在测试策略摘要里，脚本读不出来）。核不了的写进提示，不假装核过。

## 7. 已知的连带代价

- **已有产出都缺这一块。** 契约一改，盘上过去跑的产出（含归档的 `evals/token-counter/test-case-design/`）拿 `check_docs.py` 一跑就报「缺这一块」。这一轮只更新在用的 `evals/plain-language/test-case-design/`，归档那套照先例不动——它本来就已经落后好几版契约了。
- **算式是反推的。** 技能不许联网翻标准（`SKILL.md:10`），这七条算式是从各技术的定义与算例里的结果数反推出来的，逐条对得上（§4.1 的验证列）。对不上原文的风险由读的人承担：正式场合仍要拿现行版本核一遍——这一点 README 的「来源与效力」一节本来就写着。
- **T 该是几，脚本核不了。** 脚本只核「T 与这一栏列出的编号条数一致」；编号是不是识别全了，要人拿算式核。放在少数几门下（分类树最大化档、状态转移 N-switch 档）尤其要人看——那里连清单本身都可能是手写的。
- **示例那一块的 100% 是节选的 100%。** 它只说明「已识别的都覆盖了」，不说明识别全了（D13 的注写了这一层，但注是给读的人看的，脚本判不了）。
- `check_docs.py` 的机械项又多九条，产出写得不对时报错会多几行；测试条数从 65 往上涨，`README.md:128` 那一行要跟着改（改漏了下次谁读 README 就拿到个旧数）。
- 测试用例规格说明从此是五块，比其余五份长一截。
