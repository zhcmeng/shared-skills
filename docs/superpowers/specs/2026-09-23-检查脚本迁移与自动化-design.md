# 检查脚本迁移与自动化 设计

2026-09-23

## 一句话

把 `hooks/verify.sh` 与 `hooks/verify.d/` 挪出 `hooks/`，把插件内容整体挪进 `plugin/`，并让这些检查在提交前和推送后自动跑起来。

## 要解决的问题

### 起因

两件事：

1. 检查脚本跟着插件安装被拷到每个使用者的机器上，而运行时没有任何东西调用它们——只有开发本仓库时才用得上。
2. 这些检查现在只在有人手动敲 `bash hooks/verify.sh` 时才跑。全仓没有 `.github`，没有任何 `.yml`／`.yaml`／`.toml`，`.git/hooks` 是空的。等于没有自动化。

### 核实到的事实

以下每条都实测过，不是推测。

**一、插件安装是整份拷贝。** 官方文档「Plugin caching and file resolution」一节写：

> For security and verification purposes, Claude Code copies *marketplace* plugins to the user's local **plugin cache** (`~/.claude/plugins/cache`), unless the plugin loads in place.

（出于安全与校验的目的，来自插件市场的插件会被拷贝到用户本机的插件缓存目录里，除非该插件是原地加载的。）

本机实查 `~/.claude/plugins/cache/shared-skills/shared-skills/1.11.1/`，里面有 `.claude-plugin`、`skills`、`hooks`、`statusline`、`rules`、`docs`、`README.md`、`LICENSE`、`.gitattributes`、`.gitignore`——整个仓库。本机构建里跳过的东西只有 `.git` 和三个 Claude Code 自己的标记文件（`.claude-plugin-link`、`.in_use`、`.orphaned_at`）。

**二、没有任何「排除某些文件」的机制。** `.pluginignore` 不存在；`.gitignore`、`.gitattributes` 的 `export-ignore`、`package.json` 的 `files` 字段都不参与插件拷贝；`plugin.json` 与 `marketplace.json` 里也没有这类字段。

**三、把 `source` 指向子目录可以避免。** `marketplace.json` 里 `"source": "./"` 表示整个仓库就是插件根。改成 `"./plugin"` 之后，拷过去的只有 `plugin/` 这一个子目录。

**四、全套检查耗时 69 秒**（实测，本机 Windows + Git Bash）：

| 模块 | 耗时 |
|:---|---:|
| `40-notify` | 51.5 秒 |
| `50-notify-render` | 13.2 秒 |
| `10` `20` `25` `30` `60` 合计 | 约 13 秒 |

瓶颈是 Windows 上起进程慢：`40` 要调用 34 次 `hooks/notify`，每次都要起若干进程。这是环境成本，不是脚本写得差，压不下去。

**五、运行时脚本与目录位置无关**，所以重构不需要动它们：

- `hooks/hooks.json` 里写的是 `${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd`，插件根一换照样对
- `hooks/run-hook.cmd` 用 `%~dp0`（自己所在目录）
- `hooks/session-start` 用 `PLUGIN_ROOT="$(cd "${SCRIPT_DIR}/.." && pwd)"`，跟着插件根走
- `hooks/notify`、`statusline/*.py` 不引用仓库内任何路径

**六、除检查脚本外，没有别的脚本依赖这些目录的位置。** 全仓扫过 `.sh`／`.py`／`.json`／`.cmd`／`.ps1`，命中的全是注释与报错文案里的字面字符串（如 `fail "缺 hooks/notify.ps1"`），不构成路径依赖。

## 设计

### 一、目录布局

```
仓库根/                                ← 不跟着插件发出去
├── .claude-plugin/
│   └── marketplace.json               "source": "./plugin"
├── .githooks/
│   └── pre-commit                     提交前钩子
├── .github/
│   └── workflows/verify.yml           持续集成
├── checks/
│   ├── verify.sh                      入口
│   └── verify.d/
│       ├── 10-session-start.sh
│       ├── 20-statusline-sync.sh
│       ├── 25-rules-sync.sh
│       ├── 30-statusline-smoke.sh
│       ├── 40-notify.sh
│       ├── 50-notify-render.sh
│       ├── 60-wiring.sh
│       └── 70-版本号一致.sh            另一个会话新增
├── docs/  evals/
├── README.md  LICENSE
└── plugin/                            ← 只有这个进安装包
    ├── .claude-plugin/plugin.json
    ├── hooks/       hooks.json  run-hook.cmd  session-start  notify  notify.ps1
    ├── skills/      十个技能目录
    ├── rules/       file-edits.md
    └── statusline/  statusline.py  subagent-statusline.py
```

两个决定说明一下：

**`plugin/` 下不放 README 和 LICENSE。** GitHub 靠仓库根的那两份认门面与许可证，`plugin.json` 里已经有 `license` 字段。放两份会各改各的、早晚不一致。

**`checks/` 平铺，不再细分。** 起初想过按被检查的对象分（`checks/hooks/`、`checks/statusline/`……），放弃了：映射关系并非纯按目录能推出来——改 `hooks/session-start` 会连累 `20` 和 `25`，而它们不在同一个子目录里。既然横竖要额外声明，多一层目录就只是多一层。

### 二、路径改写

要改的只有检查脚本，而且是方向相反的两类：

| 类别 | 现在 | 改成 |
|:---|:---|:---|
| 检查脚本**自己**的东西 | `${SCRIPT_DIR}/verify.d` | 跟着新位置走 |
| 检查脚本**要验**的运行时文件 | `${SCRIPT_DIR}/session-start` | 指回 `plugin/hooks/` |

现在这两类都写成 `${SCRIPT_DIR}/...`，长得一模一样——这正是最容易一起改错的地方。

改法是在入口 `checks/verify.sh` 里定义三个变量，模块里一律改用变量名：

```sh
REPO_ROOT="${SCRIPT_DIR}/.."        # 仓库根
PLUGIN_DIR="${REPO_ROOT}/plugin"    # 插件根
HOOKS_DIR="${PLUGIN_DIR}/hooks"     # 运行时 hook 所在
```

于是「脚本自己」用 `${SCRIPT_DIR}`、「要验的东西」用 `${HOOKS_DIR}`，一眼分得开，下次再挪也不会混。

入口原有的三个变量随之改成：

```sh
RULES_FILE="${PLUGIN_DIR}/skills/plain-language/rules.md"
VERIFY_D="${SCRIPT_DIR}/verify.d"
statusline_src="${PLUGIN_DIR}/statusline"
rules_src="${PLUGIN_DIR}/rules"
```

模块里要改的具体位置（共 17 处，全是 `${SCRIPT_DIR}/xxx` 换成 `${HOOKS_DIR}/xxx`）：

| 文件 | 行 |
|:---|:---|
| `10-session-start.sh` | 9、57、77（77 行同时把 `cd "${SCRIPT_DIR}/.."` 换成 `cd "${REPO_ROOT}"`，把 `hooks\run-hook.cmd` 换成 `plugin\hooks\run-hook.cmd`） |
| `20-statusline-sync.sh` | 8、28、36、44 |
| `25-rules-sync.sh` | 9、37、50、58 |
| `40-notify.sh` | 51、402、410、419 |
| `50-notify-render.sh` | 6 |
| `60-wiring.sh` | 25 |

保持不动的结构约束：七个模块仍然是被入口 `source` 进同一个 shell，共享入口定义的 `fail`、`scratch_dir`、`scratch_file`、`test_home`、`statusline_src`、`rules_src`。入口注释里那条「别改成靠 `$( )` 返回值传数组——子 shell 里改的东西传不出来」继续有效。

顺带要改的注释（只是文字，不影响行为）：`hooks/notify:17`、`hooks/notify.ps1:2`、`hooks/session-start:85`、`.gitattributes:5` 里提到 `verify.sh`／`verify.d` 的地方。

还有一处不算路径依赖、但顺手要对齐的：`skills/pdf-to-md/scripts/doctor.py:157` 的提示语里写着「把整个 `skills/pdf-to-md/` 一起拷过来」。它是给使用者看的文案，说的是技能目录本身，不参与开文件，所以不改也不会坏；列在这里只是提醒别把它当成路径依赖去改。

### 三、按改动挑模块

每个模块文件头加一行声明，路径以**仓库根**为基准：

```sh
# watch: plugin/hooks/notify
```

入口新增 `--changed` 参数：读这些声明，跟 `git diff --cached --name-only` 对一遍，挑出该跑的模块。原来的「不带参数跑全部」「带子串跑部分」都不变。

**声明必须只读文件读出，不能靠 source。** 模块一被 source 就会跑起来（`10-session-start.sh` 第 9 行就执行了 `session-start`），所以必须在决定跑不跑**之前**用读文本的方式拿到声明。

匹配规则：声明里以 `/` 结尾的是目录，按前缀匹配；否则按整个路径精确匹配。这条不能省——`plugin/hooks/notify` 若按前缀匹配，会连 `plugin/hooks/notify.ps1` 一起命中，白白多跑 51 秒。

八个模块的声明：

| 模块 | watch |
|:---|:---|
| `10` | `plugin/hooks/session-start`、`plugin/hooks/run-hook.cmd`、`plugin/hooks/hooks.json`、`plugin/skills/plain-language/rules.md` |
| `20` | `plugin/hooks/session-start`、`plugin/statusline/` |
| `25` | `plugin/hooks/session-start`、`plugin/rules/` |
| `30` | `plugin/statusline/` |
| `40` | `plugin/hooks/notify`、`plugin/hooks/run-hook.cmd` |
| `50` | `plugin/hooks/notify.ps1` |
| `60` | `plugin/hooks/hooks.json` |
| `70` | `plugin/.claude-plugin/plugin.json`、`.claude-plugin/marketplace.json`、`plugin/skills/` |

（`70` 的最终声明由该模块的作者定稿。）

**三件事防止它退化成「假装跑了」：**

1. 入口检查每个模块都必须有 `watch:` 声明，缺了直接报错，不静默跳过。
2. 声明里若写了仓库中不存在的路径，报错。
3. 持续集成不带 `--changed`，永远跑全套——声明写漏了，由它兜住。

`--changed` 模式下没有模块被挑中时，打印一行说明并退出 0（这是常态：改 README 就属于这种）。这与原有的子串筛选「没匹配上就报 FAIL」不同，两种模式的语义要分开写清楚。

### 四、自动化

**提交前钩子**，`.githooks/pre-commit`：

```sh
#!/bin/sh
exec bash checks/verify.sh --changed
```

放在 `.githooks/` 而不是 `.git/hooks/`，是为了跟着仓库走、换机器不丢。要生效得跑一次：

```
git config core.hooksPath .githooks
```

每个 clone 一次。这一步要写进 README。

**持续集成**，`.github/workflows/verify.yml`：跑在 `windows-latest`，执行 `bash checks/verify.sh` 全套。

选 Windows 而不是常见的 Linux：这八个模块里有依赖 `powershell.exe` 和 `cmd.exe` 的，Linux 上会走「跳过」分支，等于大半没验。

### 五、版本号

`plugin.json` 的 `version` 从 `1.11.1` 抬到 `1.12.0`，`marketplace.json` 里 `plugins[]` 那一份同步抬。

**不抬会静默失效**：插件缓存按「市场名／插件名／版本号」分目录，版本号不变就不会重新拷贝。目录结构变了而版本号没变，结果是更新插件后跑的还是旧布局，且不报任何错。这是本次唯一「不抬就悄悄不生效」的地方。

## 不做什么

- 不给十个技能写断言。那是十个技能各自的行为契约，比本次全部工作量加起来还大，单独立项。
- 不把已有的三个技能测试（`pdf-to-md`、`download-md-images`、`test-case-design`）接进持续集成。留待以后。
- 不改运行时脚本的逻辑。本次对 `plugin/hooks/`、`plugin/statusline/`、`plugin/rules/` 下文件的改动只有注释里的路径字样。
- 不清理 `docs/` 与 `evals/`。它们现在不进安装包了（因为 `source` 指向 `plugin/`），内容本身不动。
- 不碰 README.md 与 CLAUDE.md，见下方分工。

## 分工

另一个会话负责，本次不动：

- 根 `README.md`：收录计数、技能表补 `test-case-design`、维护一节的命令与模块清单
- 根 `CLAUDE.md`：导航文件里那条命令
- `checks/verify.d/70-版本号一致.sh`：模块本体
- `skills/test-case-design/` 下的产出契约检查

本次负责：`checks/` 的建立与路径改写、`plugin/` 重构、`marketplace.json`、两个新目录（`.githooks/`、`.github/`）、版本号、以及上述脚本里的注释字样。

落地完成后要通知另一个会话，它才能改 README 与 CLAUDE.md 里那几处路径。

## 风险与未知

| 事项 | 状态 |
|:---|:---|
| GitHub 的 Windows 机器上有没有 `jq` | 未知。本机有（WinGet 装的）。没有的话 `40-notify` 会怎样，要推上去跑一次才知道 |
| `40-notify` 在持续集成环境里能否全过 | 未知，同上 |
| `git config core.hooksPath` 在 Windows 上跑 bash 脚本 | 未实测，要试一次 |
| 重构后插件能否正常安装 | 未实测，要重装一次并核对缓存目录内容 |
| `actions/checkout` 是否遵守 `.gitattributes` 的 `eol=lf` | 应当遵守（它走正常的 git 检出）。若不遵守，Windows 上会检出 CRLF，检查会误报，要加一条显式设置 |

## 怎么验证

按顺序：

1. **迁移前存基线**：`bash hooks/verify.sh` 已实测全绿、69 秒。迁移后跑 `bash checks/verify.sh`，应当同样全绿。
2. **验证路径改写没改错方向**：故意把 `plugin/hooks/notify.ps1` 的 BOM 去掉，跑 `bash checks/verify.sh`，`50` 必须报 FAIL。改回来，必须通过。这一步验的是「检查脚本还真的在检查东西」，而不只是「它自己没崩」。
3. **验证挑模块挑对了**：分别改动 `plugin/hooks/notify`、`plugin/statusline/statusline.py`、`README.md`，各跑一次 `bash checks/verify.sh --changed`，确认挑中的模块与设计里的表一致。特别是改 `README.md` 时必须一个都不跑。
4. **验证提交前钩子**：装好 `core.hooksPath` 后，故意改坏 `plugin/hooks/hooks.json` 再 `git commit`，必须被拦住。
5. **验证重构生效**：抬版本号、推送、重新安装插件，然后核对 `~/.claude/plugins/cache/shared-skills/shared-skills/1.12.0/` 下**只有 `plugin/` 的内容**，没有 `checks/`、`docs/`、`evals/`。再开一个新会话，确认 SessionStart 注入与状态栏仍然正常。
6. **验证持续集成**：推送后看 GitHub Actions 是否绿。红了要读日志定位——这是整套设计里唯一没在本机跑过的一环。
