# 测试规程：执行器、改动文件与分批落点 — 设计文档

状态：待评审

这份动 `test-case-design` 三处：测试规程规格说明加两栏（执行器、改动文件），文末加一块「各批落到哪」，自检脚本跟着查这两样。技能的产出一律是六份文档，这份设计不碰这个边界。

## 1. 由头

两个来路，指向同一件事。

**来路一：外面那套产出做出的做法。** `C:\Study\work\.claude\skills\excel-sheet-batch-md\docs\test-case\` 那套产出在 2026-09-28 改了三处——五条规程各加一行「执行器」（脚本／控制器／子代理），开头把五条分成两批（脚本批 TP-1、TP-2；模型批 TP-3、TP-4、TP-5），文末加一张「两批的落点」表说明两批各自落到哪里（pytest 与评测工具）。改完 93 条用例一条不多一条不少地落在 5 条规程里。

**来路二：本仓库自己的产出早就是这个形状。** `evals/token-counter/test-case-design/Test Case Specification.md` 的「成品落点」是两行两类：

| 成品 | 落的是哪些条目 |
|:---|:---|
| `tests/token-counter/test_count_tokens.py` | TC-1 至 TC-29…、TP-1 至 TP-4… |
| `evals/token-counter/cases/` | TC-30 至 TC-37…、TP-5… |

两套互不相干的产出，切出来的形状一样：**判据能由脚本自己判的归一处，要读一轮模型行为的归另一处；分界落在规程的边界上。**

技能现在能用「成品落点」那张表把这件事**记下来**，但记的是落成之后的账（那一块写成「还没落成」也算填了）。设计阶段这个决定是隐形的——它只在写「成品落点」那一栏的人的脑子里。这份设计把它提到台面上。

## 2. 判据：分批的依据是「判据落在哪」

分界线是这一条：

- 一条规程的全部用例，判据落在**命令、退出码、盘上的文件**上，跑一遍就有结论 → 归**脚本批**，落成能跑的测试代码。
- 判据要**读一轮模型的行为**（跑了哪条命令、派了几个代理、写了什么）→ 归**模型批**，落成评测用例。

**「执行器」是这条判据的结果，不是原因。**所以：

- 执行器那一栏可以有三种取值（脚本／控制器／子代理），分批却只有两类——控制器与子代理都归模型批。两者粒度不同，不是对不上。
- 触发条件不是「有几个执行器」，是「这套用例会落成不止一类成品」。只落一类时那张表也照写，表里一行，写明全部规程落同一处。

## 3. 决策记录

| # | 决策点 | 选了什么 | 为什么 |
|:---|:---|:---|:---|
| D1 | 回灌成什么形态 | **加两栏 + 文末加一块「各批落到哪」** | 只加栏的话，落点仍只在用例那份的「成品落点」里，那是落成之后的账；只改示例的话，这条做法不算技能的要求，只是可选项。两样都要，落点才既在设计阶段定得下来、又在落成之后对得上 |
| D2 | 那块表按不按条件写 | **无条件写**，栏也每条规程必填 | 规则形状固定，脚本里没有「什么时候才要求」这种条件判断；代价是只落一类时多一张一行的表，这点代价换的是判据可机械查 |
| D3 | 执行器取值 | **写死三个**：脚本／控制器／子代理 | 这三个词不是某个项目的私货——用得上模型的地方就有「谁在跑」这一问；用不上模型的工程全落「脚本」，取值只有一个，表里一行 |
| D4 | 另加一栏「改动文件」 | **收**，取值两个：只读／会写 | 它回答「跑之前要不要清场、跑完要不要复位」，设计阶段就定得下来，而且直接决定落成评测用例之后能不能并行、能不能重跑。与「停止与结束」栏不重复：那一栏写**怎么复位**，这一栏写**要不要复位** |
| D5 | 改动文件进不进落点表 | **不进** | 那张表的分批准则是判据落在哪，跟改不改文件无关。执行器进表是因为它解释了分法，改动文件不解释 |
| D6 | 改动文件的口径 | 只管**盘上的文件**，不管被测对象的状态；一条规程里只要有一处会写，整条标「会写」 | 被测对象的状态复位已经写在「停止与结束」栏里（那条示例就是「按 DATA-4 把连续失败次数复位为 0」），再收进来这一栏就成了两件事挤一处。混装的规程取保守值，读的人按会写准备不会出错 |
| D7 | 落点表放哪份文档 | **测试规程规格说明文末**，不并进用例那份的「成品落点」 | 分界必须落在规程边界上，表按规程列；而且它在设计阶段就要写，用例那份的「成品落点」是落成之后才填得全的 |
| D8 | 用例那份的「成品落点」改不改 | **只补一句分工**，不合并两块 | 两块答的不是同一个问题：规程那份是「分几批、各批落哪一类」，用例那份是「落在哪个具体路径、落了哪几号」。合并了就会逼着设计阶段编具体路径 |
| D9 | 文档示例怎么办 | **重排规程**，让分界落在规程边界上 | 示例现在自相矛盾：TP-1 排了 TC-5，而「成品落点」里 TC-5 落在 `evals/`、那一行的条目栏却写着 TP-2。新规矩正好逮住这处不一致，示例得改对 |
| D10 | 本体层评测加不加用例 | **新加一条**，不复用 `landing-block-recorded` | 那一条判的是用例那份里的「成品落点」，这条判的是规程那份里的两栏与落点表——不同文档、不同的一块 |
| D11 | 版本号 | 抬中间位，`1.23.0` → `1.24.0` | 多了一个能力（产出里多两栏、多一块、脚本多三条校验），不是把已有的改对 |
| D12 | 归档产出回不回填 | **不回填** | 照上一份 spec 的先例：技能先改，改完再基于技能重新生成 |

## 4. 设计

### 4.1 `references/文档模板.md` 第五节：加两栏

栏目顺序改成：唯一标识符、英文名、目标、风险等级、**执行器**、**改动文件**、启动、有序执行测试用例、与其他规程的关系、停止与结束。

**执行器**：写这条规程由什么跑起来。三个取值，各带一句判据：

| 取值 | 判据 |
|:---|:---|
| 脚本 | 不用模型。跑命令、比退出码与盘上的文件就有结论 |
| 控制器 | 要模型跑，但模型只照规则读盘上的东西、按规则分流，不派子代理；整条规程在同一轮对话里跑完 |
| 子代理 | 要模型跑，而且要派子代理真去执行（读图、跑完整链这类），会花掉子代理额度 |

取值后面可以带一句括号说明（「脚本（跑命令，比退出码与盘上文件）」）。**每条规程都要填**——它是文末那张表的依据。

**改动文件**：写跑这条规程会不会往盘上写东西。两个取值：

- **只读**：全程不改盘上的任何东西。
- **会写**：会往盘上写——建临时目录、落报告、回填文档、推进基准、删文件都算。一条规程里只要有一处会写，整条标「会写」。

判据是「跑之前要不要清场、跑完要不要复位」；复位动作写在「停止与结束」栏，这一栏只说要不要。

### 4.2 `references/文档模板.md` 第五节末：加一块「各批落到哪」

顶层小节，标题写「各批落到哪」。表样：

| 批次 | 规程 | 执行器 | 落到哪 | 说明 |
|:---|:---|:---|:---|:---|

三条规矩：

1. **分批准则是判据落在哪**（见 §2）。控制器与子代理都归后一批。
2. **分界必须落在规程边界上。**不许把一条规程劈成两半分给两处；劈开了就回 TD4 重排规程，让每条规程整体归一处。
3. **只落一类也不空着。**表里一行，写明全部规程落同一处。

另加一条跨批的编号约定：**落成评测用例的那一批，用例 id 带上规程编号前缀**（如 `tp3-tc-042-gate-any-true`）。评测报告通常逐行列用例 id，没有「规程」这一维——跑哪一批、报告里每行归哪条规程，都靠这个前缀。

### 4.3 `references/文档模板.md` 其余三处

- **第三节「测试策略摘要」**：那句「「测试是自动化执行还是人工执行」这一句不写：本技能的产出一律是模型产出，不涉及执行方式」改成指到新栏——执行方式写在测试规程规格说明的「执行器」栏，不写在模型这里。原句的理由在技能有了「成品落点」之后已经不成立（产出已经管到落成哪一类成品了）。
- **第四节「成品落点」**：补一句分工——成品不止一类时按规程分批写，与测试规程规格说明的「各批落到哪」对得上；那一块写具体落在哪个路径、落了哪几号。
- **第九节「记哪些决策」**：第 5 步那条扩成「规程按什么排的序；执行器与改动文件是怎么判的；这套用例分几批落成、按什么分的」。

### 4.6 `scripts/check_docs.py`

`check_proc` 四处改动，另加一个切块的函数：

1. **新增 `field_values(text, label)`**：照现有 `name_fields` 的做法，把某个栏目的取值收齐——加粗字段（`- **执行器**：脚本`）与两列表行（`| 执行器 | 脚本 |`）两种写法都收。栏目的粗查表 `fields` 里**不加**这两个名字：文末那张表的表头里有「执行器」三字，粗查会被它蒙混过去。
2. **两条计数校验**：`len(field_values(text, "执行器"))` 与 `len(field_values(text, "改动文件"))` 都要等于规程条数，不等就报错（照现有英文名那条的做法）。
3. **两条取值校验**：执行器的每个取值要以 `脚本`／`控制器`／`子代理` 之一**起头**；改动文件的每个取值要以 `只读`／`会写` 之一起头。不合就报错。起头而不是全等，是因为后面允许带一句括号说明。
4. **新增 `batch_block(text)` 与它的检查**：照 `place_block` 的切法（`^#{2,}\s*[^\n]*各批落到哪` 起头到下一个 `##` 为止），表头含齐 `批次`、`规程`、`落到哪` 三栏（`执行器`、`说明` 可有可无）；再从 `规程` 那一栏里提出 `TP-n`，**合起来要等于全部规程编号**——漏一条报错，冒出一个产出里没有的号也报错。

切块函数照 `place_block` 的样子单写一个，不并进去：那一个切的是用例那份的「成品落点」，`check_landing.py` 也在用它，两处认的必须是同一块。

## 7. 已知的连带代价

- 新规矩一落，`evals/token-counter/test-case-design/` 那套产出与 excel-sheet-batch-md 那套都会过不了 `check_docs.py`（缺两栏、缺那块表）。这是有意的，照 D12 不回填。
- 「只读」在自动化用例里可能很少见——建个临时目录、落份报告就算会写，那一栏会几乎全是「会写」。先按这个口径落；真跑下来发现区分度不够，再收成「跑完盘上会不会留下东西」。
- 执行器写出第四个取值时脚本会报错，因为三个取值是写死的。别的工程碰上了，往技能里加取值，不要在产出里自己造。
