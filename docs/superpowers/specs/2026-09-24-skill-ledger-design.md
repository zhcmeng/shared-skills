# 台账技能（skill-ledger） — 设计文档

- 日期：2026-09-24
- 状态：待评审
- 场景：上游 `obra/superpowers` 的 SDD（subagent-driven-development，子代理驱动开发）用一份「台账」文件扛住上下文压缩——压缩后新会话读它就能接着干，不重做已完成的任务。这个做法值得搬到本仓的技能里
- 触发点：想给某个技能加台账时没有统一依据。要么不加，要么照抄一套用不上的结构——SDD 的台账是按「计划里的任务编号」切的，还假定有 git 提交、有子代理、有最终整支复核，别的技能没有这些

## 1. 目标与读者

**目标读者**：拿到一个技能、要判断「它该不该配台账、该怎么改」的模型。

**第二读者**：仓库主人。他要能看懂模型给的每一条建议凭什么。

**成功判据**：

1. 只读本技能的文件，就能对一个具体技能给出可执行的建议清单
2. 建议里的每一条都指到那个技能的 `SKILL.md` 的哪一处，不是泛泛而谈
3. 判「不该配」时说得清理由，不硬加
4. 讲的是机制的道理（为什么这么设计），不是模板——目标技能长什么样，台账就长什么样

**明确不是目标**：

- 不改任何文件。产出是建议清单，改不改、怎么改由当时的人决定
- 不安装、不依赖 superpowers。本技能自包含，装不装上游都能用
- 不管「技能提示词该怎么写」这件更大的事。那是 `writing-for-agents` 的地盘
- 不建一套台账读写的公共脚本。各技能的台账形态不一样，强行统一等于把 SDD 的形状套到所有技能上

## 2. 已确认决策

| # | 决策点 | 结论 |
|:---|:---|:---|
| D1 | 产出形态 | **只产出建议清单，不直接改目标技能的文件** |
| D2 | 触发方式 | 只允许用户手动触发（`disable-model-invocation: true`）。模型不自动调 |
| D3 | 判据顺序 | 先判该不该配，再讲怎么加。不该配的要在结论里明说 |
| D4 | 内容口径 | 主体讲通用机制；superpowers 只作版本化出处，逐条对照放 `references/` |
| D5 | 技能结构 | 一个 `SKILL.md` ＋ `references/上游台账机制.md` ＋ `references/台账示例.md`（后者后补，见 §7） |
| D6 | 技能名 | `skill-ledger` |
| D7 | 适用范围 | 管任何仓库里的技能。结尾那道「改完跑什么检查」交给目标技能所在仓库自己的规矩，不写死本仓的 |
| D8 | 无参数时 | 只给判据与清单，当参考读；给了技能名或路径，才针对那个技能出清单 |
| D9 | 正文的顺序 | **先立标准、再诊断**：第 2 步到第 5 步只讲「一份台账该是什么样」，一个字不看目标技能；第 6 步才去读目标技能，拿标准逐块对照 |
| D10 | 结论的落点 | 三种：该配 / 已有那份够用 / 不该配。判「不该配」时第一、四节照写，中间两节省掉 |
| D11 | 结构那一步的粒度 | 第 3 步只画骨架，不写「该写什么、不该写什么、什么时候写」——那些是第 4 步的事，两边都写就是把同一件事讲两遍 |
| D12 | 示例文件的形态 | 从一份真跑过的台账**删节**出来，不是全文照抄：删掉那一次活特有的经过，留下提交号、命令与结果、决定的代价这三样 |
| D13 | 术语 | 用按字面就懂的词，不沿用上游的叫法：归属行、能当场查的东西、记哪些事每行怎么写、什么时候才准写完成行什么时候删。上游的叫法在 `references/上游台账机制.md` 的小节标题里括注保留 |
| D14 | 归属行的形状 | 首行三样：哪一次活的名字、日期、一样能当场找到它的东西。名字认不出是哪一次，日期说清这是什么时候的活，第三样能当场打开才算数 |
| D15 | 清理 | 台账干完**不自己删**：干活的提出来、说清要清哪些，**用户确认后才动手**（上游是复核干净后直接 `rm -rf`）。删不可逆，而那个目录里往往不只有台账 |
| D16 | 台账的写法 | **只追加，不改写**：写下去的行就是记录，发现写错在后面追加一行更正，不回头动那一行。改过之后它就不再是「当时真写下了什么」的凭据，恢复靠的搜前缀也没了前提 |
| D17 | 遗留那一类 | 单开一类，前缀分三类：做完的／中途定的／遗留的（原来的「还没定的」收编进来——上游的缓办与搁置其实都是**定了**的，只有真没解决的才叫没定）。遗留**一条问题一行**，带齐三样：是什么、有多严重、什么时候必须处理。后两样按 D20 用固定标识。**不另设「读者」那一栏**：去向定了，谁在什么时候读它也就定了（`defer` 由收尾前那一遍读、`park` 由后面碰这片区域的活读、`Ruling` 交到用户手上），每条行再写一遍是同一件事说两遍。发现了、不修、也不记，等于没发现 |
| D18 | 不把上游的形状当通用前提 | 上游那条路才有的环节——最终整支复核、合并、跑得动的检查、版本控制——写进正文时，要么写成条件句（「能配上一道跑得动的检查就配」「没有可跑的检查，就用提交号、文件加行号」），要么换成通用说法（「收尾之前统一过一遍」「放在产出之外」）。依据是开头那条触发点：SDD 的台账假定有 git 提交、有子代理、有最终整支复核，别的技能没有这些 |
| D19 | 并列的分支写成表格 | 凡是**并列、且逐项要对齐**的内容，一律写成表格，不写成一串顿号连起来的句子——「三类前缀分别什么时候写、带哪几样」「遗留的四个去向怎么落」「完成行末尾挂什么」「结论怎么写」都属此类。表要落到「什么情况 → 怎么办」这一层。**示例行贴着它对应的那一类给**：做完的、中途定的用示例文件里那两行真行；遗留那一类示例文件里没有实例（那次活没留下没解决的问题），给一行编的并标明是编的。**不当表格的**：「一份好台账的标准」（三条性质不同，不是并列分支）、「只追加，不改写」（一条硬规矩加几个反例）、各节的「为什么」（讲道理，表格装不下）。规矩与示例归第 4 步，第 3 步仍是骨架（D11） |
| D20 | 行首三类、严重度、去向都用固定英文标识 | 行首写 `complete`（做完的）／`Ruling`（中途定的）／`open`（遗留的）；遗留项的严重度写 `Critical` / `Important` / `Minor`，去向写 `fix` / `defer` / `park` / `Ruling`。这三组共九个词，英文、不译、每个技能一样；除此之外——行首前面那段编号、以及别的部分——按各技能的活自定。三类是下限，技能要再加一类可以、名字自己起，但这三个词不改。**理由是可预期性，也为了让「恢复靠一句搜索」真立得住**：自定的部分跨技能搜不动，而这三组词到哪儿都是这几个——搜 `complete`，到哪个技能都是「做完了」。出处：`complete` / `Ruling` / `open` 三个词都是上游台账自己的（`open` 出在修复轮汇总的 `<Y> open`，上游没拿它当行首标识）；严重度三个词照抄上游评审词表的小标题；`defer` / `park` / `Ruling` 对上游台账的 `(deferred)` / `parked` / `Ruling:`；**只有 `fix` 是正文自己起的**——上游进环那一路没有单独的标识词，靠 `fix round <R>/5` 那行汇总记。逐条对照在 `references/上游台账机制.md` |
| D21 | 编号的形式与唯一性 | 行首那个固定词前面是**编号**，标出这一行说的是哪一件活。编号**不**固定成英文标识——它跟各技能怎么切活绑得最紧；正文给四种常见形式：任务号、轮次、步骤号、那一段的名字（示例台账里的 `Task 3 之后` 就是第四种，正文直接引了它、冒号照原样）。硬规矩一条：**一个编号在整份台账里只指同一件活**，同一个编号的行挨在一起——否则恢复时「任务 3 做完了没」这句话没有确定答案。正文第 4 步那行示例与 `references/台账示例.md` 的编号写法统一成 `Task <N>`：示例文件那边是原文一字未动，在开头注明这是那次活自己的写法、照正文那张表换别的也行 |

D7 的理由：本仓的收录判据是「跟具体工程无关、别的工程拿去也能直接用」。把 `checks/verify.sh`、README 补表、抬版本号这些步骤写进技能正文，等于把本仓的维护规矩复制出第二份，而 README「维护」节才是那些规矩的唯一真相。

D8 与 D1 不冲突：两种用法产出的都是清单，区别只是「清单是给某个具体技能的」还是「清单是拿来对照的」。

## 3. 判据：什么样的技能该配台账

### 3.1 该配的四条信号

中两条以上才配。四条都不中的，结论直接写「不该配」。

| 信号 | 问法 |
|:---|:---|
| 跨上下文边界 | 这个技能的活会不会跨上下文压缩、跨会话，或者交给子代理接着干？ |
| 重做代价高 | 做到一半丢了，重来要花掉多少时间、多少外部调用、多少钱？ |
| 中途要做决定 | 规范没写清、两种合理做法要选一个，而这些决定后面的步骤还要用吗？ |
| 同一套流程连着跑多轮 | 每轮结束得记住「到哪了」吗？ |

### 3.2 不该配的三类

| 不该配 | 例子 |
|:---|:---|
| 一次调用几分钟内跑完，丢了重跑便宜 | 本仓的 `token-counter`、`md-export` 转单个文件 |
| 状态已经在产出里 | 本仓 `issue_ids.py` 的既定做法：不另存台账，基准是产出目录里那五份文档 |
| 状态已经在 git 历史或 issue tracker 里 | 提交本身就是记录，再加一份是重复 |

## 4. 台账机制的六件事

这六件事按**三个时机**挂进技能正文：开工挂「归属行」与「位置」；每完成一件事挂「记哪些事、每行怎么写」与「能当场查的东西」；收尾挂「什么时候才准写完成行、什么时候删」。「读者」不进时机表——它归第 2 步「台账的职责」，回答的是「这份文件为谁而存在」。每个时机都写出「做法」「怎么算做对了」「为什么」——为什么背后是上游跑出来的实证，只有模板没有道理，模型遇到不认识的技能时改不动。

| 事 | 做法 | 为什么 |
|:---|:---|:---|
| 归属行 | 首行写清这是哪一次活、什么时候干的，再跟一样能当场找到那一次活的东西 | 上游基线实验 25 次，担心的事没发生：控制器没有照别人的台账跳过已完成的任务，25 次全部拒绝；代价是每次恢复都要先花工具调用去查「这份是不是我的」（实测 7/13/9/10/6 次，均值 9）。归属不能靠「记得清理」——台账存在的理由就是扛崩溃和压缩，而这两种情况恰恰不给收尾的机会。归属必须写进数据本身 |
| 位置 | 一次活一个目录，目录名从那一次活的名字派生；放在产出之外——不会被当成产出的一部分交出去的地方，在版本控制下就是被忽略的工作区 | 台账是脚手架不是产出，混进产出里就会被当成要交出去的东西；上游 #1780 是一例：原先放 `.git/` 下，而 `.git/` 是运行环境保护的路径，子代理写报告被拒绝 |
| 记哪些事、每行怎么写 | 一行一件事，前缀固定，让压缩后的自己 grep 得出来；分三类——做完的、中途定的、遗留的；只往下追加，前面的行不回头改 | 上游的恢复契约就是一句 grep：有 `Task <N>: complete` 行的算已完成，不重派。遗留那一类要带齐读者与期限，是因为缺了这两样，读的人分不出该不该管它——上游把这种叫「没人读的汇总等于静默丢弃」 |
| 能当场查的东西 | 每行带上能当场查的东西：提交 SHA、`file:line`、跑过的命令与结果 | 上游基线实验里，哈希对不上的台账会被拒收。能被查证是台账被信任的前提 |
| 哪几行必须在清理前交到人手上（上游叫读者） | 定下哪几行非到人手上不可，以及什么时候交 | 上游原话「随工作区一起删掉的裁定，等于一个偷偷做的决定」。上游的读者有三个——恢复的自己、最终整支复核、用户——前两个分别由「职责」与「收尾」承担，这一项管的是第三个 |
| 什么时候才准写完成行、什么时候删 | 能配一道跑得动的检查就配，跑通才写完成行；没有可跑的检查，末尾跟提交号、文件加行号这类查得到的。干完提给用户，用户确认后才清 | 上游只在 `executing-plans` 那条路上用 `task-done` 脚本真跑测试、过了才写完成行，那条路上没法虚报完成；SDD 那条路没有这道检查，完成行由控制器自己写。**别把「有可跑的检查」当成前提**：多数技能没有脚本，这条规矩要退得回「一样能当场查的东西」。长期的记录在 git 或产出里，台账只是临时脚手架；但删不可逆，而那个目录里往往不只有台账，所以清理要用户点头 |

## 5. 落到目标技能的哪几处

建议清单要指到这三处，每处给具体写法。这三处同时是技能正文第 4 步的三个小节标题——正文按时机讲，上面那六件事里除「读者」外都挂在这三个标题底下：

| 时机 | 写什么 |
|:---|:---|
| 开工 | 建台账、写归属行（活的名字 ＋ 日期 ＋ 一样能当场找到它的东西）；已经有台账时先核对首行，不是自己那份就不碰 |
| 每完成一件事 | 追加一行，前面的行不改。分哪几类事、每行怎么写，按这个技能自己的活来定；结论后面跟一样能当场查的东西。遗留的一条问题一行，带齐是什么、有多严重、什么时候必须处理 |
| 收尾 | 什么时候才准写完成行、哪几行要交到人手上、什么时候清理；清理要用户点头 |

## 6. 建议清单的格式

产出物的形状定死，四次调用拿到的清单长得一样，人才好横向比。

```
## 结论
该配 / 已有那份够用 / 不该配 + 一句为什么

## 建议改动
| 改哪处 | 现在是什么 | 建议改成什么 | 为什么 |
（「改哪处」要指到 SKILL.md 的章节名或行号）

## 台账设计草案
归属行 / 位置 / 记哪些事、每行怎么写 / 能当场查的东西 / 哪几行必须在清理前交到人手上 / 什么时候才准写完成行、什么时候删
（顺序照第 4 步那三个时机；「交到人手上」那项见「收尾」。每项按这个技能的实际活来写，不套模板）

## 建议里不含的
（明确列出没建议做的，免得读的人以为漏了）
```

判「不该配」时，第一、四节照写，中间两节省掉。

## 7. 技能结构

```
plugin/skills/skill-ledger/
├── SKILL.md                        主流程，模型默认只读这一份
└── references/
    ├── 上游台账机制.md              上游那套的逐条对照、版本出处、核对步骤
    └── 台账示例.md                  从一份真跑过的台账删节出来的示例
```

`SKILL.md` 装判据、六件事、三处落点、清单格式。上游的细节不常用的，放 reference，不占每次的上下文。

示例是后补的，单独一个文件、不塞进 `上游台账机制.md`：那个文件管的是「上游写在哪、原话是什么、上游更新了怎么核对」，示例一件都不沾；掺进去，以后上游每发一版都得陪着复核一段跟上游无关的内容。示例取自本仓 2026-09-23 那份检查脚本迁移的台账，首行照本技能的说法重写、其余一字未动，整体删节到三十行上下、一次读完——删掉的是那一次活特有的经过（共享接口核对表、几段长裁定、后面几个任务的细节），提交号、命令与结果、决定的代价这三样一个不删。不走路径引用：那种工作区活干完就删，引用会烂。
