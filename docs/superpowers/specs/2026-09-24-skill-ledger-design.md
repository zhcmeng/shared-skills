# 台账技能（skill-ledger） — 设计文档

- 日期：2026-09-24
- 状态：待评审
- 场景：上游 `obra/superpowers` 的 SDD（subagent-driven-development，子代理驱动开发）用一份「台账」文件扛住上下文压缩——压缩后新会话读它就能接着干，不重做已完成的任务。这个做法值得搬到本仓的技能里
- 触发点：想给某个技能加台账时没有统一依据。要么不加，要么照抄一套用不上的结构——SDD 的台账是按「计划里的任务编号」切的，还假定有 git 提交、有子代理、有最终整支复核，别的技能没有这些

## 1. 目标与读者

**目标读者**：拿到一个技能、要判断「它该不该配台账、该怎么改」的模型。

**第二读者**：仓库主人。他要能看懂模型给的每一条建议凭什么。

**成功判据**：

1. 只读本技能的文件，就能对一个具体技能给出可执行的建议清单
2. 建议里的每一条都指到那个技能的 `SKILL.md` 的哪一处，不是泛泛而谈
3. 判「不该配」时说得清理由，不硬加
4. 讲的是机制的道理（为什么这么设计），不是模板——目标技能长什么样，台账就长什么样

**明确不是目标**：

- 不改任何文件。产出是建议清单，改不改、怎么改由当时的人决定
- 不安装、不依赖 superpowers。本技能自包含，装不装上游都能用
- 不管「技能提示词该怎么写」这件更大的事。那是 `writing-for-agents` 的地盘
- 不建一套台账读写的公共脚本。各技能的台账形态不一样，强行统一等于把 SDD 的形状套到所有技能上

## 2. 已确认决策

| # | 决策点 | 结论 |
|:---|:---|:---|
| D1 | 产出形态 | **只产出建议清单，不直接改目标技能的文件** |
| D2 | 触发方式 | 只允许用户手动触发（`disable-model-invocation: true`）。模型不自动调 |
| D3 | 判据顺序 | 先判该不该配，再讲怎么加。不该配的要在结论里明说 |
| D4 | 内容口径 | 主体讲通用机制；superpowers 只作版本化出处，逐条对照放 `references/` |
| D5 | 技能结构 | 一个 `SKILL.md` ＋ `references/上游台账机制.md` ＋ `references/台账实例.md`（后者后补，见 §7） |
| D6 | 技能名 | `skill-ledger` |
| D7 | 适用范围 | 管任何仓库里的技能。结尾那道「改完跑什么检查」交给目标技能所在仓库自己的规矩，不写死本仓的 |
| D8 | 无参数时 | 只给判据与清单，当参考读；给了技能名或路径，才针对那个技能出清单 |

D7 的理由：本仓的收录判据是「跟具体工程无关、别的工程拿去也能直接用」。把 `checks/verify.sh`、README 补表、抬版本号这些步骤写进技能正文，等于把本仓的维护规矩复制出第二份，而 README「维护」节才是那些规矩的唯一真相。

D8 与 D1 不冲突：两种用法产出的都是清单，区别只是「清单是给某个具体技能的」还是「清单是拿来对照的」。

## 3. 判据：什么样的技能该配台账

### 3.1 该配的四条信号

中两条以上才配。四条都不中的，结论直接写「不该配」。

| 信号 | 问法 |
|:---|:---|
| 跨上下文边界 | 这个技能的活会不会跨上下文压缩、跨会话，或者交给子代理接着干？ |
| 重做代价高 | 做到一半丢了，重来要花掉多少时间、多少外部调用、多少钱？ |
| 中途要做决定 | 规范没写清、两种合理做法要选一个，而这些决定后面的步骤还要用吗？ |
| 同一套流程连着跑多轮 | 每轮结束得记住「到哪了」吗？ |

### 3.2 不该配的三类

| 不该配 | 例子 |
|:---|:---|
| 一次调用几分钟内跑完，丢了重跑便宜 | 本仓的 `token-counter`、`md-export` 转单个文件 |
| 状态已经在产出里 | 本仓 `issue_ids.py` 的既定做法：不另存台账，基准是产出目录里那五份文档 |
| 状态已经在 git 历史或 issue tracker 里 | 提交本身就是记录，再加一份是重复 |

## 4. 台账机制的六件事

这是技能正文的骨架。每件事都要写出「怎么做」和「为什么」，为什么背后是上游跑出来的实证——只有模板没有道理，模型遇到不认识的技能时改不动。

| 事 | 做法 | 为什么 |
|:---|:---|:---|
| 身份行 | 首行写清这份台账是给哪一次活干的 | 上游基线实验 25 次，担心的事没发生：控制器没有照别人的台账跳过已完成的任务，25 次全部拒绝；代价是每次恢复都要先花工具调用去查「这份是不是我的」（实测 7/13/9/10/6 次，均值 9）。身份不能靠「记得清理」——台账存在的理由就是扛崩溃和压缩，而这两种情况恰恰不给收尾的机会。身份必须写进数据本身 |
| 位置 | 一次活一个目录，目录名从那一次活的名字派生；放 git-ignored 的工作区 | 上游 #1780：原先放 `.git/` 下，而 `.git/` 是运行环境保护的路径，子代理写报告被拒绝 |
| 行格式 | 一行一件事，前缀固定，让压缩后的自己 grep 得出来 | 上游的恢复契约就是一句 grep：有 `Task <N>: complete` 行的算已完成，不重派 |
| 可核断言 | 每行带上能当场验的东西：提交 SHA、`file:line`、跑过的命令与结果 | 上游基线实验里，哈希对不上的台账会被拒收。可核验是台账被信任的前提 |
| 读者 | 点名谁读它，以及读它做什么 | 上游原话「没人读的汇总等于静默丢弃」。上游的读者有三个：恢复的自己、最终整支复核、用户 |
| 闸门与收尾 | 能机械化的就机械化（跑过测试才写完成行）；干完删掉 | 上游只在 `executing-plans` 那条路上用 `task-done` 脚本真跑测试、过了才写完成行，那条路上没法虚报完成；SDD 那条路没有这道闸门，完成行由控制器自己写。durable 的记录在 git 或产出里，台账只是临时脚手架 |

## 5. 落到目标技能的哪几处

建议清单要指到这四处，每处给具体写法：

| 时机 | 写什么 |
|:---|:---|
| 开工 | 建台账、写身份行；已经有台账时先认身份，不是自己那份就不碰 |
| 每完成一件事 | 追加一行。写什么事件、什么格式，按这个技能自己的活来定 |
| 恢复 | 怎么读：先认首行身份，再按前缀定位到「做到哪了」，以及半途中的活怎么接 |
| 收尾 | 谁读、怎么汇总给人、什么时候删 |

## 6. 建议清单的格式

产出物的形状定死，四次调用拿到的清单长得一样，人才好横向比。

```
## 结论
该配 / 不该配 + 一句为什么

## 建议改动
| 改哪处 | 现在是什么 | 建议改成什么 | 为什么 |
（「改哪处」要指到 SKILL.md 的章节名或行号）

## 台账设计草案
身份行 / 位置 / 事件类型与行格式 / 可核断言 / 读者 / 闸门与收尾
（每项按这个技能的实际活来写，不套模板）

## 建议里不含的
（明确列出没建议做的，免得读的人以为漏了）
```

判「不该配」时，第一、四节照写，中间两节省掉。

## 7. 技能结构

```
plugin/skills/skill-ledger/
├── SKILL.md                        主流程，模型默认只读这一份
└── references/
    ├── 上游台账机制.md              上游那套的逐条对照、版本出处、核对步骤
    └── 台账实例.md                  一份真跑过的台账全文 ＋ 六件事各自落在哪
```

`SKILL.md` 装判据、六件事、四处落点、清单格式。上游的细节不常用的，放 reference，不占每次的上下文。

实例是后补的，单独一个文件、不塞进 `上游台账机制.md`：那个文件管的是「上游写在哪、原话是什么、上游更新了怎么核对」，实例一件都不沾；掺进去，以后上游每发一版都得陪着复核一段跟上游无关的内容。实例用本仓 2026-09-23 那份检查脚本迁移的台账（76 行，短到能一口气读完），全文照抄，不走路径引用——那种工作区活干完就删，引用会烂。
