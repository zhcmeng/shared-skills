# test-case-design 主文件压缩设计

日期：2026-11-04
状态：待批准
范围：`plugin/skills/test-case-design/`

## 一、为什么要改

`SKILL.md` 现在 45.9KB（314 行），是仓库里第二大的技能主文件（`skill-ledger` 19.3KB）的 2.4 倍。技能触发时它整份进入上下文，每次用都要先读一遍。

量出来的四件事：

- 104 个段落里有 43 个提到第七份、落成或 skill-up，占 61% 的篇幅。这些是按需才走的路径。
- 「只问三样输入」「第七份按需出」这类规则，在开头、第 0 步、第 7 步各写了一遍。
- 「什么时候读哪份文件」4.0KB，与主流程表的「读哪份文件」一栏重复。
- 第 298 行还写着「第 0 步答了『要出实施测评方案』的」，但第 0 步已经改成不问这件事。

## 二、目标与非目标

### 目标

1. `SKILL.md` 从 45.9KB 降到 30KB 以内（少三成半）。
2. 正常出六份的路径少读约 1.7 万字。
3. 第七份与落成的说明集中到一份文件，找得到、不重复。
4. 行为不变：产出仍是六份（按需加第七份），仍只问三样输入，脚本判据不变。

### 非目标

- 不改产出契约、栏目、编号方案。
- 不改三个脚本的判据与代码。
- 不改六份通用稿的写法。
- 不新增功能。

### 什么算失败

- 压缩后测试不过，或必须改脚本才能过。
- 某条规则在搬运中丢了，或被改成了别的意思。
- 按新文件走，走不到第七份或落成。

## 三、约束

1. `check_docs.py` 从 `SKILL.md` 现解析两张表：「必须照写的几个词」右列、「六份里不许出现的东西」左列。**这两节原地不动**，脚本不用改。
2. `test_example.py` 依赖三处，压缩时必须保留：
   - 主流程表第 0 步那一行以 `| 0 | 定开工输入` 开头，最后一格不含「测评方案」。
   - 第 0 步有一段以 `**定完判完都要落进产出**` 开头。
   - `SKILL.md` 里出现 `skill-upper` 这个词。
3. 技能自己的 `.md` 文件里不许出现「被测对象」与具体环境名（WSL2、Docker、本机 Windows），`references/评测方案/` 除外。新文件同样适用。
4. 维护者文档记着：Claude 把主流程表的「读哪份文件」一栏当穷举清单执行，不跟随正文里的交叉引用。搬走的内容必须在那一栏或紧挨着的段落里有明确入口。

## 四、改法

### 4.1 新增 `references/实施方案与落成.md`

从 `SKILL.md` 整节搬入，文字基本不动，只改相互指向。结构：

| 新文件里的节 | 从 `SKILL.md` 搬来的内容 | 现大小 |
|:---|:---|:---|
| `## 一、只出实施方案那一份` | 同名一节（两条入口、读模板第十节与示例第七节、skill-up 安装与版本核对） | 2.8KB |
| `## 二、落成那一步手上要有哪四样` | 同名一节 | 2.2KB |
| `## 三、只做落成` | 同名一节（五步） | 2.0KB |
| `## 四、成品落点与落成对照` | 同名一节（表怎么写、命令、退出码、分批） | 1.8KB |
| `## 五、skill-up 装不上、跑不了时` | 从异常处理表里抽出依赖那几行，改为指向第一节的装法 | 新增约 0.4KB |

文件开头加一句「什么时候读这一份」：用户点名要第七份时，或七份都在手上、只做落成时。

### 4.2 新增 `references/异常处理.md`

- 开头保留原有几段原则：先自己修、同一处修过一轮才告诉用户、不删用户文件、外部依赖不自动安装。
- 后面整张表搬入（环境、依赖、输入、脚本四类）。
- 依赖类那几行里，skill-up 的装法改为指向 `实施方案与落成.md` 第一节，不再重复。
- 结尾保留「只在出错时查，不是每一步开头的检查清单」。

### 4.3 `SKILL.md` 的删与留

**整节删除**：

- `## 异常处理`：换成 4 行的「撞见问题怎么办」，保留四条原则与一句「具体修法见 `references/异常处理.md`」。
- `## 只出实施方案那一份`
- `## 只做落成`
- `### 成品落点与落成对照`
- `### 落成那一步手上要有哪四样`
- `## 什么时候读哪份文件`

**新增一节 `## 第七份与落成`**，约 2KB，只写四件事：

1. 第七份只在你点名时出，可以随六份、也可以单独出；脚本、函数、库用不上。
2. 第 0 步不问、不提。
3. 落成排在文档之后，只摆配置、不跑测。
4. 两条路径都先读 `references/实施方案与落成.md`；写第七份前确认 `/skill-upper` 装着，没装照 `references/异常处理.md` 处理，装不上就终止第七份。

**新增一节 `## 参考文件怎么读`**，约 1KB，替代原来的 4KB：

- 按节读，不整份读。
- 主流程表与表后那两句已列出每步要读的节；另有三处每步都可能用到：决策依据读 `文档模板.md` 第九节，拿不准怎么填读 `文档示例.md`，技术文件第五节是算例。
- 七门技术的文件名一行列全（`references/技术/` 下，文件名与技术名相同）。
- 三个脚本按命令行用，不用读源码；`python` 按机器上的写法。

**压缩但不删**：

- `## 管到哪为止`：落成的细则搬走后，这段只留「设计出文档、落成摆配置、落成不跑测」三句。
- `## 第 0 步`：把「只问三样」「产出形式不问」「测评方案不问」「第七份不跟六份绑」四段并成一段；保留第 0 步输入表、完成准则、风险信息问法、`**定完判完都要落进产出**` 那一段。
- `## 第 7 步`：落成对照那一句改成指向新文件。
- `## 主流程`：表格不动；表后补两句指向句（见 4.5）；关于进度清单与决策依据的两段各收紧约三成，规则一条不少。

- 新文件里凡写「照『异常处理』」的地方，改成指向 `references/异常处理.md`。

### 4.5 不动的部分

- `description` 不动。
- 「必须照写的几个词」「六份里不许出现的东西」两张表不动。
- 三个脚本不动。
- 四份测试不动（除非压缩后测试暴露出真的行为变化，那时先停下来说明）。
- 主流程表的八行内容与「读哪份文件」一栏不动，只在表后补两句：「撞见报错时读 `references/异常处理.md`。」与「用户点名要第七份、或七份都在手上只做落成时，读 `references/实施方案与落成.md`。」表下面那段说明是维护者文档里实测能读到的位置。

## 六、怎么验证

1. **搬运动作可核对**：用脚本从 `git show HEAD:...SKILL.md` 取出被搬走的每一节，逐行确认它出现在新文件里（去掉首尾空白后比对）。任何一行找不到，就说明搬运漏了。
2. **交叉引用可核对**：扫 `plugin/skills/test-case-design/` 下所有 `.md`，找出所有反引号里的 `references/...md` 路径，逐个确认文件存在；再确认正文里写到的节号（第一节到第五节）在新文件里有对应标题。
3. **既有测试**：`bash checks/verify.sh test-case-design`，四份测试必须全过。
4. **脚本解析**：`python plugin/skills/test-case-design/scripts/check_docs.py --rules`，确认两张词表仍解析得出来、条数没变。
5. **人工检查**：逐段读 `SKILL.md`，对照本设计第四节，确认没有规则被改写；再读两个新文件，确认单独拿第七份的人能照着走完。

## 七、风险与应对

| 风险 | 应对 |
|:---|:---|
| 搬走的内容 Claude 找不到 | 主流程表后写两句指向句（撞见报错、第七份与落成）；其余入口写在紧挨着的段落里；不依赖正文里的顺带提及 |
| 压缩时改动规则原意 | 先搬运、后压缩；搬运逐行核对，压缩只删重复句，不改判据 |
| 测试依赖被搬走的文字 | 已核对：测试只依赖三处锚点，均保留；跑完测试确认 |
| 维护者文档再次落后 | 同一次改 `docs/maintainers/test-case-design.md`，并把两份新文件写进文件地图 |

## 八、不做的事

- 不改「固定出六份」。
- 不改「只问三样输入」。
- 不拆 `check_docs.py`。
- 不加评测批。
- 不改插件版本号之外的分发配置；实现完成、准备交付时把 `1.29.2` 抬到 `1.29.3`（两处一起）。
