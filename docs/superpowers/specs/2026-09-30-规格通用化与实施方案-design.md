# 规格通用化与实施方案 — 设计文档

日期：2026-09-30
状态：待评审

把技能 `plugin/skills/test-case-design/` 的产出契约分成两层：六份通用稿保持通用——不认任何一种测评方案、不认任何一种具体环境，可以原样拿去当代码或技能的测试依据；另加一份**按需产出**的第七份 `Implementation Specification.md`，本轮怎么落地全装在那里。同时把第 0 步的「测试运行环境」那一问取消（默认本机），换成「先判涉不涉及模型测评，涉及才问要不要一并出实施测评方案，要再问用哪个方案」。技能里另备一份 skill-up 的配置参考（上游两份文档原样随包），因为从六份通用稿走到那份实施方案，得知道 skill-up 认得哪些字段。

第一轮澄清又定下四条口径：

- **测评方案顶掉「测试运行环境」这一样开工输入**；不涉及模型测评时连问都不问，产出也只有六份。
- **是否涉及模型测评，看测试项本身**（是技能、提示词这类靠模型跑的东西就算），不看规程的「执行器」栏——后者要到第 5 步才定得下来。

- **第 0 步按顺序先判后问**：先看测试项判涉不涉及模型测评；不涉及 → 两问都不问；涉及 → 问「要不要一并出实施方案」→ 答是 → 问「用哪个测评方案」。

## 2. 判据

1. **六份通用稿不认方案、不认具体环境。** 六份里不出现任何测评方案的名字与配置文件名，也不出现 WSL2、Docker、本机 Windows 这类具体环境名。这两类词命中就报错——方案名与配置文件名六份全查，环境名不查 `Decision Basis.md`（那一份记的是过程，见 D16）。
2. **六份能独立用。** 只拿这六份，可以当代码或技能的测试依据直接往下走，不必知道有没有第七份。
3. **第七份能照着跑。** 可跑配置以原文贴出，读到的人把它拷到标注的路径上就能跑，不必再回问技能。
4. **两份之间对得上账。** 六份里定义过的每一条 `ENV-`／`DATA-` 编号，在第七份里都查得到一个落点；第七份里出现的每个编号，在六份里都有定义处。
5. **老产出不受影响。** 产出目录里没有第七份时，`check_docs.py` 照旧只查六份，不报错也不提示。

## 4. 设计

### 4.1 产出契约

| | 现在 | 改后 |
|:---|:---|:---|
| 必产 | 六份 | 六份（内容不变，措辞去方案化） |
| 按需 | — | `Implementation Specification.md`（实施方案规格说明） |

**第七份什么时候产**：测试项是技能、提示词这类靠模型跑的东西，且用户答「要一并出」；或者手上已有六份、这次只出第七份。

**第七份装什么**，照 `evals/plain-language/test-case-design/Implementation Specification.md` 的骨架：

1. 导语——把六份通用设计稿落成能跑的东西；两边冲突时以这份为准；方案按节分，将来比别的方案在同一份里再起一节
2. 一节「通用稿的编号落到哪」——`ENV-…`、`DATA-…` 逐条对到本方案的具体落点（哪个配置文件、哪一段、盘上哪个路径）
3. 每个方案一节，节里三块：
   - **说明**——跑几次、工作区怎么来、判据分几层怎么落、消息与上下文怎么渲染、跑不了原样的那几条
   - **可跑配置**——以 YAML 原文贴出，不是散文化地描述「应该配什么」；每块标好落到盘上哪个路径
   - **怎么跑、报告落在哪**——命令行、输出目录、哪些东西不进 git

**这一份不定义任何编号**：`TM-`、`TCOV-`、`TC-`、`TP-`、`DATA-`、`ENV-`、`DEC-` 一个都不新发，只引用前六份的。引用写编号，不重述内容。

### 4.2 第 0 步怎么变

**开工输入四样 → 三样**：「测试运行环境」取消。剩下三样——测试依据（用户给，没给就问）、风险信息（向用户要）、测试完成准则（自己定）。

**新加两问，按顺序**：

1. 先看测试项：是技能、提示词这类靠模型跑的东西吗？
   - 不是（一段脚本、一个函数、一个库）→ 两问都不问
   - 是 → 问「要不要一并出实施测评方案」
2. 答「要」→ 问「用哪个测评方案」（选项目前只有 skill-up，默认 skill-up）

**判「涉及模型测评」只看测试项本身**，不看规程的「执行器」栏。代价：一份技能里既有脚本层又有本体层时（如 token-counter），第 0 步就按「涉及」算。

**「测试运行环境」取消之后，`ENV-6`／`ENV-7` 改成默认本机的说法**：

| 唯一标识符 | 英文名 | 测试环境项 | 描述 |
|:---|:---|:---|:---|
| ENV-6 | procedure_run_environment | 跑测试规程的那处工作目录 | 测试规程的会话都在这处起、在这处收；每跑一条之前，把上一轮的会话与盘上改动清干净——要能重来、能隔离，不然上一轮的残留会串进下一轮的判定。**默认就是本机的一处目录**；要换到别处，在这一条上写 |
| ENV-7 | subject_execution_environment | 被测那侧的执行环境 | 被测的那个东西在哪儿跑起来——被测脚本、被测服务、被测技能各自的会话与它对盘上文件的读写都落在这处。**默认与本机是同一台**；被测的东西要跑到别处去，在这一条上写 |

`ENV-7` 的英文名从 `code_execution_environment` 改成 `subject_execution_environment`——「code」预设了被测对象是代码。

这两条现在由技能判（来源 `技能定的`），不再是用户给的输入。它们从决策依据的「用户决策」那一块挪到「模型决策」那一块，另在第 0 步记一条决策：「测试运行环境不再问用户，默认本机」。**「用户决策」那一块不会空**——风险信息照旧向用户要，风险等级那条还在。

### 4.4 第七份文档的契约

写进 `references/文档模板.md` 新加的一节「十、实施方案规格说明（第七份，按需产出）」。节里定下：

| 定什么 | 怎么定 |
|:---|:---|
| 文件名 | `Implementation Specification.md`——不带方案名；「skill-up」这个名字只出现在文档内部的小节标题里 |
| 什么时候产出 | 两种入口，见 4.5 |
| 整体结构 | 导语 ＋「一、通用稿的编号落到哪」＋ 每个方案一节 |
| 方案节的节号 | 接着「一」往下排（「二、方案：skill-up」；将来第二个方案就是「三、方案：<那门方案的名字>」） |
| 方案节的三块 | 「说明」「可跑配置（YAML 原文）」「怎么跑、报告落在哪」——三块的标题里各含这三个词，脚本按它认 |

## 7. 已知的连带代价

- **禁用词表里放 `Docker`／`WSL2`／`本机 Windows` 会误报。** 被测项目自己就跑在 Docker 里时，`ENV-7` 写「Docker」是正解，脚本却会报错。这一条是选乙的价钱：选甲（这几词只报提示）不会误报，但也就拦不住。真碰上时的出路是把措辞改掉（写「容器」而不是「Docker」），或者回技能里把那个词从表里拿掉。
- **豁免 `Decision Basis.md` 留了个口子。** 新流程下第 0 步不再问环境，决策依据里本不该再出现 `WSL2` 这类词；真写进去了脚本也不报——那一处只能靠人看。这是为了让 DEC-16 那种「记下当时定的是哪一种」的条目写得出来，换来的代价。
- **范例的 DATA-15 要动一句。** 那处措辞一改，拿旧版产出对照的人会看到一处分叉。引它的那几处（第七份的 `DATA-15` 那一行、TP-5 的「启动」栏）都不受影响——引的是编号，不是那句话。
- **第七份的 YAML 原文与盘上的实际配置会两头跑。** 文档里贴着配置，盘上也有一份真在跑的；改了这边忘了那边，两边就不一样了。本次按「文档是源、盘上照它拷」办。
- **两份上游文档会旧。** 65 KB 随包发出去，skill-up 改版后这份不跟着动，而技能里写着「不要去翻本机那份 clone」，读的人不会知道它旧了。`README.md` 里钉了 commit，是唯一的线索。
- **`check_docs.py` 多了一组条件分支。** 现在它只认「六份都在」，改后还要认「第七份在不在」——两条路都得测，测试条数会涨。
- **`SKILL.md` 里「六份」这个说法要逐处过一遍。** 现在出现 8 次，改后多数仍指那六份通用稿、意思不变，但「产出只有那六份文档」那条边界句必须动，漏改一处就会自相矛盾。
