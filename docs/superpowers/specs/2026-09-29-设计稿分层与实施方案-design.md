# 设计稿分层与实施方案 — 设计文档

日期：2026-09-29
状态：待评审

把 `evals/plain-language/test-case-design/` 那套产出分成两层：六份设计稿保持通用，不认任何一种评测方案；另加第七份 `Implementation Specification.md`，本次怎么跑全部装在那里——文件名不带方案名，方案专属的东西按节装进去、以 YAML 原文写出。同时把测试规程规格说明从三条规程改成八条——一条规程一条用例，每条自己把前置条件写全。技能本体 `plugin/skills/test-case-design/` 一个字不动，版本号不抬：这套产出是个实例，实例怎么摆不改技能的产出契约。

## 1. 由头

### 1.1 要拿 skill-up 把这套用例跑起来

`C:\Study\skill-up` 是一套用 Go 写的技能评测命令（最新发布版 v0.12.0）。它按 `eval.yaml` 加 `cases/*.yaml` 声明式配置跑一条条评测用例，回来写 `grading.json`、`benchmark.json`、`result.json` 与报告。而 `evals/plain-language/test-case-design/` 现在只是一套设计稿——八条用例、十四项数据、七项环境都写清楚了，但没有一条落成能跑的东西。

### 1.2 六份里有三处已经钉死在某一种方案上

| 位置 | 现在写的 | 问题 |
|:---|:---|:---|
| `Test Environment Requirements.md` 的 ENV-5 | 给了一条具体命令：`claude -p "<用户消息>" --append-system-prompt "$(cat plugin/skills/plain-language/rules.md)"`，还引了 `evals/rules/cases/full-paths-no-cd/` 那条先例 | 这是「怎么摆」的一种做法，不是环境本身的要求 |
| 同文件 ENV-6 | 规程在 WSL2 发行版里跑，路径按 `/mnt/c/...` 挂 | WSL2 是方案之一，不是唯一 |
| 同文件 ENV-7 | 被测代码在本机 Windows 上执行 | 同上 |

用户明说将来可能换别的方案比较实施效果（官方 `claude plugin eval`、Docker、手工跑都算），最后不一定选 skill-up。这三处这么写着，换方案时六份得跟着改一遍，改完通用稿就不通用了。

### 1.3 测试规程把多条用例串成一条

现在三条规程串着八条用例：TP-1 串五条、TP-2 串两条、TP-3 单条。串起来的理由是同组用例的前置条件相同（同一档用法、同一套环境），写一次省五遍。

两件事让这个省法不成立了：

- skill-up 一条用例起一个会话、各自算分，共用的前置条件不再共用——写「见本组共用前置条件」的那几条，落成配置时还得逐条补全。
- 用户要求：**基于某一条测试规程就能独立测试**，不必读文档别处。共用前置条件正好与这条相反。

### 1.4 核实到的事实

| 事实 | 出处 |
|:---|:---|
| 一条规程在「各批落到哪」表里必须占一行，「规程」栏只准出现一个规程号 | `plugin/skills/test-case-design/scripts/check_docs.py:542`（`len(tps) != 1` 报错） |

## 2. 判据

一条规程合格与否，看这两条：

1. **一条规程独立可测**：只读那一条规程，就能把它的前置条件摆全、跑起来、收尾，不必读文档别处，也不必先读另一条规程。
2. **通用那份不认方案**：六份通用设计稿里不出现任何一种评测方案的名字、命令行、运行位置。这些只出现在 `Implementation Specification.md` 里。

第二条有个例外：ENV-1 说的「把 `plugin/skills/plain-language/` 整个目录当作装好的技能交给 agent」是**测试项本身**长什么样，不是方案的选择——换哪个评测工具，这条都不变，留在通用稿里。

## 4. 设计

### 4.1 产出分两层

```
evals/plain-language/test-case-design/
├── Decision Basis.md                 ← 通用，只增不改（新加 DEC-17、DEC-18）
├── Test Model Specification.md       ← 通用，一个字不动
├── Test Case Specification.md        ← 通用，动三处（见 4.6）
├── Test Data Requirements.md         ← 通用，动两处（见 4.5）
├── Test Environment Requirements.md  ← 通用，动四处（见 4.4）
├── Test Procedure Specification.md   ← 通用，三条规程拆成八条（见 4.2）
└── Implementation Specification.md   ← 新增，全部方案专属内容都在这儿（见 4.8）
```

通用与方案的分界，一句话：**「要什么」留通用稿，「用哪个、怎么摆」进实施方案**。

### 4.2 `Test Procedure Specification.md`：三条拆八条

八条各占一节，标题以 `TP-n` 起头（自检按标题第一个词认规程的边界）。每条照 `文档模板.md:155` 到 `:166` 的栏目写齐：唯一标识符、英文名、目标、风险等级、执行器、改动文件、启动、有序执行测试用例、与其他规程的关系、停止与结束。

三处与现在不同：

1. **「启动」栏写全**，不再写「见本组共用前置条件」。这条规程要用的环境项与数据项逐条列出（写 ENV 与 DATA 编号指代），样本副本怎么摆、夹具从哪来都写在这一栏。
2. **「有序执行测试用例」栏只有一条**用例。
3. **「与其他规程的关系」栏统一写**「与其余七条互不依赖，先后都可以」。

「执行器」八条都写 `子代理`（每条用例要另起一个会话：把技能整套交给它、发一条用户消息、取回复与盘上的改动）。「改动文件」按原来那三档带下来：TC-1、TC-2、TC-3、TC-6 那四条经 `子代理` 改盘上的样本副本，标 `会写`；TC-4、TC-5、TC-7、TC-8 四条不动盘上任何东西，标 `只读`。

「英文名」八条照各条用例的英文名一字不差地抄（TP-1 写 `fix_only_what_should_change`，TP-2 写 `quotes_kept_and_glossed`，依次往下）。一条规程就是「这条用例怎么跑」，名字核跟着用例走最不容易写岔。原来那三个规程级的名字（`fix_what_should_change`、`restate_last_answer`、`ambient_rules_writing`）作废——一条规程只装一条用例，再单起一个名字没有用处。

「风险等级」照各条用例原来的等级抄：TP-1 至 TP-4、TP-6、TP-7 写 `高`，TP-5、TP-8 写 `中`。

文首那段导语也要重写：现在写的是「八条用例排成三条规程，排的顺序按用例之间的前置条件依赖」，改成「八条用例各占一条规程，每条自包含——读那一条就能把前置条件摆全、跑起来、收尾」。

### 4.7 `Decision Basis.md`：只增不改

原有十六条一个字不动（DEC-12、DEC-16 保留原样，读的人看得到当时的判断）。新加两条订正条目：

| 编号 | 在哪一步 | 决定 | 考虑过的其他做法 | 依据 | 依据的来源 |
|:---|:---|:---|:---|:---|:---|
| DEC-17 | 第 0 步 | **订正 DEC-16**：规程在哪跑、被测代码在哪执行，这两件事改由实施方案定；通用设计稿里只留「一处能重来、能隔离的工作目录」与「被测那侧另有一处执行环境」这两条要求 | 留着 WSL2 与本机 Windows 的写法：用户可能换别的评测方案比较实施效果，通用那份不该跟着换 | 用户要求六份尽量不专门适配某一种评测方案，另出一份实施方案 | 用户给的 |
| DEC-18 | 第 5 步 | **订正 DEC-12**：规程从三条拆成八条，一条规程一条用例，每条自己把「启动」栏写全，不抽公共前置条件 | 留着三条串着：评测工具一条用例起一个会话，共用的前置条件不再共用；抽一个「公共前置条件」小节八条一起引：与「读一条规程就能独立测试」正相反 | 用户要求每条规程独立可测、一条规程一条用例 | 用户给的 |

**两条写进「用户决策」那一块**，不写进「模型决策」。理由：这两条的口径是用户定的，「依据的来源」照实填 `用户给的`；而 `文档模板.md:266` 那条规矩把 `用户给的` 的行一律归到「用户决策」那一块，`check_docs.py` 也照着查——放进模型决策那一块会报错。订正关系写在「决定」栏里（「订正 DEC-16」「订正 DEC-12」），读的人顺着编号找得到被订正的那条。

### 4.8 `Implementation Specification.md`（新增）

**文件名不带方案名。** 「skill-up」这个名字只在文档内部的小节标题里出现，不进文件名——将来比别的方案，在同一份文档里再起一节，六份通用稿一个字不用动。

这份的内容分两块：一块是散文（跑几次、工作区怎么摆、判据怎么分两层这些说不成配置的事），一块是 **YAML 原文**——把可跑配置本身一行不差地写出来，不是散文化地描述「应该配什么」。读的人把 YAML 那几块拷到盘上对应的路径，就能跑。

文档骨架：


- 不装 Go、不编译 skill-up——那是实施方案落地时的事，规格说明这一步只出方案。

## 7. 已知的连带代价

- **八条里有七条目录名要改。** 改名的波及面：测试用例规格说明的九处判据路径、测试数据需求的五条消息、测试规程的「各批落到哪」表。改完之前，两边对不上。
- **规程文档会长一倍。** 三条「启动」栏变成八条，每条都把所有前置条件重写一遍。这是「独立可测」这条要求的价钱，用户已确认要付。
- **通用稿与实施方案之间多了一道对齐成本。** 通用稿改一处（比如 ENV-4 加了要求），实施方案要跟着补。4.8 里「通用稿的编号落到哪」那张对照表就是为这道成本准备的。
- **`Implementation Specification.md` 里的判据压缩有损耗。** 各条 `graders/*.md` 是散文，压成 `agent_judge` 的条目时会长短不一。压完的判据要在落成那一轮跑一遍看准不准，不准就回改。
- **YAML 原文与盘上的实际配置会两头跑。** 文档里贴着配置，盘上也有一份真在跑的，改了这边忘了那边，两边就不一样了。落成之后要么把盘上那份当准的、文档里只留指路，要么定一条「改了这头就同步那头」的规矩。本次先按「文档是源、盘上照它拷」办。
