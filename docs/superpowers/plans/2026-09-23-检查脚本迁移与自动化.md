# 检查脚本迁移与自动化 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把检查脚本从 `hooks/` 迁到仓库根 `checks/`，把插件内容整体挪进 `plugin/`，让检查在提交前按改动挑着跑、在推送后由 GitHub Actions 跑全套。

**Architecture:** 分两步走，每步各自可验证。第一步只挪检查脚本、把两类路径用变量分开（`SCRIPT_DIR` 是脚本自己，`HOOKS_DIR` 是被验的运行时文件），此时插件根还等于仓库根。第二步把插件内容整体挪进 `plugin/`，入口只改一行 `PLUGIN_DIR` 就完成——这是第一步引入变量的回报。之后再加按改动挑模块、提交前钩子、持续集成。

**Tech Stack:** bash（Git Bash on Windows）、git、GitHub Actions（windows-latest）、node（模块 60 用来解析 JSON）

**Spec:** `docs/superpowers/specs/2026-09-23-检查脚本迁移与自动化-design.md`

## Global Constraints

- 检查脚本一律 bash，跑在 Windows 的 Git Bash 上。仓库里没有 `.sh` 之外的语言用于检查。
- 仓库内容统一 LF 存、LF 检出（`.gitattributes` 的 `* text=auto eol=lf`）。写任何新文件都用 LF。
- 模块是**被入口 `source` 进同一个 shell** 的，共享入口定义的 `fail`、`scratch_dir`、`scratch_file`、`test_home`、`statusline_src`、`rules_src`。不要改成靠 `$( )` 返回值传数组——子 shell 里改的东西传不出来（模块 30 里记着同一类坑）。
- **断言不能写在 `$( )` 里**：`$( )` 起子 shell，在里面调 `fail` 只加在子 shell 的副本上，计数传不出来，失败会被吞掉。
- 模块文件名形如 `NN-中文名.sh`，入口按文件名排序加载，`NN` 决定顺序。
- `plugin.json` 与 `marketplace.json` 里的 `version` 必须一致（模块 70 会验）。
- 持续集成跑在 `windows-latest` 上，不能用 Linux——这套检查有依赖 `powershell.exe` 与 `cmd.exe` 的模块，Linux 上会走跳过分支。

## Review Focus

设计文档是愿景文档，下面的情况它没写，但不写不等于可以坏。每条都配了钉住它的测试，落在拥有该代码的那个任务里。

1. **暂存区是空的**（`git commit --amend`、空提交、只改了被 gitignore 的文件）。预期：挑不出任何模块，直接放行，**不报错**——这不是异常，是常态。测试在任务 3。
2. **改动清单里含被删除的文件**（`git mv` 之后的提交，旧路径显示为删除）。预期：该模块照样被挑中——文件没了正是最该跑检查的时候。测试在任务 3。
3. **`plugin/hooks/notify` 与 `plugin/hooks/notify.ps1` 的前缀关系**。预期：改 `.ps1` **不能**连带挑中 `40-notify`（那会白白多跑 51 秒）。测试在任务 3。

### Task 1: 把检查脚本迁到 `checks/`，路径指回 `hooks/`

这一步不动 `plugin/`。此时插件根仍等于仓库根，所以入口里 `PLUGIN_DIR="${REPO_ROOT}"`。

**Files:**
- Move: `hooks/verify.sh` → `checks/verify.sh`
- Move: `hooks/verify.d/` → `checks/verify.d/`（7 个模块）
- Modify: `checks/verify.sh`（路径变量）
- Modify: `checks/verify.d/10-session-start.sh`、`20-statusline-sync.sh`、`25-rules-sync.sh`、`40-notify.sh`、`50-notify-render.sh`、`60-wiring.sh`（`${SCRIPT_DIR}/x` → `${HOOKS_DIR}/x`）

```sh
    case "$out" in
      *"$m"*) fail "${desc}：不该挑 ${m} 却挑了（实际挑了：${out}）" ;;
```

```sh
#!/usr/bin/env bash
# 校验脚本的入口：查依赖、挑模块、按序加载 verify.d/ 下的模块、汇总结果。
# 每个模块只校验一件事，入口不掺业务逻辑。
#
#   bash checks/verify.sh                    跑全部
#   bash checks/verify.sh notify             只跑文件名里带 notify 的模块
#   bash checks/verify.sh --changed          只跑被本次改动影响到的模块（提交前钩子用）
#   bash checks/verify.sh --changed --list   只列出会跑哪些模块，不真跑
#
# 模块是被 source 进同一个 shell 的，共享这里定义的 fail / scratch_dir /
# scratch_file / test_home / statusline_src / rules_src。别改成靠 $( ) 返回值传数组那种写法：
# 子 shell 里改的东西传不出来（30 那块里记着同一类坑）。
set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
REPO_ROOT="$(cd "${SCRIPT_DIR}/.." && pwd)"
PLUGIN_DIR="${REPO_ROOT}/plugin"   # 插件根：会跟着插件发出去的那部分
HOOKS_DIR="${PLUGIN_DIR}/hooks"    # 运行时 hook 所在

# 下面这些变量分两类，别混：
#   SCRIPT_DIR —— 检查脚本自己的东西（verify.d 在哪）
#   REPO_ROOT / PLUGIN_DIR / HOOKS_DIR —— 被检查的运行时文件在哪
# 两者以前都写成 ${SCRIPT_DIR}/...，长得一模一样，改目录时最容易一起改错。
RULES_FILE="${PLUGIN_DIR}/skills/plain-language/rules.md"
VERIFY_D="${SCRIPT_DIR}/verify.d"
# cmd.exe 的批处理分支要从仓库根用相对路径调它（见 10 里那段说明）
RUN_HOOK_CMD_WIN='plugin\hooks\run-hook.cmd'

fails=0
fail() { echo "FAIL: $1" >&2; fails=$((fails + 1)); }

# 临时文件统一登记，退出时一起删。原来是每个小节自己 rm -rf，中途 exit 就漏下。
_scratch_list="$(mktemp)"
scratch_dir()  { local d; d="$(mktemp -d)"; printf '%s\n' "$d" >> "$_scratch_list"; printf '%s' "$d"; }
scratch_file() { local f; f="$(mktemp)";    printf '%s\n' "$f" >> "$_scratch_list"; printf '%s' "$f"; }
_cleanup() {
  local p
  while IFS= read -r p; do [ -n "$p" ] && rm -rf "$p"; done < "$_scratch_list"
  rm -f "$_scratch_list"
}
trap _cleanup EXIT

# rules.md 带 CR 时字节数会和文档记录的对不上，多半是编辑器写回的。只是提示，不算失败——
# 仓库内容应统一 LF，见 .gitattributes。
# 用 tr 数 CR，别用 grep。Git Bash 的 grep 在文本模式下匹配不到 CR，两条死路都会骗人：
# CR 取自变量时 grep "$CR" 恒为 0；grep -c $'\r' 这种写法取输出时 $'\r' 会退化成空模式，
# 返回的其实是**行数**——看着像「检测到了 CR」，其实每行都算命中
# （实测：3 行 1 个 CR 的文件返回 3，全 LF 的 3 行文件也返回 3）。
# 文件不在时别让重定向的报错漏到 stderr（先判可读，判定语义不变）。
if [ -r "$RULES_FILE" ] && [ "$(LC_ALL=C tr -dc '\r' < "$RULES_FILE" | wc -c)" -gt 0 ]; then
  echo "提示：rules.md 含 CR 行尾，字节数与文档记录对不上（多半是编辑器写回的）。仓库内容应统一 LF，见 .gitattributes"
fi

# 解析注入文本要用 node，接住它的报错要用 mktemp，比对同步过去的脚本要用 cmp。缺了就直接说清楚，别把「工具没装」误报成「JSON 不合法」
for dep in node mktemp cmp; do
  if ! command -v "$dep" >/dev/null 2>&1; then
    echo "FAIL: 需要 ${dep} 才能校验 hook" >&2
    exit 1
  fi
done

# 10、20、25 共用这个替身 HOME：session-start 会把 statusline/ 下的脚本和 rules/ 下的
# 规则同步到配置目录，不换 HOME 就会写进真实用户的 ~/.claude。校验脚本不该动真东西。
test_home="$(scratch_dir)"
statusline_src="$(cd "${PLUGIN_DIR}/statusline" 2>/dev/null && pwd)"
rules_src="$(cd "${PLUGIN_DIR}/rules" 2>/dev/null && pwd)"

# ── 参数 ───────────────────────────────────────────────────────────
by_changed=0
list_only=0
filter=""
for arg in "$@"; do
  case "$arg" in
    --changed) by_changed=1 ;;
    --list)    list_only=1 ;;
    -*) echo "FAIL: 不认识的参数「${arg}」" >&2; exit 1 ;;
    *)  if [ -n "$filter" ]; then
          echo "FAIL: 只接受一个筛选子串，多给了「${arg}」" >&2; exit 1
        fi
        filter="$arg" ;;
  esac
done

mods_all=("$VERIFY_D"/*.sh)
if [ ! -e "${mods_all[0]}" ]; then
  echo "FAIL: ${VERIFY_D} 下没有校验模块" >&2
  exit 1
fi

# ── watch 声明 ─────────────────────────────────────────────────────
# 每个模块都必须在文件头写一行 `# watch: <路径> [<路径>...]`，路径以仓库根为基准；
# 以 / 结尾的按目录前缀匹配，否则按整条路径相等匹配。
#
# 这一行只能「读」出来，不能靠 source 拿——模块一被 source 就会跑起来
# （10 第 9 行就执行了 session-start），必须在决定跑不跑之前就用读文本的方式拿到。
watch_of() { sed -n 's/^# watch:[[:space:]]*//p' "$1" | head -1; }

# 声明站不住就直接报错，不静默跳过——静默跳过等于这个模块永远不会跑，
# 而人以为检查过了。这是本仓库其他模块一直在防的那类失败。
for mod in "${mods_all[@]}"; do
  _name="${mod##*/}"
  _w="$(watch_of "$mod")"
  if [ -z "$_w" ]; then
    echo "FAIL: ${_name} 没有声明 watch（文件头缺一行「# watch: 路径」）" >&2
    exit 1
  fi
  for _p in $_w; do
    case "$_p" in
      */) [ -d "${REPO_ROOT}/${_p%/}" ] || { echo "FAIL: ${_name} 声明的目录不存在：${_p}" >&2; exit 1; } ;;
      *)  [ -e "${REPO_ROOT}/${_p}" ]   || { echo "FAIL: ${_name} 声明的路径不存在：${_p}" >&2; exit 1; } ;;
    esac
  done
done
unset _name _w _p

# ── 按改动挑模块 ───────────────────────────────────────────────────
# 一条声明路径是否命中一个改动文件。目录声明按前缀，文件声明按整条相等。
# 后半条不能省：`plugin/hooks/notify` 若按前缀匹配，会把 `plugin/hooks/notify.ps1`
# 也吃进来，白白多跑 51 秒。
watch_hits() {
  case "$1" in
    */) case "$2" in "$1"*) return 0 ;; esac ;;
    *)  [ "$2" = "$1" ] && return 0 ;;
  esac
  return 1
}

mods=("${mods_all[@]}")
if [ "$by_changed" -eq 1 ]; then
  if [ -n "${VERIFY_CHANGED_FROM:-}" ]; then
    changed="$(cat "$VERIFY_CHANGED_FROM" 2>/dev/null)"
  else
    changed="$(git -C "$REPO_ROOT" diff --cached --name-only 2>/dev/null)"
  fi

  # 夹具自己被动过（入口、模块，任何 checks/ 下的东西）：跑全套，不是只跑某一个。
  # 夹具的问题会波及所有模块，挑着跑会有漏网的。
  run_all=0
  while IFS= read -r _f; do
    case "$_f" in checks/*) run_all=1 ;; esac
  done <<EOF
$changed
EOF
  unset _f

  picked=()
  for mod in "${mods_all[@]}"; do
    if [ "$run_all" -ne 1 ]; then
      _w="$(watch_of "$mod")"
      _hit=0
      while IFS= read -r _f; do
        [ -n "$_f" ] || continue
        for _p in $_w; do
          watch_hits "$_p" "$_f" && _hit=1
        done
      done <<EOF
$changed
EOF
      unset _f
      [ "$_hit" -eq 1 ] || continue
    fi
    picked+=("$mod")
  done
  unset _w _p _hit
  # 空数组在 set -u 下的写法：先判长度再展开，bash 4.2 到 5.x 都安全
  if [ "${#picked[@]}" -eq 0 ]; then mods=(); else mods=("${picked[@]}"); fi
fi

# ── 子串筛选 ───────────────────────────────────────────────────────
if [ -n "$filter" ]; then
  _kept=()
  for mod in "${mods[@]}"; do
    case "${mod##*/}" in
      *"$filter"*) _kept+=("$mod") ;;
    esac
  done
  if [ "${#_kept[@]}" -eq 0 ]; then mods=(); else mods=("${_kept[@]}"); fi
  unset _kept
fi

# ── 跑 ─────────────────────────────────────────────────────────────
if [ "${#mods[@]}" -eq 0 ]; then
  # --changed 挑不出模块是常态（改 README 就属于这种），放行不报错。
  # 带子串筛选却一个都没匹配上则是用错了，按原来的规矩报错。
  if [ "$by_changed" -eq 1 ]; then
    [ "$list_only" -eq 1 ] || echo "本次改动没有匹配到任何检查模块"
    exit 0
  fi
  echo "FAIL: 没有模块匹配「${filter}」（可用的：${mods_all[*]##*/}）" >&2
  exit 1
fi

for mod in "${mods[@]}"; do
  name="${mod##*/}"
  if [ "$list_only" -eq 1 ]; then
    echo "$name"
    continue
  fi
  echo "── ${name}"
  # shellcheck source=/dev/null
  . "$mod"
done

[ "$list_only" -eq 1 ] && exit 0

echo
if [ "$fails" -eq 0 ]; then
  echo "全部通过"
else
  echo "${fails} 项失败" >&2
  exit 1
fi
```

```bash

git add checks/
git commit -F - <<'MSG'
feat(检查脚本): 按本次改动挑模块跑，同夹具动过则跑全套

每次提交都跑全套要 69 秒（40-notify 一项就占 51 秒——它调 34 次 hooks/notify，
Windows 上每次起进程都慢），而大部分提交改的是文档，白等。现在每个模块在文件头
声明自己盯哪些路径，入口新增 --changed 读这些声明、跟 git diff --cached 对一遍，
只跑受影响的。

声明只能读文本、不能靠 source 拿：模块一被 source 就会跑起来（10 第 9 行就执行
了 session-start），必须在决定跑不跑之前拿到。

匹配规则上目录声明以 / 结尾按前缀、文件声明按整条相等。后半条不能省：按前缀的话
plugin/hooks/notify 会把 plugin/hooks/notify.ps1 也吃进来，白白多跑 51 秒。

三条防「假装跑了」：模块缺 watch 声明直接报错；声明了仓库里不存在的路径直接报错；
改动碰到 checks/ 就跑全套（夹具的问题会波及所有模块，挑着跑会漏）。

新增模块 80-挑模块.sh 验这套挑选逻辑——挑错了表现是静默的（该跑的没跑，一路
绿灯），正是其他模块一直在防的那类失败。它靠 VERIFY_CHANGED_FROM 喂写死的改动

--changed 挑不出模块是常态（改 README 就属于这种），放行退出 0；子串筛选一个都

```

### Task 5: GitHub Actions

**Files:**
- Create: `.github/workflows/verify.yml`

**Interfaces:**
- Consumes: `checks/verify.sh`（不带参数，跑全套）
- Produces: 无（终端产物）

- [ ] **Step 1: 写工作流**

创建 `.github/workflows/verify.yml`：

```yaml
name: 检查

# 每次推送和每个拉取请求都跑一遍全套。这是兜底：本地的提交前钩子可以绕开、
# 别人 clone 后也可能没装，而且按改动挑模块万一挑漏了，只有这里能发现。
on:
  push:
  pull_request:

jobs:
  verify:
    # 必须是 Windows：这套检查里有依赖 powershell.exe 与 cmd.exe 的模块，
    # 在 Linux 上它们会走「跳过」分支，等于大半没验。
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4

      - name: 跑检查
        shell: bash
        run: bash checks/verify.sh
```

缩进必须是空格（YAML 不允许制表符）。

- [ ] **Step 2: 本地先确认这条命令能跑**

CI 上跑的就是这一条，本地先跑一遍：

```bash
cd /c/work/shared-skills
bash checks/verify.sh
```

预期：`全部通过`，退出码 0。

- [ ] **Step 3: 提交并推送**

（这一步要往 GitHub 推，属于对外动作，先跟用户确认再执行。）

```bash
cd /c/work/shared-skills
git add .github/
git commit -F - <<'MSG'
chore(检查脚本): 加 GitHub Actions，每次推送跑全套

跑在 windows-latest 上，不用 Linux：这套检查里有依赖 powershell.exe 与 cmd.exe
的模块（50 验 notify.ps1 的 BOM 与解析、10 验 cmd 批处理分支），Linux 上它们会
走跳过分支，等于大半没验。

不带 --changed，永远跑全套——本地按改动挑模块万一挑漏了，这里是唯一能发现的地方。

Co-Authored-By: Claude Code <noreply@anthropic.com>
MSG
git push
```

- [ ] **Step 4: 看 CI 结果**

推送后打开 `https://github.com/zhcmeng/shared-skills/actions` 看这次运行。

- **绿**：这一环通过。
- **红**：读日志定位。最可能的两处未知（设计文档「风险与未知」里记过）：
  1. **`jq` 在不在**——本机有（WinGet 装的），GitHub 的 Windows 机器上不确定。若 `40-notify` 因缺 `jq` 而失败，在工作流里加一步装它（`choco install jq -y`），或改用仓库里已有的 node 解析。
  2. **`actions/checkout` 是否遵守 `.gitattributes` 的 `eol=lf`**——应当遵守。若不遵守，Windows 上会检出 CRLF，检查会大面积误报，在工作流里加一步显式转换，或在 `actions/checkout` 上加 `-c core.autocrlf=false`。
  把实际原因记下来，回头补进设计文档的「风险与未知」一节。
