# 实施方案规格说明

这一份把前面六份通用设计稿落成能跑的东西。六份说的是「要什么」——模型、覆盖项、用例、规程、数据、环境；这一份说的是「用哪个、怎么摆」——这批用例交给哪套测评方案跑、每条编号落到盘上的哪个文件哪一段。**配置本身不抄进来**：它由落成那一步照这一份写进盘里，抄一份到文档里就是第二份会漂移的副本。**两边冲突时以这一份为准**：通用稿是按测试项写的、不认方案，落到具体方案上总有几处要偏，偏在哪写在每个方案的「说明」里。

方案按节分。眼下只有 skill-up 一节；将来换一套方案，在同一份里再起一节，六份通用稿一个字不用动。

## 二、方案：skill-up

### 2.1 说明

**1. 跑几次**

一次。三条规程里只有 TP-3 落成评测用例——TP-1 与 TP-2 的判据落在命令、退出码与盘上的文件上，跑一遍脚本就有结论，归可跑测试那一边（那一批这一轮还没落成）。这一批九条用例一次跑完，跑完再照第 2.2 节跑第二遍。

**2. 工作区怎么来**

每条用例开跑前，框架自己在系统临时目录下新建一个空目录当工作区，跑完删掉。技能由 `skills` 那一条装进工作区的 `.claude/skills/token-counter/`；样本由 `context.repo_fixture` 铺进去——铺的是各条用例自己那个夹具目录的**内容**，所以 `./sample.txt`、`./a.txt`、`./broken.txt` 就落在工作区根上，与用例的「输入」栏写的那几个路径对得上。夹具是逐字节写的，`broken.txt` 头两个字节的 `0xFF 0xFE` 原样带过去。原始夹具全程不动。

**3. 判据落在哪**

九条用例的判据都要读一轮技能被调用时的表现——回话里报的是几、该说明的说明了没有、有没有真去跑脚本——交给 `agent_judge` 按每条用例自己的 `judge.criteria` 判。`expect` 那一层只卡退出码，机械地卡不住「回话里说了什么」。

**4. 判据的通过口径**

九条用例都取「列出的判据全成立才算过」：每条用例的 `judge.criteria` 里那几条逐条判，过线比例显式写 `1.0`。不显式写就是按条计分、过半数就算过，而这几条的「预期结果」栏本来写的就是几样都要做到——TC-24 要是数报对了、脚本却没真跑，那不算过；TC-27 要是报出了数、缓存命中那一句没补，也不算过。

**5. 哪些字段配在批次那一层**

`environment.setup_steps`、`skills`、`judge`、`cases.parallelism` 这几个字段只认批次那一层；配到一条用例那一层不会报错，是默默丢掉的。这一批里最要留神的是 `setup_steps` 那一步——它是**整份配置级的**：九条用例每条开跑前都走一遍，建那个干净解释器。另外八条用不上它，只是白建一次。要它只落在 TC-32 那条身上做不到，只能拆成两份配置分两次跑。判官那一层同理：`judge.type` 与判官用的模型配在批次那一层，九条用例各自只写自己的 `criteria`。

**6. 这一批能不能并发**

不能，`cases.parallelism` 取 1，串着跑。TC-32 要在「那个解释器里还没装引擎」的状态下开跑，并发的话别的用例会先跑到同一个解释器上去，把引擎装进去，那一条就白跑了。

**7. 跑不了原样的那几条**

- **TC-32** 偏得最多。通用稿写的输入是用户那句问话、一句话不带别的；落到这套方案上，光靠那句话复现不出「目标机上还没装引擎」——被测那边默认用的是本机那个已装引擎的解释器，跑起来就退化成 TC-25 了。落成时在那条消息里补一句，把那个干净解释器的路径告诉它。**这是补一句话，不是改判据**：要看的还是「技能自己把引擎装好、不把安装推给用户」。
- **TC-24、TC-30、TC-31** 的样本落点与通用稿一致（`./sample.txt`、`./broken.txt`、`./a.txt`），没有出入——夹具铺的是目录内容，正好落在工作区根上。
- **TC-26 有一处环境带来的出入**：这套方案跑起来，被测那边看到的技能不止你配的那一个——这台机器上已装的其它技能照样在清单里、照样能被触发。通用稿那段输入里点着别的模型的名字，跑起来被测那边读到的正是本技能描述末句「不覆盖那个模型」，于是把它排除了，转去触发了机器上另一个管 Claude API 的技能，全程没加载本技能；判据要的那句「说明本技能不覆盖」自然也就没有。**这一条不改判据**：要看的还是「点名别的模型时，技能说明不覆盖、不给近似数」。它反查出来的是被测技能自己的毛病——描述末句把本该由它出面答的那一问排除掉了，已照这一条改掉；改完照旧拿这一条用例复验。
- **其余七条与通用稿一致，没有别的出入。**通用稿里那九条本来就是「用户说一句话、看回话里说了什么」，这套方案不装钩子、不开额外参数，都没有影响到这一层：这九条一条也不靠钩子触发，也不要求在会话开头就有常驻上下文。
- **批一那两条规程不在这份配置里跑**（见第 1 小节），不算折扣。它们要的是会动 `wheels/` 的解释器与断网，这套方案这一批一样都不摆。

### 2.2 怎么跑、报告落在哪

一批跑测共用一个时间戳目录：先取一次当前时刻，这一批的几条命令都拿它当 `--output-dir`。

```powershell
$ts = Get-Date -Format "yyyy-MM-dd-HHmm"
skill-up run C:/Study/shared-skills/evals/token-counter-round2/eval.yaml --output-dir "C:/Study/shared-skills/evals/token-counter-round2/runs/$ts"
```

报告落在 `evals/token-counter-round2/runs/<这批的时间戳>/`，底下 `iteration-1/` 是 skill-up 自己追加的——这一批里跑的第几回就是几。下一批另取一个时间戳，落进新目录，盖不掉这一批，前几批的报告都留着。**同一批里跑了两遍时怎么分辨**：两遍落在同一个时间戳目录下，谁先谁后看 `iteration-1/` 与 `iteration-2/`——`--iteration` 不传时，默认就是往后追加一个 `iteration-N/`，不改前面那几回。

**报告出哪两种格式**：配置里 `report.formats` 那一栏列的是 `json` 与 `html`。`json` 给机器读——每条判据过没过、每一步花了多久都在里面；`html` 给人看，一轮跑完直接翻它。这一栏不列 `html` 就不出 HTML，事后要补得拿 `report` 子命令从 `result.json` 另生成一份，补出来的与当场跑的混在一个目录里，分不清哪份是哪份。

**同一批至少跑两遍**，两遍结论不一致的用例照实记下来。跑第二遍不为核对结论，为的是看判据稳不稳：一轮过一轮不过的，毛病多半出在判据卡了可有可无的附带动作——被测那边有时顺带说一句、有时不说，卡上去这条用例就一轮一个样。

**跑过之后的结论记在哪**：哪几条没过、为什么、下一轮改什么，记在这一批报告里的 `result.json` 与那份 HTML 里，不另起一份、也不写回产出那几份文档。报告本身不进 git（见下一条），要留结论就留在这两处。

不进 git：仓库根的 `.gitignore` 里有两条盖得住这一批——`evals/*/runs/` 盖住整个 `runs/`，`evals/*/.clean-venv/` 盖住 `setup_steps` 现建的那个解释器。
