# 实施方案规格说明

这一份把前面六份通用设计稿落成能跑的东西。六份说的是「要什么」——测哪些模型、覆盖什么、每条用例给什么输入、判成什么样；这一份说的是「用哪套方案、怎么摆」。两边冲突时以这一份为准。

方案按节分：下面「二」是本次用的那门方案。将来要比第二门方案，在同一份里另起一节往下排，前面六份一个字不用动。

## 二、方案：skill-up

### 说明

**跑几次。**这一批九条用例一次跑完，就是 `TP-3` 排的那九条。另外两条规程（`TP-1`、`TP-2`）排的十六条用例不在这套方案上跑——它们的判据全落在标准输出、标准错误与盘上的文件上，不吃模型，落成另一批能跑的测试代码，还没落成。所以这一套只跑 `TP-3` 一条规程。

**工作区怎么来。**每条用例开跑前由框架各起一个空的临时目录当工作区，跑完删掉；上一轮留下的东西不进下一轮。被测技能由配置装进工作区的技能目录下，随技能分发的词表与引擎包跟着一起进去。用到文件样本的那几条用例，样本摆在夹具目录里，由框架铺进工作区。

**字段的作用域，有两处要留意。**一是装技能只能整批配一次，没有「这条用例装、那条不装」的配法——这一批九条都要技能，正好合用。二是工作区开跑前的准备动作也是整批级的：一批里每条用例各跑一遍，不区分这条用不用得上。`ENV-5` 那个干净解释器就是这么配的——只有最后一条用例（`TC-25`）要它，可另外八条每条开跑前也会白建一次。要它只落在一条上做不到，只能拆成两份配置分两次跑；这一批按前者摆，代价是白建八次。

**能不能并发：不能，这一批串着跑。**最后一条用例要在一个「引擎还没装」的解释器上开跑。并发跑的话，别的用例会先跑到同一个解释器上去，把引擎装进去，那一条就白跑了。配置里把并发数设成 1。

**判据分几层、怎么落到判官上。**九条的判据都在「要读执行过程」那一层：除了看回话里说了什么，还要看它是不是真去跑了脚本、跑的那一次给的是什么输入。所以每条用例都交给判官判，判官拿到的材料取默认那一档——回话正文内联，执行过程记录以文件引用给出。机械层只卡一条：整轮下来退出码是 0。

**判据的通过口径：每条判据都得成立才算过。**通用稿那九条的「预期结果」栏里写了几条，就要做到几条；过线的比例显式写成 1.0，不用默认值。一条判据得过且过，这条用例的结论就说明不了被测那边到底做没做到。

**消息与上下文怎么渲染。**用户那句话照通用稿「输入」栏里写的那一句原样接进当轮消息，不改写成转述；技能那一侧由配置装进工作区，被测那边按技能自己的描述决定要不要用它。配置文件里那份夹具是照通用稿「测试数据需求」抄过去的，抄完两处就各说各的——改一处要记得改另一处。

**跑不了原样的那几条，一条一条对。**这一段是跟通用稿的逐条对照，不是折扣清单；跟设计稿一致的那几条也点一句。

- **`TC-17` 到 `TC-25` 九条的判据，与设计稿一致，没有出入。**通用稿要的就是「读回执行过程」，这一套方案的判官默认就拿得到执行过程记录（`ENV-7` 兑现的正是这一条）。
- **`TC-19`（问别的模型的 token 数）与设计稿一致，没有出入。**判据那三条都是照通用稿「预期结果」栏来的：说明覆盖不了、不给当作答案的近似数、不拿这边的数顶替那边的数。
- **按技能自己的名字唤起，与设计稿一致。**这套方案把技能装在工作区的本地技能目录下，带插件前缀的唤起名用不了；这九条的消息都是自然语言，没有哪一条按唤起名点名，不受影响。
- **`TC-25`（首次运行）有一处折扣：`ENV-5` 那个干净解释器是整批级的。**见上面「字段的作用域」那一段——另外八条用例每条开跑前也会白建一次，白建不影响它们自己的判据。这一条要在「引擎还没装」的状态下开跑，靠并发设成 1 保住。
- **`TC-23`、`TC-24` 用到的工作区差集，与设计稿一致，没有出入。**这两条的判据落在回话与执行过程上，不落在工作区改了什么上；工作区不是 git 仓库时差集那一项会被静默省掉，不影响它们。
- **不使用钩子，与设计稿一致。**这套方案跑起来的时候钩子一律不生效，六份通用稿里没有哪一条靠钩子触发。
- **装技能时跳过评测材料那棵子树，与设计稿一致。**被测技能自己没带那棵子树。
- **单轮，与设计稿一致。**这套方案的多轮只收用户的发言，收不了被测那边上一轮说过的话；这一批九条都是单轮，用不上多轮。
- **找技能根时那一条退让警告是正常产物。**评测材料与被测技能不在一棵树里，路径基准会退到配置文件的上一层，跑起来屏幕上会打一条找不到技能文件的警告——不是错。

### 怎么跑、报告落在哪

```
C:/Users/Administrator/.local/bin/skill-up.exe run --config C:/Study/shared-skills/evals/token-counter-round3/eval.yaml --output-dir C:/Study/shared-skills/evals/token-counter-round3/runs/<yyyy-MM-dd-HHmm>
```

- 路径全写死，命令放在哪个目录下跑都是这一句。跑之前先建好那一刻的时间戳目录，`<yyyy-MM-dd-HHmm>` 按本机时间取，跑法：`Get-Date -Format "yyyy-MM-dd-HHmm"`。
- **输出目录按批分。**这一批的几条命令都传同一个 `--output-dir`；这批里跑的第几回由方案自己在下头追加一层。后一批落进新目录，盖不掉前一批。
- **同一批跑了两回以上时，哪一回是哪个看目录里那一层。**第一回是照现在的设计稿首跑；之后每一回是改过设计稿或配置之后的复核，改了什么写在这一批的报告旁边那一份里。
- **报告出两种格式：机器读的与看的网页。**两种都落在上面那个输出目录里，出哪几种在配置文件的报告那一段里列出来——不列就只有默认那一种。要 HTML 得显式列上；事后要补，从已落下的结果文件生成，不必重跑。
- **同一批至少跑两遍，两遍不一致的用例照实记下来。**跑第二遍不为核对结论，为的是看判据稳不稳：一轮过一轮不过的用例，毛病多半出在判据写得不够硬，而不是被测那边不稳定。两遍怎么分辨见上面那条。
- **结论记在哪。**这一批哪几条没过、为什么、下一轮改什么，落在这一批输出目录里的报告上；前面六份文档不回收它们。
- **不进版本库的东西：跑测的输出目录整棵不进。**版本库的忽略文件里盖住它的那一条也指名写出来。
