# 测试模型规格说明

测试项：`plugin/skills/token-counter/scripts/count_tokens.py`——用 DeepSeek 官方词表（随技能分发的 `tokenizer.json`）精确计算一段文本或一个文件的 token 数，供 API 调用前估算预算。测试依据是技能的说明文件 `SKILL.md`（用法、口径与边界、首次运行的引擎依赖）与官方词表文件本身，见文末「依据 → 模型」对应表。

本次共四个测试模型，对应四门选定的测试设计技术：判定表测试（TM-1）、等价类划分（TM-2）、状态转移测试（TM-3）、场景测试（TM-4）。

## 一、TM-1 命令行与输入来源判定表

**唯一标识符**：TM-1

**目标**：命令行参数与输入来源的选择——三种输入来源（`--text` 的字面文本、文件路径、标准输入）各在什么条件下被采用；读到不是合法 UTF-8 的字节、或指定的文件读不出来时走向哪里。本模型只描述这一层瞬时判定，不描述先后过程。

**优先级**：中。命令行与输入来源这一层未列入高风险，按一般风险处理：可行判定规则取全，不额外多导用例。

**测试策略摘要**：本模型用判定表测试。本次共选四门技术，分工如下：判定表测试管命令行这一层的瞬时判定；等价类划分（TM-2）给出正文内容与无效输入的各个类，它导出的测试覆盖项同时充当场景测试（TM-4）所用测试用例的输入取值；状态转移测试（TM-3）管引擎就绪的先后过程，即从进程启动到可以计数之间的那几步。四门同属基于规格说明的技术，擅长检出遗漏型缺陷；代码里有、依据里没有的行为（多余型缺陷）不在这四门的能力范围内，本方案未安排结构那一侧的技术来补这一类。测试完成准则：四门选定的技术，覆盖率均要求达到 100%；确实无法执行的测试覆盖项按不可行项处理，剔除时在测试用例规格说明里写明原因。

**测试模型**：判定表由条件桩与条件项、动作桩与动作项组成，每一列是一条判定规则。

| 条件与动作 | 规则 1 | 规则 2 | 规则 3 | 规则 4 | 规则 5 | 规则 6 |
|:---|:---|:---|:---|:---|:---|:---|
| 条件 C1：命令行给了 `--text` | T | F | F | F | F | F |
| 条件 C2：命令行给了文件路径 | — | T | T | T | F | F |
| 条件 C3：标准输入已接入且能读到字节 | — | — | — | — | T | T |
| 条件 C4：文件读得出来（存在且不是目录） | — | T | T | F | — | — |
| 条件 C5：读到的字节能按 UTF-8 解码 | — | T | F | — | T | F |
| 动作 A1：按 `--text` 的字面文本计数 | T | F | F | F | F | F |
| 动作 A2：读文件、去掉开头的 BOM 后计数 | F | T | F | F | F | F |
| 动作 A3：读标准输入并计数 | F | F | F | F | T | F |
| 动作 A4：输出 `tokens` 与 `chars` 两行 | T | T | F | F | T | F |
| 动作 A5：不给计数结果，在标准错误上给出提示，以非 0 状态结束 | F | F | T | T | F | T |

表里的「—」表示该条件在这条规则下不影响结果。「T」为真、「F」为假。

三条与这张表有关的说明：

——规则 1 与规则 2 同时成立时（既给了 `--text`，也给了文件路径），判定表只取规则 1：依据把 `--text` 描述为直接给一段文本，命令行给了文本就按文本数，无需再去读文件。这一条是本设计从依据推出的读法，不是依据的原话。

——规则 3、4、6 的报错措辞与退出码取值，依据没有规定；这三条规则的预期结果因此只固定两件事：不给出计数结果，且以非 0 状态结束。实际输出由用例记录，若把无效输入当作空正文数出 0 个 token，判为缺陷。

——识别出一项未规定功能：既没给 `--text`、也没给文件路径、标准输入又是终端时，依据没有规定这种用法该怎么办，测试项在这种情形下会一直等标准输入。这种情形无法在无人值守下执行，不列为测试覆盖项，本次不覆盖。

## 二、TM-2 正文内容与输出口径的等价类

**唯一标识符**：TM-2

**目标**：输入正文的各种内容形态（含空正文、含空格、含中文、以汉字开头、含官方特殊 token、代码、补充平面字符、带 BOM 的文件）、几种无效输入，以及输出一侧的两类结果与两条口径——`tokens` 与官方词表规范语义一致、`chars` 计的是字符个数。计数口径是本次唯一列入高风险的部分，本模型是它主要的落点。

**优先级**：高。模型里与计数口径直接相关的等价类按高风险处理，因此整个模型建得较细：正文内容的有效类拆到九个，不合并。

**测试策略摘要**：本模型用等价类划分。它在组合里的位置：向场景测试（TM-4）提供测试用例的输入取值；与判定表测试（TM-1）的分工是——判定表管输入来源怎么选，等价类管正文内容本身。有效测试用例取最小化方式（一条用例尽量多覆盖几个等价类），无效测试用例取一对一方式（一条用例只带一个无效输入，避免一个错误遮住另一个）。测试完成准则：等价类划分覆盖率达到 100%。

**测试模型**：等价类按处理环节分组列出。`E` 开头的是有效等价类，`N` 开头的是无效等价类，`O` 开头的是输出一侧与口径的等价类。

| 处理环节 | 等价类 |
|:---|:---|
| 输入处理：正文内容的有效等价类 | E1 纯 ASCII 文本，词与词之间有空格；E2 含中文的文本（汉字与中文标点）；E3 以汉字开头、后面接 ASCII 的文本；E4 含官方词表里特殊 token 的文本；E5 空正文（0 个字符）；E6 只有空白字符的文本（空格、制表符、换行）；E7 代码文本（含缩进、符号与换行）；E8 含补充平面字符的文本（emoji 一类，UTF-8 里占 4 字节）；E9 带 BOM 的 UTF-8 文件（BOM 是文件编码标记） |
| 输入处理：正文内容的无效等价类 | N1 文件里的字节不是合法 UTF-8；N2 文件路径不存在；N3 路径指向一个目录；N4 标准输入里的字节不是合法 UTF-8 |
| 内部处理：计数口径 | O1 `tokens` 的取值与官方词表（`tokenizer.json`）的规范语义一致；O2 `chars` 计的是解码后正文的字符个数（一个汉字算 1 个，emoji 也算 1 个），不是这段正文在 UTF-8 里占的字节数 |
| 输出处理 | O3 有效输入产出 `tokens` 与 `chars` 两行；O4 无效输入不产出计数行，给出提示并以非 0 状态结束 |

两条与本模型有关的说明：

——E9 的预期按「BOM 是文件编码标记、不属于正文」这一读法固定：同一个正文，带 BOM 与不带 BOM 应数出相同的 `tokens` 与 `chars`。依据没有点明 BOM；若测试项把 BOM 计入正文，按缺陷处理。

——O2 的名称取自依据里「chars：UTF-8 字符数」那句话。这句话有两种读法：解码之后的字符个数，或这段正文在 UTF-8 编码下占的字节数。本设计按前一种读法固定预期（「你好，世界」是 5 个字符，它在 UTF-8 里占 15 字节，预期为 5），并用一条专门用例把实际口径钉住：口径若日后改动，这条用例会失效，需要重审。

## 三、TM-3 引擎就绪流程的状态转移

**唯一标识符**：TM-3

**目标**：从正文读入之后到能开始计数之间，引擎（`tokenizers`）就绪的先后过程：引擎已经装好、装上随技能打包的 wheel、以及平台不符时联网安装这三条路，外加装不上时的终止。本模型从「正文已在手」这一状态起算——正文读入失败（TM-1 的规则 3、4、6）在到达本模型之前就已经结束进程，那几种情形由 TM-1 与 TM-2 覆盖。

**优先级**：中。引擎安装一路未列入高风险，按一般风险处理。

**测试策略摘要**：本模型用状态转移测试，取 0-switch 档（覆盖全部有效单步转移）。取这一档的依据：风险信息只把计数口径列为高风险，引擎安装这一路按一般风险处理；另外，脚本对不适用的事件本来就没有入口（引擎已装时不会再去装），硬列出无效转移会造出无法执行的测试覆盖项。测试完成准则：状态转移测试在 0-switch 档下覆盖率达到 100%。

**测试模型**：用纯文本的状态表表示。

状态：

| 状态 | 含义 |
|:---|:---|
| S1 | 正文在手，引擎状态尚未检查 |
| S2 | 引擎不可导入（检查后发现） |
| S3 | 引擎就绪（`tokenizers` 可以导入） |
| S4 | 离线安装未成，转入联网兜底 |
| S5 | 安装失败，进程以非 0 状态结束 |
| S6 | 已输出 `tokens` 与 `chars` 两行 |

有效单步转移：

| 编号 | 开始状态 | 事件（守护条件） | 动作与输出 | 结束状态 |
|:---|:---|:---|:---|:---|
| G1 | S1 | 检查引擎：已经可以导入 | 不安装 | S3 |
| G2 | S1 | 检查引擎：不可导入 | 转入安装 | S2 |
| G3 | S2 | 安装打包的 wheel：wheel 在且装得上 | 在标准错误上给出安装提示（措辞依据未规定） | S3 |
| G4 | S2 | 离线安装未成：wheel 不在，或装的时候失败 | 转入联网兜底 | S4 |
| G5 | S4 | 联网安装：成功 | 在标准错误上给出安装提示 | S3 |
| G6 | S4 | 联网安装：失败 | 结束进程，非 0 状态，不给计数结果 | S5 |
| G7 | S3 | 拿到正文并完成计数 | 输出 `tokens` 与 `chars` 两行 | S6 |

一条说明：G3 与 G5 里「在标准错误上给出安装提示」这件事，依据只说首次运行会自动装引擎，没有规定提示的措辞与去向；用例只固定「不影响标准输出上的两行计数结果」，措辞不做断言。

## 四、TM-4 端到端使用场景

**唯一标识符**：TM-4

**目标**：把测试项放回实际用法里看整条链——调用方给出正文、命令行外壳与解释器把它交给脚本、脚本数完把两行结果交回，含与其他系统的交互（命令行外壳、文件系统、Python 解释器、pip、网络）。主场景是「在装好引擎的机器上数一个文件」，其余五条是备选场景：没有引擎且不能联网的首次使用、正文不是合法 UTF-8、路径写错、很长的文本、空文件。

**优先级**：中。本模型不单独承担高风险部分，按一般风险处理。

**测试策略摘要**：本模型用场景测试。它在组合里的位置：把等价类划分（TM-2）导出的测试覆盖项当作各场景的输入取值，两条通道、一条错误路径、一条首装路径各成因完整的交互序列；场景测试不引入新的输入类，只验证这些输入类串成完整用法后仍然成立。测试完成准则：场景覆盖率达到 100%，即主场景与全部备选场景都被覆盖。

**测试模型**：每个场景一行，列出组成该场景的交互序列。序列里的标记：`U` 是调用方的动作，`S` 是测试项的动作，`X` 是其他系统的动作。

| 场景 | 类型 | 交互序列 |
|:---|:---|:---|
| 在装好引擎的机器上数一个文件 | 主场景 | U1 在命令行给出文件路径并执行；X1 命令行外壳把参数交给 Python 解释器；S1 读入文件字节并去掉开头的 BOM；S2 检查引擎：已经可以导入，不安装；S3 按官方词表计数；S4 输出两行结果，退出码 0；U2 读取结果 |
| 在没有引擎、不能联网的机器上首次使用 | 备选场景 | U1 给出正文；X1 启动解释器（无网络可用）；S1 读入正文并解码；S2 检查引擎：不可导入；S3 用随技能打包的 wheel 离线安装；S4 按官方词表计数；S5 输出两行结果，退出码 0 |
| 正文不是合法 UTF-8 | 备选场景 | U1 给出一个文件，其字节不是合法 UTF-8；S1 解码失败；S2 不给计数结果，在标准错误上给出提示，退出码非 0；U2 发现没有拿到 token 数 |
| 文件路径写错 | 备选场景 | U1 给出一个不存在的路径；S1 读文件失败；S2 不给计数结果，退出码非 0；U2 发现没有拿到 token 数 |
| 数一份很长的文本 | 备选场景 | U1 给出长文本文件；S1 读入并解码；S2 检查引擎；S3 按官方词表计数；S4 输出两行结果，退出码 0 |
| 数一个空文件 | 备选场景 | U1 给出一个 0 字节的文件；S1 读入空正文；S2 计数得到 0；S3 输出两行结果，退出码 0 |
