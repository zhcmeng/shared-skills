# 测试模型规格说明

本套产出的测试项是 token-counter 技能，目录在 `plugin/skills/token-counter/`。它的对外契约分写在两处：一处是 `SKILL.md` 的正文——用法、口径与边界、官方换版时的维护；一处是 `scripts/count_tokens.py` 文件头写明的三种调用方式与两种输出。两处合起来构成本套产出的测试依据。

这个技能是靠模型跑起来的，所以契约跨两层：一层是脚本那一层——命令怎么调、读到什么、吐出什么、退出码是几；一层是技能被调用时模型那一侧的表现——用哪个 tokenizer、哪些数算不了、别的模型问上门来怎么回话。两层各建各的模型，下面按模型分组。

## TM-1 脚本层的输入与输出等价类

**唯一标识符**：TM-1

**英文名**：eq_class_script_io

**目标**：这个模型只关注脚本那一层的输入与输出——一段文本或一个文件怎么交到脚本手里、脚本据此吐出什么。技能被调用时模型那一侧的表现不在这个模型里，那在 TM-4。

**风险等级**：高。定级依据见决策依据里第 0 步那一条：输入边界与异常是用户点名的两处高风险之一，这个模型正是收这一处的。

**测试策略摘要**：这一套选定四门技术——等价类划分、边界值分析、判定表测试、场景测试，四门同属基于规格说明这一类，都拿测试依据当设计用例的主要信息来源。四门的分工是：等价类划分划出输入与输出的取值分组，是本套的主干；边界值分析（TM-2）在它划出的有序等价类上标出边界；判定表测试（TM-3）收它收不了的那处布尔条件组合，即引擎获取路径；场景测试（TM-4）拿前面三门导出的覆盖项当输入参数，串成技能被调用时的交互序列。本模型的角色是主干，为 TM-2 与 TM-4 提供输入。测试完成准则是：四门各自识别出的测试覆盖项全部取全、全部有用例覆盖，覆盖率按 100% 要求。

**测试模型**：按处理环节列出识别出的等价类，每条一个标签，供覆盖项的可追溯性栏引用。有效等价类与无效等价类分开列；依据里没有规定、实现却做得出反应的那些情形，另列一组。

输入处理：输入源（把文本交给脚本的路径）

- E1（有效）`--text` 给出非空文本
- E2（有效）给出一个存在的 UTF-8 文本文件路径
- E3（有效）不给 `--text`、不给文件路径，由标准输入给出非空数据
- E4（无效）不给 `--text`、不给文件路径，标准输入也为空
- E5（无效）文件路径不存在
- E6（无效）文件路径指向一个目录
- E7（未规定）`--text` 与文件路径同时给出

输入处理：文件编码

- E8（有效）UTF-8，不带字节顺序标记
- E9（有效）UTF-8，带字节顺序标记
- E10（无效）不是 UTF-8 的字节序列

输入处理：文本内容

- E11（有效）纯 ASCII 字符
- E12（有效）纯中文
- E13（有效）基本平面之外的字符（如表情符号）
- E14（有效）DeepSeek 特殊 token 的字面量
- E15（有效）只由空白字符组成
- E16（边界）零字符的空文本

输出处理

- E17（有效）标准输出打印 `tokens:` 与 `chars:` 两行，退出码为 0
- E18（无效）不打印这两行，以非零退出码结束

E7 与 E16 的说明：E7 落在依据的空档里——`SKILL.md` 与脚本的文件头都只写了「三选一」的三种调用方式，没有写两个来源同时给出时听谁的。实现上 `--text` 胜出、文件被静默忽略。E16 归在边界那一组：`SKILL.md` 说「一段文本」时没有把空文本排除在外，脚本也不报错，照常吐出两个 0。

## TM-2 文本与文件的长度边界

**唯一标识符**：TM-2

**英文名**：boundary_values_text_size

**目标**：这个模型只关注长度这一个维度上的边界——文本字符数为零与为一的那条线、文件字节数为零与为一的那条线，以及带字节顺序标记的文件里标记之后的字符数那条线。这几条线是用户点名的另一处高风险「输入边界与异常」最集中落地的地方。

**风险等级**：高。定级依据同 TM-1。

**测试策略摘要**：这一套选定四门技术——等价类划分、边界值分析、判定表测试、场景测试。本模型由边界值分析建出，是它在 TM-1 划出的等价类里挑出可排序的那几个，再标出边界；它的覆盖项不与 TM-1 重复计数，两门各自的覆盖项分别计入各自的覆盖率。完成准则同前：四门各自识别出的测试覆盖项全部取全、全部有用例覆盖，覆盖率按 100% 要求。

**测试模型**：带边界的等价类。每个有序集先划出相邻的两个类，再标出它们之间那条边界；采用二值边界测试，每个边界取边界上的值与相邻类里紧挨着边界的那个值。三处边界都只有下侧——长度不能为负，所以每个有序集只识别出一条边界。

有序集 A：文本的字符长度（由 `--text` 给出的文本）

- 相邻两类：字符数为零（A0）与字符数大于零（A1）
- 边界：A0 与 A1 之间；边界上的值是 0，A1 里紧挨着边界的是 1

有序集 B：文件的字节长度（由文件路径给出的文件，不含字节顺序标记）

- 相邻两类：字节数为零（B0）与字节数大于零（B1）
- 边界：B0 与 B1 之间；边界上的值是 0，B1 里紧挨着边界的是 1

有序集 C：带字节顺序标记的文件里，标记之后的字符数

- 相邻两类：标记之后字符数为零（C0，即整个文件只有那三个字节）与大于零（C1）
- 边界：C0 与 C1 之间；边界上的值是 0，C1 里紧挨着边界的是 1

没走边界值分析的两处，记在这里备查：一是 CPython 的版本边界（`SKILL.md` 写明平台不符指非 Windows x64 或 CPython 低于 3.9），二是引擎版本边界。两处都只有再装一个解释器才落得到边界上，实施成本高于这一段能查出的缺陷；这两处要查的是「走哪条安装路径」，已由 TM-3 的三条规则各自覆盖，不再另计边界值覆盖项。这一条决定的经过见决策依据。

## TM-3 引擎获取路径

**唯一标识符**：TM-3

**英文名**：decision_table_engine_acquire

**目标**：这个模型只关注首次运行那一步——脚本发现 `tokenizers` 引擎不可用时，按什么条件走哪条路把它弄到手。这是用户点名的两处高风险之一「首次运行自动装依赖」正对着的那一处，也是这套产出里唯一会改动目标机 Python 环境的地方。

**风险等级**：高。定级依据同 TM-1。

**测试策略摘要**：这一套选定四门技术——等价类划分、边界值分析、判定表测试、场景测试。本模型由判定表测试建出。选它的理由是：这一段是布尔条件的组合，两个条件与三条动作的关系写成判定表才读得清；它也是这一套里唯一会写盘的一处，判据除了退出码还有装在盘上的东西。完成准则同前：四门各自识别出的测试覆盖项全部取全、全部有用例覆盖，覆盖率按 100% 要求。

**测试模型**：判定表。条件桩两条，动作桩三条。

条件：

- C1：目标机的 Python 环境里 `tokenizers` 已经可以导入
- C2：随技能分发的引擎 wheel 存在，且与当前平台匹配（Windows x64 且 CPython 不低于 3.9）

动作：

- A1：直接用已经装好的引擎，不做任何安装
- A2：离线安装随技能打包的 wheel
- A3：联网安装 `tokenizers`，版本号取脚本里写死的那个

| 条件与动作 | 规则 1 | 规则 2 | 规则 3 |
|:---|:---|:---|:---|
| 条件 C1：引擎已可导入 | T | F | F |
| 条件 C2：打包 wheel 可用 | — | T | F |
| 动作 A1：直接用已装的引擎 | T | F | F |
| 动作 A2：离线装打包 wheel | F | T | F |
| 动作 A3：联网装写死版本 | F | F | T |

三条规则逐条读出来：

- 规则 1：C1＝T、C2 取什么都一样——直接用已经装好的引擎，不装任何东西。这一列是合并列，同时管「引擎已装且 wheel 可用」与「引擎已装且 wheel 不可用」两种组合；两种组合落到同一个动作，故合并。
- 规则 2：C1＝F、C2＝T——离线安装打包的 wheel。
- 规则 3：C1＝F、C2＝F——联网安装写死版本的那个。C2 为假有两种成因：`wheels/` 目录里没有 wheel，或者 wheel 与当前平台不匹配（非 Windows x64，或 CPython 低于 3.9）。两种成因落同一条规则，不拆成两条——依据里这一处的前置条件只有一个「平台不符」，落到动作上没有分别。

三条规则都可行，没有星号列。

## TM-4 技能被调用时的用法场景

**唯一标识符**：TM-4

**英文名**：scenarios_skill_usage

**目标**：这个模型只关注技能被调用时模型那一侧的表现——用户带着什么需求来、技能怎么接、回话里该有哪些内容。脚本本身怎么跑不在这个模型里，那在 TM-1、TM-2、TM-3。

**风险等级**：中。用户点名的高风险是另外两处（首次运行自动装依赖、输入边界与异常），计数准确性与触发面没有点名；这个模型收的正是口径说明与跨模型回话这一片，按中风险处理。定级依据见决策依据里第 0 步那一条。

**测试策略摘要**：这一套选定四门技术——等价类划分、边界值分析、判定表测试、场景测试。本模型由场景测试建出，用的是技能与用户之间的交互序列。它与另外三门是组合关系里的一环：TM-1 与 TM-2 导出的覆盖项在这里当输入参数用，决定每条场景里拿什么文本、什么文件去跑。完成准则同前：四门各自识别出的测试覆盖项全部取全、全部有用例覆盖，覆盖率按 100% 要求。

**测试模型**：交互序列。一条主场景加八条备选场景，每条一行，用「用户」「技能」两个动作主体把序列串起来。用户算作与技能交互的另一个系统。

| 场景 | 类型 | 交互序列 |
|:---|:---|:---|
| 算一段文本或一个文件的 token 量 | 主场景 | 用户提出要算 token 量 → 技能定位到本技能目录 → 技能按输入形态选一种调用方式跑脚本 → 技能读出 `tokens:` 那一行的数 → 技能把数报给用户 |
| 只问 token 量、不问字符数 | 备选场景 | 用户只问 token 量 → 技能跑脚本 → 技能只报 token 数，不报字符数 |
| 问的是别的模型的 token | 备选场景 | 用户点名要算别的模型的 token → 技能说明本技能不覆盖那个模型 → 技能不给近似数 |
| 要估算 API 成本 | 备选场景 | 用户要估算调用成本 → 技能跑脚本给出 token 数 → 技能说明缓存命中那部分离线算不出来 |
| 文本里含 DeepSeek 特殊 token | 备选场景 | 用户给的文本里带特殊 token 的字面量 → 技能跑脚本 → 技能按官方词表把这些计入，不作特殊处理 |
| 要估算一整轮对话请求 | 备选场景 | 用户要算一条完整请求 → 技能说明得先按对话模板把消息拼装起来再计数 → 技能给出拼装后的计数办法 |
| 输入没法按 UTF-8 解码 | 备选场景 | 用户给的输入不是 UTF-8 → 技能跑脚本 → 脚本报出解码失败并指认是哪个输入 → 技能把这一情况报给用户 |
| 一次要算多个文件的总额 | 备选场景 | 用户给出多个文件 → 技能逐个跑脚本 → 技能把各文件的结果与合计一并报出 |
| 目标机上还没装引擎 | 备选场景 | 用户照常提出要算 token 量 → 技能跑脚本 → 脚本自行把引擎装好 → 技能报出数，不要求用户额外做安装动作 |
