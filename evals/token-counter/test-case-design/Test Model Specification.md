# 测试模型规格说明

测试项：`plugin/skills/token-counter/` 整门技能。它由一份技能正文（`SKILL.md`）和一支计数脚本（`scripts/count_tokens.py`）组成：技能正文管「什么时候用、怎么答、口径与边界」，脚本用随技能分发的那份官方词表按规范语义数 token，报出 token 数与字符数两行。技能靠模型驱动着跑：技能被唤起后，模型照正文把脚本调起来。测试依据取自这两份文件，见文末「依据 → 模型」对应表。

本次共四个测试模型，对应四门选定的测试设计技术：等价类划分（TM-1）、边界值分析（TM-2）、判定表测试（TM-3）、场景测试（TM-4）。

**这一层的判据分落在两处**：TM-1 至 TM-3 判的多半落在脚本这一侧——命令的输出、退出码、盘上文件上；TM-4 把整条链（技能被唤起、模型照正文调用脚本、把结果答回）串起来再走一遍，判据落在模型跑起来一路做了什么上。

## 一、TM-1 输入道与文本内容的等价类模型

- **唯一标识符**：TM-1
- **英文名**：input_route_and_text_classes
- **目标**：要数的文本从哪条道进来、进来的是哪一类内容、报回去的是什么。数得准不准里与取值形态相关的那一部分也在这里。
- **风险等级**：高。用户点名的「非法字符等」落在本模型：解不了码的字节序列、能解码但异常的字符都在这一组的取值里。用户在开工前把这一处单独说出来，正是要把这一片挑出来。
- **测试策略摘要**：等价类划分。与另外三门各建各的模型，不互相喂数据——TM-2 管字节边界上的取值，TM-3 管什么条件下走哪条安装道，TM-4 管一句请求走多远。它另有一处往外供料：本模型导出的调用方式与文本取值，用来给 TM-2 与 TM-4 的用例挑输入参数（谁给谁供料：等价类划分 → 场景测试）。测试完成准则是等价类划分覆盖率 100%，全部等价类都要有用例覆盖。
- **测试模型**：等价类清单如下，按输入处理、内部处理、输出处理三组列，类别编号沿用 `PART-`。

输入处理：调用方式

- PART-1 有效：在命令行上用 `--text` 直接给一段文本
- PART-2 有效：给一个存在的 UTF-8 文本文件的路径
- PART-3 有效：把要数的内容用管道从标准输入喂进来
- PART-4 无效：给的文件路径不存在
- PART-5 无效：给的路径指向一个目录
- PART-6 无效：字节序列的形状不合法（截断的多字节序列、非法首字节、孤立续字节），解不了码
- PART-7 无效：字节序列的形状合法但语义非法（过长编码、代理区码点、超出 U+10FFFF 的码点），解不了码
- PART-8 未规定：`--text` 与文件路径同时给时，数哪一个

输入处理：交到脚本手里的那段文本

- PART-9 有效：纯 ASCII 文本
- PART-10 有效：纯中文文本
- PART-11 有效：中英混排、含空格与换行的文本
- PART-12 有效：一个字符都没有的空文本
- PART-13 有效：文件或管道的内容以完整的字节顺序标记开头——那 3 个字节被剥掉
- PART-14 有效：`--text` 直接给的文本以字节顺序标记那个字符开头——不经解码，不被剥掉
- PART-15 有效：含 DeepSeek 特殊 token 的字面形，如 `<｜end▁of▁sentence｜>`
- PART-16 有效：含控制字符（NUL、退格这一类）
- PART-17 有效：含零宽字符与不可见格式字符（零宽空格、文本中间的字节顺序标记字符）
- PART-18 有效：含替换字符或非字符码点（U+FFFD、U+FFFE 这一类）

内部处理：词表怎么读

- PART-19 有效：按随技能分发那份词表的规范语义加载它
- PART-20 无效功能：改用另一条兼容加载路径读同一份词表

输出处理：报回来的东西

- PART-21 有效：报出 token 数与字符数两行
- PART-22 有效：用户只要 token 量时，答话里报出 token 数
- PART-23 有效：用户问调用成本时，点明离线算不出缓存命中、计费以接口返回的用量为准
- PART-24 有效：用户点名别的模型时，说明本技能不覆盖那个模型、不给近似数
- PART-25 无效功能：绕开本技能另去找一个数顶上，给出别的模型的近似 token 数
- PART-26 有效：要估一次完整对话请求时，先按对话模板把请求拼装起来再计数
- PART-27 未规定：输入走不通时（路径不存在、路径是目录、解不了码、给了两个文件）以什么方式收场

与这个模型有关的四条说明：

——PART-4 至 PART-7 这几类走不通的输入，依据里只说了输入应当是 UTF-8 文本，没说走不通时该怎么收场——它们的预期结果按「依据未规定这一处」记，落到 PART-27。

——PART-20 与 PART-25 是无效功能：依据里明令不许这么做，测试项若真这么做了，缺陷在测试项那一侧。PART-20 有一条查得到的痕迹：改用兼容加载路径之后，以中文开头的文本会被编成空序列，数出来正是 0，那个数一眼看得出来不对。

——PART-13 与 PART-14 是一对：同一个字节顺序标记，从文件或管道进来时开头那 3 个字节被剥掉，从 `--text` 直接给时原样留着——两条道的处理不同，所以分列两条。PART-17 里「文本中间的字节顺序标记字符」是第三处：它不剥、照常计数。

——PART-8 与 PART-27 是依据没有规定的两处：`--text` 与文件同时给时数哪一个、走不通时以什么方式收场。这两处造得出来、也比得出来（看数的是哪份内容、报了什么、退出码几），用例把实际行为记下来报给用户定口径。

## 二、TM-2 文本字节边界的三值边界模型

- **唯一标识符**：TM-2
- **英文名**：text_byte_boundaries
- **目标**：交过去的那段文本在字节层面的三个有序量——一次调用交过去的字符个数、一个字符在 UTF-8 里占几个字节、文本开头属于字节顺序标记的字节个数。落在区间中间的取值归 TM-1，这一门只管边界与其两侧的邻值。
- **风险等级**：高。用户点名的「非法字符等」里，解不了码的字节序列正落在「开头属于字节顺序标记的字节个数」这个量的区间外取值上（残缺的 1、2 字节形态），「字符与字节的分别」也落在前两个量上。
- **测试策略摘要**：边界值分析，取三值边界测试——每个边界识别三个覆盖项：边界上的值，以及两侧各一个增量距离的值；增量距离取所考虑数据类型的最小有效值（字符数增 1 个字符，字节数增 1 个字节）。它以 TM-1 划出的等价类为起点：先有等价类，再把其中有边界的几类挑出来标上边界（谁给谁供料：等价类划分 → 边界值分析）。取三值不取二值的理由记在决策依据里。测试完成准则是边界值覆盖率 100%，覆盖全部已识别且可行的边界值。
- **测试模型**：带边界的等价类如下。三个有序集，每个集里的元素都能从最低到最高无间断地排。

| 有序集 | 区间 | 下边界 | 上边界 |
|:---|:---|:---|:---|
| 甲：一次调用交过去的文本的字符个数 | 0 起，无上界 | 0 | 无。上界由承载它的解释器定，依据里没有可识别的取值 |
| 乙：一个字符在 UTF-8 里占的字节个数 | 1 到 4 | 1 | 4 |
| 丙：文本开头属于字节顺序标记的字节个数 | 0 到 3 | 0 | 3——一个完整的字节顺序标记恰好占 3 个字节 |

三个集在三值边界测试下识别出的边界值见测试覆盖项清单。乙那一集的两个区间外取值（占 0 个字节、占 5 个字节）、丙那一集的两个区间外取值（负数、4 个字节）、甲那一集的区间外取值（负数）在 UTF-8 里造不出来，判为不可行，剔除原因写在那几条覆盖项的描述栏里。

## 三、TM-3 首次运行装依赖的判定表模型

- **唯一标识符**：TM-3
- **英文名**：first_run_install_decision_table
- **目标**：目标解释器里能不能导入那份引擎、随技能打包的那份包在不在、装不装得上，这三件事凑在一起时脚本走哪条安装道。装完之后照常计数那一截归 TM-4。
- **风险等级**：中。首次运行会在目标机上真的装东西，装不稳会整个跑不动；但它是三条道里的一条、有明白的提示，且只发生在没装引擎的机器上。
- **测试策略摘要**：判定表测试。与其余三个模型各建各的，不互相喂数据。四门里只有这一门管安装道那一侧。测试完成准则是判定表测试覆盖率 100%，只算可行的判定规则——下表四条都可行，没有不可行的规则。
- **测试模型**：用判定表表示，见下表；表后是逐条规则清单。

| 条件与动作 | 规则 1 | 规则 2 | 规则 3 | 规则 4 |
|:---|:---|:---|:---|:---|
| 条件 C1：目标解释器里已经能导入那份引擎 | T | F | F | F |
| 条件 C2：随技能打包的那份包在（`wheels/` 下有一个包文件） | — | T | T | F |
| 条件 C3：打包那份在当前平台上装得上 | — | T | F | — |
| 动作 A1：直接用现成的引擎，一个字节都不装 | T | F | F | F |
| 动作 A2：先装上随技能打包的那份（离线、不带依赖） | F | T | F | F |
| 动作 A3：改从包索引联网装钉住的版本 | F | F | T | T |

逐条规则读出来：

- 规则 1：C1＝T——直接用现成的引擎，不装、不联网。C2、C3 在这一列写成「—」：C1 已经为真时，打包那份在不在、装不装得上，都管不到该做什么。
- 规则 2：C1＝F、C2＝T、C3＝T——先装上随技能打包的那份，装法上带 `--no-deps`，全程不联网。
- 规则 3：C1＝F、C2＝T、C3＝F——打包那份在，可它装不上，改从包索引联网装钉住的版本。
- 规则 4：C1＝F、C2＝F——打包那份压根不在，直接走联网那条道。C3 在这一列写成「—」：没有包可装，「装不装得上」无从谈起。

C3 取假有两种成因，都落在规则 3 上：当前平台与随技能打包的那份对不上（非 Windows x64，或 CPython 低于 3.9）；或者平台对得上、装的动作本身没成。两种成因下脚本的动作一样，都是改走联网那条道。脚本里钉住的版本号是 0.22.2，规则 3 与规则 4 装的就是它。

## 四、TM-4 一次计数请求的交互序列模型

- **唯一标识符**：TM-4
- **英文名**：counting_request_scenarios
- **目标**：一句请求从进来到结果报回，中间走过哪些步；以及这条序列在哪几处会分岔。
- **风险等级**：中。这一层把别处判过的放回完整链里再走一遍，不引入新的判点；用户点名的「非法字符等」已在 TM-1 与 TM-2 判高，这里按一般风险处理。
- **测试策略摘要**：场景测试（用例测试归在这一门里）。TM-1 导出的调用方式与文本取值用来给这一门的用例挑输入参数（谁给谁供料：等价类划分 → 场景测试）——场景本身照下面这条序列走，走的时候用哪段文本、走哪条调用方式，从 TM-1 那几个等价类里取。测试完成准则是场景覆盖率 100%，主场景与全部备选场景都要有用例覆盖。
- **测试模型**：用交互序列表表示。每个动作用一个标识符表示，`U` 打头的是用户那侧的动作，`S` 打头的是测试项这一侧的动作。

公共的几步先列在这里，各场景用标识符引用：

- U1：用户提出一句算 token 的请求
- S1：技能按名唤起，读到自己那份说明正文
- S2：定位到计数脚本所在的目录
- S3：把要数的文本按调用方式交给脚本，用绝对路径把脚本调起来
- S4：脚本按规范语义加载随技能分发的那份词表，数出 token 数
- S5：脚本数出字符数，把两样打成两行
- S6：技能把数报回给用户

各场景如下：

| 场景 | 类型 | 交互序列 |
|:---|:---|:---|
| 一次计数请求走完 | 主场景 | U1、S1、S2、S3、S4、S5、S6 |
| 点名的是别的模型 | 备选场景 | U1、S1、S1.1、S6.1 |
| 问的是调用成本 | 备选场景 | U1、S1、S2、S3、S4、S5、S6.2 |
| 文本要喂进一次完整对话请求 | 备选场景 | U1、S1、S2、S3.1、S4、S5、S6 |
| 目标机是干净的、没装引擎 | 备选场景 | U1、S1、S2、S3、S4.1、S5、S6 |
| 用户只要 token 量 | 备选场景 | U1、S1、S2、S3、S4、S5、S6.3 |
| 文本里含特殊 token 的字面形 | 备选场景 | U1、S1、S2、S3.2、S4、S5、S6 |
| 用户给的输入走不通 | 备选场景 | U1、S1、S2、S3.3、S6.4 |

序列里那几步的差别：

- S1.1：技能读到的说明正文里写着「只覆盖 DeepSeek 当前官方词表；点名别的模型时明确说明不覆盖，不给近似估算」这一条，序列就此分岔：报出去的只能是本词表数出来的数，且不得说成是那个模型的数。
- S6.1：说明本技能不覆盖那个模型、不给近似估算；不绕开本技能另找一个估算数冒充那个模型的数。
- S6.2：在报数之外多一句，点明离线算不出缓存命中、计费以接口返回的用量为准。
- S3.1：把文本交给脚本之前多一步，先按对话模板把这段文本拼装成一次完整请求，再交给脚本数。
- S4.1：脚本发现目标机上没装引擎，先装上随技能打包的那一份，再加载词表计数。
- S6.3：答话里报出 token 数。
- S3.2：交过去的是原样的文本，含特殊 token 字面形的那一段不转义、不拆开、不剥离。
- S3.3：用户那侧没有可数的东西交过来，或者给的那条道走不通（路径不存在、路径是目录、内容解不了码、给了两个文件）；脚本这一头以非零退出码收场。
- S6.4：照实把「这个输入数不了」说给用户，不报出任何 token 数、也不拿别的数顶上。

与这个模型有关的三条说明：

——主场景是这门技能最常见的被调用形式：用户给一段文本或一个文件路径，技能把脚本调起来、把两个数报回。判的是「数报得对不对」与「报的形态对不对」。

——备选场景 1（点名的是别的模型）判的是「被唤起之后怎么答」，兼看「该不该被唤起」：依据的说明正文里明写着这一问也照样用它，技能若被判定为不适用而排除掉、转去触发别的技能，这一条的判据自然不成立。这一处的措辞不限，判的是那个意思有没有。

——备选场景 8（输入走不通）一条盖四路成因：路径不存在、路径是目录、内容解不了码、给了两个文件。四路的收场形态不同，用例按成因分开摆、分开判；它的预期结果按「依据未规定这一处」记（见 TM-1 的 PART-27）。
