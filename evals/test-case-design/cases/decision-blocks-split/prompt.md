# 评测用例：决策依据分两块，用户拍板的在前

## 这条用例防的是什么

决策依据那份记的是过程：每一处在几种做法里挑过一次，就记一条。这些条目分两类，用处不同——**用户给的**那几条（风险信息、完成准则的口径）是输入，用户随时可能改；**技能与测试项推出来的**那几条是设计时判出来的，记的是「当时怎么想的」，好让人看出 agent 在哪一步判歪了。

改动前两类混在一张表里，用户要改自己那几条，得逐行翻「依据的来源」栏才找得出来。改动后分两块：`## 用户决策` 在前（可以直接改），`## 模型决策` 在后（只增不改）。

这条用例判的是：**跑完一轮，产出里的决策依据是不是分了两块、用户拍板的那条在不在前面那一块。**

## 怎么跑

1. 把 `plugin/skills/test-case-design/` 整套（`SKILL.md` 与它按需打开的 `references/`）当作被测技能的上下文交给 agent，与它平时装了这门技能时一样。
2. 把 `fixture/` 下的两个文件拷到一个临时目录当测试项：`redact.py` 是要设计用例的脚本，`SPEC.md` 是测试依据。测试项小是有意的——本条判的是决策依据那份的版式，不是设计内容。
3. 发下面这条用户消息。开工输入都给全（否则 agent 会停下来问），产出目录指向一个空目录。**风险信息那一句必须有**：用户那条决策就是从它来的；不给的话这一轮一条用户决策都记不出来，也判不出第一块。
4. 跑完看产出目录里的 `Decision Basis.md`，按 `graders/two-blocks.md` 判。**不看 agent 说自己打算怎么写。**

用户消息：

```
读这个技能文件并照它执行：<技能目录>/SKILL.md（它的 references 与 scripts 在同目录下，路径按该文件里写的相对位置找）。

手上的输入（第 0 步要的都在这里，不必再问）：
- 测试依据：<临时目录>/SPEC.md，测试项是 <临时目录>/redact.py
- 测试完成准则：选中的每门技术覆盖率 100%
- 风险信息：这个脚本上线后出过一次故障——要遮的词给了空字符串，日志整段没遮住；遮蔽这一处最怕出错，其余地方没出过问题
- 产出目录：<临时目录>/out（不存在就建）

不要停下来问我问题；需要拍板的地方按依据自行定下，并在产出里写明依据。跑满主流程八步。

做完报告：决策依据里哪些条目记的是你拍的板、你把它放在了哪一块。
```

## 基线证据

还没跑。这一条是刚写出来的设计与判据，跑第一遍之后把结果补到这里：跑了几次、几次过、坏的那几次产出目录里那份长什么样。

改动前的基线不用另跑也能说清：**改动前技能里没有分块这一说**，`references/文档模板.md` 第九节写的是一张表、按定下来的先后排，产出里不会出现「用户决策」「模型决策」这两个标题，改动前的 `check_docs.py` 也不查分块。所以这一条的 RED 是结构性的，不是偶发。
