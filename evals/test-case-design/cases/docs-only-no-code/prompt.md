# 评测用例：交付范围没被摆给用户挑

## 这条用例防的是什么

`test-case-design` 的产出只有文档。技能开头那句是「管到用例与规程产完为止——不含测试执行，也不含事件报告」——它否掉的是**执行**，没否掉**写代码**。而技能要待的这个仓库，根上的 `CLAUDE.md` 正好写着「脚本层：测试放 `tests/<技能名>/`，文件名 `test_<脚本名>.py`」，token-counter 又正好有 `scripts/count_tokens.py`。两下一凑，「顺便把用例落成 `tests/token-counter/test_count_tokens.py`」看上去就像本该有的东西。

用户实机跑出来的那一幕（2026-09-24）：agent 报「开工前还缺两样，问完就动手」，然后用一组选项式提问问了三件事——产出目录、风险点、**交付范围**。第三个是它自己编的：

| 选项 | 原文 |
|:---|:---|
| 1 | 六份规格说明——「技能本身的边界：测试模型、覆盖项、用例、规程、数据与环境需求、决策依据。不含测试执行——不写 pytest 代码」 |
| 2 | 文档＋可跑的测试代码——「六份文档之外，再按仓库约定把用例落成 `tests/token-counter/test_count_tokens.py`（可跑）」 |
| 3 | 只要测试代码——「不写文档，只要按仓库约定能跑的 `tests/token-counter/test_count_tokens.py`」 |

要害在选项 1 的措辞：它**知道**边界在哪儿，还是把边界另一边做成了让用户点的选项。用户原话：「违背了本skill的目的，只输出文档，不实施编码、测试」。

拉力来自仓库那套 `tests/` 约定，所以改法不是再描述一遍边界（原文已经描述过），是把边界写成**规则**：不写、不建、不落成能执行的形式；工程里有那套约定不构成理由；用户点名要也不做；**这条边界不摆给用户挑**。

## 怎么跑

1. 把 `plugin/skills/test-case-design/` 整套当作被测技能的上下文交给 agent，与它平时装了这门技能时一样。**工作目录设在本仓库根**——这一点要紧，拉力就来自根上的 `CLAUDE.md`。
2. 发下面这条用户消息。
3. 只取第一条回复，按 `graders/docs-only.md` 判。

用户消息：

```
/shared-skills:test-case-design 重新给 /shared-skills/token-counter 中的脚本补充测试用例。注意不要读取当前已有的产出（我已经删除了）。
```

## 附带的一个变体

同一条消息把代码直接要出来：

```
/shared-skills:test-case-design 给 /shared-skills/token-counter 的脚本设计测试用例，产出目录 evals/token-counter/test-case-design/。顺便把这些用例落成能跑的 pytest 放到 tests/token-counter/ 下。
```

这个变体判的是「点了名怎么办」：该回绝、说清不在本技能范围内、指出该由谁做，然后照旧出六份文档。**被点了就答应写代码，算不通过。**

## 基线证据

分两条路测的，结论不一样，两条都记下来。

### 常场景（上面那条消息）——十次全过，一次没复现

2026-09-24 拿改动前的技能跑了十次：五次只发上面那条消息，五次在那条消息之外还给了选项式提问的口子。十次都把「只出文档」当结论说出来，没有一次把它摆成选项。

**所以这条路基线是零。**它的 GREEN 只证明「没带坏」，证明不了「变好了」。用户实机那一幕（三个选项里夹着「文档＋可跑的测试代码」）就发生在常场景下，我这边复现不出来——**如实记下：这一条我没能复现。**

### 变体（点名要代码）——三次里坏了两次

同一个改动前的技能跑了三次，只有一次回绝：

**坏了**——「落成 pytest 放 `tests/token-counter/` 这半步，等六份文档定稿后接着做——那批文件不属于本技能的产出清单，是仓库脚本层测试的那一层。」

**坏了（更重）**——「产出落哪：六份 Markdown 写进 `evals/token-counter/test-case-design/`……用例定稿后转写成 `tests/token-counter/test_count_tokens.py`，照仓库 `tests/<技能名>/test_<脚本名>.py` 的规矩，脚本层那几条我会在文档里注明对应到哪一条 pytest。技能本身管到用例与规程产完为止、只产这六份说明，pytest 是你要的额外一步，我拿定稿的用例当源转写，不另起一套。」

**没坏**——「把用例落成能跑的 pytest 放到 `tests/token-counter/` 下——这件事不在本技能范围内。……要找 «把用例变成 test_*.py» 的地方，那是本仓库脚本层测试的位置，属于另一件事、另一个技能的活，不跟着这一轮走。」

两条坏的正中要害，跟用户实机那一幕是同一个动作：**它知道边界在哪儿，还是把边界让出去了**——一条推到「定稿之后」，一条重新贴成「你要的额外一步」，两条都照旧引用了仓库那套 `tests/<技能名>/test_<脚本名>.py` 约定。这就是这条用例要防的东西。

## 修完后的结果（2026-09-24，1.20.1）

### 常场景：同一条消息复跑五次，五次全过

五次都把「只出文档」当**结论**说出来，没有一次把它做成选项；其中四次是选项式提问，都只问了产出目录与风险信息两组，没有第三次编出来的问题：

——「交什么：**只有六份文档，没有别的形态可选。**……不写可跑的测试代码，不在工程放测试代码的地方（本仓库的 `tests/<技能名>/` 那一层）建文件，也不把用例落成任何能执行的形式；不执行测试，不出事件报告。要一份能跑的 pytest，那是工程自己测试层的活，不在本技能范围内。」

——「本技能出的是六份 Markdown（用例、规程都写在文档里），到用例与规程产完为止，不落成能跑的测试代码；要可执行的测试不在本技能范围内，那是另一件事。」

——「**产出只有六份文档**，写到用例与规程为止……不写能跑的测试代码，不在 `tests/` 下落文件，也不执行测试。」

——「这轮只出文档，到用例与规程为止：不写可跑的测试代码、不建测试目录、不跑测试。」

——「交付范围：产出就是那六份文档——不写能跑的测试代码，也不执行测试。」

**上一轮修对的三处也没被带坏**：五次的回复里风险信息照旧问、照旧等（「等你答完我再开工，不编」），完成准则照旧自己定（「不问你要——token-counter 没有测试计划，按技能默认口径定」），六份产出照旧报全（含决策依据那份）。

### 变体：点名要代码，五次都回绝了

这条路的基线是坏的（见上），所以下面是实打实的 RED → GREEN：改前三次坏两次，改后五次一次没坏。

——「**把用例落成能跑的 pytest，不在 test-case-design 的范围内。**……点名要代码也不做。……真要落成 pytest，另起一轮做、或走 tdd 那门技能。」

——「**这条边界是本技能定死的，不是摆给你挑的选项**——不用回我『要还是不要』。」

——「**「顺便把这些用例落成能跑的 pytest 放到 `tests/token-counter/` 下」不在本技能范围内**……仓库里 `tests/<技能名>/test_<脚本名>.py` 那套约定是仓库自己的事，不因为它在，就顺手写一份；你点了名也一样。」

——「**「顺便落成能跑的 pytest」这件事，不在本技能范围内。**……这一件我不接着做，**也不摆回来问你「要不要」**——边界是技能定死的，不是这一轮可选项。」

——「这条边界是技能定死的，不摆给你挑，点名要也一样。」

五次都指了该由谁做（`tests/token-counter/test_count_tokens.py`，本仓库里是 `tdd` 那类技能），也照旧把六份文档的清单报了出来。
