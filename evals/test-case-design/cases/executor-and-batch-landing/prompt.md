# 评测用例：规程标执行器、文末写清各批落到哪

## 这条用例防的是什么

一套用例往往落成不止一类成品：判据落在命令、退出码与盘上的文件上的，落成能跑的测试代码（pytest 这类）；判据要读一轮模型行为的，落成评测用例。设计阶段这个决定原来是隐形的——只在写「成品落点」那一栏的人的脑子里，而那一块是落成之后才填得全的。

技能该有的行为：测试规程规格说明里**每条规程标一个「执行器」**（`脚本`／`控制器`／`子代理`）、标一个「改动文件」（`只读`／`会写`），文末另起一节「各批落到哪」，把规程按落点分批列全。分界必须落在规程边界上——不许把一条规程劈成两半分给两处。

这条用例管的是**两栏与那一块在不在、列全没有**。分得对不对（判据落在哪、劈没劈开规程）还要人看，脚本判不了。

## 怎么跑

1. 把 `plugin/skills/test-case-design/` 整套（`SKILL.md` 与它按需打开的 `references/`）当作被测技能的上下文交给 agent，与它平时装了这门技能时一样。
2. 把 `fixture/` 下的两个文件拷到一个临时目录当测试项：`tidy.py` 是要设计用例的脚本，`SPEC.md` 是测试依据。**这份需求里同时有脚本行为（第 1–4 条）与技能行为（第 5–7 条）**，所以两批都该出得来——只出一批，说明 agent 没按需求里那两类判据分开。
3. 发下面这条用户消息。开工输入都给全（否则 agent 会停下来问），产出目录指向一个空目录。
4. 跑完看产出目录里的 `Test Procedure Specification.md`，按 `graders/executor-and-batch.md` 判。**不看 agent 说自己打算怎么写。**

用户消息：

```
读这个技能文件并照它执行：<技能目录>/SKILL.md（它的 references 与 scripts 在同目录下，路径按该文件里写的相对位置找）。

手上的输入（第 0 步要的都在这里，不必再问）：
- 测试依据：<临时目录>/SPEC.md，测试项是 <临时目录>/tidy.py
- 测试完成准则：选中的每门技术覆盖率 100%
- 风险信息：无高风险项
- 产出目录：<临时目录>/out（不存在就建）

不要停下来问我问题；需要拍板的地方按依据自行定下，并在产出里写明依据。跑满主流程八步。

做完报告：这一轮往磁盘写过哪些文件（完整路径），以及产出目录里那份测试规程规格说明的末尾写了什么。
```
