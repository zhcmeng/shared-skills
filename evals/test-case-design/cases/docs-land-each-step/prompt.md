# 评测用例：TD 各步的文档要随步落盘

## 这条用例防的是什么

技能跑完一轮要出五份文档（测试模型规格说明、测试用例规格说明、测试规程规格说明、测试数据需求、测试环境需求）。旧版主流程把五份全压在第 7 步一次写出，前面 TD1–TD4 的设计成果只活在上下文里。

这个设计有个不报错的失败模式：**一轮跑不完一个上下文窗口**。2026-09-23 那次真跑的实测：开工到自动压缩吃掉 167,224 token，压缩掉 15.5 万 token。那次运气好，压缩点落在五份文档刚写完、终检还没跑的时候；若压缩点早两步，TD1–TD4 的全部设计（模型、覆盖项、用例、两张对应表）盘上一份都没有，只剩摘要里的一段转述。

技能该有的行为：**每一步做完就把该步的文档写到产出目录里**，文档没落盘不算做完这一步；第 7 步只做终检（核对五份齐、把机械项跑到零错）。这样上下文被压缩时，读盘上的文档就能接着走。

## 怎么跑

1. 把 `plugin/skills/test-case-design/` 整套（`SKILL.md` 与它按需打开的 `references/`）当作被测技能的上下文交给 agent，与它平时装了这门技能时一样。
2. 把 `fixture/` 下的两个文件拷到一个临时目录当测试项：`slugify.py` 是要设计用例的脚本，`SPEC.md` 是测试依据。用这么小的测试项是有意的——本条判的是落盘时机，不是设计内容，测试项小才跑得便宜、比对得清。
3. 发下面这条用户消息。三样开工输入都给全（否则 agent 会停下来问），产出目录指向一个空目录。
4. 跑完看产出目录里有什么，按 `graders/` 下的判据判。**不看 agent 说自己打算怎么写。**

用户消息：

```
读这个技能文件并照它执行：<技能目录>/SKILL.md（它的 references 与 scripts 在同目录下，路径按该文件里写的相对位置找）。

只跑主流程的第 0 步到第 4 步（第 1 步定技术方案、第 2 步 TD1 建测试模型、第 3 步 TD2 定测试覆盖项、第 4 步 TD3 导出测试用例）。到第 4 步结束就停，不要做第 5 步及其后的任何步骤。

手上的输入（第 0 步要的三样都在这里，不必再问）：
- 测试依据：<临时目录>/SPEC.md，测试项是 <临时目录>/slugify.py
- 测试完成准则：选中的每门技术覆盖率 100%
- 风险信息：无高风险项
- 产出目录：<临时目录>/out（不存在就建）

不要停下来问我问题；需要拍板的地方按依据自行定下，并在产出里写明依据。

做完报告三件事：第 1 步选了哪几门技术及依据；四步各产出了什么（模型几个、覆盖项几条、用例几条）；这四步里你往磁盘写过哪些文件（完整路径，没有就写「无」）。
```

「到第 4 步结束就停」这半句是替代品：真跑时终结上下文的是自动压缩，评测里换成主动停——停下来的状态与压缩掉的状态是同一个：设计做完了，还没到旧版的第 7 步写盘。

## 附带的一个变体

同一条消息去掉「只跑第 0 步到第 4 步……不要做第 5 步及其后的任何步骤」，让它跑满八步。这个变体验的是分步落盘没把产出带坏：五份齐、`python scripts/check_docs.py <产出目录>` 报 0 错——与旧版流程的终点应当没有区别。

## 基线证据（2026-09-23，修之前，1.12.3）

跑一次。第 0–4 步全套做完：3 个模型、29 条测试覆盖项、29 条测试用例、两张对应表都产出来了，用时 76 秒、70,276 token、17 次工具调用。

产出目录 `out-red`：**空的**。agent 报告的原话：

——「**写盘的文件**：无。按本技能主流程，五份产出文档在第 7 步才写入指定目录，第 0 步至第 4 步是设计过程，不落文件」；

——「以上模型、覆盖项、用例与两张对应表即四步的设计成果，**可在第 7 步**照文档模板填入 `Test Model Specification.md` 与 `Test Case Specification.md`」。

这组话说明两件事：不落盘不是 agent 偷懒，是技能正文的训练结果（第 7 步那一行的原话是「按文档模板写出五份规格说明到指定目录」）；而且此时整份设计确实只存在于上下文里。

## 修完后的结果（2026-09-23，1.12.4）

同一条消息复跑一次，通过：

——**第 2 步落盘** `Test Model Specification.md`（15,085 字节），**第 4 步落盘** `Test Case Specification.md`（12,432 字节）。两次写之间隔着 TD2、TD3 的设计动作，不是最后一把写出来的；

——停在第 4 步时盘上就这两份，第 5 步及其后的一份都没有：落盘时机与该步产出一一对应，不提前、不拖后；

——这两份过得了机械检查：编号连续、对应表 32 行无留空、无禁用词。另有 3 处「缺这份文档」，报的正是第 5 步才产出的那三份，停在第 4 步本该如此；

——agent 这次自己跑了 `check_docs.py`（旧版那一次没有跑——它手上没有文档可查）。

同一次跑的代价：116,852 token、25 次工具调用、249 秒；基线是 70,276 token、17 次调用、76 秒。差额是两份文档的写作与一次机械检查。旧版在同一步不写文档，但走到第 7 步一样要写——成本是挪到了前面，不是新增。真正的差别在被打断那一次：新版从盘上接着走，旧版从零重做。

## 变体跑的结果（跑满八步，2026-09-23，1.12.4）

跑满八步，通过。每一步做完时目录里的文件与该步「落盘」一栏对得上：

| 步 | 做完时产出目录里 |
|:---|:---|
| 0 | 空（目录已建，三样输入齐） |
| 1 | 空——四个决定写进第 2 步那份的「测试策略摘要」栏，本步不落盘 |
| 2 | 追加 `Test Model Specification.md` |
| 3 | 无新增（覆盖项并进下一份） |
| 4 | 追加 `Test Case Specification.md` |
| 5 | 追加 `Test Procedure Specification.md`、`Test Data Requirements.md`、`Test Environment Requirements.md` |
| 6 | 无新增（覆盖率已满，不必回第 4 步） |
| 7 | 无新增，只跑机械检查 |

第 7 步终检跑 `check_docs.py`：**0 处错误、0 处提示**，退出码 0；五份齐、无多余文件。分步落盘没把产出写坏——机械项这一关与旧版流程的终点一个结果（旧版那一轮真跑的产出也是 0 错）。代价 134,183 token、26 次工具调用、342 秒，与旧版跑满一轮同量级。

## 这组证据的量级

基线一次、修后一次、变体一次，**各只跑了一次**。够看清「落盘时机」这一条有没有被改到，不够当统计证据用：要拿它当回归用例长期跑，应当把消息发五次以上，看五次是不是收敛到同一个形态（第 2 步落盘、第 4 步追加、第 5 步追加三份）。五次里出现两种不同的落盘时机，说明这几行字还不够紧。
