# 判据：用例目录名在，按执行顺序排，且与形制逐段对得上

只看产出目录里的 `Test Procedure Specification.md`。**不看 agent 回复里说自己打算怎么写。**

## 不通过

出现下面任何一条，就是不通过：

——**落成评测用例的那一行没有「用例目录名」栏**，或栏是空的。测试规程规格说明里凡是「执行器」写着 `控制器` 或 `子代理` 的行，这一栏都要填满；

——**一条规程一行**：一行里塞了两条以上规程、或者一条规程拆成两行，都不通过；

——**形制不对**：每条目录名写成 `tp<规程号两位>-<规程内执行位次两位>-TC-<用例编号>-<英文名>`。两段数字各两位（写 `tp1-` 是错的）；`TC-` 那段照文档里的编号写、不补零（写 `TC-01` 是错的）；最后一段是那条用例的英文名，与测试用例规格说明里那一栏一字不差；

——**位次与执行顺序对不上**：第 `MM` 条的编号，必须是该规程「有序执行测试用例」栏里第 `MM` 个。**注意位次按那一栏的次序数，不按用例编号的大小**——这一份需求里导出来的顺序与编号顺序很可能不一样；

——**清单不全**：该规程排到的用例，一条不多、一条不少、一条不重。

## 通过

上面五条一条不犯，即通过。

## 判的时候留个心

**光在回复里说「目录名按规程顺序排」不算通过**——判的是产出目录里那份文件里那一栏写了什么。

**六份文档要齐**，顺带确认一条：`python plugin/skills/test-case-design/scripts/check_docs.py <产出目录>` 报 0 错。这一栏本身就在检查范围内（缺栏、空栏、形制、位次、清单，`check_docs.py` 各报一处错），所以这一条能机械复核——但机械检查过了不等于这一条过了：脚本认的是文档里写的那一串，盘上真落成什么目录名它看不见。

**这条用例的测试项是照「两类判据都要有」造的**（`SPEC.md` 里第 1–4 条落脚本、第 5–7 条落模型）。产出里只出现一批、表里只有一行、那一栏空着，按不通过算。
