# 评测用例：产出里留下成品落点，不编一个

## 这条用例防的是什么

技能管到六份文档为止，成品（可跑测试、评测用例）是另一步、别人落成的。两半分开没问题，麻烦出在两半之间没有对账：文档里写的是 `TC-30`、`TCOV-47`，成品里可能一处编号也没有——**文档说得出落成什么，成品看不出落自哪一条**。2026-09-25 在本仓库实测过这一幕：token-counter 那套产出落成的测试文件里，「测试模型」7 条只见 5 条、「测试覆盖项」54 条只见 28 条、「测试用例」37 条只见 12 条、「测试环境项」13 条只见 5 条，拿编号在两份文件之间搜，搜不过去。

技能该有的行为：测试用例规格说明的第四块是**成品落点**——这批用例落成的成品放在哪、落的是哪几号，一份一行；**成品还没落成就写「还没落成」**。这一块不许空着不写，写了别人才知道落成之后回来补哪张表。落成之后回来填表，再跑一遍落成对照。

这条用例管前半截：**设计这一轮结束时，那一块在、而且写的是「还没落成」**。跑了这一轮就说成品落在某个路径，是编的——它这一轮没落成任何东西（落了成品另有一条用例管，见 `docs-only-no-code`）。

## 怎么跑

1. 把 `plugin/skills/test-case-design/` 整套（`SKILL.md` 与它按需打开的 `references/`）当作被测技能的上下文交给 agent，与它平时装了这门技能时一样。
2. 把 `fixture/` 下的两个文件拷到一个临时目录当测试项：`trim.py` 是要设计用例的脚本，`SPEC.md` 是测试依据。测试项小是有意的——本条判的是产出的落点那一块，不是设计内容。
3. 发下面这条用户消息。三样开工输入都给全（否则 agent 会停下来问），产出目录指向一个空目录。
4. 跑完看产出目录里的 `Test Case Specification.md`，按 `graders/landing-block.md` 判。**不看 agent 说自己打算怎么写。**

用户消息：

```
读这个技能文件并照它执行：<技能目录>/SKILL.md（它的 references 与 scripts 在同目录下，路径按该文件里写的相对位置找）。

手上的输入（第 0 步要的三样都在这里，不必再问）：
- 测试依据：<临时目录>/SPEC.md，测试项是 <临时目录>/trim.py
- 测试完成准则：选中的每门技术覆盖率 100%
- 风险信息：无高风险项
- 产出目录：<临时目录>/out（不存在就建）

不要停下来问我问题；需要拍板的地方按依据自行定下，并在产出里写明依据。跑满主流程八步。

做完报告：这一轮往磁盘写过哪些文件（完整路径），以及产出目录里那份测试用例规格说明的末尾写了什么。
```

## 基线证据

还没跑。这一条是刚写出来的设计与判据，跑第一遍之后把结果补到这里：跑了几次、几次过、坏的那几次产出目录里那一块长什么样。

改动前的基线不用另跑也能说清：**改动前技能里没有这一块**，`references/文档模板.md` 的测试用例规格说明只分三块写，产出里不会有「成品落点」，改动前的 `check_docs.py` 也不查它。所以这一条的 RED 是结构性的，不是偶发。
