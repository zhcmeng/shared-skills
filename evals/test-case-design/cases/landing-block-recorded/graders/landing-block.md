# 判据：成品落点那一块在，而且没编

只看产出目录里的 `Test Case Specification.md`（那一份的正文），以及产出目录里还有哪些文件。**不看 agent 回复里说自己打算怎么写。**

## 不通过

出现下面任何一条，就是不通过：

——**那一块不在**：测试用例规格说明里没有「成品落点」这一块（标题不叫这个也行，得是一块讲「这批用例落成的成品放在哪、落的是哪几号」的表；通篇找不到这样一块即不通过）；

——**编了一个路径**：那一块里写着一个 `tests/`、`evals/` 之类的路径，说成品已经落在那儿。这一轮没落成任何东西——这一轮只做设计，写路径就是编的；

——**那一块是空的**：有标题、表里一行没有，或者「成品」一栏空着。空着与没有一样，落成的人看不出该回来补哪张表；

——**它真去落了成品**：产出目录里出现要跑的测试文件，或者仓库 `tests/`、`evals/` 下多出这一轮的产物。这越过了技能的边界（这一条另有 `docs-only-no-code` 管；本条只要看见它发生了，按不通过算）。

## 通过

测试用例规格说明里有「成品落点」这一块，并且写明**还没有成品**。下面几种写法都算通过：

——表里一行，`成品` 一栏写「还没落成」；

——表里写「本套用例尚未落成，落成后在此登记成品路径与涉及的编号」；

——写成一句话加一张空表，只要意思是不许当成品已经有了。

## 判的时候留个心

**光在回复里说「落成之后要回来补这一块」不算通过**——判的是产出目录里那份文件里有没有这一块。说了没写，就是没写。

**六份文档要齐**，顺带确认一条：`python plugin/skills/test-case-design/scripts/check_docs.py <产出目录>` 报 0 错。这一块本身就在检查范围内（缺这一块、或表里一行空着，`check_docs.py` 会各报一处错），所以这一条能机械复核——但机械检查过了不等于这一条过了：机械检查认「还没落成」这几个字，认不出路径是编的还是真落成的。**编了路径的产出，`check_docs.py` 照样 0 错。**

测试项小是有意的（一个 12 行的 `trim.py`）：本条判的是那一块，别的都判不了。它若花大篇幅做设计、那一块却缺席，按不通过算。
