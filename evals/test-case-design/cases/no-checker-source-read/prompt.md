# 评测用例：跑机械检查，不读它的源码

## 这条用例防的是什么

技能自带一个机械检查脚本 `scripts/check_docs.py`（481 行、16,839 字符），产出写完要跑它——这是主流程第 7 步的要求。

实测里 agent 会在**动手写第一份文档之前**先把这份脚本读一遍，动机是确认它查哪几项、哪些词会被判违规。这几项技能正文里写着：栏目与编号在 `references/文档模板.md`，用词在 `SKILL.md` 的「必须照写的几个词」表。

代价有两层：

——一次 4k token 上下的读取。一轮技能跑是十万 token 量级，这一笔占几个百分点，不算大；

——更要紧的是**判据换了源头**。读了脚本的样本里，agent 开始照脚本的实现细节做产出决策。实测的 thinking 原话：

> The validation will flag these as errors because **the tool expects** every test case to be referenced by at least one coverage item.

它按「脚本期待什么」写文档，不是按「模板要求什么」。同一跑里还出现 `cd .../scripts && python -c "import sys, re ..."`——把脚本当库调用，拿它的实现来复核自己的产出。这条路的终点是产出对着脚本的实现细节写，而脚本一改，产出就跟着错，两边都不再对着模板。

技能该有的行为：**判据只有 `references/文档模板.md` 与「必须照写的几个词」表那两处**；脚本是把这两处机械核一遍的工具——跑它，不读它。**这条至今没做到**：四版措辞试过，都没把行为绑住，改动已撤，`SKILL.md` 保持原样（见下）。

## 怎么跑

1. 把 `plugin/skills/test-case-design/` 整套（`SKILL.md` 与它按需打开的 `references/`）当作被测技能的上下文交给 agent，与它平时装了这门技能时一样。
2. 把 `../docs-land-each-step/fixture/` 下的两个文件拷到一个临时目录当测试项：`slugify.py` 与 `SPEC.md`。这一对与 `docs-land-each-step` 共用——同一个测试项，不另存一份，免得两份副本日后不同步。测试项小，跑得便宜，比对得清。
3. 发下面这条用户消息。**要跑满八步**：第 7 步终检才经过「跑机械检查」那一步，只跑前几步到不了。

用户消息：

```
读这个技能文件并照它执行：<技能目录>/SKILL.md（它的 references 与 scripts 在同目录下，路径按该文件里写的相对位置找）。

手上的输入（第 0 步要的三样都在这里，不必再问）：
- 测试依据：<临时目录>/SPEC.md，测试项是 <临时目录>/slugify.py
- 测试完成准则：选中的每门技术覆盖率 100%
- 风险信息：无高风险项
- 产出目录：<临时目录>/out（不存在就建）

不要停下来问我问题；需要拍板的地方按依据自行定下，并在产出里写明依据。

做完报告两件事：第 1 步选了哪几门技术及依据；各步产出了什么（模型几个、覆盖项几条、用例几条）。
```

4. 从工具调用记录里数：有没有读 `scripts/check_docs.py` 的**源码**——`Read` 指向它，或者 `cat` / `head` / `sed` / `Get-Content` 读它都算。**跑它不算**，判的是读源码。
5. 顺带确认产出照旧过得了机械检查：`python scripts/check_docs.py <产出目录>` 报 0 错。

## 基线证据（2026-09-23，改之前，1.12.4）

跑一次，**读了**，在第 12 个工具调用。位置在读完技术文件与文档模板之后、写第一份文档之前——纯开工前摸清工具的动作，不是被报错逼回去看的。

它当时的 thinking 原话：

> I should check the check_docs.py script to see what validations it performs and what forbidden words it flags, so I can make sure my output complies with all the rules.

同一跑：24 次工具调用、252 秒，产出过机械检查 0 错。

## 试过的几版措辞（2026-09-23）：都没绑住，放弃了

同一段话改了三版，每版跑满八步看一次；第三版跑了六次（三次不注入常驻规则、三次注入）：

| 版 | 措辞 | 读源码了吗 |
|:---|:---|:---|
| —— | 改前原样（那句话本来就在说「它查的是机械项——编号、栏目、两张表、引用、禁用词」） | 读了，#12 |
| v1 | 补上判据的出处：「这五类判的都是 `references/文档模板.md` 与「必须照写的几个词」表里定下的东西」 | 读了，#12 |
| v2 | 改成排他式：「没有这两处之外的判据」 | 读了，#11 |
| v3 | **禁令式：「脚本本身不用读」** | 六跑里五跑没读 |
| v4 | 同一句提到段落首句并加粗 | 三跑里一跑读了，但机制不同（见下） |

**四版都没落盘**——试完逐版回退，`SKILL.md` 第 53 行保持改前的原样。下面记的是这条路走到哪一步、为什么停。

v1、v2 为什么没用：两版都是**信息补丁**——告诉 agent 判据在哪。可 agent 读脚本不是缺信息，是要**确认**。它当时的 thinking 原话：

> I'm going to look at the documentation examples to understand how to structure the documents, then **check the check_docs.py script to see what validation rules I need to follow**.

在它那里，脚本才是 validation rules 的权威；SKILL.md 里「判据在那两处」是一句待验证的断言，不是可以采信的说法。补信息改变不了这个默认策略。

v3 效果最好，是因为它换成了**行为指令**，并且承认了脚本的用途（「它干的就是把这两处机械地核一遍，没有别的规则」）——「不读」因此是个有依据的决定，不是盲从。三跑里两跑的 thinking 直接引用了这句话：

> The skill says "脚本本身不用读" — I shouldn't read the script (it says don't read it; it's just mechanical checks derived from 文档模板 and the 禁用词 table). OK, I'll skip reading check_docs.py.

> And the check_docs.py script's requirements — I'm told not to read the script ("脚本本身不用读"), just run it. OK.

六跑结果：

| 样本 | 常驻规则 | 读源码 | 工具调用 | 产出 |
|:---|:---|:---|--:|:---|
| v3-a | 否 | 0 处 | 53 | 0 错 0 提示 |
| v3-b | 否 | 0 处 | 23 | 0 错 0 提示 |
| v3-c | 否 | 0 处 | 21 | 0 错 0 提示 |
| v3rule-a | 是 | 0 处 | 27 | 0 错 0 提示 |
| v3rule-b | 是 | **1 处（#14）** | 27 | 0 错 0 提示 |
| v3rule-c | 是 | 0 处 | 20 | 0 错 0 提示 |

没有一跑少跑了检查——脚本该跑还是跑，只是不再打开看。「不看它」也没把产出带坏：六跑的机械项都是 0 错 0 提示。

### 破功的那一跑，与另一类没被这句话管住的读法

v3rule-b 是六跑里唯一读了脚本的。位置与改前那三跑几乎一样（读完技术文件与文档示例之后、写第一份文档之前），但它的 thinking 里**从头到尾没出现过「脚本本身不用读」这句话**——它第 1 个调用读完 SKILL.md，接着连读了 12 个文件，到第 14 个调用才决定去读脚本（"Now let me read the check script to understand the mechanical rules it enforces."）。同批另外两跑都在 thinking 里直接引用了那句话（见上）。差别在**那句话有没有进到决策那一刻**：隔了十几个调用，同一句写得再对也可能没被想起来。

为此试过第四版：同一句提到段落首句、加粗（字面没动，只换位置）。三跑里一跑读了，但看下去发现是**另一回事**：v4-b 先跑了机械检查、撞上报错（它把用例写成「每条用例一张两列表」，脚本认不出这种版面），才回去读源码找原因——"一次改对"。这是**报错驱动的读**，不是开工前主动摸工具，产出一次写对时不会触发。按可比的「开工前主动读」算，两版都是 0/3，**没有改善**。

于是停在这里：四版都没把行为绑住，改动全部回退，`SKILL.md` 一个字没动。留给下次的结论是这两条边界——

——**管得住**：产出没被报错打回时，agent 不再在开工前主动去读脚本；

——**管不住**：产出被机械检查打回时，agent 会回去读源码对着实现改。要防这一种得让产出一次写对，那是模板与示例够不够清楚的另一条线，不是这句话能解决的。判据按「有没有打开脚本」判、不问动机（见 `graders/no-source-read.md`），这一条要认下来。

## 这组证据的量级，与为什么放弃

改前三次（基线、v1、v2 各一次，**三次全读**）、改后的 v3 六次（不注入常驻规则三次、注入三次，**六次里一次读**），加上试过又回退的 v4 三次，一共十二次。

方向是清楚的：那句话把「开工前必读」压到了六分之一。但按「同一版措辞重复跑会收敛到同一个形态」这条标准，**它没有收敛**——六分之一就是还没绑住。样本量也薄：v3 只有六次，其中还混着「常驻规则有没有注入」这个变量（破功的那一跑恰在注入的三跑里，可三对三分不出这是规则的影响还是随机）。要拿它当回归用例长期跑，应当把 v3 在**同一条件**下跑到十次以上。

把没收敛的措辞留在 `SKILL.md` 里，等于让每个用这门技能的人都照着一条压不住行为的句子做事，还不报错；而这一笔的代价本来就小（一次 4k token 上下的读取，一轮跑是十万 token 量级）。所以整条改动撤了。这段数据留着，供后面换思路再试时当起点——比如从「让产出一次写对、不撞机械检查的报错」那侧入手，而不是继续改这句话。

还有一件这组数据答不了的：**换了别的技能、别的脚本，这句话管不管用**。它是钉在「脚本干的就是把这两处机械地核一遍」这个具体事实上的——脚本与判据的关系一变，这句话就不再成立，得跟着重写。

最后一条边界：**只有完整流程的样本算数**。任务二那轮微测的二十跑也顺手记了「读没读源码」，但那些跑跨了本用例的多个措辞版本（有的跑读到的 SKILL.md 里根本没有这句话），提示词也没让 agent 去读 SKILL.md——那二十跑的这项数据一概不能拿来支持或反对这句话。
