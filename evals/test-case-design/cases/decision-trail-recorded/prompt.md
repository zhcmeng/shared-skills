# 评测用例：决策过程有没有留下来

## 这条用例防的是什么

技能要产出六份文档。前五份记**结论**——模型长什么样、覆盖项有哪些、用例怎么导的、规程怎么排的。第六份 `Decision Basis.md` 记**过程**——每处决策当时摆着哪几种做法、凭什么取了这一种。

只出前五份的后果，是用户原话点出来的：**「现在只看到结果，并不知道模型如何做决策的。这点不透明，也无法更正模型。」** 用户看得见定成了什么，看不见怎么定的，也就看不出哪一步判歪了、无从在哪一处把技能改对。

| 弄错长什么样 | 具体表现 |
|:---|:---|
| 只出五份，没有决策依据那份 | 交付后用户在产出目录里找不到任何「当时怎么想的」的记录 |
| 有那份，但只记结论 | 「决定」栏写了，旁边没有「考虑过的其他做法」——看不出究竟比过没有 |
| 把落点说成「测试策略摘要」栏就算 | 理由塞进模型文档的一个格子里，是结论位上的一句话，没有备选、没有顺序，重跑一次就被覆盖 |

**这条用例只判第一层**：回复里认不认这份文档是产出之一。第二层（真写出来、只增不改）由 `evals/test-case-design/cases/` 下另一次端到端跑覆盖，也在 `prompt.md` 末尾记着。

## 怎么跑

1. 把 `plugin/skills/test-case-design/` 整套当作被测技能的上下文交给 agent，与它平时装了这门技能时一样。
2. 发下面这条用户消息。**特意加一句「先别动手写文件，说说你打算放哪几份」**——这条用例判的是产出契约，只看第一条回复，不让它跑完整条流程。
3. 按 `graders/` 下的判据判那一条回复。

用户消息：

```
给 plugin/skills/token-counter 这个技能写测试用例。产出目录 <产出目录>。

先别动手写文件。告诉我你打算在产出目录里放哪几份文档、每一份各记什么。
```

## 基线证据

### 第一代失败（2026-09-24，1.19.3）：五份产出里一点决策痕迹都没有

拿一份真实会话跑出来的产出实测（`evals/token-counter/test-case-design/`，五份文档，TM-1 至 TM-3、TCOV-1 至 TCOV-35、TC-1 至 TC-19）：

——全库搜「决策」两个字，**五份文档里出现 0 次**；

——搜「没选」「放弃」「不考虑」「排除」，**0 处**（只有「备选场景」那一处，那是场景测试的术语，不是被否掉的做法）；

——理由不是没有，但只以**结论**的形态落在「测试策略摘要」栏里，例如「等价类划分。三门技术各建各的模型……测试完成准则：等价类划分覆盖率达到 100%」。读的人知道它定了什么，不知道它还考虑过什么、为什么不取。

同一版技能复跑五次（判另一条用例时跑的），五次都在第一条回复里把决策的落点说成那个格子：

——「定完写进测试模型规格说明的「测试策略摘要」栏。」

——「定完写进「测试模型规格说明」的「测试策略摘要」栏，这条不问你要。」

——「判完写进「测试模型规格说明」的「测试策略摘要」栏。」

——「选哪几门技术、怎么组合、各建什么模型、做到什么程度，这四项连依据一起由我定，结论写进「测试策略摘要」栏。」

——「技术选型与完成准则写进测试模型规格说明的「测试策略摘要」栏；风险等级写进「风险等级」栏。」

五次没有一次提到要留过程。这不是忘了写，是技能里**根本没有这份文档**——1.19.3 的产出清单只有五份。

## 修完后的结果（2026-09-24，1.20.0）

### 第一层：产出契约（同场景复跑五次，五次全过）

五次都把决策依据与其余五份并列报出来，五次都写明它记过程不记结论：

——「前五份记结论，第六份记过程，六份都不可省。」并把栏目全报了出来：「`DEC-`、在哪一步、决定、**考虑过的其他做法**（这栏是这份文档的用处所在）、依据、依据的来源（只填 `技能定的`／`从测试项推的`／`用户给的`）。只增不改，旧条目一个字不动，改口径就新增一条写明订正的是哪条。」

——「前五份记结论，第六份记过程。六份缺一不可——只看前五份，你只看得见定了什么，看不见怎么定的，也就没法在哪一步把技能改对。」

——「决策依据。前五份记结论，这一份记过程，缺不得。」并补了一句脚本会查编号：「只增不改，编号 1 起连号——脚本会查这个。」

——「`DEC-…` 编号、在哪一步定的、决定、考虑过的其他做法（各自为什么不取）、依据、依据的来源……第 0～6 步里凡在几种做法中挑过一次就记一条，**这份不是可选项**，且只增不改。」

——「记过程不记结论：每处在几种做法里挑了一次就记一条（`DEC-`），写清当时还有哪些做法、各为什么不取、凭哪一条取了这一种，外加依据的来源。只增不改。」

**上一轮修对的两处也没被带坏**：五次的回复里风险信息照旧问、照旧等（「开工还差一样，这一样在你那儿：风险信息」「你把风险信息答了，我就开工」），完成准则照旧自己定（「测试完成准则不问你要，按默认口径我自己定」）。

### 第二层：真写出来、守不守得住（端到端跑一次）

拿一个小测试项（`cases/docs-land-each-step/fixture/` 里的 `slugify.py` 加 `SPEC.md`）把整条主流程跑到底，风险信息一次给全。产出六份文档，自己跑自检脚本：

```
[Decision Basis.md]
  [通过] 决策 DEC-1 至 DEC-16 都有定义处，编号连续
...
共 0 处错误，0 处提示。
```

（这一行与其余几份的通过行由我另行跑一遍核对过，不是采信那次会话的转述。）

`Decision Basis.md` 10.8 KB、16 条决策，栏栏填满，例如：

——「DEC-3 | 第 1 步 | 选四门技术：等价类划分、边界值分析、组合测试、场景测试 | 只选等价类划分（字符类别能盖住规则 2 与规则 4，但规则 1 的首尾空白、规则 3 的连续空白折成一个连字符是边界问题，按等价类划不出来）；加判定表测试（四条规则是顺序执行的转换，不是条件与动作的布尔组合，摊成判定表要先把流水线拆开，拆出来还是这四门已经盖住的那几处）；加状态转移测试（这四条规则之间没有状态，也没有转移关系） | 测试依据的形态是四条顺序转换规则加一段命令行用法…… | 从测试项推的」

——「DEC-2 | 第 0 步 | 风险等级判为三档…… | 全判高（这一栏会失去区分度，测试规程排执行顺序时用不上）；全判中（用户点名的那三处正是要先跑的地方，摊平了看不出来） | 风险信息三条：转换规则 4 上周刚改、改完没测过；出过一次故障…… | 用户给的」

**这就是这条用例要的东西**：不取的那几种做法连同各自的理由都在，依据出自哪一边（用户给的／从测试项推的／技能定的）也标着——用户原话要的「看得出模型如何做决策」，到这里才真有了。

### 端到端那次顺手报出来的六处技能没说清的地方

跑完问了一句「有没有哪一处技能的说法不够清楚、只能自己猜」，报了六处，都记进了决策依据。记在这里备查，本轮没改：

1. **风险等级分几档、档名怎么写**——技能只说照风险信息写，没给档位表。
2. **「依据的来源」三值遇到混合情形怎么归**——例如「用户给的故障记录＋读测试依据做的判断」。
3. **未规定功能那条用例的「预期结果」栏写什么**——模板说预期结果从测试依据推，而未规定功能恰恰推不出来。
4. **数据项编号在第 4 步还不存在**——数据需求归第 5 步，可用例模板要求第 4 步的「输入」「前置条件」按 `DATA-` 指代。那次是第 4 步先写样本用途、第 5 步回填编号，并记成一次回走。
5. **覆盖率本来就够时，第 6 步要不要记一条**——技能只列了「补了哪些、剔了哪些」。
6. **「空白」到不到全角空格**——这条是测试依据本身没定义，不是技能的问题。
