# 判据：判定表的每条规则，在同一份文档里查得到

只看产出目录里的 `Test Model Specification.md`（那一份的正文）。**不看 agent 回复里说自己打算怎么写。**

## 不通过

出现下面任何一条，就是不通过：

——**表头只有编号，全篇没有逐条说明**：模型用了判定表，表头写的是「规则 1」「判定规则 1」这类编号，而同一份文档里没有一处逐条讲这些编号各是什么——读者拿着一个编号，查不到它对应哪些条件取什么值、落到哪些动作；

——**不写死取值的列没交代**：表里有合并列或不可行组合（取值栏写「—」「*」或留空），而文档没有说明这一列覆盖哪些条件组合（不可行的那条则要写明为什么不可行）；

——**引了编号却查不到**：文档别处引到「规则 N」（风险等级、说明段、可追溯性栏里都可能有），而这条规则在同一份文档里查不到定义。

## 通过

上面三条一条不犯，即通过。定义写多长不管——一行一条、读得出这条规则说的是哪几种情形、落到什么动作，就算数。写在表后面、写在「与这张表有关的说明」前面，或者写成同一节里的另一张清单，都算；**只要在同一份文档里**。

## 判的时候留个心

——**定义摆在哪一份里是要紧的**：判定表的规则只在 `Test Case Specification.md` 的覆盖项清单里交代过、模型这份里查不到，按不通过算——模型这份的说明段一引「规则 5」，读者就得在两份文档之间来回翻。

——**规则建得对不对不管**：合并列合并得对不对、需求里那几条有没有漏、动作有没有写全，是判断，脚本也判不了，这一条只管「查不查得到」。

——**判定表压根没出现**时（比如只建了等价类划分或边界值分析模型），这一条没跑到位：记下来重跑，别按通过算，也别按不通过算。
