# 评测用例：判定表的规则要逐条写得出来

## 这条用例防的是什么

判定表的表头只写「规则 1」「规则 2」……这些编号。编号本身不说明任何事：读者要知道「规则 5」是什么，得横着扫过表里每一列的取值与动作，再自己在脑子里拼一遍。表一宽、或者有几列是合并列（取值栏写「—」，这条规则同时管两种条件组合），就拼不出来了。合并列尤其麻烦：它管的不是一种情形，是两种。

技能该有的行为：模型这份文档里，判定表的每条规则都要能单独读出来——编号加条件取值加落到哪些动作，一行一条；合并列要写明它覆盖哪些条件组合，不可行的规则要写明为什么不可行。文档别处引「规则 N」时，读者在同一份文档里就能查到它。

这条用例管的是**每条规则在不在、查不查得到**。规则建得对不对（合并得对不对、需求里有几条漏了）还要人看，脚本判不了。

## 怎么跑

1. 把 `plugin/skills/test-case-design/` 整套（`SKILL.md` 与它按需打开的 `references/`）当作被测技能的上下文交给 agent，与它平时装了这门技能时一样。
2. 把 `fixture/` 下的两个文件拷到一个临时目录当测试项：`approve.py` 是要设计用例的脚本，`SPEC.md` 是测试依据。这份需求是三项布尔条件判一个去处，走的正是判定表那一门——**产出里没出现判定表，说明这一条没跑到位，重跑**。
3. 发下面这条用户消息。三样开工输入都给全（否则 agent 会停下来问），产出目录指向一个空目录。
4. 跑完看产出目录里的 `Test Model Specification.md`，按 `graders/rule-list.md` 判。**不看 agent 说自己打算怎么写。**

用户消息：

```

手上的输入（第 0 步要的三样都在这里，不必再问）：

```

## 基线证据

改动前跑了一轮，**不通过**。坏在第一条上。

产出目录里的 `Test Model Specification.md`，TM-1 就是判定表（`approval_decision_table`）：表头写着「判定规则 1」到「判定规则 6」，3 条条件、3 条动作、6 条规则。表后面只有一段话，讲的是规则 3 与规则 6 那两列用 `*` 合并了 C3 的两种取值——**没有一处逐条讲这 6 个编号各是什么**。读者要问「判定规则 5 是什么」，得横着扫过 C1、C2、C3 三行、再看动作那三行，自己在脑子里拼出「金额超过 500 元、有发票附件、有违规记录 → 拒绝并记一条违规」。

另外两条没犯：合并列交代了；文档别处没有引了却查不到的编号。`check_docs.py` 报 0 错 0 提示——这一条本来就不在它的检查范围内。

改动后复跑两轮，**两轮都通过**：

——第一轮：TM-1 表后跟了一份 8 条规则的清单，从「规则 1：C1＝T、C2＝T、C3＝T——自动通过。」到规则 8，一行一条，条件取值与去向都在。这一轮 agent 把 C3 写成正面条件（「近 12 个月没有违规记录」），8 种组合都凑得出来，所以表里没有合并列、也没有不可行规则——判据里「不写死取值的列要交代」那一条这一轮没被用到。

——第二轮：TM-1 是 6 条规则，表后同样一份清单；规则 3 与规则 6 那两列的「—」各带一句「这条规则同时管两种组合：C3＝F 与 C3＝T」，并把依据里那句「有没有违规记录都一样」引了出来；清单末尾还写了一句「不可行的规则：没有」。判据三条都过。

两轮的建模选择不一样（一轮 8 条规则、一轮 6 条规则），清单都在——这条要求落在 `references/文档模板.md` 第三节那处结构位上，不靠当轮怎么建模。

改动前的现成证据：`evals/plain-language/test-case-design/Test Model Specification.md` 是本技能跑出来的一套真实产出，其中 TM-2、TM-3 两个模型就是判定表，表头只有「规则 1」到「规则 5」，全篇没有一处逐条说明这些编号各是什么——说明段里照样引「规则 3 与规则 5 管的是……」，读者得回头扫列才拼得出来。改动前的技能里也没有这条要求：`references/文档模板.md` 第三节的「测试模型」栏只说「把模型本体展示出来」，`references/技术/判定表测试.md` 第一节讲的是判定表怎么读，没讲写进产出时每条规则要不要单独交代，`references/文档示例.md` 那套示例里一个判定表模型都没有。所以这一条的 RED 是结构性的，不是偶发。
