# 场景测试

## 一、测试模型

场景测试的测试模型是交互序列，由一组与测试项相关的场景构成，其中每个场景涵盖一组交互序列。这个模型可以用图形表示，也可以用纯文本表示。

场景测试应使用测试项与其他系统之间的交互序列模型（在此周境中，用户通常被认为是其他系统），以测试所涉及的测试项使用流程。

场景测试是在分析测试依据的基础上，以动作序列的形式产生测试项行为的模型，该动作序列组成了贯穿测试项的工作流。

在场景测试中，测试模型应包含：

——“主”场景，测试项的预期典型动作序列，或无典型动作序列时所采取的一个任意选择；

——“备选”场景表示测试项可选择的（非主）场景。

注1：备选的场景包括非正常使用、极端或压力条件、异常和错误处理。

注2：场景测试通常在功能测试中用于产生“端到端测试”，比如系统测试或者验收测试。

注3：在许多情况下，将已识别的测试场景交由业务用户等相关方评审并达成共识，是一项推荐的实践做法。

场景测试的一种常见形式是用例测试，其采用了测试项的用例模型来描述测试项如何与一个或多个参与者交互，以测试相关测试项的交互序列（即场景）。

注4：在用例测试中，用例模型用于描述参与者如何触发测试项的各种动作。参与者可以是用户或其他系统。

注5：事务流测试通常也被归为场景测试这一类型。

## 二、测试覆盖项

场景测试的测试覆盖项是场景，分主场景与备选场景。

测试覆盖项应是从测试模型中确定的主场景和备选场景。

场景测试没有覆盖档位可选，要求覆盖主场景和备选场景。

## 三、导出测试用例

导出测试用例应遵循以下步骤：

应导出场景测试的测试用例，每个场景（测试覆盖项）至少被一个测试用例覆盖。

a）选择当前测试用例要执行的一个测试场景。

b）确定输入值以执行测试用例覆盖的测试场景。

c）将输入应用于测试依据，确定测试用例的预期结果。

d）重复步骤 a) 至 c)，直到达到所要求的测试覆盖率级别。

## 四、覆盖率

覆盖率按 C＝N÷T 计算，三个量在这门技术里各指什么如下：

——C 场景是场景的覆盖率；

——N 是执行的测试用例所覆盖的场景数量；

——T 是场景的总数量。

要求覆盖主场景和备选场景。

## 五、算例

下面的算例完整走一遍从测试依据到覆盖率的过程。本份的算例有两个：第一个是场景测试的通用模式，第二个是用例测试。

**示例1：场景测试的通用模式**

### 测试依据

考虑一个测试项 withdraw_cash，是自动取款机（ATM）系统的一部分，测试依据如下：

withdraw_cash 功能允许有银行账户的用户通过 ATM 机从他们的账户取款。取款要求用户有一个激活的账户、一张有效的卡和匹配的密码以及一台可工作的 ATM。当取款完成后，账户余额扣除取款金额，打印取款回执条，ATM 可用于为下一位用户服务。

根据用户的需求定义下面的场景：

基本场景：成功从账户取款。

可选场景：不支持取款，因为：

- 用户的银行卡不能被 ATM 识别，被拒绝
- 用户输入密码错误不多于 2 次
- 用户输入密码错误 3 次，ATM 吞卡
- 用户选择存款或转账，不选择取款
- 用户选择了错误账户，此账户在插入的卡中不存在
- 用户输入的取款金额是无效的
- ATM 中现金不足
- 用户输入不符合面额的取款金额
- 用户输入的取款金额是超过了每日最大取款金额
- 用户银行账户中的金额不足

在现实中，还可能出现其他情况的场景，例如用户在取款过程中的某个点上选择取消。

本算例的覆盖率要求是覆盖主场景和备选场景。

### 测试覆盖项

在场景测试中，需要覆盖的测试覆盖项包括主场景和备选场景（即用户和系统交互的事件流用序列组成一个场景）。在规格说明中描述了 11 个场景，包括 1 个主场景和 10 个备选场景：

- TCOV-1：取款成功（主场景）
- TCOV-2：银行卡不能被 ATM 识别（备选场景）
- TCOV-3：用户输入密码错误次数小于 3 次（备选场景）
- TCOV-4：用户输入密码错误次数等于 3 次（备选场景）
- TCOV-5：用户选择存款或转账（备选场景）
- TCOV-6：用户选择错误账户（备选场景）
- TCOV-7：用户输入无效提款金额（备选场景）
- TCOV-8：ATM 中现金不足（备选场景）
- TCOV-9：用户输入不符合面额的取款金额（备选场景）
- TCOV-10：用户输入的取款金额超过每日最大的金额（备选场景）
- TCOV-11：用户银行账户中的金额不足（备选场景）

### 测试用例

选择要覆盖的一个场景来导出测试用例，确定测试用例的输入以执行测试用例所覆盖的路径、确定测试的预期结果，重复上述步骤直到覆盖所有要求的场景。测试用例的步骤通常用自然语言的格式说明。

注：在每个测试用例中，可以选择多种输入来填充每个输入字段。可使用[等价类划分](等价类划分.md)为每个输入字段确定一组值。

3 条测试用例的前置条件相同：取款要求用户需有一个激活的账户、一张有效的卡和匹配的密码以及一台工作的 ATM。

表中「演练的场景路径」一栏是该用例执行的交互序列，「输入」一栏列出该用例为各个输入字段取的取值，「预期结果」一栏列出用例执行后应得到的结果。

| 用例编号 | 测试用例名称 | 演练的场景路径 | 输入 | 测试覆盖项 | 被测场景 | 预期结果 |
|:---|:---|:---|:---|:---|:---|:---|
| TC-1 | 取款成功 | U1、S1.1、U2、S2.1、U3.1、U4、S4.1、U5、S5.1、S6、S7、S8、S9、U6 | 有效客户账户的有效银行卡 - 假设 293910982246 有效；正确密码 - 假设 5652 正确且与银行卡匹配；ATM 余额 - 50,000 元；客户账户余额 - 100 元；取款金额 - 50 元 | TCOV-1 | 取款成功 | 成功从客户账户取款；ATM 余额为 49 950 元；客户账户余额为 50 元；ATM 是激活的、可操作的，等待插入一张客户银行卡 |

### 覆盖率

已识别的场景总数量 T＝11（1 个主场景加 10 个备选场景）；3 条测试用例覆盖到的场景数量 N＝3，其余 8 个场景未导出测试用例；覆盖率 C 场景＝N÷T＝3÷11＝27.3%。

**示例2：用例测试**

### 测试依据

考虑测试项 change_password 的用例：

| 字段 | 内容 |
|:---|:---|
| 用例 ID | UC001 |
| 用例 | 修改密码 |
| 目的 | 允许用户修改现有的密码，以输入新的密码 |
| 执行者 | 用户 |
| 说明 | 本用例允许用户修改现有的密码，以输入新的密码 |
| 触发动作 | 用户点击主菜单界面上的“修改密码”按钮 |
| 前置条件 | 用户已登录系统 |
| 异常 | 无 |
| 规则 | 新密码需与当前密码不同；新密码长度需至少有 8 位；系统用星号(*) 显示所有当前和新密码字符 |
| 常规 | 新用户首次登录系统时使用；通常每个用户每年平均使用两次；用户可以随时点击“修改密码”按钮 |

用例中的场景与步骤：

| 场景名称 | 步骤 |
|:---|:---|
| 基本流 | 1 -；2 系统显示“修改密码”界面；3 用户正确输入当前密码；4 用户正确输入新密码；5 用户重新正确输入新密码；6 用户点击确定；7 系统显示信息“成功修改密码” |
| 可选流 - 当前密码输入错误 | 3.1 -；3.2 用户输入正确的新密码；3.3 用户重新输入正确的新密码；3.4 用户点击确定；3.5 系统错误信息提示“当前密码输入错误，请重试”，并且定位到当前密码输入框 |
| 可选流 - 新密码长度少于 8 位 | 4.1 -；4.2 用户点击 OK；4.3 系统错误信息提示“新密码长度至少需要 8 位，请重试” |
| 可选流 - 新密码和当前密码一致 | 5.1 -；5.2 用户点击确定；5.3 系统错误信息提示“新密码需不同于当前密码，请重试” |
| 可选流 - 两次输入的新密码不一致 | 6.1 -；6.2 用户点击确定；6.3 系统错误信息提示“新密码不一致，请重试” |

表中步骤前的数字是步骤号；“-”表示这一步在用例里没有给出描述，基本流的第 1 步与各可选流的第 1 个步骤都是这样。

也可能出现其他情况的场景，如用户输入无效形式的新密码。

本算例的覆盖率要求是覆盖基本场景和可选场景。
