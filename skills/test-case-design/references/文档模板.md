# 文档模板

本文定下五份规格说明的字段名全集与编号方案，是全库的依据：各门技术的算例、文档示例、主流程里的产出说明都按这套写，不另造字段名。

五份规格说明的文件名即文档名——`测试模型规格说明.md`、`测试用例规格说明.md`、`测试规程规格说明.md`、`测试数据需求.md`、`测试环境需求.md`，写入调用时指定的目录。

栏名后括号里的节号（`9.2.3` 这类）标的是这一栏的出处，供实现与复核对照；写产出文档时不要带出去，产出文档里不出现任何出处与节号。

## 一、通用信息

所有测试文档共用一组通用信息元素，第 6 章共列 8 项（6.2.1～6.2.8）。本技能只保留一项：

- **唯一标识符**（6.2.1）：唯一标识测试文档或记录。文档级用「文档名 ＋ 版本」；条目级（每个模型、每条覆盖项、每条用例、每条规程、每条数据项、每项环境项）用第二节的编号方案。五份规格说明、每个条目都带这一项。

其余 7 项**有意不收**，不是漏掉：

| 不收的项 | 节号 | 这一项管什么 |
|:---|:---|:---|
| 发布组织 | 6.2.2 | 负责准备和发布文档的组织，含作者信息 |
| 审批权限 | 6.2.3 | 负责签署文档的人员，含评审人员、管理人员 |
| 变更历史 | 6.2.4 | 自文档创建以来对其所做的所有更改的记录 |
| 状态 | 6.2.5 | 文档处于「尚未开始」「设计中」「审核中」「已批准」中的哪个 |
| 范围 | 6.2.6 | 文档对主题领域的覆盖范围，含包含项、排除项、假设项、限制条件 |
| 引用文档 | 6.2.7 | 引用的外部与内部文档清单，以及系统、软件和测试信息的储藏库 |
| 词汇表 | 6.2.8 | 文档中术语、缩略语和首字母缩写词的说明 |

不收的理由：这 7 项都是文档进入发布与审批流程时才要的信息，值要靠被测项目的文档管理安排才能定；本技能的产出是设计过程的中间产物，不参与那套流程。

唯一标识符是例外——它收，因为编号方案由本技能自己给（见第二节），不依赖组织安排。

## 二、唯一标识符方案

原文只规定了要有唯一标识符，没规定怎么编。本技能直接给出这套方案：

| 对象 | 编号写法 |
|:---|:---|
| 测试模型 | `TM-1`、`TM-2`…… |
| 测试覆盖项 | `TCOV-1`、`TCOV-2`…… |
| 测试用例 | `TC-1`、`TC-2`…… |
| 测试规程 | `TP-1`、`TP-2`…… |
| 测试数据项 | `DATA-1`、`DATA-2`…… |
| 测试环境项 | `ENV-1`、`ENV-2`…… |

- 从 1 起顺序递增，不跳号、不复用；引用时写全编号。
- 编号在对象的生存周期内不改——它承担追溯，改了追溯就断。
- 可以用工具生成，也可以按这套规则手工编。
- 数据项与环境项不冠 `TD`／`TE` 前缀：这两个前缀已被活动代号占用（TD1～TD4 那一组），混在一起读不清。
- 项目已有编号惯例就跟随惯例，没有就用这套。

## 三、测试模型规格说明（9.2）

一个任务往往建多个测试模型——每门选定的技术建各自的模型。每个模型把这六栏写齐，一份文档里按模型分组。

- **唯一标识符**（9.2.2）：照第二节给编号（`TM-…`），用于把这个模型与所有其他模型区分开。可工具生成，也可按规则手工编；生存周期内不改，因为它承担追溯。
- **目标**（9.2.3）：写这个模型关注测试项的哪一部分。测试模型只描述测试项的某一个方面，不写全貌，这一栏就是把「是哪一个方面」点明。这句话通常直接当模型的标题用。
- **优先级**（9.2.4）：写风险等级，不是随手标高低。高风险的模型要建得更细、导出的覆盖项取全，低风险的可取子集，所以这一栏是「做到什么程度」的承接点。等级从开工输入的风险信息来。
- **测试策略摘要**（9.2.5）：写清三件事——用了哪几门测试设计技术、它们怎么组合、测试完成准则（要求的覆盖率）是什么。组合要写明分工：谁为谁提供输入、哪门技术补哪类缺陷。这是依据落地的地方，写不出依据就停下来问，不要空着，也不要自己编一个。
  - 「测试是自动化执行还是人工执行」这一句不写：本技能的产出一律是模型产出，不涉及执行方式。
- **测试模型**（9.2.6）：把模型本体展示出来。可用自然语言、形式化语言、表格、图形或其他适当格式，也可直接引用已有的工作产品（例如源代码）。用哪种表示法取决于所需的测试覆盖率；模型的具体形态由选定的技术反推（状态转移测试建状态图、判定表测试建判定表，见各技术文件），不自由发挥。
- **可追溯性**（9.2.7）：写这个模型取自测试依据的哪一部分。落点是文档末尾的「依据 → 模型」对应表（格式见第八节），不另设栏目，也不另建追踪矩阵文件。

## 四、测试用例规格说明（9.3）

分三块写：测试覆盖项清单、测试用例、末尾的「覆盖项 ↔ 用例」对应表。一条覆盖项导出多少条用例，由测试完成准则（要求的覆盖率）和该覆盖项的风险等级定——准则低于 100% 时并非每条覆盖项都要有用例，高风险覆盖项通常多导。

### 测试覆盖项（9.3.2）

从测试模型应用选定技术导出。清单里每条覆盖项写这几栏：

- **唯一标识符**（9.3.2.2）：照第二节给编号（`TCOV-…`），用于与其他覆盖项区分。生存周期内不改，它承担追溯。覆盖项数量过多或变动性过高、编号难以为继时，可以改用工具建立测试用例与测试模型之间的对应关系，并在文档里说明用的是哪种方式。
- **描述**（9.3.2.3）：写这个覆盖项是什么——按导出它所用的那门技术，预期由测试用例覆盖的那个属性。例如某等价类是有效类还是无效类、某条状态转换、判定表里的某条规则、分类树上的某个类别。附带的信息也写在这一栏。
- **优先级**（9.3.2.4）：写风险等级，不是随手标高低。高优先级覆盖项先于低优先级覆盖项被覆盖与执行；高风险覆盖项还要多导用例（见本节开头）。
- **可追溯性**（9.3.2.5）：写这条覆盖项出自哪个模型——至少填模型编号，必要时写到模型里的哪个元素（哪条状态、哪条转换、哪条规则、哪个类别）。覆盖项清单里留一栏放它就行，不另建追踪矩阵文件。

### 测试用例（9.3.3）

每条用例写这几栏：

- **唯一标识符**（9.3.3.2）：照第二节给编号（`TC-…`），用于与其他用例区分。生存周期内不改，它承担追溯。
- **目标**（9.3.3.3）：写这条用例的测试重点与目标，一句话说清它要验证什么。这一栏通常直接当用例的标题用，例如「验证传送带不移动时盖板的锁定功能」。
- **优先级**（9.3.3.4）：写风险等级。可行时高优先级用例先于低优先级用例执行。等级随它覆盖的那条覆盖项来；同一条覆盖项导出的多条用例可共用同一等级，个别用例另有理由时可单独定并说明。
- **可追溯性**（9.3.3.5）：写这条用例覆盖了哪些测试覆盖项。这一项不单独设栏目——由文档末尾的「覆盖项 ↔ 用例」对应表承接（格式见第八节）。
- **前置条件**（9.3.3.6）：写执行这条用例所需的测试环境状态、测试数据，以及与执行相关的全部特殊约束条件。例如执行启动前被测对象应处的状态，包括要准备好的测试数据、当前所处的界面或页面。可以写成明确的状态描述，也可以写「先执行某某用例」，那条用例会把前置条件摆好。多条用例共用的环境在文档里统一说明一次即可，不必逐条重复。
- **输入**（9.3.3.7）：规定测试项达到「可以把预期结果与实际结果进行比对」的状态所需的各项操作。详细程度以照着能执行为准；操作之间有先后关系的要写明关联关系（例如时序关系）；必要时把各项操作依次编号。输入可以是数据，也可以是事件（例如按钮点击）；数据可以直接给具体数值，也可以按名称指代（如常量表、事务文件、数据库、普通文件、终端报文、内存驻留区、操作系统传递的参数值）。
- **预期结果**（9.3.3.8）：写测试项在满足前置条件、接收指定输入之后，应产生的预期输出和运行行为。需要校验的输出逐个给预期值，必要时带允许误差范围，运行行为里的响应时间就是典型。还可以写把预期结果与实际结果进行比较所需的各项操作，例如检查某个字段的输出内容、等批处理作业运行完并打印检查报告、关闭测试项后重新启动以检查存储的数据。

## 五、测试规程规格说明（9.4）

一条规程把一组测试用例按执行顺序串起来，带启动动作与收尾动作。逐栏写：

- **唯一标识符**（9.4.2）：照第二节给编号（`TP-…`），用于区分不同的测试规程。生存周期内不改，它承担追溯。
- **目标**（9.4.3）：写这条规程的重点或目标，一句话，通常直接当标题用。
- **优先级**（9.4.4）：需要时写，写风险等级。
- **启动**（9.4.5）：写执行本规程中的测试用例之前必需的准备动作——通常就是把第一条用例的前置条件摆好所需的那几步操作。
- **有序执行测试用例**（9.4.6）：按执行顺序排列本规程要跑的测试用例，可依次编号。这个列表可以是对测试用例的引用，也可以是测试用例的复制列表。要写清这个顺序允许变动的程度，即哪些位置可以调换。如果规程中一条或多条用例的执行结果没有为随后的用例准备好前置条件，就在两条之间补上准备前置条件的操作。
- **与其他规程的关系**（9.4.7）：写这条规程与其他规程存在的依赖关系——哪几条要在它之前执行、哪几条与它同时执行、哪几条在它之后执行。
- **停止与结束**（9.4.8）：写有序停止执行本规程所需的操作，以及规程执行完毕后所需的收尾操作，例如终止记录、把测试数据库复位。

## 六、测试数据需求（9.5）

一条数据项一行，写这两栏：

- **唯一标识符**（9.5.2）：照第二节给编号（`DATA-…`），用于区分不同的测试数据项。
- **描述**（9.5.3）：写每个测试数据元素的特定名称和所需值或值的范围。某项数据需要匿名化或以其他方式处理时，一并写明。

有意不收这四栏：**责任**（9.5.4，谁负责使测试数据可用）、**需要的周期**（9.5.5，什么时候要用、用多久）、**重置需求**（9.5.6，测试过程中要不要把数据重置）、**归档或清除**（9.5.7，测试完成后归档或清除的时机和方式）。它们都要靠被测项目的组织安排与排期才能定，本技能的产出是设计阶段的中间产物，不落这些安排。这是决策，不是漏掉。

## 七、测试环境需求（9.6）

一项环境项一行，写这三栏：

- **唯一标识符**（9.6.2）：照第二节给编号（`ENV-…`），用于区分不同的测试环境项。生存周期内不改，它承担追溯。
- **测试环境项**（9.6.3）：识别执行测试规程所需的测试环境的每个要素。要素要能支撑规程执行前的设置、执行中和执行后的各项活动。环境项不能完全反映运行（生产）环境时，写清它代表或偏离运行环境的程度。类型可作提示：硬件、中间件、软件（如特定系统或浏览器）、与其他系统和接口系统的接口、外围设备（如打印机）、移动设备（如手机、平板电脑）、通信方式、工具、信息安全性、场地（如房间大小、桌椅和背景噪音水平）、配件（如特别预先印好的纸张表格），也可按需另立类型。
- **描述**（9.6.4）：把环境项写到能照着实施的详细程度——精确命名的特定版本和配置的硬件或软件；测试过程中需要在特定时间点运行以支持测试的批处理作业也列出来，例如要求每晚运行一套常规批处理作业以反映生产环境。

有意不收这两栏：**责任**（9.6.5，谁负责搭建并使环境项可用）、**需要的周期**（9.6.6，什么时候要用、用多久）。理由同第六节：要靠被测项目的组织安排与排期才能定。

## 八、对应表格式

两张对应表承接可追溯性，都用 Markdown 表格，各自附在所属文档末尾。

**「依据 → 模型」表**，附在测试模型规格说明末尾：

| 依据的出处 | 模型编号 | 说明 |
|:---|:---|:---|

- 依据的出处：写这段依据在哪里——依据文档名加条目号或段落名（如需求编号、规格说明里的哪一节）。
- 模型编号：照这段依据建出来的模型的编号（`TM-…`）。一个模型照多处依据建就写多行，一行一处依据。
- 说明：这个模型取自这段依据的哪一部分、覆盖它的哪个方面。

**「覆盖项 ↔ 用例」表**，附在测试用例规格说明末尾：

| 覆盖项编号 | 覆盖项描述 | 覆盖它的用例编号 |
|:---|:---|:---|

- 覆盖项编号：`TCOV-…`。一条覆盖项一行，全部覆盖项都要列上。
- 覆盖项描述：一句话说清这条覆盖项是什么，与覆盖项清单里的描述一致即可——不看清单也读得懂这张表。
- 覆盖它的用例编号：把覆盖它的用例编号都写上（`TC-…`，多条用顿号分开）。**这条覆盖项还没有任何用例覆盖时，这一栏留空——空着的行就是覆盖率自检要看的地方**，一眼看得出缺哪些。

测试规程不另出对应表：规程的「有序执行测试用例」栏本身就是测试用例编号的有序列表，用例到规程的追溯靠它。

**字段完整性核对**：附录 A 的映射表逐栏列了应／宜／可，本文件的清单与它逐栏对过。该表用的是比正文少一的节号（表里的 8.2～8.6 就是本文件的 9.2～9.6），核对时按栏名对，不按编号对。第六、七节点明不收的那几栏，在附录 A 里同样列着——不收是决策，不是遗漏。各节的「概述」不是可填的栏目，它讲的是这份文档整体怎么用，其中影响填写的内容已并入下面的栏内说明。
