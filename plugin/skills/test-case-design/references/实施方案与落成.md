# 实施方案与落成

**什么时候读这一份**：用户点名要实施方案规格说明（第七份）时；或七份都在手上、只做落成时。六份通用稿的设计不走这一份。

## 一、只出实施方案那一份

第七份（`Implementation Specification.md`，实施方案规格说明）**只在用户点名要的时候出**——第 0 步不问、也不提。点名有两种：跟六份一起要，或者手上已经有六份、这次只要这一份；两条入口都不影响那六份。

**它只对靠模型跑的对象有用。**第七份是把六份落成能跑的测评配置的，对象得是技能、提示词这类靠模型跑的东西。一段脚本、一个函数、一个库不吃这一套——用户点名要也照实说这一份用不上（那种对象要落成的是工程里能跑的测试，不在这门技能范围内），产出仍是那六份。**判「靠不靠模型跑」只看测试项本身**，不看规程的「执行器」栏——那一栏要到第 5 步才定得下来；两者都有的测试项（比如一份技能的中心逻辑靠模型跑）按「有用」算。

**方案目前只有 skill-up，直接照它走，不问用哪个。**

**一、随六份一起出。**六份走完第 7 步终检之后再出这一份——它要对账的六类编号到第 5 步才齐，早出了对不上。写之前读 `references/文档模板.md` 第十节（契约）与 `references/文档示例.md` 第七节（填写示例）；**先确认 `~/.claude/skills/skill-upper/` 在不在**：不在再看 `skill-up` 命令能不能用（`--help`／`validate` 核字段名），都没有就问用户要不要帮装——默认装全局 `~/.claude/skills/skill-upper/`、不进项目目录，不照印象写，不退回公网文档，也不去找本机的 skill-up 克隆。**`skill-up` 命令不能跑时第七份不写**：照 `references/异常处理.md` 问用户要不要帮装，装好并用 `--version` 确认后再写；不装或装不上就终止第七份。找得到的，**照它 `references/` 下那几份把这一份里要写进去的命令与字段名逐条核对（核对的是字段名，不是核对这份文档的版本）**——**别照印象写**：写了不存在的开关、或漏了必填的那一项，要等到落成、跑校验时才撞见，那时通用稿已经定了稿。核完再读 `references/评测方案/skill-up/usage-notes.md`，把落点与折扣写准（工作区怎么起、哪几条在这个方案上跑不了原样）。

**二、单独出。**手上已经有六份产出，这次只出第七份——和上面那条路并列，**不重出已有的文档**。走法：读盘上那六份（对账要对测试环境需求与测试数据需求两份）；照入口一读的那几份核对，并照 `references/文档模板.md` 第十节写，落到同一个产出目录里；**跳过取号**——这一份不定义任何编号，一个都不新发。

写完之后照旧跑一遍 `python scripts/check_docs.py <产出目录>`，第七份在目录里时那一组会一并查。

## 二、落成那一步手上要有哪四样

**落成那一步读四样，落成的人四样都要在手上**：

1. **六份通用稿**——消息正文从测试用例规格说明的「输入」栏来，判据从「预期结果」栏来；执行顺序与分几批从测试规程规格说明的「有序执行测试用例」与「各批落到哪」来；样本的字节与正文从测试数据需求来；环境项从测试环境需求来；模型与覆盖项从测试模型规格说明与覆盖项清单来。**第七份不把它们重述一遍**，只读第七份落不出东西。
2. **第七份（实施方案规格说明）**——哪几条规程在这一套里跑、落成什么形式、落在哪个路径、编号在盘上怎么留痕，都在那一份里。**落点账也在这份里**：这一批落了没、成品落在哪个路径，写在这一份方案节末尾的「成品落点」表里，不必回通用稿找。**通用稿不认任何一种测评方案**，只读通用稿也不知道该摆成什么。
3. **`/skill-upper` 技能下 `references/` 那几份**——配置字段怎么填、命令怎么用，以它为准。**它没写到的、或者与第 4 样冲突的，以第 4 样为准**：它那几份里有与本技能实测对不上的话（Windows 支不支持就是一处，见第 4 样）。
4. **`references/评测方案/<方案名>/usage-notes.md`**——这套方案**实际跑起来是什么样**：工作区怎么起、哪几样东西铺不进去、哪几条跑不了原样。前三样讲「要什么」，这一样讲「实况」——落成时撞上的正是后者。**写第七份的「说明」那一块时也读它**（见第一节），那几条的事实从这里取。**两边的话对不上时以它为准**；它没写到的标「待确认」，不写成事实、也别照印象补。**读它之前先跑一次 `skill-up --version`，与它顶部的版本行对一下；不一致时，涉及运行时行为的几条标「待确认」，别当事实写。`skill-up` 没装时第七份不写**：先问用户要不要帮装，默认全局（用户级）安装、不进项目目录，装好并用 `--version` 确认后才继续；不装或装不上就终止第七份。写通用稿不受影响。

## 三、只做落成

**入口**：七份都在手上（六份通用稿 ＋ 第七份），用户点名要落成。**不重出、不改写那七份的设计内容**——这一步只往盘上摆东西、回来补一张表。

1. **读那四样**——各取什么见第二节。第七份是要照的那一份：哪几条规程在这一套里跑、落成什么形式、落在哪个路径、编号在盘上怎么留痕，都在它里面。
2. **照第七份摆文件**——`eval.yaml`、用例配置、夹具落到第七份「通用稿的编号落到哪」那张表点名的路径上。**配置原文由这一步写**：第七份里不贴它；字段怎么填照 `/skill-upper` 技能下 `references/` 那几份，实况照 usage-notes。**编号照抄**——连字符写不成换成下划线、数字不补零、一条一个号不写成范围（见 `references/文档模板.md` 第二节「落成约定」），照第七份里「编号在盘上怎么留痕」那一处下笔。
3. **回来补「成品落点」表**——第七份方案节末尾那一块，**一行一个成品路径**。写法与三条约束见 `references/文档模板.md` 第十节。
4. **跑一遍落成对照**——`python scripts/check_landing.py <产出目录> <成品路径 ...>`；成品住在评测材料根那一层时，路径一条条点出来（见第四节）。**它报出来的差异改到零错再收手**：哪一条编号在成品里找不到、成品里哪个号没有出处，都是账没对上（退 3 是「还没落成」，不是错）。
5. **把偏离写进第七份**——落成时哪几条没照原样落、偏在哪、为什么（夹具几套并成一套、某几样铺不进工作区、相对路径的基准退让这类，**都是脚本看不见的**），一条一条写进第七份方案节「说明」那一块，跟通用稿逐条对照。**不改 `usage-notes.md`**：装机上那份是只读的。

## 四、成品落点与落成对照

**这一块住在第七份的方案节里，是那一节的最后一块。**它记这一批落了没、成品落在哪个路径——六份通用稿里一个字都不写这些（通用稿不认任何一种测评方案，落点与进度都是方案的事）。**表里一行一个成品路径**；还没落成就写「还没落成」，是那一块里的一句话、不占表里的一格；分几批落成时两种写法并存。写法与三条约束见 `references/文档模板.md` 第十节。

**落成之后回来把这张表填上，再跑一遍对照：**

```
python scripts/check_landing.py <产出目录> [成品路径 ...]
```

**成品住在评测材料根那一层（那一层还住着 `runs\` 这些跑测产物）时，命令上把成品路径一条条点出来**——别把整个上一层指过去：

```
python scripts/check_landing.py <产出目录> eval.yaml cases fixtures
```

它拿产出里定义过的编号去成品里找出处：六类条目（模型、覆盖项、用例、规程、数据项、环境项）在成品里一条也找不着，或者成品里冒出一个产出里没有的号，都算错。**成品里每条条目的编号都要搜得到**——代码里写不成连字符就换成下划线（`TC-30` 写成 `TC_30`），照抄编号，不补零、一条一个号不写成范围。

它的退出码：`0` 两边对得上；`1` 有对不上的地方；`2` 用法或路径有问题、或者那一块的表坏了；`3` 没有可对照的成品——**第七份整份不在**，或者这一块写着「还没落成」。**退 3 不是错**，看见它跳过就行，别当失败记。**分几批落成时照查**：那一块里既列了已落成的表、又写着「还没落成」交代剩下几处时，两向对照照样跑，只有「定义了却没在成品里出现」那一条降成提示。

## 五、skill-up 装不上、跑不了时

**写第七份缺 `skill-up` 是硬停**：先找 `~/.claude/skills/skill-upper/`，再看 `skill-up --version` 能不能跑；都没有就问用户要不要帮装，默认装全局（用户级）、不进项目目录，装好 `skill-up --version` 确认后再继续。**不装或装不上就终止第七份**，通用稿不受影响。

装好之后，版本与 `usage-notes.md` 顶部对不上时，把那一份当历史版本用：能跑 `skill-up` 核的当场核，拿不准的标「待确认」，别当事实写。照第一节的核法走。
