# 文档示例

本文把六份产出文档的填写示例收在一起，让读者看到填好的文档长什么样。

六节是同一个项目的一套产出：一个互联网产品的手机号验证码登录。六份文档互相对得上——用例与规程里引的 `DATA-…`、`ENV-…` 编号，在测试数据需求与测试环境需求里都指得到定义处；覆盖项追溯到测试模型；规程排的是测试用例；决策依据里的每一条，在其余五份里都能看到它落成了什么。编号按本技能的方案编（`TM-`、`TCOV-`、`TC-`、`TP-`、`DATA-`、`ENV-`、`DEC-`），见[文档模板](文档模板.md)第二节。

除决策依据外，五份里的每条条目还带一个英文名，紧挨着编号写。名字是按条目的中文目标压出来的，看得出这条是干什么的就行。

项目已有自己的编号惯例时可以跟随惯例；有一处要留意：本技能的[自检脚本](../scripts/check_docs.py)按 `DATA-…`／`ENV-…` 这两个前缀认编号，跟着项目自己的惯例编时，这一项自检过不了（报「一个编号都没有」）——要么改用本技能这套编号，要么这一项自己看。

文中凡以「注：」起头的行，都是本文加的说明，不是文档内容。

## 一、测试模型规格说明

### TM-1 登录状态转移模型

- **唯一标识符**：TM-1
- **英文名**：login_state_transition
- **目标**：手机号加短信验证码这一个环节的登录路径。账号注册、找回密码、第三方登录都不在这个模型里。
- **风险等级**：高。登录是所有功能的入口，它走不通，其余功能都用不上。等级取自开工输入的风险信息。
- **测试策略摘要**：状态转移测试。没有与别的技术组合——登录的分支集中在「发码、校验、锁定」这条链上，一条条走完即可。测试完成准则是状态转换 100% 覆盖，含依据里写明的无效转换。
- **测试模型**：用状态转换表表示，见下表。

| 转换 | 起始状态 | 事件 | 结束状态 | 动作与输出 |
|:---|:---|:---|:---|:---|
| T1 | S1 未登录 | 提交已注册的手机号并请求验证码 | S2 已发码 | 下发一条 6 位数字验证码 |
| T2 | S2 已发码 | 提交正确的验证码 | S3 已登录 | 建立登录会话 |
| T3 | S2 已发码 | 提交错误的验证码，连续失败未满 5 次 | S2 已发码 | 连续失败次数加一，提示验证码错误 |
| T4 | S2 已发码 | 提交错误的验证码，本次为连续第 5 次 | S4 锁定 | 锁定该账号 15 分钟 |
| T5 | S3 已登录 | 退出登录 | S1 未登录 | 销毁登录会话 |
| T6 | S4 锁定 | 锁定时长满 15 分钟 | S1 未登录 | 自动解锁，连续失败次数清零 |

依据里写明的无效转换有两条：S1 未登录就直接提交验证码；S4 锁定期间提交正确的验证码。两条都不该放行。

### TM-2 手机号与验证码输入的等价类划分模型

- **唯一标识符**：TM-2
- **英文名**：phone_and_code_partitions
- **目标**：手机号与验证码这两个输入框的取值要求，与登录路径无关。
- **风险等级**：中。输入校验被绕过不会直接导致登录失败，但会放进本不该放行的请求。等级取自开工输入的风险信息。
- **测试策略摘要**：等价类划分。与 TM-1 各建各的模型，不互相喂数据——TM-1 管状态怎么走，TM-2 管输入收不收。测试完成准则是等价类划分覆盖率 100%。
- **测试模型**：等价类清单如下，类别编号沿用 `PART-`。

- 手机号的有效类：11 位数字，且该号已注册（PART-1）
- 手机号的无效类：未注册（PART-2）
- 手机号的无效类：不是 11 位数字（PART-3）
- 手机号的无效类：含非数字字符（PART-4）
- 验证码的有效类：6 位数字（PART-5）
- 验证码的无效类：不是 6 位数字（PART-6）
- 验证码的无效类：含非数字字符（PART-7）

文档末尾的「依据 → 模型」对应表：

| 依据的出处 | 模型编号 | 说明 |
|:---|:---|:---|
| 需求 REQ-LOGIN-01 | TM-1 | 手机号与验证码的登录路径，含发码、登录成功与退出 |
| 需求 REQ-RISK-02 | TM-1 | 连续 5 次失败后锁定账号、15 分钟后自动解锁 |
| 需求 REQ-LOGIN-03 | TM-2 | 手机号与验证码这两个输入的取值要求 |

注：TM-1 的模型本体也可以画成状态迁移图。本文改用表列出，是为了让图里那些标号看得见。

### 测试用例

一行一条用例：

| 唯一标识符 | 英文名 | 目标 | 风险等级 | 前置条件 | 输入 | 预期结果 |
|:---|:---|:---|:---|:---|:---|:---|
| TC-1 | registered_phone_gets_code | 验证已注册的手机号能取到验证码 | 高 | ENV-1 就位，浏览器停在测试环境的登录页；DATA-1 里那个已注册号未被锁定 | 在手机号框填入 DATA-1 的已注册号，点「获取验证码」 | 提示「验证码已发送」；ENV-2 的沙箱登记到一条发往该手机号的短信；页面转到验证码输入框 |
| TC-2 | correct_code_logs_in | 验证正确的验证码能登录成功 | 高 | 先执行 TC-1，该手机号处于已发码状态 | 在验证码框填入 DATA-2 记录的验证码，点「登录」 | 跳转到首页，右上角显示该账号的昵称；登录服务建立登录会话 |
| TC-3 | five_failures_lock_account | 验证连续 5 次失败后账号被锁定 | 高 | 先执行 TC-1；DATA-4 记录的连续失败次数为 0 | 在验证码框填入一个错误验证码并提交，重复 5 次 | 前 4 次都提示「验证码错误」；第 5 次提交后提示「账号已锁定，请 15 分钟后重试」，登录服务把该手机号置为锁定 |
| TC-4 | correct_code_rejected_while_locked | 验证锁定期间正确的验证码也不放行 | 高 | 先执行 TC-3，该手机号处于锁定状态；DATA-4 记录的锁定剩余时长大于 0 | 在验证码框填入 DATA-2 记录的验证码，点「登录」 | 提示「账号已锁定，请 15 分钟后重试」；不建立登录会话，页面留在登录页 |
| TC-5 | unregistered_phone_gets_no_code | 验证未注册的手机号取不到验证码 | 中 | ENV-1 就位，浏览器停在登录页 | 在手机号框填入 DATA-1 里那个未注册号，点「获取验证码」 | 提示「该手机号未注册」；ENV-2 的沙箱没有新增发往该手机号的短信 |
| TC-6 | wrong_length_code_rejected | 验证位数不对的验证码被拒 | 中 | 先执行 TC-1，该手机号处于已发码状态 | 在验证码框填入 DATA-3 里那个 5 位数字，点「登录」 | 提示「请输入 6 位验证码」；请求不发给登录服务 |
| TC-7 | code_with_letters_rejected | 验证含非数字字符的验证码被拒 | 中 | 先执行 TC-1，该手机号处于已发码状态 | 在验证码框填入 DATA-3 里那个含字母的验证码，点「登录」 | 提示「验证码只能是数字」；请求不发给登录服务 |

## 三、测试规程规格说明

### TP-1 登录的正向路径与输入校验

| 唯一标识符 | TP-1 |
|:---|:---|
| 英文名 | happy_path_and_input_checks |
| 目标 | 把登录的正向路径与两个输入框的格式校验按顺序跑一遍。 |
| 风险等级 | 高 |
| 执行器 | 脚本 |
| 改动文件 | 会写 |
| 启动 | ENV-1 就位后打开浏览器，访问测试环境的登录页；确认 ENV-3 的登录服务测试实例可用；按 DATA-1 核对两个手机号的状态，确认已注册号未处于锁定状态。 |
| 有序执行测试用例 | TC-1、TC-2、TC-5、TC-6、TC-7 |
| 与其他规程的关系 | 无。本规程跑完后再跑 TP-2。 |
| 停止与结束 | 退出登录并清除浏览器会话。 |

### TP-2 账号锁定与锁定期间的拒绝

| 唯一标识符 | TP-2 |
|:---|:---|
| 英文名 | account_lock_and_locked_rejection |
| 目标 | 验证连续失败触发的锁定，以及锁定期间正确的验证码也不放行。 |
| 风险等级 | 高 |
| 执行器 | 控制器 |
| 改动文件 | 会写 |
| 启动 | 先执行 TP-1；ENV-1 就位，浏览器停在登录页；按 DATA-1 确认已注册号未处于锁定状态。 |
| 有序执行测试用例 | TC-1、TC-3、TC-4 |
| 与其他规程的关系 | 在 TP-1 之后执行。 |

### 各批落到哪

| 批次 | 规程 | 执行器 | 落到哪 | 用例目录名 | 说明 |
|:---|:---|:---|:---|:---|:---|
| 脚本批 | TP-1 | 脚本 | `tests/login/test_login.py` |  | 判据是页面上的提示文案与沙箱里的登记，脚本跑一遍就有结论 |
| 模型批 | TP-2 | 控制器 | `evals/login/cases/` | tp02-01-TC-1-registered_phone_gets_code、tp02-02-TC-3-five_failures_lock_account、tp02-03-TC-4-correct_code_rejected_while_locked | 判据跨到登录服务里的状态（账号被置为锁定、锁定期间不建会话），交给模型驱动着逐条读 |

注：TP-2 里又排了一次 TC-1，是因为 TC-3 的前置条件要求手机号处于已发码状态。同一个用例被多条规程排到，是正常的。落成评测用例时，这样一条用例会落成两个目录，各带自己那条规程的前缀——TP-1 不在评测批里，所以本范本只有 TP-2 那份。

注：两条规程都写着「会写」——它们执行当中都会改动登录服务与短信沙箱。什么样才是「只读」：规程执行当中只读测试项、比一比结果，一个字节都不动它。为跑规程而搭的环境、备的数据不算——建临时目录、摆样本、清场都属搭场子，写在「启动」栏里，见[文档模板](文档模板.md)第五节。

## 七、实施方案规格说明

注：这一节的小标题比上面六节都浅一级（`###`／`####` 而不是 `##`／`###`），因为第七份正文本身就多一层嵌套——测试把范本按节切开、标题降一级之后，这几级正好落回产出里的样子。

这份把上面六份通用设计稿落成能跑的东西。六份说的是「要什么」——模型、覆盖项、用例、规程、数据、环境；这一份说的是「用哪个、怎么摆」——这批用例交给哪套测评方案跑、每条编号落到盘上的哪个文件哪一段。**配置本身不抄进来**：它由落成那一步照这一份写进盘里，抄一份到文档里就是第二份会漂移的副本。**两边冲突时以这一份为准**：通用稿是按测试项写的、不认方案，落到具体方案上总有几处要偏，偏在哪写在每个方案的「说明」里。

方案按节分。眼下只有 skill-up 一节；将来换一套方案，在同一份里再起一节，六份通用稿一个字不用动。

### 二、方案：skill-up

#### 2.1 说明

**1. 跑几次**

一次。两条规程里只有 TP-2 落成评测用例——TP-1 的判据落在页面提示与沙箱登记上，跑一遍脚本就有结论，归可跑测试那一边，不在这份配置里。

**2. 工作区怎么来**

每条用例开跑前，框架自己在系统临时目录下新建一个空目录当工作区，跑完删掉。`ENV-3` 那条夹具由 `context.repo_fixture` 铺进去，原始夹具不动。

**3. 判据落在哪**

`TC-1`、`TC-3` 的判据要读一轮模型的行为（它跑了哪一步、把登录服务置成什么样），交给 `agent_judge` 按 `judge.criteria` 逐条判；`TC-4` 的判据落在工作区里那份会话记录上，用 `rule_based` 判。

**4. 跑不了原样的那几条**

- `ENV-1` 那两台浏览器不在这份配置里造，落地时改成本机装好的那两个——偏在哪写在上面那张对账表的说明栏里。
- `ENV-2` 那台短信网关沙箱用桩件顶：接口形状照抄，只记账不外发。沙箱与生产网关本来就有的那处偏离（不校验发送频次上限）照旧在，`TC-3` 判的是锁定，不碰频次。
- 这三条（`TC-1`、`TC-3`、`TC-4`）的其余部分与设计稿一致，没有出入。`TC-2`、`TC-5`～`TC-7` 本来就不在这份配置里跑（见第 1 小节），不算折扣。

#### 2.2 怎么跑、报告落在哪

一批跑测共用一个时间戳目录：先取一次当前时刻，这一批的几条命令都拿它当 `--output-dir`。

```powershell
$ts = Get-Date -Format "yyyy-MM-dd-HHmm"
skill-up run evals/login/eval.yaml --output-dir "evals/login/runs/$ts"
```

报告落在 `evals/login/runs/<这批的时间戳>/`，底下 `iteration-1/` 是 skill-up 自己追加的——这一批里跑的第几回就是几。下一批另取一个时间戳，落进新目录，盖不掉这一批，前几批的报告都留着。

不进 git：仓库根的 `.gitignore` 里那条 `evals/*/runs/` 把整个 `runs/` 盖住了。
