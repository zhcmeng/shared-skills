# 文档模板

本文定下六份文档的字段名全集、编号方案与英文名的形制，是全库的依据：文档示例与主流程里的产出说明都按这套写，不另造字段名；技术文件里的算例是给读者看过程的简表，不是产出的表样，产出照第三节至第七节、第九节的栏目填。

六份文档写入用户指定的目录。**文件名用英文，正文写中文**——文件名与本文用的中文名一一对应：

| 文档（本文与 SKILL.md 里的叫法） | 文件名 |
|:---|:---|
| 测试模型规格说明 | `Test Model Specification.md` |
| 测试用例规格说明 | `Test Case Specification.md` |
| 测试规程规格说明 | `Test Procedure Specification.md` |
| 测试数据需求 | `Test Data Requirements.md` |
| 测试环境需求 | `Test Environment Requirements.md` |
| 决策依据 | `Decision Basis.md` |

前五份记结论，第六份记过程——理由与写法见第九节。

## 一、通用信息

所有测试文档共用一组通用信息元素，共 8 项。本技能只保留一项：

- **唯一标识符**：唯一标识测试文档或记录。文档级就用文件名（见上）；条目级（每个模型、每条覆盖项、每条用例、每条规程、每条数据项、每项环境项、每条决策）用第二节的编号方案。每个条目都带这一项。

其余 7 项**有意不收**，不是漏掉：

| 不收的项 | 这一项管什么 |
|:---|:---|
| 发布组织 | 负责准备和发布文档的组织，含作者信息 |
| 审批权限 | 负责签署文档的人员，含评审人员、管理人员 |
| 变更历史 | 自文档创建以来对其所做的所有更改的记录 |
| 状态 | 文档处于「尚未开始」「设计中」「审核中」「已批准」中的哪个 |
| 范围 | 文档对主题领域的覆盖范围，含包含项、排除项、假设项、限制条件 |
| 引用文档 | 引用的外部与内部文档清单，以及系统、软件和测试信息的储藏库 |
| 词汇表 | 文档中术语、缩略语和首字母缩写词的说明 |

不收的理由：这 7 项都是文档进入发布与审批流程时才要的信息，值要靠被测项目的文档管理安排才能定；本技能的产出是设计过程的中间产物，不参与那套流程。

唯一标识符是例外——它收，因为条目级的编号方案由本技能自己给（见第二节），不依赖组织安排。

## 二、唯一标识符与英文名

每条条目有两个名字：**编号**供文档内部追溯，**英文名**供下游把这条条目落成代码时用。这一节两个都定。

唯一标识符要有，但怎么编没规定。本技能直接给出这套方案：

| 对象 | 编号写法 |
|:---|:---|
| 测试模型 | `TM-1`、`TM-2`…… |
| 测试覆盖项 | `TCOV-1`、`TCOV-2`…… |
| 测试用例 | `TC-1`、`TC-2`…… |
| 测试规程 | `TP-1`、`TP-2`…… |
| 测试数据项 | `DATA-1`、`DATA-2`…… |
| 测试环境项 | `ENV-1`、`ENV-2`…… |
| 决策 | `DEC-1`、`DEC-2`…… |

- 从 1 起顺序递增，不跳号、不复用；引用时写全编号。
- 编号在对象的生存周期内不改——它承担追溯，改了追溯就断。
- **号由 `scripts/issue_ids.py` 发，不自己推算**：写条目前跑一次 `python scripts/issue_ids.py <产出目录> <前缀> --count <这批要几个>`，照它打出来的号写。它每次现读产出目录里那六份文档、取已经定义过的条目里最大的号加一，不另存台账；号也不回收——删条目腾出来的号不给后来的条目用。
- 数据项与环境项不冠 `TD`／`TE` 前缀：这两个前缀已被活动代号占用（TD1～TD4 那一组），混在一起读不清。
- 项目已有编号惯例就跟随惯例，没有就用这套；跟随惯例时把那个前缀照传给脚本（如 `Lid-`），照旧由它发号。

### 英文名

**每条条目都要有一个英文名**（决策依据那份除外）。它是这条条目落成代码时的名字核：下游把用例落成可跑的测试、把数据项落成常量、把规程落成一组测试时，拿它拼函数名、类名、变量名。文档内部追溯照旧用编号，两者互不影响。

| 对象 | 英文名写在哪 |
|:---|:---|
| 测试模型、测试规程 | 紧挨着「唯一标识符」写，跟它同一种形式——模型写成加粗字段，规程写进那张两列表里 |
| 测试覆盖项、测试用例、测试数据项、测试环境项 | 表里紧挨着「唯一标识符」右边新起一栏 |

- **形制**：小写字母起头，只含小写字母、数字、下划线（`file_not_utf8`、`main_scenario`）。大写驼峰、空格、中文都不行——下游要按自己的规矩转大小写（类名转驼峰、常量转全大写），名字核得是它转得动的那一种。
- **只写名字本身，不带编号**：写 `file_not_utf8`，不写 `tc_11_file_not_utf8`。编号由下游自己拼，这一栏里带了编号，拼出来就成了 `test_tc_11_tc_11_…`。
- **必填，不留空**：空着等于这个名字还是留给下游每次现取，同一批用例换个会话就换一批名字，那正是这一栏要消掉的毛病。
- **照「目标」或「描述」栏取**：让人不看中文也认得出这条是干什么的。取得准不准由人看，自检只管形制。
- **决策依据那份不给英文名**：它记的是过程，不落成任何对象，下游也没有哪样东西要照它命名。

两张对应表（见第八节）不加这一栏：那里靠编号追溯，名字在定义处给一次就够了。

### 落成约定

条目落到**成品**里时——成品指这条产出落成的可跑测试、评测用例——按下面这套写。成品里的**编号**是对照用的：拿文档里的 `TC-30` 去成品里搜要能搜到，成品里出现一个编号也要指得回文档里的哪一条。两边对不上，读的人就得猜哪份是新的。

| 条目 | 在成品里写成什么 |
|:---|:---|
| 测试模型 `TM-` | 写进它那一组用例的分组说明里（测试类的说明、文件头的分组说明） |
| 测试覆盖项 `TCOV-` | 写进覆盖它的那条用例处（用例的说明里，或那条用例上方的一行注释） |
| 测试用例 `TC-` | 写进这条用例的名字里（`test_TC_30_text_request_counts_exactly`）；评测用例写进 `prompt.md` 的正文（「用例 TC-30」） |
| 测试规程 `TP-` | 写进那一组的分组说明、或执行顺序的说明里 |
| 测试数据项 `DATA-` | 写进取它的那处：常量名或字典键 `"DATA-9"`；文件类样本另写明「按 DATA-9 的字节造」 |
| 测试环境项 `ENV-` | 写进用到它的那处：环境那一段的说明里、运行条件的说明里 |
| 决策 `DEC-` | **只在成品与产出有出入时写**：成品里写明是照哪条决策这么落的、差在哪；两边一致就不写 |

- **写法**：连字符在成品里写不成，就换成下划线（`TC-30` 写成 `TC_30`）；数字照原样、不补零（不写 `TC_03`、`TC_030`）。就这两种写法，别的一种不认——认宽了，拿着编号搜反倒要多试几种写法。
- **六类都要出现**：模型、覆盖项、用例、规程、数据项、环境项的每一条，在成品里至少出现一次。**一条覆盖项写一个号，不写成范围**——`TCOV-26～TCOV-31` 这样写，中间那几个就搜不到了。
- **成品里的编号不重编**：文档里是几号就写几号。落成时发现条目对不上，回文档改，不在成品里另起一套。
- **名字照英文名取**：成品里的函数名、类名、常量名从英文名来，不另取一批。
- **落成之后回来补一句**：把测试用例规格说明的「成品落点」表填上（见第四节），再跑一遍落成对照（命令见 `SKILL.md`）。落成是另一件事、另一步做的；这里只把两边对上号。

## 三、测试模型规格说明

一个任务往往建多个测试模型——每门选定的技术建各自的模型。每个模型把这六栏写齐，一份文档里按模型分组。

- **唯一标识符**：照第二节由脚本给编号（`TM-…`），用于把这个模型与所有其他模型区分开。生存周期内不改，因为它承担追溯。
- **英文名**：照第二节取，紧挨着「唯一标识符」写。
- **目标**：写这个模型关注测试项的哪一部分。测试模型只描述测试项的某一个方面，不写全貌，这一栏就是把「是哪一个方面」点明。
- **风险等级**：高风险的模型要建得更细、导出的覆盖项取全，低风险的可取子集，所以这一栏是「做到什么程度」的承接点。等级照主流程第 0 步判下来的风险信息写，不随手标高低。
- **测试策略摘要**：写清三件事——用了哪几门测试设计技术、它们怎么组合、测试完成准则（要求的覆盖率）是什么。组合要写明分工：谁为谁提供输入、哪门技术补哪类缺陷。这是依据落地的地方，不要空着——写不出依据，说明第 0 步那几样开工输入还没定下来，回那一步定完再写。
  - 「测试是自动化执行还是人工执行」这一句不写在这份里：执行方式写在测试规程规格说明的「执行器」栏，模型这份不重复一遍。
- **测试模型**：把模型本体展示出来。可用自然语言、形式化语言、表格、图形或其他适当格式，也可直接引用已有的工作产品（例如源代码）。用哪种表示法取决于所需的测试覆盖率；模型的具体形态由选定的技术反推（状态转移测试建状态图、判定表测试建判定表，见 `技术/状态转移测试.md`、`技术/判定表测试.md`），不自由发挥。
  - **判定表当模型时，每条规则要能单独读出来**：表头只写「规则 N」，编号本身不说明任何事——表后面跟一份清单，一个编号一行，写清这条规则管哪些条件取值、落到哪些动作；合并列写明它覆盖哪几种组合，不可行的规则写明为什么不可行。文档别处引「规则 N」时，读者要在同一份文档里查得到（详见 `技术/判定表测试.md`）。
- **可追溯性**：写这个模型取自测试依据的哪一部分。落点是文档末尾的「依据 → 模型」对应表（格式见第八节），不另设栏目，也不另建追踪矩阵文件。

## 四、测试用例规格说明

分五块写：测试覆盖项清单、测试用例、「覆盖项 ↔ 用例」对应表、覆盖率自检、成品落点。一条覆盖项导出多少条用例，由测试完成准则（要求的覆盖率）和该覆盖项的风险等级定——准则低于 100% 时并非每条覆盖项都要有用例，高风险覆盖项通常多导。

### 测试覆盖项

从测试模型应用选定技术导出。清单里每条覆盖项写这几栏：

- **唯一标识符**：照第二节给编号（`TCOV-…`），用于与其他覆盖项区分。生存周期内不改，它承担追溯。覆盖项数量过多或变动性过高、编号难以为继时，可以改用工具建立测试用例与测试模型之间的对应关系，并在文档里说明用的是哪种方式。
- **英文名**：照第二节取，紧挨着「唯一标识符」右边新起一栏。
- **描述**：写这个覆盖项是什么——按导出它所用的那门技术，预期由测试用例覆盖的那个属性。例如某等价类是有效类还是无效类、某条状态转换、判定表里的某条规则、分类树上的某个类别。附带的信息也写在这一栏。
- **风险等级**：完成准则低于 100% 时按它挑子集；高风险覆盖项还要多导用例（见本节开头）。这一等级随导出的用例带下去，测试规程排执行顺序时取用。等级照主流程第 0 步判下来的风险信息写，不随手标高低。
- **可追溯性**：写这条覆盖项出自哪个模型——至少填模型编号，必要时写到模型里的哪个元素（哪条状态、哪条转换、哪条规则、哪个类别）。覆盖项清单里留一栏放它就行，不另建追踪矩阵文件。

### 测试用例

每条用例写这几栏：

- **唯一标识符**：照第二节给编号（`TC-…`），用于与其他用例区分。生存周期内不改，它承担追溯。
- **英文名**：照第二节取，紧挨着「唯一标识符」右边新起一栏。
- **目标**：写这条用例的测试重点与目标，一句话说清它要验证什么。这一栏通常直接当用例的标题用，例如「验证传送带不移动时盖板的锁定功能」。
- **风险等级**：需要时写，照它覆盖的那条覆盖项的风险等级写，同一条覆盖项导出的多条用例通常共用同一等级。测试规程排执行顺序时取用这一栏的等级。
- **可追溯性**：写这条用例覆盖了哪些测试覆盖项。这一项不单独设栏目——由文档末尾的「覆盖项 ↔ 用例」对应表承接（格式见第八节）。
- **前置条件**：写执行这条用例所需的测试环境状态、测试数据，以及与执行相关的全部特殊约束条件。例如执行启动前测试项应处的状态，包括要准备好的测试数据、当前所处的界面或页面。可以写成明确的状态描述，也可以写「先执行某某用例」，那条用例会把前置条件摆好。多条用例共用的环境在测试环境需求里统一说明一次即可，不必逐条重复。凡用到测试数据或测试环境要素，写编号指代（「样本 DATA-7」「ENV-2 那台机器」），不重述内容——一份内容是……的文件、一台装了什么版本的机器，都写在测试数据需求与测试环境需求那两份里，这里只说编号。
- **输入**：规定测试项达到「可以把预期结果与实际结果进行比对」的状态所需的各项操作。详细程度宜与执行人员的知识水平相适应；操作之间有先后关系的要写明关联关系（例如时序关系）；必要时把各项操作依次编号。输入可以是数据，也可以是事件（例如按钮点击）；数据可以直接给具体数值，也可以按名称指代（如常量表、事务文件、数据库、普通文件、终端报文、内存驻留区、操作系统传递的参数值）。已经列进测试数据需求的数据一律按编号指代——写「按 DATA-3 取」，不在这里重述那份数据长什么样。
- **预期结果**：写测试项在满足前置条件、接收指定输入之后，应产生的预期输出和运行行为。需要校验的输出逐个给预期值，必要时带允许误差范围（如响应时间这类运行行为）。还可写把预期结果与实际结果进行比较所需的各项操作。

### 覆盖率自检

第四块，第 6 步自检时填：一门选定的技术一行，写这一门（这一档）识别出多少条覆盖项、其中多少条已被用例覆盖、算出来的覆盖率是多少，与完成准则对这一门的要求并排列出来。

| 技术（档位） | 覆盖项编号 | 覆盖项总数 T | 已被用例覆盖 N | 覆盖率 N÷T | 完成准则要求 |
|:---|:---|:---|:---|:---|:---|
| 状态转移测试（全转移） | TCOV-1～TCOV-8 | 8 | 8 | 8÷8＝100% | 100% |
| 等价类划分 | TCOV-9～TCOV-15 | 7 | 7 | 7÷7＝100% | 100% |

- **技术（档位）**：一行一门选定的技术；选了档的把档写在括号里，没有覆盖档位的那几门只写技术名。同一门技术建了多个模型的合在一行；同一门按两档各算一遍的写两行。
- **覆盖项编号**：这一门（这一档）识别出来的、计入分母的覆盖项编号，连续的写成范围（`TCOV-1～TCOV-18`）。**判为不可行、已剔除的不列**——剔除原因照旧写在覆盖项清单的描述栏，不在这里重说一遍。
- **覆盖项总数 T**：这一栏列出来的条数。写之前拿这门技术的算式核一遍（见[覆盖率与完成准则](覆盖率与完成准则.md)第二节），核不上回第 3、4 步补。
- **已被用例覆盖 N**：这些编号里，对应表「覆盖它的用例编号」栏非空的条数。
- **覆盖率 N÷T**：写成 `N÷T＝xx.x%`；保留一位小数，整数不写小数。
- **完成准则要求**：照测试模型规格说明的「测试策略摘要」里这门技术那一条抄；两处不一致时改这一处。不到要求时先回第 4 步补用例，确实覆盖不了的按不可行项剔除并记原因，补完这一块跟着改。

### 成品落点

第五块，落成之后回来填：这批用例落成的**成品**（可跑测试、评测用例）放在哪、落的是哪一批条目。

| 成品 | 落的是哪些条目 |
|:---|:---|
| `tests/<技能名>/test_<脚本>.py` | TC-1～TC-29 与它们的覆盖项、TM-1～TM-4、TP-1～TP-4、DATA-1～DATA-17、ENV-1～ENV-9 |

- **成品**：写路径，一份成品一行；路径按跑检查时的当前目录算（一般就是项目根）。成品还没落成就写「还没落成」——**这一块不许整个不写**：写了这一块，落成的人才知道回来补哪张表。
- **成品不止一类时，按规程分批写**：两行的条目栏各自只写它那一批的规程编号与用例编号，别交叉。分法写在测试规程规格说明的「各批落到哪」那一块，这里写的是具体落在哪个路径、落了哪几号。
- **落的是哪些条目**：这一批成品里落了哪几号，可以写成范围；这一栏是给人看的，成品里要一条一个号写全（见第二节「落成约定」）。
- **验收**：落成之后跑一遍 `python scripts/check_landing.py <产出目录>`——不给成品路径时它就从这张表里取，六类编号在两边对不上会报出来。落成之前这笔账没结，产出与成品各说各的，拿编号搜不过去。

## 五、测试规程规格说明

一条规程把一组测试用例按执行顺序串起来，带启动动作与收尾动作。逐栏写：

- **唯一标识符**：照第二节给编号（`TP-…`），用于区分不同的测试规程。生存周期内不改，它承担追溯。
- **英文名**：照第二节取，紧挨着「唯一标识符」写。
- **目标**：写这条规程的重点或目标，一句话，通常直接当标题用，标题以规程编号起头（`TP-1 登录的正向路径`）——自检按标题的第一个词认这条规程从哪儿起、到哪儿止，前头加了「一、」这类序号就认不出来了。
- **风险等级**：需要时写。跨规程的执行先后写进「与其他规程的关系」栏。
- **执行器**：写这条规程由什么跑起来，取值三个——`脚本`（不用模型：跑命令、比退出码与盘上的文件就有结论）、`控制器`（要模型跑，但模型只照规则读盘上的东西、按规则分流，不派子代理；整条规程在同一轮对话里跑完）、`子代理`（要模型跑，而且要派子代理真去执行，会花掉子代理额度）。取值后面可以带一句括号说明。**每条规程都要填**——它是文末「各批落到哪」那张表的依据。
- **改动文件**：写跑这条规程会不会改动测试项，取值两个——`只读`（规程执行当中只读测试项、比一比结果，不改它）、`会写`（规程执行当中会改动测试项：写它的文件、推进它的状态）。一条规程里只要有一处会写，整条标「会写」。**为跑这条规程而做的环境与数据准备不算**：建临时目录、摆样本、清场、重建夹具都是搭场子，照旧写在「启动」栏里；收尾那一栏写的复位动作也不参与判定，那一栏说的是「复位成什么样」。判据一句话：规程执行当中，测试项有没有被动过？
- **启动**：写执行本规程中的测试用例之前必需的准备动作——通常就是把第一条用例的前置条件摆好所需的那几步操作。凡用到测试环境或测试数据要素，写编号指代（「ENV-1 就位」「按 DATA-2 备好样本」），不重述内容。
- **有序执行测试用例**：按执行顺序排列本规程要跑的测试用例，可依次编号。这个列表可以是对测试用例的引用，也可以是测试用例的复制列表。可定义这个顺序允许变动的程度，即哪些位置可以调换。规程中一条或多条用例的执行结果没有为随后的用例准备好前置条件时，可在两条之间添加准备前置条件的操作。这一类动作写在本栏里，每条动作写在它服务的那条用例前面。
- **与其他规程的关系**：写这条规程与其他规程存在的依赖关系——哪几条要在它之前执行、哪几条与它同时执行、哪几条在它之后执行。
- **停止与结束**：写有序停止执行本规程所需的操作，以及规程执行完毕后所需的收尾操作（例如终止记录、把测试数据库复位）。

### 各批落到哪

测试规程规格说明的末尾另起一节，标题写「各批落到哪」，把这套规程按落点分批：

| 批次 | 规程 | 执行器 | 落到哪 | 用例目录名 | 说明 |
|:---|:---|:---|:---|:---|:---|

- **分批准则是判据落在哪**：一条规程的全部用例，判据落在命令、退出码、盘上的文件上，跑一遍就有结论的，归一批，落成能跑的测试代码；判据要读一轮模型的行为（跑了哪条命令、派了几个代理、写了什么）的，归另一批，落成评测用例。「执行器」那一栏里的「控制器」与「子代理」都归后一批——两者粒度不同，不是对不上。
- **分界必须落在规程边界上**：不许把一条规程劈成两半分给两处。劈开了就回第 5 步重排规程，让每条规程整体归一处。
- **只落一类也不空着**：表里一行，写明全部规程落同一处。
- 落成评测用例的那一批，**用例 id 带上规程编号前缀**，前缀与位次一起编进用例目录的名字：`tp01-01-TC-1-fix_only_what_should_change`。四段各是什么：
  1. `tp<规程号两位>`——这条用例归哪条规程，照本行「规程」栏那条填。一位数前面补零：写 `tp01`，不写 `tp1`。
  2. `<规程内执行位次两位>`——这条用例在该规程的「有序执行测试用例」栏里排第几，就写几，一位数前面同样补零。**位次按那一栏的次序数，不按用例编号的大小**——按前置与后置条件排出来的次序与编号序本来就可以不一样。
  3. `TC-<用例编号>`——照第二节的「落成约定」写：`TC-42`，大写、不补零。
  4. `<英文名>`——照第二节取的那个英文名，一字不差地抄过来。
- **一条规程一行，按执行顺序列全。**「用例目录名」这一栏里，每条落成评测用例的规程占一行，把该规程全部用例的目录名按执行顺序列出来，顿号隔开。少一条、多一条、位次写错、重一条，都算错。落成可跑测试的那一批（「执行器」栏是`脚本`的行）这一栏空着。
- **为什么这么编**：评测工具按目录名的字母序跑，名字排成什么顺序就跑成什么顺序；`--case` 接的也是目录名。用例编号本身不补零（第二节），于是 `TC-10` 会在字母序里跑到 `TC-2` 前面。执行顺序要单独编一段，两段数字都定成两位，字母序才等于「先规程号、再规程内位次」。
- **超过 99 条时整套一起改三位**：规程数或用例数到了三位数，两段位次都改成三位。不许有的两位有三位——混着写字母序就错位。
- **位次与目录名都由脚本打**：写这一栏之前跑一次 `python scripts/issue_ids.py <产出目录> --case-dirs`，照它打出来的抄（跑法与时机见 `SKILL.md`）。手数「排第几」是这条链上唯一一处会数错的地方。
- **同一条用例被两条规程排到时**落成两个目录，各带自己那条规程的前缀——名字不一样，字母序里也各归各的规程。盘上的目录名与文档里写的一字不差；报告里那一列怎么显示是工具的事。文档里的编号仍要照第二节「落成约定」在成品里原样出现一次，[落成对照脚本](../scripts/check_landing.py)认的只有那一种写法。

## 六、测试数据需求

一条数据项一行，写这四栏。测试数据需求描述的是执行测试规程所需的数据：

- **唯一标识符**：照第二节给编号（`DATA-…`），用于区分不同的测试数据项。
- **英文名**：照第二节取，紧挨着「唯一标识符」右边新起一栏。
- **描述**：写每个测试数据元素的特定名称和所需值或值的范围。某项数据需要匿名化或以其他方式处理时，一并写明。
- **重置需求**：写这条数据项在测试过程中要不要复位、怎么复位。要复位的写清复位动作是什么；不要复位的写「不需要」。判断方法：跑完用这条数据项的用例之后，下一条用例的前置条件还成立吗——不成立就要复位。这一栏不留空，不要复位的写「不需要」也算填了。

有意不收这三栏：**责任**（谁负责使测试数据可用）、**需要的周期**（什么时候要用、用多久）、**归档或清除**（测试完成后归档或清除的时机和方式）。这三样只服务于人的排期与职责分工——谁去备数据、几号到几号用、跑完谁去清，本技能的产出是给模型读着建测试用例、执行测试用的，用不上。这是本技能有意做的剪裁，是决策，不是漏掉。

「归档或清除」还管着另一件事——跑完要清掉什么。那件事已经有落点：写在测试规程的「停止与结束」栏里，不在这里另设一栏。

**重置需求**不收进来过——它和上面三样不是一类，前一轮把它一并砍了。它回答的是「跑下一条用例之前要不要把数据复位」，由测试本身的设计决定，设计阶段就定得下来，也直接决定用例怎么排、跑完做什么。收。

## 七、测试环境需求

一项环境项一行，写这四栏：

- **唯一标识符**：照第二节给编号（`ENV-…`），用于区分不同的测试环境项。生存周期内不改，它承担追溯。
- **英文名**：照第二节取，紧挨着「唯一标识符」右边新起一栏。
- **测试环境项**：识别执行测试规程所需的测试环境的每个要素。要素要能支撑规程执行前的设置、执行中和执行后的各项活动。环境项不能完全反映运行（生产）环境时，宜说明它代表或偏离运行环境的程度。例如：硬件、中间件、软件（如特定系统或浏览器）、与其他系统和接口系统的接口、外围设备（如打印机）、移动设备（如手机、平板电脑）、通信方式、工具、信息安全性、场地（如房间大小、桌椅和背景噪音水平）、配件（如特别预先印好的纸张表格），也可按需另立类型。
- **描述**：把环境项写到能照着实施的详细程度——精确命名的特定版本和配置的硬件或软件；测试过程中需要在特定时间点运行以支持测试的批处理作业也列出来，例如要求每晚运行一套常规批处理作业以反映生产环境。

第 0 步判下的**测试运行环境**是这一节的第一批环境项：头两条一条写测试规程在哪儿跑、一条写被测那侧在哪儿执行，**两条默认都是本机**；要换到别处（另一台机器、一个容器、一台设备）就写在那一栏上。这两条是技能判的，来源记 `技能定的`；其余各条再按用例与规程的需要往外补。

有意不收这两栏：**责任**（谁负责搭建并使环境项可用）、**需要的周期**（什么时候要用、用多久）。理由同第六节：这两样只服务于人的排期与职责分工，本技能的产出是给模型读着建测试用例、执行测试用的，用不上。这是本技能有意做的剪裁。

## 八、对应表格式

两张对应表承接可追溯性，都用 Markdown 表格，各自附在所属文档末尾。

**「依据 → 模型」表**，附在测试模型规格说明末尾：

| 依据的出处 | 模型编号 | 说明 |
|:---|:---|:---|

- 依据的出处：写这段依据在哪里——依据文档名加条目号或段落名（如需求编号、规格说明里的哪一节）。
- 模型编号：照这段依据建出来的模型的编号（`TM-…`）。一个模型照多处依据建就写多行，一行一处依据。
- 说明：这个模型取自这段依据的哪一部分、覆盖它的哪个方面。

**「覆盖项 ↔ 用例」表**，附在测试用例规格说明末尾：

| 覆盖项编号 | 覆盖项描述 | 覆盖它的用例编号 |
|:---|:---|:---|

- 覆盖项编号：`TCOV-…`。一条覆盖项一行，全部覆盖项都要列上。
- 覆盖项描述：一句话说清这条覆盖项是什么，与覆盖项清单里的描述一致即可——不看清单也读得懂这张表。
- 覆盖它的用例编号：把覆盖它的用例编号都写上（`TC-…`，多条用顿号分开）。**这条覆盖项还没有任何用例覆盖时，这一栏留空——空着的行就是覆盖率自检要看的地方**，一眼看得出缺哪些。

测试规程不另出对应表：规程的「有序执行测试用例」栏本身就是测试用例编号的有序列表，用例到规程的追溯靠它。

两张对应表都不带英文名：名字在条目自己的定义处给一次就够，这里是按编号对上号的地方，多抄一遍只会多一处能写岔的地方。

## 九、决策依据

其余五份记的是**结论**——模型长什么样、覆盖项有哪些、用例怎么导的。这一份记**过程**——每处决策当时摆着哪几种做法、凭什么取了这一种。**分两块写**，块名与装法见下一小节；一条决策一行，两块里都按定下来的先后排：

| 唯一标识符 | 在哪一步 | 决定 | 考虑过的其他做法 | 依据 | 依据的来源 |
|:---|:---|:---|:---|:---|:---|

- **唯一标识符**：照第二节给编号（`DEC-…`）。这份文档不给英文名（见第二节）：它记的是过程，不落成任何对象。
- **在哪一步**：这条决策在主流程第几步定的，写「第 0 步」到「第 6 步」。后面的条目步骤号不会比前面小——回走那几次除外，回走时照实写回去的那一步。**落成那一轮定下的事写「落成」**（用例落成时换掉了哪几处、成品按什么落的）——成品落成不在主流程那几步里，别硬编一个步号塞进去。
- **决定**：定了什么。一句话说清，不翻别的文档也读得懂。
- **考虑过的其他做法**：当时摆在桌上的另外几种做法，各自为什么不取。**这一栏是这份文档的用处所在**——只写选中的那个，等于把过程抹掉，看不出究竟比过没有。确实只有一种做法可想，写「只此一种」并说清为什么。
- **依据**：凭哪一条定的。依据是读出来的事实，就写出自哪里（测试项里的哪一处、用户答的哪一句）。
- **依据的来源**：只填三个值之一——`技能定的`、`从测试项推的`、`用户给的`。**四样开工输入里哪几样用户没给，就是靠这一栏看出来的**：同一段流程里哪些决定有用户依据、哪些是技能自己判的，一眼分得开。

### 分两块写

块名照下面写死（脚本认这两个名字），两块的表头一模一样：

| 块 | 装哪几条 | 能不能改 |
|:---|:---|:---|
| `## 用户决策` | 「依据的来源」栏写着 `用户给的` 的那几条 | **可以直接改** |
| `## 模型决策` | 其余几条（`技能定的`、`从测试项推的`） | 只增不改 |

每条只归一块：「依据的来源」栏只填三个值之一，哪一行该归哪一块是确定的，脚本也按这个查。

**「用户决策」那一块放在前面，为的是让用户一眼看到自己拍板的那几条、随手就能改。**这一块可以直接改——旧的样子 git 里看得到，不必照「只增不改」另起一条写订正；改完由用户说一声，把其余五份里跟着变的地方一并改掉（比如风险等级改了，测试模型规格说明的「风险等级」栏与各条覆盖项的等级都要跟着动）。块首写一句把这些说清，照这个意思写：

> 这几条是你拍板的——「依据的来源」栏写着 `用户给的`。可以直接改，旧的样子 git 里看得到；改完让 agent 把其余五份里跟着变的地方一并改掉。

「模型决策」那一块开头也写一句，写明它只增不改。

**一条用户决策都没有时，第一块整块不写**，只写「模型决策」。正常情形不会这样：风险信息是向用户要的，至少能记下一条。

### 记哪些决策

判据是：**这一步有没有在几种做法里挑**。有就记，没有就不记。

要记的：

- 第 0 步：测试完成准则照什么口径定（有测试计划照取、没有按默认 100%）；风险等级是怎么判出来的。
- 第 1 步：四个决定各记一条——选哪几门技术、怎么组合、各建什么模型、做到什么程度。
- 第 2 步：模型建到多细；同一个对象能建成两种形态时取的哪一种。
- 第 3 步：覆盖项取全还是取子集；三门带档位的技术各选了哪一档、为什么。
- 第 4 步：一对一方式还是最小化方式；输入值在哪几个候选里挑的。
- 第 5 步：规程按什么排的序；执行器与改动文件是怎么判的；这套用例分几批落成、按什么分的；测试数据项与测试环境项收到哪一层。
- 第 6 步：覆盖率不够时补了哪些、按什么补的；判为不可行项剔除的是哪几条、凭什么。
- 落成：用例落成时换掉了哪几处（环境条件、外部依赖、跑不起来的步骤）、成品按什么落的（哪些落成可跑代码、哪些落成评测用例、怎么分的）。没动过的就不记。

不记的：照本文填栏目、照技术文件导出覆盖项这一类只有一种做法的动作——那是执行，不是决策。技能已经定死的事（模型形态由技术决定）同理，不占条目。

### 只增不改

**「模型决策」那一块里，旧条目一个字不改。** 后面发现前面定错了、或者情况变了要换口径，不动那一条，新增一条，在「决定」栏里写明订正的是哪一条、为什么改。

回走（第 6 步发现覆盖率不够、回第 4 步补用例）也一样：补出来的决策接着往后面编号，不回填到前面去。往已有的产出目录里接着做时，先跑一次 `python scripts/issue_ids.py <产出目录> DEC- --count <这批要几条>`，照它发的号往下写。

**「用户决策」那一块不吃这一条**——那几条是用户给的输入，不是判出来的结论，可以直接改。旧值 git 里看得到，不必在文档里留一条订正链：链子会把「现在是什么」埋到文件末尾，而用户要的正是「现在是什么」。改动的记录交给 git，不在这份文档里体现。

**为什么这么严**：这份文档的用处就是让「当时怎么想的」留得下来，好让人看出哪一步判歪了、好在哪一处把技能改对。改了旧条目，改的正是要看的那一段——留一份被修过的过程比不留还糟：它看着像过程，其实已经是结论了。这一条管的是判出来的那几条——模型怎么建、覆盖项取全没有、用例怎么导的；用户给的输入不归它管，那几条要能改，风险信息变了整套产出才调得动。

脚本按这个查：编号必须是 1 起连号（两块合起来数），中间缺号或最大号大于行数，都会被报成「只增不改」被破坏。两块分得对不对也查：「用户决策」那一块里混进别的来源、`用户给的` 那几条留在「模型决策」那一块里、决策表不在这两块里，都报错。

## 十、实施方案规格说明（第七份，按需产出）

前九节定的是六份**通用稿**：它们不认任何一种测评方案、不认任何一种具体环境，可以原样拿去当代码或技能的测试依据。这一节定**第七份**——把六份落成能跑的东西的那一份。

**什么时候产出**：两种入口，见 `SKILL.md` 的「只出实施方案那一份」——随六份一起出，或者手上已有六份、另起一次会话只出这一份。

| 定什么 | 怎么定 |
|:---|:---|
| 文件名 | `Implementation Specification.md`——**不带方案名**。方案名只出现在文档内部的小节标题里 |
| 整体结构 | 一句导语 ＋「一、通用稿的编号落到哪」＋ 每个方案一节 |
| 方案节的节号 | 接着「一」往下排：「二、方案：skill-up」；将来比第二个方案就是「三、方案：<那门方案的名字>」 |
| 方案节的三块 | 「说明」「可跑配置（YAML 原文）」「怎么跑、报告落在哪」——三块的标题里各含这三个词 |
| 编号 | **一个都不新发**，只引用前六份的。引用写编号，不重述内容 |
| 与六份冲突时 | 以这一份为准，导语里写明 |
| 用词 | 六份里不许出现的词（方案名、配置文件名、具体环境名），这一份里正该出现——`scripts/check_docs.py` 不吃那张表 |

**这样分是为了六份能单独用。**六份可以拿来当代码或技能的测试依据直接往下走，不必知道有没有第七份；出实施方案可能是另一步、另一次会话的事。

### 导语

第一个 `##` 之前那一段。写清三件事：这一份把六份通用设计稿落成能跑的东西、六份说的是「要什么」这一份说的是「用哪个、怎么摆」、两边冲突时以这一份为准。再写一句方案按节分，将来比别的方案在同一份里另起一节，六份一个字不用动。

### 一、通用稿的编号落到哪

一张表，把六份里定义过的每一条 `ENV-…`、`DATA-…` 对到本方案里的具体落点：

| 通用稿的编号 | 本方案里落在哪 | 说明 |
|:---|:---|:---|
| ENV-6 | 每条用例各建一个的临时工作区 | 跑完就删，重试与迭代各起一个 |
| DATA-15 | `cases/tp05-01-TC-7-file_blocked_reports_where/fixture/只读样本.md` | 没有写权限的文档样本 |

- **通用稿的编号**：一条一行，`ENV-…` 与 `DATA-…` 分开排。**六份里定义过的每一条都要在这一列出现**——这一份里用不上的，照旧列一行，在说明栏写清为什么用不上。少一条就报错。
- **这一列的号照盘上那六份抄，不自己编**：上面表里的 `ENV-6`、`DATA-15` 只是示例的号（那是 `evals/plain-language/` 那套的），换一套产出就是另一批号。号由 `scripts/issue_ids.py` 按产出目录往下发（见第二节），这一份不新发任何号。
- **本方案里落在哪**：写具体落点——哪个配置文件的哪一段、盘上哪个路径。写不出具体落点，说明那一条还没落成，别含糊过去。
- **说明**：一句话说清这条落点管什么。两边不一致的地方（哪一条落不成原样、偏在哪）写在这一栏。
- **这一列里的编号都要指得到定义处**：通用稿里没有的号（`ENV-9` 这种）写了一律报错。改通用稿的时候对着这张表看：哪一条加了要求，这一节就要跟着补一个落点。

**「落到盘上哪个路径」那一栏按什么算**：产出目录与落成的成品**不同层**。产出目录（那七份文档）是**评测材料根下的一个子目录**；落成的配置、用例目录、夹具、报告放在它的**上一级**，与产出目录并列。

```
evals/plain-language/         ← 评测材料根：落成的东西住这儿
├── eval.yaml                 运行一的配置
├── cases/                    用例配置，一条一个 yaml
├── fixtures/                 夹具
├── results/                  报告（不进 git）
└── test-case-design/         ← 产出目录：六份通用稿 ＋ 第七份实施方案
```

所以那一栏写的是**从评测材料根算起**的相对路径（`eval.yaml`、`cases/…`），不是从产出目录算。

### 每个方案一节

标题写「<节号>、方案：<方案名>」。节里三块，标题里各含下面三个词，脚本按它们认：

**说明**——散文写清这套方案怎么落地：

- 跑几次，每次跑哪几条规程、为什么这么分
- 工作区怎么来：谁建的、里面进哪几样东西、跑完怎么清
- 判据分几层、怎么落到这套方案的判官上
- 消息与上下文怎么渲染（用户的输入怎么拼、技能或配置怎么进上下文）
- **跑不了原样的那几条**：通用稿是按测试项写的、不认方案；落到这一套方案上，总有几条没法照着原样跑。一条一条写明是哪条、偏在哪、为什么。**跟通用稿一致的那几条也点一句「与设计稿一致，没有出入」**——这一段是跟通用稿的逐条对照，不是折扣清单。它管的是：读判据的人分得清一条用例判不过是环境摆法造成的，还是被测的东西真有问题；通用稿里本来就写着不一样的不算折扣（比如某一条本来就不装技能、本来就走两轮）。**事实从同目录的 `references/评测方案/<方案名>/capabilities-and-limits.md` 里取，不靠实测**——那份里写着的（钩子一律不生效、工作区不是 git 仓库时差集被静默省掉、装技能跳过 `evals/` 子树）直接引；那份里没写到的，标成「待确认」，不写成事实

**可跑配置（YAML 原文）**——**以 YAML 原文贴出来，不是散文化地写「应该配什么」**。每一块前面标好它落到盘上哪个路径；把这几块拷到那些路径上就能跑。每块都要 `yaml.safe_load` 得过。

**怎么跑、报告落在哪**——命令行（路径写全）、输出目录、哪些东西不进 git。跑之前怎么先验一遍配置也写在这里。

### 六份里不许出现的词，这一份里正该出现

`skill-up`（方案名）、`eval.yaml`／`case.yaml`（那个方案自己的配置文件名）在六份通用稿里一个都不许出现，在这一份里正该出现；`SKILL.md` 的「六份里不许出现的东西」那张表里另列的几个具体环境名同理——**那张表是这些词的唯一出处**，这里不再抄一遍。

**脚本按这个分两套查**：六份吃禁用词表，这一份不吃；这一份另查骨架、三块、YAML、编号对账，以及六份那份表里另外半截——不带技能的出处（`references/`、`GB/T`、`TD1`～`TD4`）。

**这一份不进 `DOCS`。**`check_docs.py` 里那份名单既是「缺这份文档」的检查表，也是「哪些号定义过」的全集，`issue_ids.py` 发号拿它当基准。第七份不定义任何编号、只引用前六份的，进了那份名单，它那张对账表的表首格会被当成定义处，缺这份文档时还会误报。
