# 测试用例设计

本技能内容基于 GB/T 38634 系列标准的修订征求意见稿整理。

本技能自包含：不要联网去搜这份标准，也不要翻本仓库里的标准存档——搜到的多是二手转述，与标准正文对不上，翻存档也只会把上下文撑爆。技能里没覆盖到的细节，直接问用户，不猜也不翻。

产出六份 Markdown，写入用户指定的目录：

| 文档 | 文件名 |
|:---|:---|
| 测试模型规格说明 | `Test Model Specification.md` |
| 测试用例规格说明 | `Test Case Specification.md` |
| 测试规程规格说明 | `Test Procedure Specification.md` |
| 测试数据需求 | `Test Data Requirements.md` |
| 测试环境需求 | `Test Environment Requirements.md` |
| 决策依据 | `Decision Basis.md` |

前五份记结论，最后一份记过程——每处决策当时摆着哪几种做法、凭什么取了这一种。**这一份不是可选项**，没有它，用户只看得见你定了什么，看不见你怎么定的，也就没法在哪一步把技能改对。写法见 `references/文档模板.md` 第九节。

**只有文件名是英文的，正文一律写中文**——标题、栏目、表格、说明都不例外。别把「英文文件名」当成「英文文档」，产出照旧是中文。中文说明文件里提到这几份文档时，用上表左列的中文名。

目录由用户或调用本技能的上位技能给出；没给就先问，不猜默认路径；目录不存在就建。

**产出只有那六份文档，到用例与规程产完为止。**不写可跑的测试代码，不建工程里放测试代码的目录，也不把用例落成任何能执行的形式；不执行测试，不出事件报告。工程里另有放测试代码的地方与命名约定（`tests/` 之类），那是那个工程自己的事——不因为它在，就顺手往那儿写一份；要落成能跑的代码，是上游或另一个技能的活。用户点名要代码也不做：回一句「这件事不在本技能范围内」并指出去哪儿做，然后照旧出文档。

## 主流程

八步按顺序走，中途允许回走。表里的「选中的技术文件」，指第 1 步选定的那几门技术各自在 `references/技术/` 下的那一份；「落盘」一栏写这一步做完要把哪份文档写进产出目录。

| 步 | 做什么 | 读哪份文件 | 落盘 |
|:---|:---|:---|:---|
| 0 | 定开工输入：测试依据与风险信息向用户要，测试完成准则按测试项自己定 | `references/覆盖率与完成准则.md` 第三、四节 ＋ 下文的「第 0 步」 | 决策依据（完成准则照什么口径定、风险等级怎么判出来的） |
| 1 | 定技术方案：选哪几门技术、怎么组合、各建什么模型、做到什么程度。四个决定每个都要写出依据 | `references/技术选型与组合.md` ＋ `references/流程.md` | 决策依据（四个决定各一条） |
| 2 | TD1 建测试模型：分析依据，按选定技术确定模型表示方法，建模型，记录依据与模型的可追溯性 | `references/流程.md` ＋ 选中的技术文件 ＋ `references/文档模板.md` | 测试模型规格说明、决策依据（模型建到多细） |
| 3 | TD2 定测试覆盖项：对模型套用技术导出覆盖项，按风险定等级，记录可追溯性 | 同上 | 决策依据（覆盖项取全还是取子集、带档位的选了哪一档）——覆盖项并进下一步那份 |
| 4 | TD3 导出测试用例：定前置条件、选输入值、定预期结果，记录可追溯性 | 同上 | 测试用例规格说明、决策依据（一对一还是最小化、输入值怎么选的） |
| 5 | TD4 编测试规程：给用例排序，识别测试数据和环境需求，记录可追溯性 | `references/流程.md` ＋ `references/文档模板.md` | 测试规程规格说明、测试数据需求、测试环境需求、决策依据（规程按什么排序、数据项与环境项收到哪一层） |
| 6 | 自检：算覆盖率，判断是否达到完成准则 | `references/覆盖率与完成准则.md` | 决策依据（补了哪些、剔了哪些、凭什么）——缺的回第 4 步补，并改掉盘上那份 |
| 7 | 终检：核对六份都在产出目录里，把机械项跑到零错 | — | — |

**每步的完成标准：该步「落盘」一栏的文档已经写到产出目录里。** 每步做完随即落盘，不留到最后一起写——中途上下文若被压缩，读盘上的文档就能接着走，不必重做。

**决策依据随做随记，而且只增不改。** 判据是「这一步有没有在几种做法里挑」：在挑就记一条，写清当时摆着哪几种、各为什么不取、凭什么取了这一种；只有一种做法的动作（照模板填栏目、照技术文件导出覆盖项）不记。**旧条目一个字不改**——后面发现前面定错了，新增一条写明订正的是哪条，原来那条留着；回走补出来的决策接着往后面编号。

只写结论不写过程，等于把判断留在你自己脑子里：用户只看得见结果，看不见你在哪一步判歪了，也就无从在哪一处把技能改对。**别为了「看起来干净」回头去修旧条目**——被修过的过程比不留还糟，它看着像过程，其实已经是结论了。栏目与写法见 `references/文档模板.md` 第九节。

写产出时照 `references/文档模板.md` 的栏目填，一个栏目不缺、也不多造；产出文档里只写测试内容，不把技能文件里的节号与出处带出去。

**每条条目除编号外还要一个英文名**，紧挨着编号写（决策依据那份不给）。它是这条条目落成代码时的名字核——下游拿它拼函数名、类名、变量名，照抄产出里的，不每次现取一批新的。形制与取法见 `references/文档模板.md` 第二节。**这一栏不改变开头那条边界**：产出照旧只有那六份文档，写不写代码不在这份技能里。

**条目编号一律由脚本发，不自己推算。** 写条目前先取号，照它打出来的号写：

```
python scripts/issue_ids.py <产出目录>                   七种编号各用到几号，先看一眼
python scripts/issue_ids.py <产出目录> TC- --count 8     取这一批的号，一行一个
```

前缀照写：`TM-`、`TCOV-`、`TC-`、`TP-`、`DATA-`、`ENV-`、`DEC-`；项目自己的编号惯例照传（如 `Lid-`）。**第 0 步起，每一步写新条目前先取这一批的号**，写完照旧随即落盘——盘上那份就是下一批号的基准；自检发现缺覆盖项、回第 4 步补用例时，补之前重新取一次。手上已有一批用例、往已有文档里接着编时，先跑一次不带前缀的那条，看七种编号各到几号了，再接着取。

脚本只读不写，基准就是产出目录里那六份文档，不另存台账。`--count` 给多了不占号——一批要 8 个、只用掉 5 个，下次发号仍从盘上接着往下，不留洞。编号的规矩（从 1 起、不跳号、不回收空号、生存周期内不改）见 `references/文档模板.md` 第二节。

产出入库前跑一遍这个：

```
python scripts/check_docs.py <产出目录>
```

它查的是机械项——编号连不连续、栏目齐不齐、两张对应表有没有留空、引用的编号指不指得到（引了没有定义处的算错误，定义了却没人引的算提示）、有没有漏进禁用词。**决策依据那一条另有一套**：编号必须是 1 起连号，缺号或最大号大于行数都报错——那说明有旧条目被删掉或被改写过，而这份文档只增不改。报错就先改完再说，别把带错的产出交出去。判断性的东西它管不了：模型建得对不对、覆盖项取全没有、用例导得够不够，那些还得自己看。往已有文档里补用例的那条路，补完一样跑一遍。

第 6 步算下来覆盖率不够，缺哪些覆盖项，看「覆盖项 ↔ 用例」对应表里留空的行。缺的先回第 4 步补用例——只要覆盖项还能被执行、还能被用例覆盖，就得补上。确实覆盖不了的，要能证明它无法被执行或无法被测试用例覆盖，才按 `references/覆盖率与完成准则.md` 的规矩当不可行项剔除，并把原因记下来。这张表随测试用例规格说明一起落盘（格式见 `references/文档模板.md` 第八节）：覆盖率不够时看的就是它里面留空的行，补完用例把盘上那份一并改掉。流程允许回走，不是一次过。

**手上已经有一组用例、不是从零设计时**，走法不同：先看这组用例有没有测试覆盖项清单。有，就照第 6 步算覆盖率、按 `references/覆盖率与完成准则.md` 判够不够，缺的覆盖项按第 4 步补用例（补之前重新取号）；没有，就先按第 1–3 步补出模型与覆盖项，再回到第 6 步。这条路第 0 步那三样照样要——没有完成准则判不了够不够，没有风险信息定不了风险等级。补出来的覆盖项与用例写进 `Test Case Specification.md`：原来没有这份就新写一份，已有一份就往里补。其余四份按需更新，**不重出这几份文档，也不为了套流程把已有用例推倒重来。** 决策依据那份只往后加，不重写。

## 第 0 步：定开工输入

三样开工输入缺一不可——后面每一步「做到什么程度」都由它们定。三样的来路不同，**其中两样长在用户那边，一样由你自己定**：

| 开工输入 | 从哪来 | 缺了怎么办 |
|:---|:---|:---|
| 测试依据 | 用户给的那个对象：给的是路径、技能名、代码或需求文本，就去读它，读出来的对外契约就是测试依据 | 没给就问，不猜要测什么 |
| 风险信息 | **向用户要**：哪里风险高、近期改过哪里、出过什么故障 | **拿到再开工**，不自己编 |
| 测试完成准则（要求的覆盖率） | **自己定**：被测项目已有测试计划的照计划取；没有的按下面的默认口径定 | 不问用户 |

**完成准则的默认口径：选定技术识别出的测试覆盖项全部取全、全部要有用例覆盖，即覆盖率按 100% 要求。**有覆盖档位的三门——分类树方法、组合测试、状态转移测试——档位按风险级别选；选低档不等于降准则，那一档识别出的覆盖项照样全部覆盖。低于 100% 要从覆盖项里挑子集，挑的时候得逐条说明放弃了什么，比全覆盖更难交代，所以默认不这么做。单个脚本、单个功能、一段需求这类场合没有测试计划，正是这条口径的用武之地。

**风险信息问什么、怎么问。**问的是只有项目里的人才知道的事：这个测试项最近改过哪里、出过什么故障、哪一块最怕出错。从测试项本身看出来的那几处（对外承诺的准确性、不可回退的副作用、边界与异常输入）问的时候一并摊出来，让他在这上面增删，别让他从零想。**不要问「风险等级定几级」**——定级是你根据他答的内容判的，判完落进产出文档的「风险等级」栏；把定级本身推回去，等于把第 3 步该干的活外包出去。

**定完判完都要落进产出**：完成准则与风险等级写进测试模型规格说明的「测试策略摘要」栏与「风险等级」栏，接着往下做，不必再等用户点头。

**只问缺的开工输入，别的都不问。**第 0 步要问的就是上表里标着「向用户要」的那几样——测试依据没给就问测试依据，风险信息要问，产出目录没给也要问。**交付范围不问**：「这次交到哪一步」「要不要顺便把用例落成能跑的代码」「要不要跑一遍看看」这类，本技能产出什么已经定死了（见开头那段），不是摆给用户挑的选项。把一件已经有答案的事做成选项，用户只能猜你本来该做什么，还得替你承担边界。第 1 步那四个决定同理：材料可以摊开讲，选择不摆成菜单。

## 第 1 步：四个决定，各自要有依据

第 1 步要定四件事，每件都得说得出依据：

| 决定 | 依据从哪来 |
|:---|:---|
| 选哪几门技术 | 从本技能详写的七门里选。判断材料见 `references/技术选型与组合.md` 第一、三节——第一节是质量特性到技术的映射表；第三节是七门各自拿什么当模型、建它时依据里要有什么，测试依据本身的形态——它本身就是一张状态图、一张判定表，还是一段散文——靠这两栏看；另有那份文件列的几项实际因素，七门之外的换用见那份文件末节。**这一项本技能明确不给方案**——业界对哪门技术有效性最高没有共识，本技能只给材料，不给结论。不给的是「什么时候选什么」那套规则；**选哪几门仍要你自己连同依据定下来**，选择与依据一起写进「测试策略摘要」栏。材料不够就如实说，不编规则 |
| 怎么组合 | 本技能给的几组搭配：一门技术的产出喂给另一门（等价类划分的覆盖项作场景测试的输入参数等）；以及用七门之外的技术补本技能这几门漏掉的那类缺陷（见那份文件第二节末） |
| 各建什么模型 | 技术决定模型形态——状态转移测试建状态图、判定表测试建判定表。选定技术后模型形态就定了；形态由技术反推，不自由发挥 |
| 做到什么程度 | 测试完成准则（要求的覆盖率）和风险级别。模型建到多细、覆盖项取全还是取子集、高风险处要不要多导用例，都由这两样定；其余可调之处见 `references/技术选型与组合.md` 第四节 |

依据只有三个来源，每一步、每一栏都要能归到其中之一；归不到的，先看缺的是哪一类：

| 来源 | 有哪些 | 技能能不能自己给 |
|:---|:---|:---|
| ① 技能自己给的 | 模型形态由技术决定、覆盖项怎么导出、输入值怎么选、预期结果从测试依据推、规程按前后置依赖排序、环境项的类型清单、编号方案 | 能，写进 references |
| ② 从测试依据与测试项推出来的 | 测试完成准则（要求的覆盖率），以及选型要权衡的四项实际因素（风险等级、关键程度、应用领域、实施成本）里能从测试项看出来的那些 | 能，推法见「第 0 步」与 `references/技术选型与组合.md` 第一节末 |
| ③ 只有用户那儿有的 | 测试依据、风险信息 | 不能，向用户要；这两样不齐不勉强开工 |

- **② 那几样不要摆给用户挑**：都从测试项本身看得出来，判完写进产出即可。被测项目已有测试计划的，照计划取，不另判。
- **③ 那几样不要自己编**：测试依据是「要测什么」，风险信息是「这个项目怕什么」——测试项本身都看不出来，编出来的只是推测，看着再合理也一样。
- **判断不等于编**：② 那几样判成什么样，都要说得出看的是测试项的哪一处；说不出的，回「第 0 步」看该看哪几处，不随手填一个数充数。
- **依据要落进产出，不是心里想过就算**：技术选型与完成准则写进测试模型规格说明的「测试策略摘要」栏；风险等级写进「风险等级」栏。写不进产出的依据等于没有依据。

## 必须照写的几个词

产出文档里，这几个词照左列写，不要换成右列。它们与本领域更常见的说法只差一点，不单列出来最容易写错，写错了就跟技能其余部分对不上。

| 本技能要求 | 容易写成 | 为什么 |
|:---|:---|:---|
| 测试模型 | 测试条件 | 「测试条件」在别处更常见，最容易顺手写上；本技能全库统一用前者 |
| 测试依据 | 测试的证据、测试数据 | 它是设计用例所依据的信息源 |
| 测试项 | 测试用例、被测对象 | 指被测的那个东西 |
| 测试覆盖项 | 覆盖点、覆盖目标 | 指模型里要被覆盖的那个元素 |
| 测试规程 | 测试脚本、测试流程 | 指用例的执行顺序，加启动与收尾动作 |
| 测试用例规格说明 | 测试用例文档 | 它是正式的文档名 |
| 应／宜／可 | 统写成「要」 | 顺手把这三个字改成「要」，会把原话的语气带偏 |
| 有效测试用例／无效测试用例 | 正确用例／错误用例 | 导出方法那组术语的固定说法 |
| 一对一方式／最小化方式 | 逐条方式／最少用例方式 | 同上，指选择测试覆盖项组合的两种方法 |
| 测试完成准则 | 测试完备性准则、测试充分性准则 | 后两个名指的是同一件事；本技能全库统一用「测试完成准则」，不跟着换 |
| 未规定功能 | 未定义行为、未指定功能 | 指测试依据中未予以明确的那些功能——测试项若执行了依据里没写的功能，缺陷在测试项或依据那一侧 |
| 风险等级 | 优先级 | 「优先级」自带顺序的意思，写着写着就变成规定执行顺序；排执行顺序是测试规程的事，这一栏只是个等级 |

## 几处边界

**技术文件只覆盖 TD1–TD3，不覆盖 TD4。** 七份技术文件讲的是建模型、定覆盖项、导出用例这三步；规程怎么排序、怎么编，只在 `references/流程.md` 里讲，技术文件里不出现。走到 TD4 时不必再翻技术文件。

**测试计划那一层（管理级）只作接口。** 测试完成准则优先从被测项目已有的测试计划里取，没有计划的按「第 0 步」的默认口径自己定；风险信息这一层给不出时，向用户问一句（见「第 0 步」）。测试方针、测试计划的编写、测试执行、事件报告都不在本技能范围内。

**七门之外的技术：只告知，不代做。** 看出某处更适合七门之外的技术时，明确告诉用户「这里更适合 X」，并说明 X 管什么，但不替用户做。七门之外还有哪些、各自管什么，见 `references/技术选型与组合.md` 的末节。

## 什么时候读哪份文件

每次都用得上的是这五份（第六份「决策依据」的写法也在 `references/文档模板.md` 里，不另开文件）：

- `references/流程.md`：走到 TD1–TD4 每一步时读——四步各要做什么、每步该记录哪一段可追溯性（依据 → 模型 → 覆盖项 → 用例 → 规程）都在这里；末尾有一个从测试依据走到测试规程的完整示例。
- `references/技术选型与组合.md`：第 1 步定技术方案时读——选哪几门技术、怎么组合、各建什么模型与建它时依据里要有什么、做到什么程度，以及七门之外技术的换用告知。
- `references/文档模板.md`：写产出时读——六份文档各有哪些栏目、各栏怎么填、编号方案、两张对应表的格式、决策依据那份只增不改的规矩。
- `references/文档示例.md`：对着模板拿不准该填成什么样时读——六份文档合起来是一套完整的填写示例，讲的是同一个互联网项目。
- `references/覆盖率与完成准则.md`：第 6 步自检时读——覆盖率怎么算、算到什么程度算够、缺的覆盖项与不可行项怎么处理。

第 1 步定完技术方案后，选中的哪几门就读哪几门，没选中的不必读：

- `references/技术/等价类划分.md`
- `references/技术/分类树方法.md`
- `references/技术/边界值分析.md`
- `references/技术/组合测试.md`
- `references/技术/判定表测试.md`
- `references/技术/状态转移测试.md`
- `references/技术/场景测试.md`——用例测试归在这门里

七份的文件名就是技术名，选了哪门读哪份。

技术文件各自自包含：给出测试依据，照着就能建模型、定覆盖项、导出用例、算覆盖率。只有一处例外——组合测试那门在参数没有约束时，要求先用等价类划分或边界值分析把取值范围收窄；其余各门读一份就够，不必再翻别的技术文件。
