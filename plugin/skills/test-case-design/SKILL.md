## 这门技能做什么

做法是从「要测什么」一路推到「按什么顺序测」：建测试模型、定覆盖项、导出用例、编测试规程。

产出六份 Markdown，写入用户指定的目录：

| 文档 | 文件名 |
|:---|:---|
| 测试模型规格说明 | `Test Model Specification.md` |
| 测试用例规格说明 | `Test Case Specification.md` |
| 测试规程规格说明 | `Test Procedure Specification.md` |
| 测试数据需求 | `Test Data Requirements.md` |
| 测试环境需求 | `Test Environment Requirements.md` |
| 决策依据 | `Decision Basis.md` |
| 实施方案规格说明（第七份，按需产出） | `Implementation Specification.md` |

前五份记结论，「决策依据」记过程——每处决策当时摆着哪几种做法、凭什么取了这一种。**这一份分两块写**：前面一块是用户拍板的（可以直接改），后面一块是你判出来的（只增不改），写法见 `references/文档模板.md` 第九节。**第七份按需产出**：第 0 步答了「要一并出实施测评方案」的才出，走法见下文「只出实施方案那一份」。这一份里还记着这一批落了没、成品落在哪个路径（见下文「成品落点与落成对照」）——六份通用稿里一个字都不写这些。

**只有文件名是英文的，正文一律写中文**——标题、栏目、表格、说明都不例外。提到这几份文档时用上表左列的中文名。

目录由用户或调用本技能时给出；没给就先问，不猜默认路径；目录不存在就建。

内容取自 GB/T 38634 系列标准的修订征求意见稿；技能文件没覆盖到的细节，直接问用户，不猜。

## 管到哪为止：设计出文档，落成摆配置

**设计那一步产出只有那六份文档，到用例与规程产完为止。**不写可跑的测试代码，也不把用例落成任何能执行的形式；不建放测试代码的目录，不执行测试，不出事件报告。工程里另有 `tests/` 之类的约定，那是那个工程自己的事——不因为它在，就顺手往那儿写一份。**第七份也在这门技能范围内**：照样只有文档。

**落成排在文档之后。**能跑的那些（可跑测试、评测用例）是从这六份推出来的——成品里每条条目的编号都要搜得回文档里的那一条，评测用例的目录名照测试规程的编号与位次编（见下文「成品落点与落成对照」）。**用户直接点名要能跑的用例、手上还没有文档时，照旧先把这六份出完**（涉及模型测评的，第七份按需一并出），再照下文「只做落成」那一节落；七份都在手上、只点名要落成的，直接走那一节。

**落成只摆配置，不跑测。**那一步照第七份把 `eval.yaml`、用例配置、夹具摆到盘上，回来补「成品落点」表，再跑一遍落成对照——到此为止。**跑起来看结果、照结论改判据是另一件活**（用 `/skill-upper`），不在这门技能里。

## 主流程

八步按顺序走，中途允许回走。表里的「选中的技术文件」，指第 1 步选定的那几门技术各自在 `references/技术/` 下的那一份；「落盘」一栏写这一步做完要把哪份文档写进产出目录。

| 步 | 做什么 | 读哪份文件 | 落盘 |
|:---|:---|:---|:---|
| 0 | 定开工输入：测试依据、风险信息向用户要；先看测试项判涉不涉及模型测评，涉及才问要不要一并出实施测评方案、要再问用哪个测评方案；测试完成准则按测试项自己定 | `references/覆盖率与完成准则.md` 第三、四节 ＋ 下文的「第 0 步」 | 决策依据（完成准则照什么口径定、风险等级怎么判出来的、测试运行环境为什么默认本机） |
| 1 | 定技术方案：选哪几门技术、怎么组合、各建什么模型、做到什么程度。四个决定每个都要写出依据 | `references/技术选型与组合.md` ＋ `references/流程.md` | 决策依据（四个决定各一条） |
| 2 | TD1 建测试模型：分析依据，按选定技术确定模型表示方法，建模型，记录依据与模型的可追溯性 | `references/流程.md` 第二节 ＋ 选中的技术文件第一~四节 ＋ `references/文档模板.md` 第三、八节 | 测试模型规格说明、决策依据（模型建到多细） |
| 3 | TD2 定测试覆盖项：对模型套用技术导出覆盖项，按风险定等级，记录可追溯性 | `references/流程.md` 第三节 ＋ 选中的技术文件第二、四节 | 决策依据（覆盖项取全还是取子集、带档位的选了哪一档）——覆盖项并进下一步那份 |
| 4 | TD3 导出测试用例：定前置条件、选输入值、定预期结果，记录可追溯性 | `references/流程.md` 第四节 ＋ 选中的技术文件第三、四节 ＋ `references/文档模板.md` 第四、八节 | 测试用例规格说明、决策依据（一对一还是最小化、输入值怎么选的） |
| 5 | TD4 编测试规程：给用例排序，标执行器与改动文件，按落点分批，识别测试数据和环境需求，记录可追溯性 | `references/流程.md` 第五节 ＋ `references/文档模板.md` 第五、六、七节 | 测试规程规格说明、测试数据需求、测试环境需求、决策依据（规程按什么排序、执行器与改动文件怎么判的、分几批落成、数据项与环境项收到哪一层） |
| 6 | 自检：算覆盖率，判断是否达到完成准则；判据落在「要读执行过程」那一层的用例逐条过一遍，看有没有卡住可有可无的附带动作 | `references/覆盖率与完成准则.md` | 测试用例规格说明（覆盖率自检那一块）、决策依据（补了哪些、剔了哪些、凭什么）——缺的回第 4 步补，并改掉盘上那份 |
| 7 | 终检：核对六份都在产出目录里（第 0 步答了要出实施方案的，那份也在），把机械项跑到零错；成品已经落成的，再把落成对照跑到零错 | — | — |

**每步的完成标准：该步「落盘」一栏的文档已经写到产出目录里。** 每步做完随即落盘，不留到最后一起写——中途上下文被压缩时，读盘上的文档就能接着走。第 2–5 步（TD1 建模型、TD2 定覆盖项、TD3 导出用例、TD4 编规程）按表里「读哪份文件」一栏走，做法在那些文件里，这一份不重述。

**决策依据随做随记，分两块写。** 判据是「这一步有没有在几种做法里挑」：在挑就**先记一条，再照它做**——写清当时摆着哪几种、各为什么不取、凭什么取了这一种；只有一种做法的动作（照模板填栏目、照技术文件导出覆盖项）不记。**「依据的来源」栏写着 `用户给的` 那几条，单独写进前面一块（`## 用户决策`）**——用户要能一眼看到自己拍板的、随手就改，所以这一块可以直接改，旧值交给 git；**其余几条写进后面一块（`## 模型决策`），只增不改**——旧条目原样留着，推翻了前面的就新增一条写明订正的是哪条，回走补出来的接着往后面编号。**只写结论不写过程，等于把判断留在你自己脑子里**：用户只看得见结果，看不见你在哪一步判歪了，也就无从在哪一处把技能改对；被修过的过程比不留还糟，它看着像过程，其实已经是结论了。两块怎么分、块首各写一句什么，见 `references/文档模板.md` 第九节。

## 第 0 步：定开工输入

三样开工输入缺一不可——后面每一步「做到什么程度」都由它们定，其中两样长在用户那边，一样由你自己定：

| 开工输入 | 从哪来 | 缺了怎么办 |
|:---|:---|:---|
| 测试依据 | 用户给的那个对象：给的是路径、技能名、代码或需求文本，就去读它，读出来的对外契约就是测试依据 | 没给就问，不猜要测什么 |
| 风险信息 | **向用户要**：哪里风险高、近期改过哪里、出过什么故障 | **拿到再开工**，不自己编 |
| 测试完成准则（要求的覆盖率） | **自己定**：被测项目已有测试计划的照计划取；没有的按下面的默认口径定 | 不问用户 |

**测试运行环境不问了，默认就是本机。**测试规程在哪儿跑、被测那侧在哪儿执行，这两处都由你自己判，判完在第 5 步落成测试环境需求那两条环境项（写法见 `references/文档模板.md` 第七节）——不要再拿这个去问用户，这两处绝大多数场合下本来就是本机。

**完成准则的默认口径：选定技术识别出的测试覆盖项全部取全、全部要有用例覆盖，即覆盖率按 100% 要求。**有覆盖档位的三门——分类树方法、组合测试、状态转移测试——档位按风险级别选；选低档不等于降准则，那一档识别出的覆盖项照样全部覆盖。低于 100% 要从覆盖项里挑子集，挑的时候得逐条说明放弃了什么，比全覆盖更难交代，所以默认不这么做。

**风险信息问什么、怎么问。**问的是只有项目里的人才知道的事：这个测试项最近改过哪里、出过什么故障、哪一块最怕出错。从测试项本身看出来的那几处（对外承诺的准确性、不可回退的副作用、边界与异常输入）问的时候一并摊出来，让他在这上面增删，别让他从零想。**不要问「风险等级定几级」**——定级由你根据他答的内容判，判完落进产出文档的「风险等级」栏。

**测评方案那两问：先判、再问，涉及才问。**问之前先看**测试项本身**——它是技能、提示词这类靠模型跑的东西吗？

- **不是**（一段脚本、一个函数、一个库）——两问都不问，产出只有六份。
- **是**——先问「要不要一并出实施测评方案」：
  - 答**不要**——产出只有六份；
  - 答**要**——接着问「用哪个测评方案」。目前只支持 skill-up，默认就取 skill-up，别的方案先不支持。

**判「涉不涉及模型测评」只看测试项本身**，不看规程的「执行器」栏——那一栏要到第 5 步才定得下来。所以两者都有的测试项（比如一份技能的中心逻辑靠模型跑）按「涉及」算。

**答了「要」不等于这一轮就出第七份。**这一份也可以另起一次会话、手上已经有六份时单独出，走法见下文「只出实施方案那一份」。

**选了哪个方案不进六份。**六份通用稿一个字都不提拔了哪门方案——方案名与它自己的配置文件名在六份里都算禁用词（见「六份里不许出现的东西」）。方案的选择落在第七份的节名上：「<节号>、方案：<方案名>」，决策依据里也不记；没有第七份时，它哪儿都不落。

**定完判完都要落进产出**：完成准则与风险等级写进测试模型规格说明的「测试策略摘要」栏与「风险等级」栏；测试运行环境那两条（默认本机）到第 5 步落成测试环境需求里的环境项，来源记 `技能定的`。技术选型同理，写进「测试策略摘要」栏——写不进产出的依据等于没有依据。落完接着往下做，不必再等用户点头。

**只问缺的开工输入，别的都不问。**第 0 步要问的就是上表里标着「向用户要」的那几样，加上判下来该问的那两问、没给的产出目录。**交付范围不问**：「这次交到哪一步」「要不要顺便把用例落成能跑的代码」「要不要跑一遍看看」这类，本技能产出什么已经定死了（见开头那段）。第 1 步那四个决定同理：材料可以摊开讲，选择不摆成菜单。

## 第 1 步：四个决定，各自要有依据

| 决定 | 依据从哪来 |
|:---|:---|
| 选哪几门技术 | 从本技能详写的七门里选。材料见 `references/技术选型与组合.md` 第一、三节——第一节是质量特性到技术的映射表，第三节是七门各自拿什么当模型、建它时依据里要有什么（测试依据本身是一张状态图、一张判定表，还是一段散文，靠这两栏看）；另有那份文件列的几项实际因素，七门之外的换用见其末节。**这一项本技能明确不给方案**：业界对哪门技术有效性最高没有共识，本技能只给材料，不给结论——「选哪几门」仍要你自己连同依据定下来。材料不够就如实说，不编规则 |
| 怎么组合 | 本技能给的几组搭配：一门技术的产出喂给另一门（等价类划分的覆盖项作场景测试的输入参数等）；以及用七门之外的技术补本技能这几门漏掉的那类缺陷（见那份文件第二节末） |
| 各建什么模型 | 技术决定模型形态——状态转移测试建状态图、判定表测试建判定表；形态由技术反推，不自由发挥 |
| 做到什么程度 | 测试完成准则（要求的覆盖率）和风险级别。模型建到多细、覆盖项取全还是取子集、高风险处要不要多导用例，都由这两样定；其余可调之处见 `references/技术选型与组合.md` 第四节 |

依据只有三个来源，每一步、每一栏都要能归到其中之一；归不到的，先看缺的是哪一类：

| 来源 | 有哪些 | 技能能不能自己给 |
|:---|:---|:---|
| ① 技能自己给的 | 模型形态由技术决定、覆盖项怎么导出、输入值怎么选、预期结果从测试依据推、规程按前后置依赖排序、环境项的类型清单、编号方案 | 能，写进 references |
| ② 从测试依据与测试项推出来的 | 测试完成准则（要求的覆盖率），以及选型要权衡的四项实际因素（风险等级、关键程度、应用领域、实施成本）里能从测试项看出来的那些 | 能，推法见「第 0 步」与 `references/技术选型与组合.md` 第一节末 |
| ③ 只有用户那儿有的 | 测试依据、风险信息 | 不能，向用户要；这两样不齐不勉强开工 |

- **② 那几样不要摆给用户挑**：都从测试项本身看得出来，判完写进产出即可。
- **③ 那几样不要自己编**：测试依据是「要测什么」，风险信息是「这个项目怕什么」——测试项本身都看不出来，编出来的只是推测。
- **判断不等于编**：② 那几样判成什么样，都要说得出看的是测试项的哪一处；说不出的，回「第 0 步」看该看哪几处，不随手填一个数充数。

## 第 6 步：自检

覆盖率不够时，缺哪些覆盖项看「覆盖项 ↔ 用例」对应表里留空的行。缺的先回第 4 步补用例——只要覆盖项还能被执行、还能被用例覆盖，就得补上；确实覆盖不了的，要能证明它无法被执行或无法被测试用例覆盖，才按 `references/覆盖率与完成准则.md` 的规矩当不可行项剔除，并把原因记下来。补完用例把盘上那份一并改掉（这张表的格式见 `references/文档模板.md` 第八节）。算出来的覆盖率连同 N、T 落进测试用例规格说明的「覆盖率自检」那一块——一行一门选定的技术，栏目见 `references/文档模板.md` 第四节。**T 要先拿这门技术的算式核一遍**（见 `references/覆盖率与完成准则.md` 第二节）——算出来多少条，清单里就该有多少条；核不上说明识别漏了或多了，回第 3 步补。

**判据落在「要读执行过程」那一层的用例，逐条再读一遍「预期结果」那一栏**（两个取值见 `references/文档模板.md` 第四节）。一条一条问：「这一条要是没做到，算不算这条用例没过？」拿不准的，多半是卡了一个可有可无的附带动作——同一件事，被测那边有时顺带说一句、有时不说，卡上去这条用例就一轮过一轮不过。删掉那一条；要留着，就在决策依据里记一条说明为什么留着。

**「输入」栏写的是用户会说的那句话的用例，逐条再读一遍那一栏。**一句一句问：「没看到后面接的那份样本的人，读这句话能不能唯一定下要数的是哪一段？」请求里带「这段」「上面那段」这类指代时，一句话里常常有两个东西可指——请求本身、接在后面的那份样本，会话里还常带着别的文本（工作区里那份说明之类）——被测那边两遍能各取一个，而判据钉的是样本自己的数。实测：同一批七条里三条两遍全败，报回来的都是会话里那份说明的数。**读不出唯一所指的，改请求那句话本身**——点明「冒号后面这一整行」「下面这一行」这类；别只在栏里补一句说明，说明是写给摆输入的人看的，被测那边看不到。只数命令行参数、文本原样抄在引号里的用例不必过这一条。

## 第 7 步：终检

产出入库前跑一遍 `python scripts/check_docs.py <产出目录>`——报错就先改完再说，别把带错的产出交出去。它管机械项，**管不了判断性的东西**（模型建得对不对、覆盖项取全没有、用例导得够不够）——那些还得自己看。有一条容易漏：**决策依据的编号必须 1 起连号**，缺号或有旧条目被删改过都报错。**它会拒绝什么，跑 `python scripts/check_docs.py --rules` 一次打全**——禁用词、认哪些节标题、认哪几栏、哪些取值写死了，不用产出目录；写一份就跑一次，比七份写全再跑省事。往已有文档里补用例的那条路，补完一样跑一遍。

成品已经落成的，终检时还要跑一遍落成对照把账对上（表在第七份的方案节里）——命令、退出码、分几批落成时怎么算，见下文「成品落点与落成对照」。

## 写产出时的通用规矩

### 写条目前先取号

**条目编号一律由脚本从盘上推，不自己推算。** 写条目前先取号，照它打出来的号写：

```
python scripts/issue_ids.py <产出目录>                   七种编号各用到几号，先看一眼
python scripts/issue_ids.py <产出目录> TC- --count 8     取这一批的号，一行一个
```

前缀照写：`TM-`、`TCOV-`、`TC-`、`TP-`、`DATA-`、`ENV-`、`DEC-`；项目自己的编号惯例照传（如 `Lid-`）。**第 0 步起，每一步写新条目前先取这一批的号**；自检发现缺覆盖项、回第 4 步补用例时，补之前重新取一次。手上已有一批用例、往已有文档里接着编时，先跑一次不带前缀的那条，看七种编号各到几号了，再接着取。

脚本只读不写，**基准就是产出目录里那六份文档**，不另存台账——每跑一次都从盘上重新数一遍。所以从零写的一批取到的号就是 1 起连号，盘上写到几号就接着往下；`--count` 给多了不占号。编号的规矩（从 1 起、不跳号、不回收空号、生存周期内不改）见 `references/文档模板.md` 第二节。

**落成评测用例的那一批，用例目录名也由脚本打。** 规程那几栏落盘之后、写文末「各批落到哪」之前，先跑一次：

```
python scripts/issue_ids.py <产出目录> --case-dirs
```

它照「有序执行测试用例」栏数一遍位次，一条规程一行打出整条目录名（`tp01-01-TC-1-fix_only_what_should_change`），照抄进那张表新加的「用例目录名」栏。**位次别自己数**——那是这条链上唯一一处会数错的地方。形制、补零、一条规程一行怎么填，见 `references/文档模板.md` 第五节。

### 产出里要有的东西

写产出时照 `references/文档模板.md` 的栏目填，一个栏目不缺、也不多造；产出文档里只写测试内容，不把技能文件里的节号与出处带出去。

**每条条目除编号外还要一个英文名**，紧挨着编号写（决策依据那份不给）。它是这条条目落成代码时的名字核——下游拿它拼函数名、类名、变量名，照抄产出里的，不每次现取一批新的。形制与取法见 `references/文档模板.md` 第二节。

### 成品落点与落成对照

**这一块住在第七份的方案节里，是那一节的最后一块。**它记这一批落了没、成品落在哪个路径——六份通用稿里一个字都不写这些（通用稿不认任何一种测评方案，落点与进度都是方案的事）。**表里一行一个成品路径**；还没落成就写「还没落成」，是那一块里的一句话、不占表里的一格；分几批落成时两种写法并存。写法与三条约束见 `references/文档模板.md` 第十节。

**落成之后回来把这张表填上，再跑一遍对照：**

```
python scripts/check_landing.py <产出目录> [成品路径 ...]
```

**成品住在评测材料根那一层（那一层还住着 `runs\` 这些跑测产物）时，命令上把成品路径一条条点出来**——别把整个上一层指过去：

```
python scripts/check_landing.py <产出目录> eval.yaml cases fixtures
```

它拿产出里定义过的编号去成品里找出处：六类条目（模型、覆盖项、用例、规程、数据项、环境项）在成品里一条也找不着，或者成品里冒出一个产出里没有的号，都算错。**成品里每条条目的编号都要搜得到**——代码里写不成连字符就换成下划线（`TC-30` 写成 `TC_30`），照抄编号，不补零、一条一个号不写成范围。

它的退出码：`0` 两边对得上；`1` 有对不上的地方；`2` 用法或路径有问题、或者那一块的表坏了；`3` 没有可对照的成品——**第七份整份不在**，或者这一块写着「还没落成」。**退 3 不是错**，看见它跳过就行，别当失败记。**分几批落成时照查**：那一块里既列了已落成的表、又写着「还没落成」交代剩下几处时，两向对照照样跑，只有「定义了却没在成品里出现」那一条降成提示。

### 落成那一步手上要有哪四样

**落成那一步读四样，落成的人四样都要在手上**：

1. **六份通用稿**——消息正文从测试用例规格说明的「输入」栏来，判据从「预期结果」栏来；执行顺序与分几批从测试规程规格说明的「有序执行测试用例」与「各批落到哪」来；样本的字节与正文从测试数据需求来；环境项从测试环境需求来；模型与覆盖项从测试模型规格说明与覆盖项清单来。**第七份不把它们重述一遍**，只读第七份落不出东西。
2. **第七份（实施方案规格说明）**——哪几条规程在这一套里跑、落成什么形式、落在哪个路径、编号在盘上怎么留痕，都在那一份里。**落点账也在这份里**：这一批落了没、成品落在哪个路径，写在这一份方案节末尾的「成品落点」表里，不必回通用稿找。**通用稿不认任何一种测评方案**，只读通用稿也不知道该摆成什么。
3. **`/skill-upper` 技能下 `references/` 那几份**——配置字段怎么填、命令怎么用，以它为准。**它没写到的、或者与第 4 样冲突的，以第 4 样为准**：它那几份里有与本技能实测对不上的话（Windows 支不支持就是一处，见第 4 样）。
4. **`references/评测方案/<方案名>/usage-notes.md`**——这套方案**实际跑起来是什么样**：工作区怎么起、哪几样东西铺不进去、哪几条跑不了原样。前三样讲「要什么」，这一样讲「实况」——落成时撞上的正是后者。**写第七份的「说明」那一块时也读它**（见「只出实施方案那一份」），那几条的事实从这里取。**两边的话对不上时以它为准**；它没写到的标「待确认」，不写成事实、也别照印象补。

## 手上已经有一组用例、不是从零设计时

先看这组用例有没有测试覆盖项清单。有，就照第 6 步算覆盖率、按 `references/覆盖率与完成准则.md` 判够不够，缺的覆盖项按第 4 步补用例（补之前重新取号）；没有，就先按第 1–3 步补出模型与覆盖项，再回到第 6 步。第 0 步那几样照样要——没有完成准则判不了够不够，没有风险信息定不了风险等级。补出来的覆盖项与用例写进 `Test Case Specification.md`（原来没有就新写一份，已有一份就往里补），其余四份按需更新。**不重出这几份文档，也不为了套流程把已有用例推倒重来**；决策依据那份只往后加。

## 只出实施方案那一份

第七份（`Implementation Specification.md`，实施方案规格说明）有两条入口，都不影响那六份：

**一、随六份一起出。**第 0 步答了「要一并出实施测评方案」的，六份走完第 7 步终检之后再出这一份——它要对账的六类编号到第 5 步才齐，早出了对不上。写之前读 `references/文档模板.md` 第十节（契约）与 `references/文档示例.md` 第七节（填写示例）；**先确认 `/skill-upper` 技能装着**（`~/.claude/skills/skill-upper/`），没装就让用户装，装着的**照它 `references/` 下那几份把这一份里要写进去的命令与字段名逐条核过**——**别照印象写**：写了不存在的开关、或漏了必填的那一项，要等到落成、跑校验时才撞见，那时通用稿已经定了稿。核完再读 `references/评测方案/skill-up/usage-notes.md`，把落点与折扣写准（工作区怎么起、哪几条在这个方案上跑不了原样）。

**二、单独出。**手上已经有六份产出，这次只出第七份——和上面那条路并列，**不重出已有的文档**。走法：读盘上那六份（对账要对测试环境需求与测试数据需求两份）；问一句「用哪个测评方案」（默认 skill-up）；照入口一读的那几份核对，并照 `references/文档模板.md` 第十节写，落到同一个产出目录里；**跳过取号**——这一份不定义任何编号，一个都不新发。

写完之后照旧跑一遍 `python scripts/check_docs.py <产出目录>`，第七份在目录里时那一组会一并查。

## 只做落成

**入口**：七份都在手上（六份通用稿 ＋ 第七份），用户点名要落成。**不重出、不改写那七份的设计内容**——这一步只往盘上摆东西、回来补一张表。

1. **读那四样**——各取什么见上文「落成那一步手上要有哪四样」。第七份是要照的那一份：哪几条规程在这一套里跑、落成什么形式、落在哪个路径、编号在盘上怎么留痕，都在它里面。
2. **照第七份摆文件**——`eval.yaml`、用例配置、夹具落到第七份「通用稿的编号落到哪」那张表点名的路径上。**配置原文由这一步写**：第七份里不贴它；字段怎么填照 `/skill-upper` 技能下 `references/` 那几份，实况照 usage-notes。**编号照抄**——连字符写不成换成下划线、数字不补零、一条一个号不写成范围（见 `references/文档模板.md` 第二节「落成约定」），照第七份里「编号在盘上怎么留痕」那一处下笔。
3. **回来补「成品落点」表**——第七份方案节末尾那一块，**一行一个成品路径**。写法与三条约束见 `references/文档模板.md` 第十节。
4. **跑一遍落成对照**——`python scripts/check_landing.py <产出目录> <成品路径 ...>`；成品住在评测材料根那一层时，路径一条条点出来（见上文「成品落点与落成对照」）。**它报出来的差异改到零错再收手**：哪一条编号在成品里找不到、成品里哪个号没有出处，都是账没对上（退 3 是「还没落成」，不是错）。
5. **把偏离写回去**——落成时哪几条没照原样落、偏在哪、为什么（夹具几套并成一套、某几样铺不进工作区、相对路径的基准退让这类，**都是脚本看不见的**），一条一条写进第七份方案节「说明」那一块，跟通用稿逐条对照。**usage-notes 里没有的折扣，一并回写进 usage-notes 的对应那一节**，句末标「实测，<版本>」，并在它文末那张「已核过」清单里补一笔——体例见那一份文末。

## 必须照写的几个词

产出文档里，这几个词照左列写，不要换成右列：

| 本技能要求 | 容易写成 | 为什么 |
|:---|:---|:---|
| 测试模型 | 测试条件 | 「测试条件」在别处更常见，最容易顺手写上；本技能全库统一用前者 |
| 测试依据 | 测试的证据、测试数据 | 它是设计用例所依据的信息源 |
| 测试项 | 测试用例、被测对象 | 指被测的那个东西 |
| 测试覆盖项 | 覆盖点、覆盖目标 | 指模型里要被覆盖的那个元素 |
| 测试规程 | 测试脚本、测试流程 | 指用例的执行顺序，加启动与收尾动作 |
| 测试用例规格说明 | 测试用例文档 | 它是正式的文档名 |
| 应／宜／可 | 统写成「要」 | 顺手把这三个字改成「要」，会把原话的语气带偏 |
| 有效测试用例／无效测试用例 | 正确用例／错误用例 | 导出方法那组术语的固定说法 |
| 一对一方式／最小化方式 | 逐条方式／最少用例方式 | 同上，指选择测试覆盖项组合的两种方法 |
| 测试完成准则 | 测试完备性准则、测试充分性准则 | 后两个名指的是同一件事，本技能统一用前者 |
| 未规定功能 | 未定义行为、未指定功能 | 指测试依据里未予以明确的那些功能 |
| 风险等级 | 优先级 | 「优先级」自带顺序的意思，容易变成规定执行顺序；排执行顺序是测试规程的事 |

## 六份里不许出现的东西

六份通用稿要能原样拿去当代码或技能的测试依据，所以它们不认任何一种测评方案、也不认任何一种具体环境。下面这些词**六份产出里一个都不许出现**——它们该怎么写、第七份里正该出现的是什么，见 `references/文档模板.md` 第十节。

| 词 | 为什么 |
|:---|:---|
| skill-up | 测评方案的名字。用哪个方案是第七份的事，通用稿不认 |
| eval.yaml | 同上，那个方案自己的配置文件名 |
| case.yaml | 同上 |
| graders/ | 同上，那个方案给每条用例的判据留的目录名。判据本身照写不误（ENV-3 说的就是它），但落在哪个目录、叫什么文件名，是那个方案的事，通用稿不点名 |
| WSL2 | 具体环境名。要写就写「默认就是本机」，或者写这一条环境项管的是什么 |
| Docker | 同上 |
| 本机 Windows | 同上；「本机」两个字就够，不必点名是哪个系统 |

`scripts/check_docs.py` 按这张表左列查，命中就报**错**，不降成提示。范围分两档：**方案名、它自己的配置文件名、它给判据留的目录名**六份全查；**具体环境名**查五份，`Decision Basis.md` 除外——那一份记的是过程，「当时定的是本机 Windows」是照实记，不是违规。

**第七份反过来**：方案名与配置文件名在那一份里正该出现，但**配置原文不抄进去**——配置由落成那一步照第七份写进盘里，抄一份进来就是第二份会漂移的副本，漂了还不报错。**「成品落点」那一块也住在那一份里**（方案节末尾，见 `references/文档模板.md` 第十节）：它在通用稿里时，路径得绕开这张表上的词、还得避开住着跑测产物的那一层——搬走之后前一条不成立了，后一条照旧（那里会读出散号，与通用不通用无关）。

## 方法上的几处边界

**技术文件只覆盖 TD1–TD3，不覆盖 TD4。** 建模型、定覆盖项、导出用例这三步在技术文件里；规程怎么排序、怎么编只在 `references/流程.md` 里讲。走到 TD4 时不必再翻技术文件。

**测试计划那一层（管理级）只作接口。** 完成准则优先从被测项目已有的测试计划里取，风险信息这一层给不出时向用户问一句（见「第 0 步」）。测试方针、测试计划的编写、测试执行、事件报告都不在本技能范围内。

**七门之外的技术：只告知，不代做。** 看出某处更适合七门之外的技术时，明确告诉用户「这里更适合 X」并说明 X 管什么，但不替用户做。七门之外还有哪些、各自管什么，见 `references/技术选型与组合.md` 末节。

## 什么时候读哪份文件

**这几份都按节读，不整份读**——要用的节，前文各步里点着；读法通则见常驻规则里「读文件」那一条。**技术文件第一~四节是「怎么做」，第五节的算例是示范，拿不准时再读**。

每次都用得上的是这五份（第六份「决策依据」的写法也在 `references/文档模板.md` 里，不另开文件）：

- `references/流程.md`：走到 TD1–TD4 每一步时读——四步各要做什么、每步该记录哪一段可追溯性（依据 → 模型 → 覆盖项 → 用例 → 规程），末尾有一个从测试依据走到测试规程的完整示例。
- `references/技术选型与组合.md`：第 1 步定技术方案时读——选哪几门技术、怎么组合、各建什么模型与建它时依据里要有什么、做到什么程度，以及七门之外的换用告知。
- `references/文档模板.md`：写产出时读——六份文档各有哪些栏目、各栏怎么填、编号方案、两张对应表的格式、编号与英文名怎么落到成品里、决策依据分两块与只增不改的规矩，以及第七份的骨架契约（第十节：每个方案一节，节里四块，末一块是成品落点与落成进度）。
- `references/文档示例.md`：对着模板拿不准该填成什么样时读——六份文档合起来是一套完整的填写示例，另有一节是第七份的。
- `references/覆盖率与完成准则.md`：第 6 步自检时读——覆盖率怎么算、算到什么程度算够、缺的覆盖项与不可行项怎么处理。

第 0 步答了「要出实施测评方案」的，写第七份之前先确认 `/skill-upper` 技能装着；没装就让用户装——配置字段怎么填、命令怎么用都在它 `references/` 下那几份里。装着的再读技能里这一份：

- `references/评测方案/skill-up/usage-notes.md`——这个方案实际跑起来是什么样、做不到什么、哪里要挑，含 `/skill-upper` 没写到的几条：写「说明」那一块里「工作区怎么来」与「跑不了原样的那几条」时用它。**那几条的事实从这里取，不靠实测**；这里没写到的标成「待确认」，不写成事实，也别照印象补。**落成那一步也读它**——工作区怎么起、哪几样铺不进去、哪几条跑不了原样，正是落成时撞上的（见「只做落成」）。

第 1 步定完技术方案后，选中的哪几门就读哪几门：

- `references/技术/等价类划分.md`
- `references/技术/分类树方法.md`
- `references/技术/边界值分析.md`
- `references/技术/组合测试.md`
- `references/技术/判定表测试.md`
- `references/技术/状态转移测试.md`
- `references/技术/场景测试.md`——用例测试归在这门里

`scripts/` 下那三个脚本（`check_docs.py`、`check_landing.py`、`issue_ids.py`）**按命令行用就行，不用读它们的内容**。**命令里的 `python` 按你机器上的写法来**——只装了 Python 3、没给 `python` 这个名字的（不少 Linux 与 macOS 上就是），写成 `python3`。

技术文件各自自包含：给出测试依据，照着就能建模型、定覆盖项、导出用例、算覆盖率。只有一处例外——组合测试那门在参数没有约束时，要求先用等价类划分或边界值分析把取值范围收窄。
