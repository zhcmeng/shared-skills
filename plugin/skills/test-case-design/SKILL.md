# 测试用例设计

本技能内容基于 GB/T 38634 系列标准的修订征求意见稿整理。

本技能自包含：不要联网去搜这份标准，也不要翻别处存着的标准正文——搜到的多是二手转述，与标准正文对不上，翻存档也只会把上下文撑爆。技能里没覆盖到的细节，直接问用户，不猜也不翻。

产出六份 Markdown，写入用户指定的目录；第 0 步答了「要一并出实施测评方案」的，另出一份 `Implementation Specification.md`（实施方案规格说明），见下文「只出实施方案那一份」：

| 文档 | 文件名 |
|:---|:---|
| 测试模型规格说明 | `Test Model Specification.md` |
| 测试用例规格说明 | `Test Case Specification.md` |
| 测试规程规格说明 | `Test Procedure Specification.md` |
| 测试数据需求 | `Test Data Requirements.md` |
| 测试环境需求 | `Test Environment Requirements.md` |
| 决策依据 | `Decision Basis.md` |

前五份记结论，最后一份记过程——每处决策当时摆着哪几种做法、凭什么取了这一种。**这一份分两块写**：前面一块是用户拍板的（可以直接改），后面一块是你判出来的（只增不改）。**这一份不是可选项**：没有它，用户只看得见你定了什么，看不见你怎么定的，也就没法在哪一步把技能改对。写法见 `references/文档模板.md` 第九节。

**只有文件名是英文的，正文一律写中文**——标题、栏目、表格、说明都不例外。别把「英文文件名」当成「英文文档」，产出照旧是中文。中文说明文件里提到这几份文档时，用上表左列的中文名。

目录由用户或调用本技能的上位技能给出；没给就先问，不猜默认路径；目录不存在就建。

**产出只有那六份文档，到用例与规程产完为止。**不写可跑的测试代码，不建工程里放测试代码的目录，也不把用例落成任何能执行的形式；不执行测试，不出事件报告。工程里另有放测试代码的地方与命名约定（`tests/` 之类），那是那个工程自己的事——不因为它在，就顺手往那儿写一份；要落成能跑的代码，是上游或另一个技能的活。用户点名要代码也不做：回一句「这件事不在本技能范围内」并指出去哪儿做，然后照旧出文档。**第七份也在这门技能范围内**：它装的是「这套方案怎么落地」，照样只有文档、不写可跑的代码；配置原文也不抄进来——那由落成那一步写进盘里。

## 主流程

八步按顺序走，中途允许回走。表里的「选中的技术文件」，指第 1 步选定的那几门技术各自在 `references/技术/` 下的那一份；「落盘」一栏写这一步做完要把哪份文档写进产出目录。

| 步 | 做什么 | 读哪份文件 | 落盘 |
|:---|:---|:---|:---|
| 0 | 定开工输入：测试依据、风险信息向用户要；先看测试项判涉不涉及模型测评，涉及才问要不要一并出实施测评方案、要再问用哪个测评方案；测试完成准则按测试项自己定 | `references/覆盖率与完成准则.md` 第三、四节 ＋ 下文的「第 0 步」 | 决策依据（完成准则照什么口径定、风险等级怎么判出来的、测试运行环境为什么默认本机） |
| 1 | 定技术方案：选哪几门技术、怎么组合、各建什么模型、做到什么程度。四个决定每个都要写出依据 | `references/技术选型与组合.md` ＋ `references/流程.md` | 决策依据（四个决定各一条） |
| 2 | TD1 建测试模型：分析依据，按选定技术确定模型表示方法，建模型，记录依据与模型的可追溯性 | `references/流程.md` ＋ 选中的技术文件 ＋ `references/文档模板.md` | 测试模型规格说明、决策依据（模型建到多细） |
| 3 | TD2 定测试覆盖项：对模型套用技术导出覆盖项，按风险定等级，记录可追溯性 | 同上 | 决策依据（覆盖项取全还是取子集、带档位的选了哪一档）——覆盖项并进下一步那份 |
| 4 | TD3 导出测试用例：定前置条件、选输入值、定预期结果，记录可追溯性 | 同上 | 测试用例规格说明、决策依据（一对一还是最小化、输入值怎么选的） |
| 5 | TD4 编测试规程：给用例排序，标执行器与改动文件，按落点分批，识别测试数据和环境需求，记录可追溯性 | `references/流程.md` ＋ `references/文档模板.md` | 测试规程规格说明、测试数据需求、测试环境需求、决策依据（规程按什么排序、执行器与改动文件怎么判的、分几批落成、数据项与环境项收到哪一层） |
| 6 | 自检：算覆盖率，判断是否达到完成准则；判据落在「要读执行过程」那一层的用例逐条过一遍，看有没有卡住可有可无的附带动作 | `references/覆盖率与完成准则.md` | 测试用例规格说明（覆盖率自检那一块）、决策依据（补了哪些、剔了哪些、凭什么）——缺的回第 4 步补，并改掉盘上那份 |
| 7 | 终检：核对六份都在产出目录里（第 0 步答了要出实施方案的，那份也在），把机械项跑到零错；成品已经落成的，再把落成对照跑到零错 | — | — |

**每步的完成标准：该步「落盘」一栏的文档已经写到产出目录里。** 每步做完随即落盘，不留到最后一起写——中途上下文若被压缩，读盘上的文档就能接着走，不必重做。

**决策依据随做随记，分两块写。** 判据是「这一步有没有在几种做法里挑」：在挑就记一条，写清当时摆着哪几种、各为什么不取、凭什么取了这一种；只有一种做法的动作（照模板填栏目、照技术文件导出覆盖项）不记。**「依据的来源」栏写着 `用户给的` 那几条，单独写进前面一块（`## 用户决策`）**——用户要能一眼看到自己拍板的、随手就改，所以这一块可以直接改，旧值交给 git；**其余几条写进后面一块（`## 模型决策`），只增不改**——后面发现前面定错了，新增一条写明订正的是哪条，原来那条留着；回走补出来的决策接着往后面编号。两块怎么分、块首各写一句什么，见 `references/文档模板.md` 第九节。

只写结论不写过程，等于把判断留在你自己脑子里：用户只看得见结果，看不见你在哪一步判歪了，也就无从在哪一处把技能改对。**别为了「看起来干净」回头去修「模型决策」那一块里的旧条目**——被修过的过程比不留还糟，它看着像过程，其实已经是结论了。（「用户决策」那一块反过来：那几条是用户给的输入，本来就该能改。）栏目与写法见 `references/文档模板.md` 第九节。

写产出时照 `references/文档模板.md` 的栏目填，一个栏目不缺、也不多造；产出文档里只写测试内容，不把技能文件里的节号与出处带出去。

**每条条目除编号外还要一个英文名**，紧挨着编号写（决策依据那份不给）。它是这条条目落成代码时的名字核——下游拿它拼函数名、类名、变量名，照抄产出里的，不每次现取一批新的。形制与取法见 `references/文档模板.md` 第二节。**这一栏不改变开头那条边界**：产出照旧只有文档，写不写代码不在这份技能里。

**产出里还要留下成品落在哪。**测试用例规格说明分五块写，第五块是「成品落点」：这批用例落成的**成品**（可跑测试、评测用例）放在哪个路径，一份一行；成品还没落成就写一句「还没落成」——**是那一块里的一句话，不占表里的一格**（占了格子，落成对照会把那一格当成路径去读）——这一块不许空着不写。**分几批落成时两种写法并存**：已经落成的列成表，剩下没落的用那句话交代还差哪几处；一条都还没落成时，列表一行都不写，只写那句话；每落完一批就回来把这一批补上。**成品落成之后回来把这张表填上，再跑一遍对照**：

```
python scripts/check_landing.py <产出目录> [成品路径 ...]
```

它拿产出里定义过的编号去成品里找出处：六类条目（模型、覆盖项、用例、规程、数据项、环境项）在成品里一条也找不着，或者成品里冒出一个产出里没有的号，都算错。**成品里每条条目的编号都要搜得到**——代码里写不成连字符就换成下划线（`TC-30` 写成 `TC_30`），照抄编号，不补零、一条一个号不写成范围；写法与要求见 `references/文档模板.md` 第二节的「落成约定」。这条不改变开头那段边界：**落成是别人的活**，本技能不写那些代码，只管产出里留没留落点、两边对没对上。

它的退出码：`0` 两边对得上；`1` 有对不上的地方；`2` 用法或路径有问题；`3` 产出里写着「还没落成」，没有可对照的成品——**退 3 不是错**，就是这一批还没落成，看见它跳过就行，别当失败记。**分几批落成时照查**：那一块里既列了已落成的表、又写着「还没落成」交代剩下几处时，两向对照照样跑，只有「定义了却没在成品里出现」那一条降成提示——还没落的那几处本来就查不到，报成错只会逼人一次把表填全，那就没有分批了；已经落成的那一处真漏了，提示里看得见。

**落成那一步读三样，这一份技能里哪一样都没重述，落成的人三样都要在手上**：

1. **六份通用稿**——各条用例的消息正文从测试用例规格说明的「输入」栏来，判据从「预期结果」栏来；执行顺序与分几批从测试规程规格说明的「有序执行测试用例」与「各批落到哪」来；样本的字节与正文从测试数据需求来；环境项从测试环境需求来；模型与覆盖项从测试模型规格说明与覆盖项清单来。**第七份不把它们重述一遍**（配置原文一个字不贴），只读第七份落不出东西。
2. **第七份（实施方案规格说明）**——哪几条规程在这一套里跑、落成什么形式、落在哪个路径、编号在盘上怎么留痕，都在那一份里。**通用稿不认任何一种测评方案**，只读通用稿也不知道该摆成什么。
3. **`/skill-upper` 技能下 `references/` 那几份**——配置字段怎么填、命令怎么用，以它为准，这一份技能里不再抄一遍。

**条目编号一律由脚本从盘上推，不自己推算。** 写条目前先取号，照它打出来的号写：

```
python scripts/issue_ids.py <产出目录>                   七种编号各用到几号，先看一眼
python scripts/issue_ids.py <产出目录> TC- --count 8     取这一批的号，一行一个
```

前缀照写：`TM-`、`TCOV-`、`TC-`、`TP-`、`DATA-`、`ENV-`、`DEC-`；项目自己的编号惯例照传（如 `Lid-`）。**第 0 步起，每一步写新条目前先取这一批的号**，写完照旧随即落盘——盘上那份就是下一批号的基准；自检发现缺覆盖项、回第 4 步补用例时，补之前重新取一次。手上已有一批用例、往已有文档里接着编时，先跑一次不带前缀的那条，看七种编号各到几号了，再接着取。

脚本只读不写，**基准就是产出目录里那六份文档**，不另存台账——它不记「发到几号了」，每跑一次都从盘上重新数一遍。所以从零写的一批，取到的号就是 1 起连号；盘上已经写到几号，就接着往下。`--count` 给多了不占号——一批要 8 个、只用掉 5 个，下次发号仍从盘上接着往下，不留洞。编号的规矩（从 1 起、不跳号、不回收空号、生存周期内不改）见 `references/文档模板.md` 第二节。

**落成评测用例的那一批，用例目录名也由脚本打。** 规程那几栏落盘之后、写文末「各批落到哪」之前，先跑一次：

```
python scripts/issue_ids.py <产出目录> --case-dirs
```

它照「有序执行测试用例」栏数一遍位次，一条规程一行打出整条目录名（`tp01-01-TC-1-fix_only_what_should_change`），照抄进那张表新加的「用例目录名」栏。**位次别自己数**——那是这条链上唯一一处会数错的地方。形制、补零、一条规程一行怎么填，见 `references/文档模板.md` 第五节。

产出入库前跑一遍这个：

```
python scripts/check_docs.py <产出目录>
```

它查的是机械项——编号连不连续、栏目齐不齐、两张对应表有没有留空、覆盖率那一块的数对不对得上（T 等于覆盖项编号栏列出的条数、N 等于对应表里非空的条数、覆盖率栏的算式算得对）、引用的编号指不指得到（引了没有定义处的算错误，定义了却没人引的算提示）、落成评测用例的那几行「用例目录名」栏与规程的执行顺序对不对得上（少一条、多一条、位次写错都算错）、有没有漏进禁用词。**词表不写在脚本里**：两条禁令都从本技能里那两张表解析出来（「必须照写的几个词」的右列、「六份里不许出现的东西」的左列），改表就是改判据。**产出目录里有第七份时另起一组查它**：骨架（导语、对账表、`方案：`节）、每个方案节里两块齐不齐与次序、**六类编号**两个方向对不对得上（对账表六类都收：模型、覆盖项、用例、规程、数据项、环境项，少一类的落点就报错）。**决策依据那一条另有一套**：编号必须是 1 起连号，缺号或最大号大于行数都报错——那说明有旧条目被删掉或被改写过，而这份文档只增不改；两块分得对不对也查，「用户决策」那一块里混进别的来源、`用户给的` 那几条留在「模型决策」那一块里、决策表不在这两块里，都报错。报错就先改完再说，别把带错的产出交出去。判断性的东西它管不了：模型建得对不对、覆盖项取全没有、用例导得够不够，那些还得自己看。往已有文档里补用例的那条路，补完一样跑一遍。

第 6 步算下来覆盖率不够，缺哪些覆盖项，看「覆盖项 ↔ 用例」对应表里留空的行。缺的先回第 4 步补用例——只要覆盖项还能被执行、还能被用例覆盖，就得补上。确实覆盖不了的，要能证明它无法被执行或无法被测试用例覆盖，才按 `references/覆盖率与完成准则.md` 的规矩当不可行项剔除，并把原因记下来。这张表随测试用例规格说明一起落盘（格式见 `references/文档模板.md` 第八节）：覆盖率不够时看的就是它里面留空的行，补完用例把盘上那份一并改掉。算出来的覆盖率连同 N、T，落进测试用例规格说明的「覆盖率自检」那一块（格式见 `references/文档模板.md` 第四节）：一行一门选定的技术，写这一门识别出多少条覆盖项、其中多少条已被用例覆盖、算出来的覆盖率是多少，与完成准则对这一门的要求并排列出来。**T 要先拿这门技术的算式核一遍**（见 `references/覆盖率与完成准则.md` 第二节）——算出来多少条，清单里就该有多少条；核不上说明识别漏了或多了，回第 3 步补。流程允许回走，不是一次过。

**判据落在「要读执行过程」那一层的用例，自检时逐条再读一遍「预期结果」那一栏。**这一栏的两个取值见 `references/文档模板.md` 第四节。一条一条问：「这一条要是没做到，算不算这条用例没过？」拿不准的，多半是卡了一个可有可无的附带动作——同一件事，被测那边有时顺带说一句、有时不说，卡上去这条用例就一轮过一轮不过。删掉那一条；要留着，就在决策依据里记一条说明为什么留着，别让它悄悄待在那儿。

**成品落成之后，另跑一遍落成对照**：

```
python scripts/check_landing.py <产出目录>
```

它查的是产出与成品对不上号的地方：产出里定义了、成品里一处也没出现的编号，成品里冒出来、产出里没有定义处的编号，都报错。产出与成品是**一起看的两半**——文档写得再齐，成品里搜不到那些号，拿编号就对不上；落成之后没跑过这一遍，这笔账就没结。

**手上已经有一组用例、不是从零设计时**，走法不同：先看这组用例有没有测试覆盖项清单。有，就照第 6 步算覆盖率、按 `references/覆盖率与完成准则.md` 判够不够，缺的覆盖项按第 4 步补用例（补之前重新取号）；没有，就先按第 1–3 步补出模型与覆盖项，再回到第 6 步。这条路第 0 步那几样照样要——没有完成准则判不了够不够，没有风险信息定不了风险等级。补出来的覆盖项与用例写进 `Test Case Specification.md`：原来没有这份就新写一份，已有一份就往里补。其余四份按需更新，**不重出这几份文档，也不为了套流程把已有用例推倒重来。** 决策依据那份只往后加，不重写。

## 第 0 步：定开工输入

三样开工输入缺一不可——后面每一步「做到什么程度」都由它们定。三样的来路不同，**其中两样长在用户那边，一样由你自己定**：

| 开工输入 | 从哪来 | 缺了怎么办 |
|:---|:---|:---|
| 测试依据 | 用户给的那个对象：给的是路径、技能名、代码或需求文本，就去读它，读出来的对外契约就是测试依据 | 没给就问，不猜要测什么 |
| 风险信息 | **向用户要**：哪里风险高、近期改过哪里、出过什么故障 | **拿到再开工**，不自己编 |
| 测试完成准则（要求的覆盖率） | **自己定**：被测项目已有测试计划的照计划取；没有的按下面的默认口径定 | 不问用户 |

**测试运行环境不问了，默认就是本机。**测试规程在哪儿跑、被测那侧在哪儿执行，这两处都由你自己判，判完在第 5 步落成测试环境需求那两条环境项（写法见 `references/文档模板.md` 第七节）——不要再拿这个去问用户：绝大多数场合下这两处本来就是本机，问了只是让用户重复一遍。

**完成准则的默认口径：选定技术识别出的测试覆盖项全部取全、全部要有用例覆盖，即覆盖率按 100% 要求。**有覆盖档位的三门——分类树方法、组合测试、状态转移测试——档位按风险级别选；选低档不等于降准则，那一档识别出的覆盖项照样全部覆盖。低于 100% 要从覆盖项里挑子集，挑的时候得逐条说明放弃了什么，比全覆盖更难交代，所以默认不这么做。单个脚本、单个功能、一段需求这类场合没有测试计划，正是这条口径的用武之地。

**风险信息问什么、怎么问。**问的是只有项目里的人才知道的事：这个测试项最近改过哪里、出过什么故障、哪一块最怕出错。从测试项本身看出来的那几处（对外承诺的准确性、不可回退的副作用、边界与异常输入）问的时候一并摊出来，让他在这上面增删，别让他从零想。**不要问「风险等级定几级」**——定级是你根据他答的内容判的，判完落进产出文档的「风险等级」栏；把定级本身推回去，等于把第 3 步该干的活外包出去。

**测评方案那两问：先判、再问，涉及才问。**问之前先看**测试项本身**——它是技能、提示词这类靠模型跑的东西吗？

- **不是**（一段脚本、一个函数、一个库）——两问都不问，产出只有六份。
- **是**——先问「要不要一并出实施测评方案」：
  - 答**不要**——产出只有六份；
  - 答**要**——接着问「用哪个测评方案」。目前只支持 skill-up，默认就取 skill-up，别的方案先不支持。

**判「涉不涉及模型测评」只看测试项本身**，不看规程的「执行器」栏——那一栏要到第 5 步才定得下来，第 0 步判不了。代价写在明处：一个测试项里既有脚本层又有本体层时（比如一份技能的中心逻辑靠模型跑），第 0 步就按「涉及」算。

**答了「要」不等于这一轮就出第七份。**这一份也可以另起一次会话、手上已经有六份时单独出，走法见下文「只出实施方案那一份」。

**选了哪个方案不进六份。**六份通用稿一个字都不提拔了哪门方案——方案名与它自己的配置文件名在六份里都算禁用词（见「六份里不许出现的东西」）。方案的选择落在第七份的节名上：「<节号>、方案：<方案名>」。所以决策依据里也不记这一条；没有第七份时，它哪儿都不落。

**定完判完都要落进产出**：完成准则与风险等级写进测试模型规格说明的「测试策略摘要」栏与「风险等级」栏；测试运行环境那两条（默认本机）到第 5 步落成测试环境需求里的环境项，来源记 `技能定的`。落完接着往下做，不必再等用户点头。

**只问缺的开工输入，别的都不问。**第 0 步要问的就是上表里标着「向用户要」的那几样——测试依据没给就问测试依据，风险信息要问，判下来该问的那两问也要问，产出目录没给也要问。**交付范围不问**：「这次交到哪一步」「要不要顺便把用例落成能跑的代码」「要不要跑一遍看看」这类，本技能产出什么已经定死了（见开头那段），不是摆给用户挑的选项。把一件已经有答案的事做成选项，用户只能猜你本来该做什么，还得替你承担边界。第 1 步那四个决定同理：材料可以摊开讲，选择不摆成菜单。

## 只出实施方案那一份

第七份（`Implementation Specification.md`，实施方案规格说明）有两条入口，都不影响那六份：

**一、随六份一起出。**第 0 步答了「要一并出实施测评方案」的，六份走完第 7 步终检之后再出这一份——它要对账的六类编号到第 5 步才齐，早出了对不上。写之前读 `references/文档模板.md` 第十节（契约）与 `references/文档示例.md` 第七节（填写示例）；**先确认 `/skill-upper` 技能装着**（它就装在 `~/.claude/skills/skill-upper/`），没装就停下来让用户装，别照着印象写。装着的**先读它 `references/` 下那几份**——命令行怎么用、批次那一层有哪些字段、一条用例有哪些字段、判官有哪几种，各是一份；这一份里要写进去的每一条命令、每一个字段名，写之前照着核一遍。**别照印象写**：写了不存在的开关，或者漏了必填的那一项，要等到落成、跑校验的时候才撞见，那时通用稿已经定了稿。核完再读 `references/评测方案/skill-up/usage-notes.md`——读它是为了把落点与折扣写准（工作区怎么起、哪几条在这个方案上跑不了原样）。**配置原文不抄进这一份**。

**二、单独出。**手上已经有六份产出，这次只出第七份——和上面那条路并列，**不重出已有的文档**。走法：

1. 读盘上那六份，主要是测试环境需求与测试数据需求两份——对账要对它们；
2. 问一句「用哪个测评方案」（默认 skill-up）；
3. 确认 `/skill-upper` 技能装着（没装就让用户装，别照着印象写）；读它 `references/` 下那几份，把这一份里要写进去的命令与字段名逐条核过；再读 `references/评测方案/skill-up/usage-notes.md`，照 `references/文档模板.md` 第十节写这一份，落到同一个产出目录里；
4. 写之前先取号这一步**跳过**：这一份不定义任何编号，一个都不新发。

**这一份不吃「六份里不许出现的东西」那张表**——方案名与配置文件名在这一份里正该出现。

写完之后照旧跑一遍自检，第七份在产出目录里时那一组会一并查：

```
python scripts/check_docs.py <产出目录>
```

那一组查骨架（导语、对账表、`方案：`节）、每个方案节里两块齐不齐与次序对不对、六类编号两个方向对不对得上。**这一份里不贴配置原文**——配置由落成那一步照这一份写进盘里；抄一份进来，盘上那份一改就是第二份会漂移的副本，漂了还不报错。

## 第 1 步：四个决定，各自要有依据

第 1 步要定四件事，每件都得说得出依据：

| 决定 | 依据从哪来 |
|:---|:---|
| 选哪几门技术 | 从本技能详写的七门里选。判断材料见 `references/技术选型与组合.md` 第一、三节——第一节是质量特性到技术的映射表；第三节是七门各自拿什么当模型、建它时依据里要有什么，测试依据本身的形态——它本身就是一张状态图、一张判定表，还是一段散文——靠这两栏看；另有那份文件列的几项实际因素，七门之外的换用见那份文件末节。**这一项本技能明确不给方案**——业界对哪门技术有效性最高没有共识，本技能只给材料，不给结论。不给的是「什么时候选什么」那套规则；**选哪几门仍要你自己连同依据定下来**，选择与依据一起写进「测试策略摘要」栏。材料不够就如实说，不编规则 |
| 怎么组合 | 本技能给的几组搭配：一门技术的产出喂给另一门（等价类划分的覆盖项作场景测试的输入参数等）；以及用七门之外的技术补本技能这几门漏掉的那类缺陷（见那份文件第二节末） |
| 各建什么模型 | 技术决定模型形态——状态转移测试建状态图、判定表测试建判定表。选定技术后模型形态就定了；形态由技术反推，不自由发挥 |
| 做到什么程度 | 测试完成准则（要求的覆盖率）和风险级别。模型建到多细、覆盖项取全还是取子集、高风险处要不要多导用例，都由这两样定；其余可调之处见 `references/技术选型与组合.md` 第四节 |

依据只有三个来源，每一步、每一栏都要能归到其中之一；归不到的，先看缺的是哪一类：

| 来源 | 有哪些 | 技能能不能自己给 |
|:---|:---|:---|
| ① 技能自己给的 | 模型形态由技术决定、覆盖项怎么导出、输入值怎么选、预期结果从测试依据推、规程按前后置依赖排序、环境项的类型清单、编号方案 | 能，写进 references |
| ② 从测试依据与测试项推出来的 | 测试完成准则（要求的覆盖率），以及选型要权衡的四项实际因素（风险等级、关键程度、应用领域、实施成本）里能从测试项看出来的那些 | 能，推法见「第 0 步」与 `references/技术选型与组合.md` 第一节末 |
| ③ 只有用户那儿有的 | 测试依据、风险信息 | 不能，向用户要；这两样不齐不勉强开工 |

- **② 那几样不要摆给用户挑**：都从测试项本身看得出来，判完写进产出即可。被测项目已有测试计划的，照计划取，不另判。
- **③ 那几样不要自己编**：测试依据是「要测什么」，风险信息是「这个项目怕什么」——测试项本身都看不出来，编出来的只是推测，看着再合理也一样。
- **判断不等于编**：② 那几样判成什么样，都要说得出看的是测试项的哪一处；说不出的，回「第 0 步」看该看哪几处，不随手填一个数充数。
- **依据要落进产出，不是心里想过就算**：技术选型与完成准则写进测试模型规格说明的「测试策略摘要」栏；风险等级写进「风险等级」栏。写不进产出的依据等于没有依据。

## 必须照写的几个词

产出文档里，这几个词照左列写，不要换成右列。它们与本领域更常见的说法只差一点，不单列出来最容易写错，写错了就跟技能其余部分对不上。

| 本技能要求 | 容易写成 | 为什么 |
|:---|:---|:---|
| 测试模型 | 测试条件 | 「测试条件」在别处更常见，最容易顺手写上；本技能全库统一用前者 |
| 测试依据 | 测试的证据、测试数据 | 它是设计用例所依据的信息源 |
| 测试项 | 测试用例、被测对象 | 指被测的那个东西 |
| 测试覆盖项 | 覆盖点、覆盖目标 | 指模型里要被覆盖的那个元素 |
| 测试规程 | 测试脚本、测试流程 | 指用例的执行顺序，加启动与收尾动作 |
| 测试用例规格说明 | 测试用例文档 | 它是正式的文档名 |
| 应／宜／可 | 统写成「要」 | 顺手把这三个字改成「要」，会把原话的语气带偏 |
| 有效测试用例／无效测试用例 | 正确用例／错误用例 | 导出方法那组术语的固定说法 |
| 一对一方式／最小化方式 | 逐条方式／最少用例方式 | 同上，指选择测试覆盖项组合的两种方法 |
| 测试完成准则 | 测试完备性准则、测试充分性准则 | 后两个名指的是同一件事；本技能全库统一用「测试完成准则」，不跟着换 |
| 未规定功能 | 未定义行为、未指定功能 | 指测试依据中未予以明确的那些功能——测试项若执行了依据里没写的功能，缺陷在测试项或依据那一侧 |
| 风险等级 | 优先级 | 「优先级」自带顺序的意思，写着写着就变成规定执行顺序；排执行顺序是测试规程的事，这一栏只是个等级 |

## 六份里不许出现的东西

六份通用稿要能原样拿去当代码或技能的测试依据，所以它们不认任何一种测评方案、也不认任何一种具体环境。下面这些词**六份产出里一个都不许出现**——它们该怎么写、第七份里正该出现的是什么，见 `references/文档模板.md` 第十节。

| 词 | 为什么 |
|:---|:---|
| skill-up | 测评方案的名字。用哪个方案是实施方案规格说明那一份的事，通用稿不认 |
| eval.yaml | 同上，那个方案自己的配置文件名 |
| case.yaml | 同上 |
| graders/ | 同上，那个方案给每条用例的判据留的目录名。判据本身照写不误（ENV-3 说的就是它），但落在哪个目录、叫什么文件名，是那个方案的事，通用稿不点名 |
| WSL2 | 具体环境名。要写就写「默认就是本机」，或者写这一条环境项管的是什么 |
| Docker | 同上 |
| 本机 Windows | 同上；「本机」两个字就够，不必点名是哪个系统 |

`scripts/check_docs.py` 按这张表左列查，命中就报**错**，不降成提示。范围分两档：**方案名、它自己的配置文件名、它给判据留的目录名**六份全查；**具体环境名**查五份，`Decision Basis.md` 除外——那一份记的是过程，「当时定的是本机 Windows」是照实记，不是违规。

第七份（实施方案规格说明）**不吃这张表**：那一份里正该出现方案名与配置文件名。

## 几处边界

**技术文件只覆盖 TD1–TD3，不覆盖 TD4。** 七份技术文件讲的是建模型、定覆盖项、导出用例这三步；规程怎么排序、怎么编，只在 `references/流程.md` 里讲，技术文件里不出现。走到 TD4 时不必再翻技术文件。

**测试计划那一层（管理级）只作接口。** 测试完成准则优先从被测项目已有的测试计划里取，没有计划的按「第 0 步」的默认口径自己定；风险信息这一层给不出时，向用户问一句（见「第 0 步」）。测试方针、测试计划的编写、测试执行、事件报告都不在本技能范围内。

**七门之外的技术：只告知，不代做。** 看出某处更适合七门之外的技术时，明确告诉用户「这里更适合 X」，并说明 X 管什么，但不替用户做。七门之外还有哪些、各自管什么，见 `references/技术选型与组合.md` 的末节。

## 什么时候读哪份文件

每次都用得上的是这五份（第六份「决策依据」的写法也在 `references/文档模板.md` 里，不另开文件）：

- `references/流程.md`：走到 TD1–TD4 每一步时读——四步各要做什么、每步该记录哪一段可追溯性（依据 → 模型 → 覆盖项 → 用例 → 规程）都在这里；末尾有一个从测试依据走到测试规程的完整示例。
- `references/技术选型与组合.md`：第 1 步定技术方案时读——选哪几门技术、怎么组合、各建什么模型与建它时依据里要有什么、做到什么程度，以及七门之外技术的换用告知。
- `references/文档模板.md`：写产出时读——六份文档各有哪些栏目、各栏怎么填、编号方案、两张对应表的格式、成品落点那一块、编号与英文名怎么落到成品里、决策依据那份分两块与只增不改的规矩，以及第七份（实施方案规格说明）的骨架契约（第十节）。
