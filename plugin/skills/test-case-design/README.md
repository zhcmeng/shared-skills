# test-case-design

为一段需求或一个功能设计测试用例——从测试模型一路做到测试规程，产出五份 Markdown 规格说明。

这份 README 是给人看的：Claude 跑这个技能时不读它，读的是 [SKILL.md](./SKILL.md) 和它按需打开的 `references/` 下那几份参考文档。背景、来源、效力这些话因此都写在这里，技能本体里不写。

## 什么时候会触发

会话里出现这类活，技能会自己触发：

- 给某段需求或某个功能写测试用例
- 改一改已有的一组用例
- 判断一组用例覆盖得够不够

也可以点名调用：直接说「用 test-case-design 给这段需求写用例」就行。斜杠命令按安装方式走——随本仓库的插件装是 `/shared-skills:test-case-design`，只把这个目录放进某个工程的 `.claude/skills/` 下则是 `/test-case-design`。

## 调用时要给什么

要给的其实只有两样：

| 给什么 | 指什么 |
|:---|:---|
| 测试依据 | 要测的那段需求、那个功能或那个脚本本身——给路径、技能名或需求文本都行，Claude 会去读它，用例从它推出来 |
| 产出目录 | 五份 Markdown 写到哪儿。没给会先问，不猜默认路径；目录不存在会自动建 |

另外两样——测试完成准则（要求的覆盖率）与风险信息——不用你给，Claude 按测试项的特点自己判：完成准则默认取 100%（选定技术识别出的测试覆盖项全部要有用例覆盖），风险信息按「出了错谁会受影响、代价多大、能不能回退」这类特点定。项目里已有测试计划的，照计划取，不另判。两样判完都写进产出——完成准则进「测试策略摘要」栏、风险等级进「风险等级」栏——判得对不对，看文档就知道，不必开工前先答一轮。

## 产出什么

五份 Markdown，都写进指定的输出目录。**文件名是英文的，正文写中文**——别把英文文件名当成英文文档，产出照旧全中文；技能自己的说明文件也是中文。

| 文件 | 装什么 |
|:---|:---|
| `Test Model Specification.md` | 每个测试模型的目标、测试策略摘要与模型本体，末尾附「依据 → 模型」对应表 |
| `Test Case Specification.md` | 测试覆盖项清单与测试用例，加「覆盖项 ↔ 用例」对应表 |
| `Test Procedure Specification.md` | 用例的执行顺序，含启动与收尾 |
| `Test Data Requirements.md` | 用例与规程要用的数据，逐条列出 |
| `Test Environment Requirements.md` | 测试规程要在什么环境上跑，逐项列出 |

每份的栏位、编号方案与对应表格式见 [文档模板](references/文档模板.md)；填起来长什么样，[文档示例](references/文档示例.md) 里有一整套填写示例。

## 管到哪为止

到五份规格说明产出为止。**不含测试执行，也不含测试事件报告**——用例编完、规程排好就收工；跑不跑、跑出问题怎么上报，不在技能范围里。

再往外还有两处不碰：

- **测试方针与测试计划的编写**不在范围内。开工要的测试完成准则与风险信息，被测项目已有测试计划的照计划取；没有的按测试项的特点自己判并写进产出，不反问你要。
- **技术只详写了七门**（列在下面的文件结构里）。哪一处更适合别的技术，Claude 会告诉你那门管什么、这里该不该换，但不会拿七门里的某一门顶替着做。

## 来源与效力

技能内容取自 **GB/T 38634 系列标准的修订征求意见稿**，是一份还在修订、公开征求意见的材料。**它不是现行标准**，这一点有三个实际后果：

- **内容可能与现行版本有出入。** 这份材料汇总意见后还会再改，技能里的做法、用词、覆盖率口径都来自它，不保证与后来的正式版本一致。
- **正式场合要另行核对。** 对外交付、合规检查、写进合同这类场合，别拿这份技能当依据；需要引用版本的地方，自己用现行版本核一遍。
- **产出里没有出处标注。** 五份文档只写测试内容，不带引用与出处，别把它当成可引用的权威文本。

技能本体因此做成自包含的：会话里不去联网找这份材料，也不翻本仓库的存档；技能没覆盖到的细节，Claude 直接问用户。Claude 会读的那几份（`SKILL.md` 与 `references/`）里，出处只在 `SKILL.md` 开头那一句来源说明里出现，别处没有。

## 文件结构，与想改行为该动哪个文件

```text
skills/test-case-design/
├── README.md                  你正在读的这份（Claude 不读）
├── SKILL.md                   主流程，Claude 默认只读这一份
├── references/
│   ├── 流程.md                 四步流程：模型、覆盖项、用例、规程
│   ├── 文档模板.md             五份产出的栏位与编号
│   ├── 文档示例.md             五份产出的填写示例
│   ├── 覆盖率与完成准则.md      覆盖率怎么算、多少算够
│   ├── 技术选型与组合.md       选哪几门技术、怎么组合、做到什么程度
│   └── 技术/
│       ├── 等价类划分.md
│       ├── 分类树方法.md
│       ├── 边界值分析.md
│       ├── 组合测试.md
│       ├── 判定表测试.md
│       ├── 状态转移测试.md
│       └── 场景测试.md
├── scripts/
│   ├── check_docs.py          产出写完自检：编号、栏目、对应表、禁用词
│   └── issue_ids.py           写条目前的取号：读盘上五份文档，发下一批编号
```

七门技术一门一份文件——改一门碰不到别的，用不上的那几门也不占地方。

上面那两个脚本的测试不在这个目录里：它们在仓库根的 `tests/test-case-design/` 下，一个脚本一份。装着技能一起发出去的东西里不含测试。

想改技能行为，按下表动文件。README 只讲是什么、给什么、产出什么，不写做法：改做法细节不用回头改它；但 README 里复述别处事实的地方（开工要哪几样、五份产出的名字与内容、文件结构、来源与效力这些），那边改了这边要跟着改。拿不准就把你改掉的说法在 README 里搜一遍。

| 想改什么 | 动哪个文件 |
|:---|:---|
| 流程本身、开工要哪几样、用词纪律、什么时候读哪份参考 | `SKILL.md` |
| 四步各自的任务条目与要记录的可追溯性、完整示例 | `references/流程.md` |
| 产出的栏名、编号方案、对应表格式 | `references/文档模板.md` |
| 产出的填写示例 | `references/文档示例.md` |
| 覆盖率怎么算、各技术的要求、算完够不够怎么判 | `references/覆盖率与完成准则.md` |
| 选型与组合（含七门各拿什么当模型、建它时依据里要有什么）、做到什么程度、七门之外的换用告知 | `references/技术选型与组合.md` |
| 某一门技术的内容 | `references/技术/<那门>.md` |
| 产出自检查哪些机械项 | `scripts/check_docs.py`，改完跑 `python tests/test-case-design/test_check_docs.py`（在仓库根跑） |
| 写条目前的取号 | `scripts/issue_ids.py`，改完跑 `python tests/test-case-design/test_issue_ids.py`（在仓库根跑）。它认「哪些号已经用过」用的是 `check_docs.py` 里的判定，两边别分叉 |

文件之间互相引用，写法有两种：多数文件用 Markdown 相对链接，`SKILL.md` 与 `references/文档模板.md` 里是反引号包着的路径（那是给 Claude 照着读的指令，不是给人点的链接）。改文件名时两种都要一起改——稳妥的办法是拿文件名全文搜一遍，只搜 `](` 会漏掉反引号那一类。

## 两个脚本的脾气

`check_docs.py` 是产出写完的自检，测试十二条：先造一套合规产出确认它判过，再逐处改坏、确认每处都被逮住。

**禁用词表不在脚本里**，是从 `SKILL.md` 的「必须照写的几个词」那条表解析出来的。所以改那张表，脚本跟着变，不用两边各改一遍。反过来说：那张表的写法变到解析不出来时，脚本会直接报错退出，不会静默放过——它宁可停下，也不拿一份空表去判。

`issue_ids.py` 是写条目前的取号。它**不另存台账**，基准就是产出目录里那五份文档，靠直接调 `check_docs.py` 的判定（`import check_docs`）算「哪些号已经用过」。这份判定不许在 `issue_ids.py` 里另写一份：两边一旦分叉，发出去的号就会撞上文档里已有的号。
