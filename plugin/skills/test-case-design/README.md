# test-case-design

为一段需求或一个功能设计测试用例——从测试模型一路做到测试规程，产出六份 Markdown 文档。

这份 README 是给人看的：Claude 跑这个技能时不读它，读的是 [SKILL.md](./SKILL.md) 和它按需打开的 `references/` 下那几份参考文档。背景、来源、效力这些话因此都写在这里，技能本体里不写。

## 什么时候会触发

会话里出现这类活，技能会自己触发：

- 给某段需求或某个功能写测试用例
- 改一改已有的一组用例
- 判断一组用例覆盖得够不够

也可以点名调用：直接说「用 test-case-design 给这段需求写用例」就行。斜杠命令按安装方式走——随本仓库的插件装是 `/shared-skills:test-case-design`，只把这个目录放进某个工程的 `.claude/skills/` 下则是 `/test-case-design`。

## 调用时要给什么

要给三样：

| 给什么 | 指什么 |
|:---|:---|
| 测试依据 | 要测的那段需求、那个功能或那个脚本本身——给路径、技能名或需求文本都行，Claude 会去读它，用例从它推出来 |
| 风险信息 | 这个测试项哪里最怕出错、最近改过哪里、出过什么故障。这几样只有你知道，Claude 从测试项本身看不出来，所以会先问，你答了才开工 |
| 产出目录 | 六份 Markdown 写到哪儿。没给会先问，不猜默认路径；目录不存在会自动建 |

判下来涉及模型测评时（测试项是技能、提示词这类靠模型跑的东西），还会问两句：**要不要一并出实施测评方案**；答要再问**用哪个测评方案**——目前只支持 skill-up，默认就是它。不涉及的话这两句都不问，产出只有六份。测试项是一段脚本、一个函数、一个库时就是不涉及。

还有一样不用你给：**测试完成准则**（要求的覆盖率）由 Claude 自己定——默认取 100%（选定技术识别出的测试覆盖项全部要有用例覆盖），项目里已有测试计划的照计划取。定完写进产出的「测试策略摘要」栏，做的什么口径看文档就知道。

风险信息问回来之后，风险等级由 Claude 判——问你的是「哪里怕出错」，不是「风险定几级」。测试运行环境不再问了：默认就是本机，落成产出里「测试环境需求」那两条环境项——一条写规程在哪儿跑、一条写被测那侧在哪儿执行——由 Claude 自己判。

## 产出什么

六份 Markdown，都写进指定的输出目录；涉及模型测评、并且答了「要一并出」时，另出一份实施方案规格说明。**文件名是英文的，正文写中文**——别把英文文件名当成英文文档，产出照旧全中文；技能自己的说明文件也是中文。

| 文件 | 装什么 |
|:---|:---|
| `Test Model Specification.md` | 每个测试模型的目标、测试策略摘要与模型本体，末尾附「依据 → 模型」对应表 |
| `Test Case Specification.md` | 测试覆盖项清单与测试用例，加「覆盖项 ↔ 用例」对应表、第 6 步算出来的「覆盖率自检」，末尾一块「成品落点」 |
| `Test Procedure Specification.md` | 用例的执行顺序，含启动与收尾 |
| `Test Data Requirements.md` | 用例与规程要用的数据，逐条列出 |
| `Test Environment Requirements.md` | 测试规程要在什么环境上跑，逐项列出 |
| `Decision Basis.md` | 每一处决策当时摆着哪几种做法、凭什么取了这一种；**分两块写**：前一块是你拍板的（可以直接改），后一块是 Claude 判出来的（只增不改） |
| `Implementation Specification.md` | **按需产出**。把六份通用稿落成能跑的东西：哪条编号落到哪个配置文件、哪一段、盘上哪个路径，可跑配置以 YAML 原文贴出。不定义任何新编号，只引用前六份的 |

第七份什么时候产：测试项是技能、提示词这类靠模型跑的东西，且答了「要一并出」；也可以手上已有六份、另起一次会话只出这一份。它是**按方案分节**的——目前只有 skill-up 一节；将来比别的方案在同一份里再起一节，六份通用稿一个字不用动。

前五份记结论，第六份记过程。**决策依据那份是这次专门加上的**：只看前五份，你只看得见 Claude 定了什么，看不见它怎么定的——哪一步判歪了也看不出来，也就无从把技能改对。所以每在几种做法里挑一次就记一条，写明取的那一种与不取的那几种各是什么理由。

这一份分两块，为的是**你一眼看到自己拍板的那几条、随时能调**：

- **上面一块是你拍板的**——「依据的来源」栏写着 `用户给的` 的那几条（完成准则、风险等级这些）。**可以直接改**：旧的样子 git 里看得到，不必另起一条写订正；改完让 Claude 把其余五份里跟着变的地方一并改掉。
- **下面一块是 Claude 判出来的，只增不改**——条目只往后加，后面的决定推翻了前面的，新增一条写明订正了哪条，旧条目原样留着。那些条目留着的是「当时怎么想的」，好让你看出它哪一步判歪了、好在哪一处把技能改对。

每份的栏位、编号方案与对应表格式见 [文档模板](references/文档模板.md)；填起来长什么样，[文档示例](references/文档示例.md) 里有一整套填写示例。

除决策依据外，五份里的每条条目还带一个**英文名**，紧挨着编号写——`TC-11` 的英文名是 `file_not_utf8`。它是这条条目落成代码时的名字核：下游照它拼函数名、类名、变量名，同一套产出每次生成的名字才是同一个，不会换个会话就换一批。决策依据不带这一栏——那份记的是过程，不落成任何对象。

产出里还留着一块**成品落点**（测试用例规格说明的第五块）：这批用例落成的可跑测试、评测用例放在哪个路径，一份一行；还没落成就写「还没落成」。**落成之后回来把那张表填上，再跑一遍对照**——产出里定义了、成品里却一处也没出现的编号，成品里冒出来、产出里没有定义处的编号，都报出来。要点是在成品里**每条条目的编号都搜得到**：照抄编号，代码里写不成连字符就换成下划线（`TC-30` 写成 `TC_30`），不补零、不写成范围。落成之后回来对一次账，是为了让成品与文档能互相对上：拿着文档里的编号去成品里搜能搜到，成品里看到一个号也知道它出自哪一条。

## 管到哪为止

到文档为止，**产出就是那六份（加按需的一份第七份）**——用例编完、规程排好就收工。

**不写可跑的测试代码，也不跑测试。**用例只落在文档里，不会变成工程里那种能执行的测试文件，也不出测试事件报告。工程里本来有放测试代码的地方和命名约定（比如 `tests/` 下按脚本名建文件），那是那个工程自己的事——不因为它在那儿就顺手写一份；要真落成代码，是另一步、另一个技能的活。你点名要代码，Claude 会说明这不在本技能范围内、该由谁做，然后照旧把六份文档出完——**这条边界不摆给你挑**。落成那一步做完回来，Claude 会跑一遍 `check_landing.py` 对账——**那一步只读成品，不写成品**，读的是别人落下来的代码与评测用例。第七份也在这门技能范围内，但它同样只有文档——**第七份里贴的 YAML 是给人拷的，技能不照着它去建目录、也不跑评测**。

再往外还有两处不碰：

- **测试方针与测试计划的编写**不在范围内。开工要的测试完成准则由 Claude 自己定，项目已有测试计划的照它取；风险信息这一层给不出时，Claude 来问你要。
- **技术只详写了七门**（列在下面的文件结构里）。哪一处更适合别的技术，Claude 会告诉你那门管什么、这里该不该换，但不会拿七门里的某一门顶替着做。

## 来源与效力

技能内容取自 **GB/T 38634 系列标准的修订征求意见稿**，是一份还在修订、公开征求意见的材料。**它不是现行标准**，这一点有三个实际后果：

- **内容可能与现行版本有出入。** 这份材料汇总意见后还会再改，技能里的做法、用词、覆盖率口径都来自它，不保证与后来的正式版本一致。
- **正式场合要另行核对。** 对外交付、合规检查、写进合同这类场合，别拿这份技能当依据；需要引用版本的地方，自己用现行版本核一遍。
- **产出里没有出处标注。** 六份文档只写测试内容，不带引用与出处，别把它当成可引用的权威文本。

技能本体因此做成自包含的：会话里不去联网找这份材料，也不翻本仓库的存档；技能没覆盖到的细节，Claude 直接问用户。Claude 会读的那几份（`SKILL.md` 与 `references/`）里，出处只在 `SKILL.md` 开头那一句来源说明里出现，别处没有。

## 三个脚本的脾气

`check_docs.py` 是产出写完的自检，测试九十八条：先造一套合规产出确认它判过，再逐处改坏、确认每处都被逮住。

用到的第三方库只有 `PyYAML`（查第七份里贴的 YAML 解析不解析得过），而且**只在真要用的时候才导入**——产出目录里有第七份时才需要它。缺了它不静默跳过那一项：报成一条错误，让你看得见（装上就行：`pip install pyyaml`）。六份那一路、取号、落成对账都不碰 YAML，缺它也不受影响——那三个脚本是一起 `import` 的，导入写在顶上就会连坐。

**禁用词表不在脚本里**，是从 `SKILL.md` 的「必须照写的几个词」那条表解析出来的。所以改那张表，脚本跟着变，不用两边各改一遍。反过来说：那张表的写法变到解析不出来时，脚本会直接报错退出，不会静默放过——它宁可停下，也不拿一份空表去判。

`issue_ids.py` 是写条目前的取号。它**不另存台账**，基准就是产出目录里那六份文档，靠直接调 `check_docs.py` 的判定（`import check_docs`）算「哪些号已经用过」。这份判定不许在 `issue_ids.py` 里另写一份：两边一旦分叉，发出去的号就会撞上文档里已有的号。

`check_landing.py` 是成品落成之后的对账，测试二十一条。它不生成品路径时就从「成品落点」表里取，所以那张表填糊了它会直接说「没拿到成品路径」而不是猜。两处特意写死：**产出目录里那几份文档不算成品**（六份通用稿加按需的第七份——第七份的对账表里什么编号都有，不排掉的话它会把数据项与环境项那两条正向检查顶过去）——不写死的话，把产出目录整个当成品路径传进去，文档里什么编号都有，它会报「全过」，那种全过比报错还会骗人；**不是 UTF-8 的文件跳过并说一声**——样本文件是测试数据，编号不会写在它的字节里，读不动就报错的话谁都得在命令上把样本一份份挑出去。
