# 技能台账建议

给一个技能，判断它该不该配台账，再给出「改哪几处、怎么改」的建议清单。

**产出是建议，不是改动。** 这个技能不碰目标技能的任何文件——改不改、怎么改，由拿到建议的人定。

**台账是什么**：一个跨上下文压缩活下来的文件。会话被压缩、换一个会话接着干、或者交给子代理去做之后，读它就知道「做到哪了、中途定了什么、为什么」，不必从头再来。

## 第 0 步：先确认拿到的是技能

一个技能的形状：**一个目录，里面有 `SKILL.md`**，而 `SKILL.md` 开头是 `---` 包起来的一段元信息。同目录下可能还有写给人看的说明文件，那不是 `SKILL.md`，判断形状时不用管它。

| 拿到的是 | 怎么办 |
|:---|:---|
| 一个技能的名字 | 按目录名把它找出来——仓库的 `skills/`、`plugin/skills/` 下，或者配置目录的 `skills/` 下 |
| 一个技能的目录，或者它里面的 `SKILL.md` | 认**那个目录**是技能：`SKILL.md` 是技能的一部分，不是另一个东西 |
| 一个不属于任何技能的普通 Markdown、一个没有 `SKILL.md` 的目录、一个不存在的路径 | **直说这不是技能，停下**。别硬凑一份清单出来 |
| 什么都没给 | 跳过这一步：直接把第 1 步到第 7 步的判据与清单给出去，当参考读 |

## 第 1 步：判该不该配

### 四条信号，中两条以上才配

| 信号 | 问法 |
|:---|:---|
| 跨上下文边界 | 这个技能的活会不会跨上下文压缩、跨会话，或者交给子代理接着干？ |
| 重做代价高 | 做到一半丢了，重来要花掉多少时间、多少外部调用、多少钱？ |
| 中途要做决定 | 规范没写清、两种合理做法要选一个，而这些决定后面的步骤还要接着用吗？ |
| 同一套流程连着跑多轮 | 每轮结束得记住「上一轮到哪了」吗？ |

### 不该配的三类

| 不该配 | 例子 |
|:---|:---|
| 一次调用几分钟内跑完，丢了重跑便宜 | 翻译一篇文章、数一段文本有多少字这类活 |
| 状态已经在产出里 | 产出的文件本身就写着进度——比如一份要填五个栏目的文档，填到哪一栏一眼看得出 |
| 状态已经在提交历史或问题单里 | 提交记录本身就是记录，再加一份是重复 |

**四条信号一条都不中时，结论直接写「不该配」，并说清为什么。** 别为了显得有用而硬加——配一套记账的负担，比不配更贵。

三类是**排除**条件，只在状态**完全**落在那里时才排除：只是部分落在那里——比如提交里有代码，但中途定了什么、为什么这么定，没记下来——仍按四条信号判。两类同时够格时先看三类：是真的「完全」就不配，不是就按信号走。

判成「不该配」就直接跳到第 7 步。

## 第 2 步：总则

下面到第 5 步，讲的都是「一份台账该是什么样」，一个字不看目标技能——先把标准立起来，第 6 步才拿它去诊断。这几步是第 7 步出清单要用的准绳：清单里那两节就是照它们填的。

### 台账的职责

它是扛住上下文边界的那个文件：会话被压缩、换一个会话接着干、或者活交给子代理去做之后，接手的一方读它就知道做到哪了、中途定了什么、为什么这么定。

它记的是**状态与决定**，不是活本身。长期的记录落在提交历史或产出里，台账是临时的脚手架。

### 只追加，不改写

**这条是硬规矩：写下去的行就是记录，不回头改。**

- 发现前面某行写错了，在后面追加一行把更正说清楚，不回去动那一行。
- 通篇重写、顺手把格式整一整、把几行并成一行，都算改写。
- **为什么**：台账是忠实的记录——写下去什么样，就是当时真写下了什么。改过之后读的人分不出哪一版是当时的，恢复也就没了依靠；而恢复本来靠的就是搜前缀（第 4 步「每完成一件事」），搜的前提是行不挪位置。

### 什么进台账、什么不进

**判据两条，中一条就写**：这件事丢了之后，接着做的人要白做一遍；或者没别人知道，毛病会被带着往下走。

| 这种情况 | 写不写 | 为什么 |
|:---|:---|:---|
| 从产出、提交历史或盘上直接读得回来的 | 不写 | 抄一遍是白占地方，还多一处会过期 |
| 中途做的决定 | 写 | 读的人靠它判断这条决定该不该推翻 |
| 发现了、没当场解决的 | 写 | 不写就等于没发现，后面的人不知道有这条 |
| 长的原始输出（测试日志之类） | 写一行 | 原文放旁边，不占台账的地方 |

上面每一条**怎么写**，在第 4 步「每完成一件事」那张表里。

### 一份好台账的标准

- **每个结论都挂着能当场查的东西**：提交号、文件加行号、跑过的命令和结果。写得能被查证，是台账被信任的前提。
- **每条决定都写了代价**：没有「错了要付什么」那一段，读的人没法判断该不该推翻它。
- **短是结果，不是标准**。决定长短的是「有没有把能从别处查回来的东西抄进来」，不是目标行数。同一个数字每处都要现算，那多写一行反而省事；提交里已经有的代码再抄一遍，多一行都是白占地方。

## 第 3 步：一份台账的结构

一次活一个目录，目录里一份台账文件。打开它，从上到下是这么几块：

```text
<一次活的目录>/
└─ 台账文件
   ├─ 第 1 行    这份台账归哪一次活、什么时候的活，后面跟一样能当场找到它的东西
   ├─ 分节       正文按轮次或任务分段，同一轮里的几件事挨在一起
   ├─ 说结论的行 开头是编号加一个固定的词，标出这是哪一类事（做完的／中途定的／遗留的）；
   │            末尾跟一样能当场查的东西（提交号、文件加行号、跑过的命令和结果）
   └─ 挂证据的行 实测出来的东西（基线、跑红的、跑绿的），`-` 开头，
                挨着写在它撑的那条结论上面，不走那三个词
```

下面第 4 步按三个时机讲，每一节讲的都是这上面的一块。

## 第 4 步：三个时机怎么写

### 开工：归属行、位置

**做法**：一次活一个目录，目录名从那一次活的名字派生，放在产出之外——不会被当成产出的一部分交出去的地方（在版本控制下，就是被忽略的工作区）；文件第一行写清这份台账是给哪一次活、什么时候干的。

**怎么算做对了**：已经有台账时，先看首行是不是自己那份；不是自己那份就不碰——不往里写，也不照它跳过任务。

**为什么**：台账会被下一个会话读到。归属不能靠「用完记得清理」——台账存在的理由就是扛崩溃和上下文压缩，而这两种情况恰恰不给收尾的机会，所以归属必须写进数据本身。

**示例**——首行的形状：

```text
# 台账 — <这一次活的名字>（<日期>；<能当场找到那一次活的东西>）
```

示例文件里那份填进去是这样：

```text
# 台账 — 检查脚本迁移与自动化（2026-09-23；计划：docs/superpowers/plans/2026-09-23-检查脚本迁移与自动化.md）
```

名字是人起的，认不出是哪一次；日期说清这是什么时候的活；最后那一样能当场打开，才认得出是不是自己要接着干的那件事。

### 每完成一件事：记哪些事、每行怎么写、能当场查的东西

**做法**：追加一行，一行一件事。行首是**编号**加一个固定的词：编号标出这一行说的是哪一件活，那个词标出这是哪一类事——**那三个词每个技能都一样，英文，不译**。结论后面跟一样能当场查的东西。

台账里还有一类行不套那三个词：**实测出来的东西**——基线、跑红的、跑绿的、跑挂的输出。`-` 开头，挨着写在它撑的那条结论行上面（示例文件里每个任务开头那几行就是这个位置）。写不写还是按第 2 步那两条判据：丢了要让人白做一遍的，就得写下来。

编号按这个技能自己怎么切活来定：

| 编号写成什么 | 什么时候用 | 例子 |
|:---|:---|:---|
| 任务号 | 活是切成几个任务做的 | `Task 3: complete (…)` |
| 轮次 | 活是同一套流程连着跑好几轮的 | `第 2 轮: open: …` |
| 步骤号 | 活是照一份步骤清单走的 | `Step 4: complete (…)` |
| 那一段的名字 | 活没切成编号的单位，或者这几行不归某一个单位 | `Task 3 之后：Ruling: …`（示例文件里就有这一行，冒号照它原样） |

一个编号在整份台账里只指同一件活，同一个编号的行挨在一起。

| 标识 | 哪一类 | 什么时候写 | 必须带哪几样 |
|:---|:---|:---|:---|
| `complete` | 做完的 | 这件事做完了 | 末尾一样能当场查的东西 |
| `Ruling` | 中途定的 | 本来没人定过的事，你定了——规范没写清、计划没提、用户中途改了主意、本该用户拍板而替他拍了 | 三段：定了什么、为什么、错了要付什么代价 |
| `open` | 遗留的 | 发现了、还没解决。**要当场修的也先写这一行再动手** | 三样：是什么、有多严重、什么时候必须处理 |

三类是下限。这个技能要是还有别的状态要记，可以再加一类、名字自己起——但这三个词固定，不改。

遗留那一类**一条问题一行**，行首写 `open`。三样里有两样用固定标识——「有多严重」用严重度、「什么时候必须处理」用去向。**上面这三类，加上这两组，一共九个词，每个技能都一样，英文，不译**；除此之外的部分按这个技能自己的活来定。

| 严重度 | 判的人给的是什么结论 | 接着怎么落 |
|:---|:---|:---|
| `Critical` | 不修不行 | 进 `fix` |
| `Important` | 不修的话，这件事就不能算可信 | 进 `fix` |
| `Minor` | 修不修都行——覆盖可以更广、措辞可以更好这类 | 留到收尾前那一遍分判 |

| 去向 | 什么时候是这条 | 怎么办 |
|:---|:---|:---|
| `fix` | 重到不能带着这次活交出去 | 先照遗留那一类记一行，再当场修；修完追一行记结果（照「做完的」那一类） |
| `defer` | 是真的，但不至于现在修 | 先记着，**收尾前那一遍读它**——那时看得到全貌，才分判得出哪些必须修 |
| `park` | 是真的，但没有东西建在它上面 | 记着不修，配一条 `Ruling` 说清它为什么站得住；**后面有活要碰同一处时，动手前先看这条** |
| `Ruling` | 是真的，而且承重——后面的活建在它上面 | 当场写成一条独立裁定（「中途定的」那一类）——**写进台账就是交到用户手上的办法**；收尾前把它拿出来给人看，并带进后面的活 |

**怎么算做对了**：按第 2 步那两条判据过一遍。发现了、不修、也不记，等于没发现——不许静默丢弃。长的原始输出放旁边单独一个文件，这一行只指过去。已经写下的行不回头改；写错了，在后面追加一行把更正说清楚。

**为什么**：恢复靠的就是一句搜索——带 `complete` 的那几行说明这些事不用重做。标识固定，压缩后的自己才一眼搜得出来，换个技能也照样搜得动。遗留那一类为什么要标去向：去向定了，谁在什么时候读它也就定了。反过来，一条记下来却没人会看的遗留项，跟没记一样——上游把这种叫「静默丢弃」。要当场修的那条也先记一行再动手——只留修完之后的结果，就把「发现过什么」抹掉了：修到一半丢了上下文，重来的人连要找什么都不知道。行首三类、严重度、去向都用固定的英文标识，是因为其余部分每个技能自定、跨技能搜不动，而这九个词到哪儿都是这几个——换个人接手，一眼看得出哪条做完了、哪条急、哪条已经定了去向。

**示例**——示例文件里那两行（第一行是「中途定的」，第二行是「做完的」）：

```text
Task 1: Ruling: 入口头部注释的 `bash hooks/verify.sh` 一并改成 `checks/verify.sh`（计划 Step 4 没提这两行）— 该文件刚搬走，留着这两行就是指向一个不存在的路径，而这个提交本身是要独立成立的 — 代价：任务 3 Step 4 是整份重写入口，不存在锚点冲突，若我判断错，只是多改一次两行注释。
Task 1: complete (commits 72d9c09..af4cd4b, tests: bash checks/verify.sh → 全部通过)
```

`Ruling` 那行三段都在——定了什么、为什么、错了付什么；`complete` 那行末尾挂着提交号和跑过的命令与结果。开头 `Task 1:` 那一段是那次活自己的编号，换个技能按那个技能的活另起；跟着的 `Ruling` 与 `complete` 是固定的那三个词之二。去向那一栏写 `Ruling` 的意思就是「这条要写成一条独立的裁定行」，像上面第一行那样。

「遗留的」那一类示例文件里一条都没有（那次活没留下没解决的问题）。照上面那几张表写，先是空的形状，再是填出来的样子：

```text
<编号>: open: <是什么>（<严重度>／<去向>）
Task 2: open: 新增的检查没覆盖 macOS 那条分支（Minor／defer）
```

下面那行是编的，不是从哪份真台账里抄的。

### 收尾：什么时候才准写完成行、什么时候删

**做法**：完成行末尾挂一样能当场查的东西，挂什么看这个技能有没有跑得动的检查：

| 有没有跑得动的检查 | 末尾挂什么 |
|:---|:---|
| 有 | 那道检查跑过的命令与结果。**跑过了才追加，跑挂了什么都不写** |
| 没有 | 提交号、文件加行号这类查得到的 |

活干完，把「这份台账连同它的目录可以清了」提给用户，说清要清哪些；**用户点头才动手**，动手前把还要留的东西交出去（没进提交的裁定、下一个会话还要用的判断）。

**收尾前那一遍**：把遗留的那几行统一过一遍，分判哪些必须在收尾之前修掉——一条一条临时判看不出轻重，看全貌才判得准。中途做的决定靠**当时写下的那一行**交到用户手上（「中途定的」那一类），不是收尾时补说一遍——收尾前把这几行拿出来给人看；清掉之后再想给人看就没了。

**怎么算做对了**：每条完成行末尾都挂着一样能当场查的东西；配了检查的，那道检查真跑过。

**为什么**：完成行是「这件事不用重做」的唯一凭据，虚报一次，后面所有恢复都建在假账上。所以凡是能交给命令判的，就别交给写的人自觉——过了才准写，是唯一能挡住虚报的办法；靠人自己守，就总有守不住的时候。

删是另一回事：它不可逆，而那个目录里往往不只有台账——任务简报、日志、别的会话放在这儿的半成品都可能在。台账只是临时脚手架，长期记录不靠它，但「它是临时的」不等于「谁都可以随手删」。

**示例**：上面那行完成行末尾的 `tests: bash checks/verify.sh → 全部通过`，是「有检查」那一档留下的痕迹；同一个括号前半段 `commits 72d9c09..af4cd4b`，是「没有检查」时也要挂的那一样。

## 第 5 步：整份示例

要具体样子，就读整份：`references/台账示例.md`。它是从一份真跑过的台账删节出来的，三十来行，一次读完。

**它是示例，不是模板。** 它长成那样，是因为那次活长成那样——有提交、有跑得动的检查脚本、分成了几个任务。换个技能，这些条件不一样，台账就该长成另一个样子。要看的是**一份台账站住需要哪些东西凑齐**，不是把它的形状搬过去。

## 第 6 步：看目标技能现在把状态记在哪、够不够用

读目标技能，找出它现在把状态记在哪——进度文件、待办清单、产出目录，或者某个工具留下的工作区目录。然后拿第 3 步那份结构当清单，一块一块查：

| 块 | 查什么 |
|:---|:---|
| 第 1 行 | 有没有写清这份记录归哪一次活 |
| 分节 | 能不能一眼看出做到哪了 |
| 每一行 | 说结论的行：那三个词在不在、后面跟没跟一样能当场查的东西、遗留项标没标严重度与去向。挂证据的行：实测结果在不在它撑的那条结论旁边 |
| 位置 | 在不在产出之外、不会被当成产出的一部分交出去 |
| 收尾 | 有没有说清什么时候才算做完、什么时候删，以及动手前谁点头 |

再用第 2 步那两条反向查一遍：有没有把能从提交历史或产出里直接读回来的东西抄进去；有没有说清写下的行不回头改。

产出一张表，三列：**块 → 现状 → 缺什么**。第 7 步「建议改动」那节的「现在是什么」一列，就是从这张表来的。

目标技能压根没有状态文件时，这一步空手而过。

## 第 7 步：出清单

四节，固定这个形状：

```text
## 结论
该配 / 已有那份够用 / 不该配 + 一句为什么

## 建议改动
| 改哪处 | 现在是什么 | 建议改成什么 | 为什么 |
```
