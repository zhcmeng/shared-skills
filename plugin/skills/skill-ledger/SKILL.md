# 技能台账建议

给一个技能，判断它该不该配台账，再给出「改哪几处、怎么改」的建议清单。

**产出是建议，不是改动。** 这个技能不碰目标技能的任何文件——改不改、怎么改，由拿到建议的人定。

**台账是什么**：一个跨上下文压缩活下来的文件。会话被压缩、换一个会话接着干、或者交给子代理去做之后，读它就知道「做到哪了、中途定了什么、为什么」，不必从头再来。

## 第 0 步：先确认拿到的是技能

一个技能的形状：**一个目录，里面有 `SKILL.md`**，而 `SKILL.md` 开头是 `---` 包起来的一段元信息。同目录下可能还有写给人看的说明文件，那不是 `SKILL.md`，判断形状时不用管它。

给的是名字、不是路径时，先按目录名把它找出来——仓库的 `skills/`、`plugin/skills/` 下，或者配置目录的 `skills/` 下。给的是某个技能的 `SKILL.md` 文件本身，认它**所在的那个目录**是技能：`SKILL.md` 是技能的一部分，不是另一个东西。

**认出来之后，顺带看一眼这个技能现在把状态记在哪**：有没有进度文件、待办清单、产出目录，或者某个工具留下的工作区目录。有的话，下面第 3 步末尾那条规矩就适用——清单要说的是「已有那份够不够用」，不是建议再加一份。

拿到的不是这个形状——一个不属于任何技能的普通 Markdown 文件、一个没有 `SKILL.md` 的目录、一个不存在的路径——**直说这不是技能，停下**。别硬凑一份清单出来。

没给参数时跳过这一步：直接把下面第 1 步到第 4 步的判据与清单给出去，当参考读。

## 第 1 步：判该不该配

### 四条信号，中两条以上才配

| 信号 | 问法 |
|:---|:---|
| 跨上下文边界 | 这个技能的活会不会跨上下文压缩、跨会话，或者交给子代理接着干？ |
| 重做代价高 | 做到一半丢了，重来要花掉多少时间、多少外部调用、多少钱？ |
| 中途要做决定 | 规范没写清、两种合理做法要选一个，而这些决定后面的步骤还要接着用吗？ |
| 同一套流程连着跑多轮 | 每轮结束得记住「上一轮到哪了」吗？ |

### 不该配的三类

| 不该配 | 例子 |
|:---|:---|
| 一次调用几分钟内跑完，丢了重跑便宜 | 翻译一篇文章、数一段文本有多少字这类活 |
| 状态已经在产出里 | 产出的文件本身就写着进度——比如一份要填五个栏目的文档，填到哪一栏一眼看得出 |
| 状态已经在提交历史或问题单里 | 提交记录本身就是记录，再加一份是重复 |

**四条信号一条都不中时，结论直接写「不该配」，并说清为什么。** 别为了显得有用而硬加——配一套记账的负担，比不配更贵。

三类是**排除**条件，只在状态**完全**落在那里时才排除：只是部分落在那里——比如提交里有代码，但中途定了什么、为什么这么定，没记下来——仍按四条信号判。两类同时够格时先看三类：是真的「完全」就不配，不是就按信号走。

## 第 2 步：六件事

台账就六件事。每件都要写清「怎么做」和「为什么」——只有做法没有道理，遇到没见过的技能就改不动了。

| 事 | 做法 | 为什么 |
|:---|:---|:---|
| 身份行 | 首行写清这份台账是给哪一次活干的 | 台账会被下一个会话读到。上游为这条做过 25 次基线实验，担心的事没发生——模型并没有照别人的台账跳过没做的事，25 次全部拒绝；但每次拒绝之前都先花工具调用去证明「这份不是我的」，最贵的一次花了 13 次。没有身份行，真实仓库里就出现临时绕道：自己另起文件名躲开别人的台账、简报被覆盖、该忽略的文件进了提交。身份不能靠「记得清理」——台账存在的理由就是扛崩溃和压缩，而这两种情况恰恰不给你收尾的机会，身份必须写进数据本身 |
| 位置 | 一次活一个目录，目录名从那一次活的名字派生；放在被版本控制忽略的工作区里，不进提交 | 放在 `.git/` 下面会被运行环境的保护路径拦掉，子代理往那儿写文件直接被拒——上游踩过这个坑 |
| 行格式 | 一行一件事，前缀固定，让压缩后的自己一眼搜得出来 | 恢复靠的就是一句搜索：有「完成」前缀的那行说明这件事做完了，不重做 |
| 可核断言 | 每行带上能当场查证的东西——提交号、文件名加行号、跑过的命令和它的结果 | 上游的基线实验里，提交号对不上的台账会被直接拒收。写得能被查证，是台账被信任的前提 |
| 读者 | 点名谁读它、读它做什么 | 没人读的记录等于没写。上游点到读者的地方有三处，各读各的：恢复的自己、最后那道整支复核、用户 |
| 闸门与收尾 | 能机械化的就机械化——跑过测试才写完成行；活干完就删掉 | 上游只在其中一条路上放了这道闸门：`executing-plans` 用脚本真跑测试、过了才追加完成行，那条路上没法虚报完成。另一条路（SDD）没有闸门，完成行由控制器自己照模板写——同一个上游，两条路不一样。长期记录落在提交历史或产出里，台账只是临时脚手架 |

## 第 3 步：落到哪几处

建议清单要指到这四处，每处给具体写法：

| 时机 | 写什么 |
|:---|:---|
| 开工 | 建台账、写身份行。已经有台账时**先认身份**——首行不是自己那份就不碰 |
| 每完成一件事 | 追加一行。写哪几类事件、写成什么格式，按这个技能自己的活来定 |
| 恢复 | 怎么读：先认首行身份，再按前缀定位到「做到哪了」；半途的活怎么接（比如末行是「修复第 N 轮」，说明还在循环里，从下一轮接） |
| 收尾 | 谁读、怎么汇总给人、什么时候删 |

**目标技能已经有状态文件时，清单要说的是「已有那份够不够用」，不是建议再加一份。**

## 第 4 步：出清单

四节，固定这个形状：

```
## 结论
该配 / 不该配 + 一句为什么

## 建议改动
| 改哪处 | 现在是什么 | 建议改成什么 | 为什么 |
（「改哪处」要指到 SKILL.md 的章节名或行号）

## 台账设计草案
身份行 / 位置 / 事件类型与行格式 / 可核断言 / 读者 / 闸门与收尾
（每项按这个技能的实际活来写，不套模板）

## 建议里不含的
（明确列出没建议做的，免得读的人以为漏了）
```

判「不该配」时第一、四节照写，中间两节省掉。

要写「台账设计草案」那一节时，先看一份真跑过的台账长什么样：`references/台账实例.md` 里整份抄了一份，旁边标出六件事各自落在哪一行。照它那个形状，内容按目标技能自己的活写。

目标技能已经有台账或状态文件时，「已有那份够不够用」写进第一节「结论」那一句，要改的地方进第二节的表格——不另开一节。

清单用跟用户对话的语言写（默认中文），不跟着目标技能正文的语言跑。
