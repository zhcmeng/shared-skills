# 台账实例

一份真跑过的台账，全文抄在下面，旁边标出「六件事」各自落在这份台账的哪里。

**这是实例，不是模板。** 它长成这样，是因为那次活长成这样：有 git 提交、有跑得动的检查脚本、分成了三个任务。换个技能，这些条件不一样，台账就该长成另一个样子。要看的是一份台账站住需要哪些东西凑齐，不是把这份的形状搬过去。

原文是 `C:\work\shared-skills\.superpowers\sdd\2026-09-23-检查脚本迁移与自动化\progress.md`。那个目录属于一次活，活干完整个删掉；这份副本留在这儿，免得它跟着一起没了。抄过来的日期是 2026-09-24，一字未改。

## 六件事各自落在哪

| 六件事 | 在这份台账里 |
|:---|:---|
| 身份行 | 第 1 行，`# SDD ledger — plan: <计划文件路径>`。计划路径写在首行里，谁读到都知道这是不是自己那份 |
| 位置 | 文件自己待的目录：`.superpowers/sdd/2026-09-23-检查脚本迁移与自动化/`——目录名是计划文件名去掉 `.md`。整个 `.superpowers/` 不进提交 |
| 行格式 | 三类前缀，各管一类事：`Task N: Ruling:`（裁定）、`Task N: complete (commits ...)`（做完）、`### 任务 N（提交 xxxxxxx）`（那一轮的经过）。压缩后搜 `Task ` 就能定位到做到哪了 |
| 可核断言 | 每处结论后面都跟着能当场查的东西：提交号（`72d9c09..af4cd4b`）、跑过的命令加结果（`bash checks/verify.sh → 全部通过`）、原样抄下来的报错（`FAIL: session-start 没有输出`）、实测的数字（`1m42s`、`17 项连锁失败`） |
| 读者 | 这份没点名，靠文件自己说明白——压缩后接着做的那个人读整个文件。要点名时怎么写，见下；那是**一句指路**，不是必写的一栏 |
| 闸门与收尾 | 三条 `complete` 行末尾都带 `tests: <命令> → <结果>`——这三行是脚本真跑过检查才追加的，跑挂了什么都不写。收尾是活干完把整个目录删掉 |

### 要点名读者时，另一份是这么写的

同仓 2026-09-20 那份 pdf-to-md 的台账，开头第 5 行点名了谁读它、读它做什么：

> **待裁清单在 `deferred.md`**（与本文件同目录）——把散在下面的 defer 条目按「要不要动、动哪儿」重排过……每份派发都从这份里摘「不许动」的那几类带上；最终整支复核直接看它。

一句话里两个读者：派活的（摘「不许动」的带上）、最后复核的（直接看它）。没有这一句，那份清单就是写了没人看的。

这一句的作用是**指路**——告诉读到的人「你要的东西在隔壁那个文件里」，顺带点了谁用它。它不是在台账里开一栏写「读者：某某」。「读者」是设计台账时要答的问题，答案通常落在别处：写成这样一句指路，或者由文件本身的结构说明白。上游没有「读者」这一栏。

## 这份台账好在哪

- **短是结果，不是标准。** 上游没有任何行数规定，只规定了一件事的粒度：每做完一件事一行。这份 76 行，是因为那次活只有三个任务、每个任务一轮就过。活多、修复轮次多的台账会长得多，那是正常的——**决定长短的是「有没有把能从别处查回来的东西抄进来」，不是目标行数。** 提交里已经有的代码、盘上已经有的产出，再抄一遍，多一行都是白占地方；反过来，同一个数字每处都要现算，那多写一行反而省事。
- **每个结论都挂着证据。** 说「与预测一致」就附上实测输出；说「全部通过」就附上命令和耗时。
- **每条裁定都写了代价。** `Ruling:` 行一律三段：定了什么、为什么、错了要付什么。第三段是这份台账最值钱的地方——没有它，读的人没法判断这条裁定该不该推翻。
