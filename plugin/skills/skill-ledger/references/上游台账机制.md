# 上游台账机制（obra/superpowers）

- 仓库：`https://github.com/obra/superpowers`
- 版本：v6.4.1
- commit：`5bf4e78011075bcfc0dc295f0724994cd123ee71`
- 日期：2026-09-18

`SKILL.md` 那套机制是从这里提取的。这份文件写明：六件事在上游分别写在哪、原话是什么，复核剩下的发现分哪几类、各去哪，以及上游更新后怎么核对。

**`SKILL.md` 正文不依赖这份文件**——它是给要追根、或者要核对上游有没有改的人看的。不谈来源，那份技能照样能用。

下面每条 `文件:行号` 都对着上面那个 commit。

## 六件事在上游怎么落

### 归属行（上游叫身份行）

上游台账首行固定写 `# SDD ledger — plan: <计划文件路径>`（`skills/subagent-driven-development/SKILL.md:148-149`）。读到台账第一件事是认这一行：首行不是自己这份计划的，就不碰。

上游为这条做过 **25 次**基线实验，想验证的坏事**没有出现**：控制器没有照别人的台账跳过没做的事，25 次全部拒绝——15 次认出那是别的计划的台账，另 10 次连「名义上属于自己计划」的台账也拒了（`docs/superpowers/specs/2026-07-06-sdd-plan-scoped-workspace-eval-results.md:45-55`）。

复现出来的是**代价**，不是错误率：

- **每次恢复都要先核对首行。** 最接近真实崩溃恢复的那一轮里，五个控制器为了证明「这份台账不是我的」，分别花了 7、13、9、10、6 次工具调用，平均 9 次（同文件 `:59-64`）。
- **首行没写归属，真实仓库里就出现临时绕道。** 一个工作区攒下三个计划的 68 个文件，第二个计划的控制器只好自己另起 `progress-p2.md`、`p2-task-N-report.md` 这类名字躲开第一个计划的台账；简报在共用的默认路径上被静默覆盖；本该忽略的文件两次进提交，靠两个清理提交才收拾掉（同文件 `:66-82`）。

上游因此把归属当成**结构问题，不是清理问题**：「任何只靠一次活结束时清理的修法，恰恰在这个台账要扛的崩溃与压缩场景里失效」（`docs/superpowers/specs/2026-07-06-sdd-plan-scoped-workspace.md:42-45`）。

### 位置

一次活一个目录，由 `skills/subagent-driven-development/scripts/sdd-workspace` 算出来：`<仓库根>/.superpowers/sdd/<计划名>/`。目录下同时写一个自忽略的 `.gitignore`，让整个工作区不出现在 `git status` 里，也不会被误提交。

早先放在 `.git/sdd/` 下，改掉的原因是运行环境把 `.git/` 当**保护路径**，拒绝代理往那里写文件——实现子代理写自己的报告时被拦住，跑到一半断掉（`scripts/sdd-workspace:21-25`、`RELEASE-NOTES.md:167`，上游 #1780）。

代价写在同一条发布说明里：工作区是被忽略的临时文件，`git clean -fdx` 会连台账一起删掉，那时候只能从 `git log` 恢复。

### 记哪些事、每行怎么写（上游叫行格式）

一行一件事，前缀固定。完成行有两个模板（`skills/subagent-driven-development/SKILL.md:437-439`）：

`Task <N>: complete (commits <base7>..<head7>, review clean)`

`Task <N>: complete (commits <base7>..<head7>, <K> parked)`

后一个是在断路器被触发、搁置了 K 条之后写的。字段只有三样：任务号、提交范围（7 位短 SHA）、收尾条件。

修复轮写成 `Task <N>: fix round <R>/5 (<X> addressed, <Y> open — <finding one-liners>; commits <a7>..<b7>)`（同文件 `:406`）；有争议没定的写成 `Task <N>: Ruling: <finding> — <what you decided and why>`（同文件 `:422`）。

**一个任务有哪三种状态**——不靠某个字段，靠行的种类推出来（同文件 `:141-145`）：

| 状态 | 判据 |
|:---|:---|
| 做完 | 有 `Task <N>: complete` 行；不重派 |
| 还在环里 | 末行是 fix round；从下一轮接着跑 |
| 没做完 | 上面两种都不是；从第一个没有 `complete` 行的任务续 |

所以恢复契约就是一句搜索。上游的计划文本把它写成了形式化的一句：「一个任务算 DONE 当且仅当有 `Task <N>: complete` 行」（`docs/superpowers/plans/2026-07-15-sdd-fix-loop-redesign.md:24`）。

### 能当场查的东西（上游叫可核断言）

每行的提交号都能当场查。上游基线实验里，10 份自称完成的台账有 5 份因为引用的提交号在仓库里根本不存在被拒收——原话是「它声称的提交在本仓库历史里一个都找不到」（`docs/superpowers/specs/2026-07-06-sdd-plan-scoped-workspace-eval-results.md:49-50`、`:86-96`）。

另外 5 份引用的是**真的、也确实属于本计划**的提交，但里面的代码是空壳，和「复核干净」的说法对不上，同样被拒（同文件 `:50-53`）。所以能核的不只是提交号在不在，还有它到底提交了什么。

### 哪几行必须在清理前交到人手上（上游叫读者）

上游点到读者的地方有三处，各读各的：

| 谁读 | 读什么 |
|:---|:---|
| 恢复后的自己 | 整个文件——它是「恢复地图」：提交在 git 里，台账负责指出做到哪了（`skills/subagent-driven-development/SKILL.md:150-152`） |
| 最终整支复核 | 缓办与搁置那几行，用来分判哪些必须在合并前修（同文件 `:450-455`） |
| 人 | 所有 `Ruling:` 行——最后汇总给用户，用户据此返工（同文件 `:473-480`） |

**表里那个「合并」是指什么**：上游那条路在分支上干活，干完把分支并回主线——那一下就是合并。分界线落在这里，是因为并回去之后这些毛病就进主线了。

人那一栏上游写得很直：「随工作区一起删掉的裁定，等于一个偷偷做的决定」（同文件 `:480`）。另一处更短：「没人读的汇总等于静默丢弃」（同文件 `:364`）。

**人这一栏两条路不一样，别写混**：SDD 那条路的收尾只按 `Ruling:` 字面扫——「把台账里每一行含 `Ruling:` 的行，预检裁定、搁置发现、断路器裁定全算上，按做出顺序收进最终消息」，缓办项不进这份清单（同文件 `:473-477`）。把缓办项也列给人看的是 `executing-plans` 那条路：写进最终消息的「Deferred minors」栏，并且「Minor 永不进修复轮，也永不变成裁定」（`skills/executing-plans/SKILL.md:271-275`）。

### 什么时候才准写完成行、什么时候删（上游叫闸门与收尾）

**写入前的检查**：只在 `executing-plans` 那条路上有——完成行由 `skills/executing-plans/scripts/task-done` 这个脚本跑完测试才追加，原话是「跑挂的那次什么都不记；这件事就不算完成」（`skills/executing-plans/SKILL.md:224-231`）。

**SDD 那条路没有这道检查**：完成行由控制器自己写——上游原文是「append the completion line to the ledger in the same message as your other bookkeeping」，后面跟着两个行模板（`skills/subagent-driven-development/SKILL.md:433-439`）。上游自己也记过手工追加确实发生过（`docs/superpowers/specs/2026-07-06-sdd-plan-scoped-workspace.md:37`）——所以这道检查是那条路的做法，不是整个上游的性质。

**收尾**：最终整支复核干净、修改也合进去之后，`rm -rf <工作区>` 整个删掉——记录交回给 git 历史（`skills/subagent-driven-development/SKILL.md:482-484`）。

## 复核剩下的分哪几类、各去哪

一条发现没当场修掉，落进台账的方式有三种：

| 上游的叫法 | 判据 | 台账里写成什么 | 谁读、什么时候处理 |
|:---|:---|:---|:---|
| `Minor` | 复核者判「覆盖可以更广」、润色建议这类（`skills/subagent-driven-development/task-reviewer-prompt.md:147-152`） | `Task <N>: minor (deferred): <one-liner>`（`skills/subagent-driven-development/SKILL.md:361-362`） | 最终整支复核，用来分判哪些必须在合并前修；**永不进修复环** |
| `Out-of-Scope Observations` | 复核者发现的毛病完全在修复 diff 之外（`skills/subagent-driven-development/re-review-prompt.md:55-62`） | 同上，也记成 deferred minor（`skills/subagent-driven-development/SKILL.md:399-403`） | 同上；**永不延长环** |
| `parked` | 只在修复环到顶（第 5 轮）时才准用：复核者错了、或本就可争；或者「是真的，但下游没有东西建在它上面」（`skills/subagent-driven-development/SKILL.md:415-419`） | `Task <N>: parked — <finding> — Ruling: <why the code stands>`（同文件 `:416`） | 最终复核「两边都看得到」；下一个要碰同一区域的任务，派发里带一个指向它的指针（同文件 `:278-279`） |

**到顶时还有第三种去向，别和搁置混了**：发现是真的**且承重**——后面的任务建在它上面，或者它暴露了计划缺陷——这时不许搁置，要写成一条独立的 `Task <N>: Ruling: <finding> — <what you decided and why>`，并带进下一个任务的派发（同文件 `:420-425`）。上游原话：「静默搁置一个结构性失败，等于让每个依赖任务都建在它上面」；只有「缺陷让每条前路都变成猜测」时才停。搁置也只在到顶时才准——「提前裁定以结束环，是『预判』换了个名字」（同文件 `:427-429`）。

**这一节要说白**：上游没有一处把这些写成「三类遗留问题」这样的固定分类，上面这张表是从「没当场修掉的发现落进台账的哪一格」归纳出来的。分类面在上游是两个：一个是**严重度**（`Critical` / `Important` / `Minor`，外加 `⚠️ Cannot verify from diff` 与 `plan-mandated` 两个特别标注），一个是**去向**（进环／缓办／搁置／裁定）。表里是去向面。

**正文把这三组固定成了标识**：行首三类行写 `complete` / `Ruling` / `open`，遗留项的严重度写 `Critical` / `Important` / `Minor`，去向写 `fix` / `defer` / `park` / `Ruling`——英文、不译、每个技能一样。除这三组，行首前面那段编号与其余部分按各技能的活自定。跟上游的词逐个对：

| 正文的标识 | 上游的写法 |
|:---|:---|
| `complete` | 上游台账写 `Task <N>: complete (commits <base7>..<head7>, review clean)`（`skills/subagent-driven-development/SKILL.md:437-439`）。上游的恢复契约就钉在这个词上：「一个任务算 DONE 当且仅当有 `Task <N>: complete` 行」（`docs/superpowers/plans/2026-07-15-sdd-fix-loop-redesign.md:24`） |
| `Ruling` | 上游台账写 `Task <N>: Ruling: <finding> — <what you decided and why>`（同文件 `:422`）。**这个词在正文里担两处**：既是「中途定的」那一类行的标识，也是承重那条遗留的去向——去向写 `Ruling`，意思就是「这条要写成一条独立的裁定行」，两处指的是同一种行 |
| `open` | 上游在修复轮的汇总行里用这个词：`Task <N>: fix round <R>/5 (<X> addressed, <Y> open — <finding one-liners>; commits <a7>..<b7>)`（同文件 `:406`）。**上游没拿它当行首标识**——行首那一位上游留给严重度，写成 `Task <N>: minor (deferred): <one-liner>`（同文件 `:361-362`）。正文把它提成第三类行的标识，好让三类各有一个词，搜一遍就分得开 |
| `Critical` / `Important` / `Minor` | 评审词表里的小标题一字不差：`#### Critical (Must Fix)`、`#### Important (Should Fix)`、`#### Minor (Nice to Have)`（`skills/subagent-driven-development/task-reviewer-prompt.md:176-178`）。三者各指什么也照上游：不是什么都算 `Critical`；`Important` 是「不修的话这个任务就不能算可信」；覆盖可以更广、措辞可以更好这类是 `Minor`（同文件 `:147-152`） |
| `defer` | 上游台账写 `(deferred)`，如 `Task <N>: minor (deferred): <one-liner>`（`skills/subagent-driven-development/SKILL.md:362`） |
| `park` | 上游台账写 `parked`，如 `Task <N>: parked — <finding> — Ruling: <why the code stands>`（同文件 `:416`） |
| `fix` | **正文自己起的，上游没有这个词。** 上游进环那一路没有单独的标识词——一条发现够重就再派一轮修，靠 `Task <N>: fix round <R>/5 (…)` 那一行汇总记（同文件 `:406`、`:372`）。正文把它提成一个去向词，好让四个去向摆在同一层上 |

## 上游更新了怎么核对

1. 拉上游的 `RELEASE-NOTES.md`，或者仓库的 release 页，看有没有新版本条目。
2. 对着上面那条演进史，看「机制落在上游哪几个文件」那张表里的五个路径有没有出现在新条目里。
3. 有就更新本文件头部的版本号、commit 与日期，并改对应那几段。**`SKILL.md` 不用动**——它只讲道理，出处与版本都留在本文件里。
4. **核对时以成品 `SKILL.md` 为准，计划文本只作设计意图。** 两者有几处写法对不上：`Task <N>: BLOCKED — <one-liner>` 只写在计划里，成品没有这条行格式（`docs/superpowers/plans/2026-07-15-sdd-fix-loop-redesign.md:23`）；搁置行的 `Ruling:` 成品是大写、计划两处是小写（同文件 `:22`、`:630`）；`fix round` 的发现列表成品写 `<finding one-liners>`、计划写 `<finding one-liner>[; …]`（同文件 `:20`）。
