# whatis

## 判据

**一个完全没听过它的人，读完能不能得到一个不走样的印象，并且知道下一步该问什么？**

两条都要。只讲清楚、不留出口，读者拿了几句总结就走，还得自己想「然后呢」。

**站在用的人的角度写，不站在做它的人的角度。** 读者关心「它能替我干什么、什么时候别用它」，不关心它内部结构有多精巧。

## 输出

对话里一段，一屏看完。骨架固定，顺序不变：

```
**<对象>** —— <一句话，它是什么>

**是什么**
<两三句：解决什么问题、从哪来、谁在用>

**能做什么**
<动词开头的具体能力，三到五条，每条一行>

**大概原理**
<一段话：它凭什么能做到上面那些事>

**什么场景用**
<什么时候该用；什么时候别用>

**想继续了解可以问**
A. <问题>
B. <问题>
C. <问题>

来源：<链接，仅查了网才写>
```

**一句话排在最前，不放结尾。** 那是读者唯一一定会读的一行。

## 各段的分寸

| 段 | 写成什么 |
|:---|:---|
| 一句话 | 一行，30 字内。不用「强大的」「灵活的」「一站式」 |
| 是什么 | 两三句，讲清它填的是哪个坑 |
| 能做什么 | 3–5 条，动词开头，每条一行。想举例子就举一句话的场景，不贴命令和代码 |
| 大概原理 | 一段话，日常语言。读者的反应该是「原来如此」，不是「结构图呢」 |
| 什么场景用 | 该用、别用各一两句。别用那句最容易被省，也最有用 |
| 来源 | 一行，一两个链接。凭已知知识答的就不写 |

全篇一屏（400 字上下，不含追问清单）。写不下就砍，不缩字号。

## 追问清单

三到五条，编号 A/B/C/D。**每条是一个能直接回答的问题，不是一个话题**——读者回一个字母，就接着讲。

关键是**按这个对象现编**，不套模板。各条落在不同方向：

| 对象类型 | 方向 |
|:---|:---|
| 仓库 / 工具 | 跟我的场景搭不搭、怎么上手、谁在维护、跟我已经在用的 X 比 |
| 概念 / 术语 | 举个带数字的例子、跟邻近概念的区别、什么情况下不成立 |

「它有什么替代品」是废话，「它跟 pgvector 比怎么样」才是问题。**能点名就点名**——点不出来说明还没了解够。

## 查到哪儿为止

**仓库、工具、产品、公司 —— 一律查一次再写。** 版本、维护状况、近期变化是最容易过时的部分，凭记忆写就是等着出错。本地有就翻 README、目录树、包元数据（`package.json`、`pyproject.toml`、`Cargo.toml`）；没有就搜，抓到官方仓库或官网首屏即停。

**概念、术语 —— 讲得准就不查。** 查了多半只是印证已知，白花时间。

**用户直接给了 URL 或本地路径 —— 直接读，不再搜。**

「大概原理」说不清时，才多读一层；到入口文件为止。

## 查不到就说查不到

速览最容易出的错是**一本正经地编**——冷门仓库、新概念，凭印象补细节，读者分辨不出来。

定不准的地方写「不确定」，或者干脆不写。宁可短一截，不能假一句。
