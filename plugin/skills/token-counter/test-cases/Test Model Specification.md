# 测试模型规格说明

测试项：`skills/token-counter/scripts/count_tokens.py`（DeepSeek token 精确计数脚本）。

## TM-1 等价类模型（等价类划分）

**唯一标识符**：TM-1

**目标**：把测试项的输入与输出划成一批处理方式相同的等价类。管的是「哪些输入走同一条处理路径、哪一类输入会被拒绝」，以及 token 数与字符数各按什么口径算出来。

**优先级**：高。风险信息只给出一条——「数出来的 token 不准」。本模型的等价类正落在计数口径上：是否走官方词表、特殊 token 算几个、字符数按什么单位算。

**测试策略摘要**：

- 本任务共用四门技术：等价类划分、组合测试（成对档）、判定表测试、场景测试。四门都在基于规格说明这一类里，依据都是测试项本身的源码与用法说明。
- 组合方式：等价类划分把「文本内容形态」这个原本取值不固定的维度收窄成 6 个有限取值，交给组合测试当参数 B 的取值域；判定表测试单独接管「来源选定与解码成败」这一段布尔条件的组合；场景测试覆盖带环境前置条件的端到端流程。本模型的分工是给另外三个模型提供取值域与处置预期。
- 测试完成准则：各门技术识别出的测试覆盖项，100% 都要有测试用例覆盖。本模型识别出 22 个等价类，取全，不取子集。
- 已知缺口：这四门都只擅长检出遗漏型缺陷，检出不了多余型缺陷。补结构那一侧适合用分支测试——它按控制流上的分支逐条覆盖，本测试项的 `ensure_tokenizers()` 有「已装引擎／装打包 wheel／联网装」三条分支，`read_source()` 有「取 `--text`／读文件／读标准输入」三条分支。该技术不在本次选用的四门里，这里只作说明，不代做。

**测试模型**：

| 处理环节 | 类号 | 等价类 | 有效／无效 |
|:---|:---|:---|:---|
| 输入处理：文本来源 | EP-S1 | 命令行只给出 `--text`，其值为一个字符串 | 有效 |
| 输入处理：文本来源 | EP-S2 | 命令行给出一个位置参数，该路径存在且可读 | 有效 |
| 输入处理：文本来源 | EP-S3 | 命令行既不给 `--text` 也不给位置参数，标准输入中有数据 | 有效 |
| 输入处理：文本来源 | EP-S4 | 命令行同时给出 `--text` 与位置参数 | 无效 |
| 输入处理：文本来源 | EP-S5 | 位置参数给出的路径不可读（不存在，或指向目录） | 无效 |
| 输入处理：文本来源 | EP-S6 | 参数形式不合命令行约定（给出多个位置参数，或给出未知选项） | 无效 |
| 输入处理：文本内容 | EP-C1 | 纯 ASCII 文本 | 有效 |
| 输入处理：文本内容 | EP-C2 | 纯中文文本 | 有效 |
| 输入处理：文本内容 | EP-C3 | 中英混排、含空格与换行、含首尾空白 | 有效 |
| 输入处理：文本内容 | EP-C4 | 含基本平面外字符（如 emoji） | 有效 |
| 输入处理：文本内容 | EP-C5 | 含 DeepSeek 特殊 token 的字面量（如 `<｜end▁of▁sentence｜>`） | 有效 |
| 输入处理：文本内容 | EP-C6 | 空文本 | 有效 |
| 输入处理：数据编码 | EP-E1 | 字节来源的数据是合法 UTF-8，按 `utf-8-sig` 解码成功 | 有效 |
| 输入处理：数据编码 | EP-E2 | 字节来源的数据不是合法 UTF-8，解码抛出异常 | 无效 |
| 内部处理：token 计数 | EP-I1 | 按 `tokenizer.json` 的规范语义计数，不经过任何兼容转换层 | 有效 |
| 内部处理：token 计数 | EP-I2 | 文本中的 DeepSeek 特殊 token 字面量按官方词表算作一个特殊 token | 有效 |
| 内部处理：字符计数 | EP-H1 | 算的是解码后文本的字符数（Unicode 码点个数），不是 UTF-8 字节数 | 有效 |
| 内部处理：字符计数 | EP-H2 | 字节来源（文件、标准输入）的 BOM 被解码环节剥除，不计入字符数 | 有效 |
| 内部处理：字符计数 | EP-H3 | `--text` 的值不过解码环节，其中的 U+FEFF 计入字符数 | 有效 |
| 输出处理 | EP-O1 | 标准输出打印两行：`tokens: N` 与 `chars: M` | 有效 |
| 输出处理 | EP-O2 | 打印 `not valid UTF-8: <来源标识>` 并以状态码 1 退出，不打印结果 | 无效 |
| 输出处理 | EP-O3 | 以未捕获的异常终止，不打印结果 | 无效 |

**未规定功能**：测试依据中未予以明确、而测试项会执行到的功能，识别出两处，两处都是依据或测试项的缺陷线索：

- EP-S4 那一类（命令行同时给出 `--text` 与位置参数）。用法说明只列了三种单独用法，没有写这个组合该怎么处理；测试项实际执行的是「`--text` 优先、位置参数被静默忽略」，这个优先级在依据里找不到出处。
- EP-S5 那一类（位置参数给出的路径不可读）。依据没有规定路径不可读时该怎么办；测试项直接把异常抛到顶层，用户看到的是一段调用栈，不是一句可读的错误说明。

**可追溯性**：本模型取自测试项源码的三个部分——`read_source()` 的字节读取与解码、`count_tokens()` 的计数写法、`main()` 的输出与 argparse 定义；对应关系见文末对应表。

## TM-2 组合模型（组合测试，成对档）

**唯一标识符**：TM-2

**目标**：管三个维度两两之间的搭配——文本来源、文本内容形态、BOM 形态。管的是「换个来源传同一段文本，结果还一样吗」这类只在搭配处才暴露的问题。

**优先级**：高。这三个维度的搭配直接决定报出来的 token 数，正是风险信息点名的「数出来的 token 不准」。

**测试策略摘要**：

- 用组合测试，取成对档，依据是：三个维度的两两交互是这类脚本的缺陷高发处（`--text` 的值不走解码环节，字节来源的 BOM 会被剥掉，报错信息按来源取不同标识），而三个维度的三重交互没有对应的独立机制支撑；完全组合档为 3×6×2＝36 条组合，其中相当一部分不产生新的行为分支，实施成本与检出收益不成比例。
- 组合方式：参数「文本内容形态」的 6 个取值来自 TM-1 的 EP-C1 至 EP-C6，即由等价类划分收窄取值域后交给本模型；本模型再把搭配结果交给 TM-4 的场景使用。
- 测试完成准则：本模型的测试覆盖项 100% 都要有测试用例覆盖。成对档识别出 36 个 P-V 对成对组合，取全，不取子集。
- 本模型的三个参数都不含「数据不是合法 UTF-8」这一情形：字节不是合法 UTF-8 时没有「解码后的文本」可言，内容形态无从谈起，硬凑出来的搭配是伪组合。这一类输入交由 TM-3 的判定表处理。

**测试模型**：

参数取值表如下，共 3 个参数、11 个 P-V 对。

| 参数 | 取值 | P-V 对 |
|:---|:---|:---|
| A 文本来源 | 命令行给出 `--text` | PV-1 |
| A 文本来源 | 命令行给出一个文件路径 | PV-2 |
| A 文本来源 | 不给文本来源参数，读标准输入 | PV-3 |
| B 文本内容形态 | 纯 ASCII | PV-4 |
| B 文本内容形态 | 纯中文 | PV-5 |
| B 文本内容形态 | 中英混排、含空格与换行、含首尾空白 | PV-6 |
| B 文本内容形态 | 含基本平面外字符（emoji） | PV-7 |
| B 文本内容形态 | 含 DeepSeek 特殊 token 的字面量 | PV-8 |
| B 文本内容形态 | 空文本 | PV-9 |
| C BOM 形态 | 无 BOM | PV-10 |
| C BOM 形态 | 带 BOM | PV-11 |

「带 BOM」这个取值在三个来源下的所指不同，这是本模型要盯住的地方：

- 来源是文件或标准输入时，指数据的字节以 `EF BB BF` 开头，解码环节会把它剥掉；
- 来源是 `--text` 时，指字符串以 U+FEFF 开头，这个字符不过解码环节，会原样计入字符数。

**可追溯性**：本模型取自 `main()` 的 argparse 定义与 `read_source()` 的两条分支（来源维度）、`utf-8-sig` 解码写法（BOM 维度）；内容形态维度取自 TM-1。见文末对应表。

## TM-3 判定表模型（判定表测试）

**唯一标识符**：TM-3

**目标**：管「文本从哪儿取、取到的数据能不能解码」这四个条件组合起来之后，测试项走哪条路、给出什么输出。管的是来源选定与报错，不管数算得准不准。

**优先级**：中。风险信息列出的是「数出来的 token 不准」，本模型不管计数准确性，管的是「能不能算出来、报错报得对不对」。四个条件里有两个涉及依据未规定的行为（EP-S4、EP-S5），是依据缺陷线索的落点。

**测试策略摘要**：

- 用判定表测试。选它的依据是：来源选定这一段本身就是一组布尔条件到动作的映射，条件之间还相互牵制（文件路径都没给，就谈不上文件存不存在），判定表正是表示这类关系的模型形态。
- 组合方式：本模型接管「非法 UTF-8 字节」这一类输入的组合判定，与 TM-2 分工——TM-2 只管三个维度的两两搭配，不含非法字节；报错信息里的来源标识（文件路径还是 `<stdin>`）由本模型管。
- 测试完成准则：本模型的测试覆盖项 100% 都要有测试用例覆盖。识别出 6 条判定规则，6 条全部可行，取全。
- 本模型的分母与 TM-2 分开算：成对覆盖率覆盖不了判定表规则，两者各算各的。

**测试模型**：

判定表如下。「T」表示该条件为真，「F」表示该条件为假，「*」表示该条件在这一列不影响结果。

| 条件与动作 | 规则 1 | 规则 2 | 规则 3 | 规则 4 | 规则 5 | 规则 6 |
|:---|:---|:---|:---|:---|:---|:---|
| 条件 C1：命令行为 `--text` 提供了值 | T | F | F | F | F | F |
| 条件 C2：命令行提供了位置参数 | * | T | T | T | F | F |
| 条件 C3：该路径存在且可读 | * | T | T | F | * | * |
| 条件 C4：取到的字节按 `utf-8-sig` 解码成功 | * | T | F | * | T | F |
| 动作 A1：取 `--text` 的值作文本 | T | F | F | F | F | F |
| 动作 A2：读取文件字节作文本 | F | T | T | T | F | F |
| 动作 A3：读取标准输入字节作文本 | F | F | F | F | T | T |
| 动作 A4：打印 `tokens: N` 与 `chars: M` 两行，状态码 0 | T | T | F | F | T | F |
| 动作 A5：打印 `not valid UTF-8: <来源标识>`，状态码 1 | F | F | T | F | F | T |
| 动作 A6：以未捕获异常终止，状态码 1 | F | F | F | T | F | F |

关于表的两点说明：

- 规则 1 把「只给 `--text`」与「`--text` 和位置参数都给」合并成了一列：C2 取真取假都不影响动作，按判定表的化简规矩可以合并。合并掉的那半列正是 TM-1 里的 EP-S4，属未规定功能。
- 规则 4 与规则 3 分成两条：路径不可读（C3＝F）和路径可读但字节非法（C3＝T、C4＝F）走的是不同的路——前者把异常抛到顶层，后者给出一句可读的报错。

**可追溯性**：本模型取自 `main()` 的 argparse 定义与 `read_source()` 的分支写法——`args.text is not None` 的那次判断、文件与标准输入的两路读取、`UnicodeDecodeError` 的捕获与报错文案。见文末对应表。

## TM-4 场景模型（场景测试）

**唯一标识符**：TM-4

**目标**：管用户与测试项之间从头到尾的交互序列，含依赖引擎没装时的自动安装。管的是「一次完整的调用能不能走通、走不通时用户看到什么」。

**优先级**：中。主场景与三类报错场景与计数准确性直接相关，判为高；引擎自动安装的三条场景风险信息未提及，判为低。「与线上口径核对」那条是唯一能验证「数得准不准」的外部手段，判为高。

**测试策略摘要**：

- 用场景测试。选它的依据是：本测试项除输入输出之外还有环境状态这一层——依赖引擎在与不在，走的是完全不同的三条路，这一段用前面两个模型的「单次调用」视角看不出来。
- 组合方式：场景里每一步的输入取值沿用 TM-1 与 TM-2 已经定下来的取值域，本模型不另造输入值；引擎安装那三条场景补的是 TM-1、TM-2、TM-3 都覆盖不到的环境前置条件。
- 测试完成准则：本模型的测试覆盖项 100% 都要有测试用例覆盖。识别出 1 个主场景加 10 个备选场景，共 11 个，取全。
- 「与线上口径核对」这一条要联网并持有 DeepSeek API 凭据，是本任务里唯一不依赖本机词表、能独立验证 token 数的手段。运维上不可用时，这一条只能记为未执行，不能算通过。

**测试模型**：

交互序列如下。表中 U 是用户（或其他系统）的动作，S 是测试项的动作。

| 场景 | 类型 | 交互序列 |
|:---|:---|:---|
| 文件路径计数成功 | 主场景 | U1 给出一个 UTF-8 文本文件的路径、S1 读取文件字节、S2 按 `utf-8-sig` 解码、S3 按官方词表计数、S4 打印 `tokens: N`、S5 打印 `chars: M`、U2 读到两行数值 |
| `--text` 直接给文本 | 备选场景 | U1 在命令行用 `--text` 给出文本、S1 取该字符串、S2 按官方词表计数、S3 打印 `tokens: N`、S4 打印 `chars: M`、U2 读到两行数值 |
| 管道送入标准输入 | 备选场景 | U1 把文本经管道送给测试项、S1 读取标准输入字节、S2 按 `utf-8-sig` 解码、S3 按官方词表计数、S4 打印 `tokens: N`、S5 打印 `chars: M`、U2 读到两行数值 |
| 文件路径不可读 | 备选场景 | U1 给出一个不存在的路径、S1 读取文件字节失败、S2 把异常抛到顶层、U2 看到一段调用栈而非结果 |
| 文件不是合法 UTF-8 | 备选场景 | U1 给出一个内容不是合法 UTF-8 的文件、S1 读取文件字节、S2 解码失败、S3 打印 `not valid UTF-8: <文件路径>` 并退出、U2 看不到 `tokens` 与 `chars` |
| 标准输入不是合法 UTF-8 | 备选场景 | U1 把非法字节经管道送入、S1 读取标准输入字节、S2 解码失败、S3 打印 `not valid UTF-8: <stdin>` 并退出、U2 看不到 `tokens` 与 `chars` |
| 装打包 wheel 后计数成功 | 备选场景 | U1 在没有装引擎的环境里运行、S1 查不到引擎、S2 在标准错误打印安装提示、S3 用打包的 wheel 离线装上引擎、S4 按官方词表计数、S5 打印两行、U2 读到两行数值 |
| 转联网安装后计数成功 | 备选场景 | U1 在没有装引擎、打包 wheel 也用不上的环境里运行、S1 查不到引擎、S2 尝试装打包 wheel 未成功、S3 在标准错误打印联网安装提示、S4 从 PyPI 装上指定版本、S5 按官方词表计数、S6 打印两行、U2 读到两行数值 |
| 联网安装也失败 | 备选场景 | U1 在没有装引擎、打包 wheel 用不上、又不通网的环境里运行、S1 查不到引擎、S2 装打包 wheel 未成功、S3 联网安装失败、S4 把异常抛到顶层、U2 看到一段调用栈而非结果 |
| 参数形式不合约定 | 备选场景 | U1 给出多个位置参数或一个未知选项、S1 打印用法说明、S2 打印一行错误说明、S3 以状态码 2 退出、U2 看不到 `tokens` 与 `chars` |
| 与线上口径核对 | 备选场景 | U1 把同一段文本发给 DeepSeek API、S1 从返回里取出 `usage` 的输入 token 数、U2 再照主场景跑一次本脚本、S3 打印两行、U2 比对两边数值 |

**可追溯性**：主场景与「`--text` 直接给文本」「管道送入标准输入」两条取自模块说明里的「Usage」段；三类报错场景取自 `read_source()` 的异常处理与 argparse 的行为；引擎安装三条取自 `ensure_tokenizers()` 的三级依赖解析；口径核对取自 `count_tokens()` 的计数口径与模块说明里关于计费口径的说明。见文末对应表。
